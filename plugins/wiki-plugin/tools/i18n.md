# 다국어(i18n) 작업 절차서

이 위키의 번역·언어 추가 작업이 따라야 하는 **단일 기준 체크리스트**입니다. 어떤 언어(en/zh/ja/…)든 아래 순서를 그대로 따르면 누락이 없습니다.

## 구조 한눈에

| 조각 | 위치 | 폴백 |
|---|---|---|
| 문서 본문 | `docs/<lang>/<path>` (한국어 원본과 **같은 상대 경로** — `list` 노드의 `path`, 없으면 flat `<문서명>`) | 파일 없으면 `docs/ko/` |
| 화면(UI) 문구 | `i18n.js`의 `STRINGS.<lang>` (`STR()`/`STRF()` 사용) | 키 없으면 `STRINGS.ko` |
| 내비 라벨·태그 | `list` 노드의 `label_<lang>` / `tags_<lang>` (폴더는 `title_<lang>`) | 없으면 한국어 `label`/`tags` |
| 지식 인덱스 | `tools/doc-entries.<lang>.json` (오버레이) → `data/knowledge-index.<lang>.json` | 파일 없으면 ko 인덱스 |
| 지도 문서 | `docs/<lang>/ai-map` (km-* 하이드레이션 id 유지) | 없으면 ko ai-map |
| 클러스터 표시명 | `tools/clusters.json`의 `<lang>` 배열 | 없으면 ko 라벨 |
| 개념 표시명 | `tools/concepts.<lang>.json`의 `labels`(ko 키 → 표시명) — **키는 번역하지 않는다** | 매핑 없으면 키 그대로 |
| 계층 경로 표시 | 인덱스의 `sectionL`(폴더 `title_<lang>`) — `section`은 canonical 조인 키 | 없으면 `section` |
| 지식 관계 근거 | `doc-entries.<lang>.json`의 `relations[].evidenceRef`(target로 매칭) | 없으면 ko 문구 |

언어 선택: 설정 → 기본 설정 → 언어 (`s.lang`, 사이트 기본값 `config.json defaults.lang`). 변경 저장 시 새로고침으로 일괄 적용. **저장된 값이 없으면 첫 방문에 자동 감지**(2026-07-26, `app.js detectLang()`): `navigator.language`가 한국어 계열(ko*)이 아니면 `en` — 설정에서 명시로 고르면 그 값이 항상 우선한다(이를 위해 `HARD_DEFAULTS.lang`은 `''`(자동)이다 — `'ko'`로 두면 비한국어 브라우저의 명시적 한국어 선택이 setOrClear에서 지워진다).

## 핵심 원칙 (반드시 지킬 것)

1. **본문 파생 데이터는 본문 번역과 한 몸.** 문서의 `label_<lang>`·`tags_<lang>`·`doc-entries.<lang>.json`의 title/summary 오버레이는 **그 문서의 본문을 번역하는 PR에서 함께** 갱신한다. 본문보다 먼저 하지 않는다(제목↔본문 불일치 방지). Introduction 6편이 선례.
2. **UI 문구(STRINGS)는 본문과 무관하게 선행 가능.** 새 UI 문구를 코드에 추가할 때는 반드시 `STR()`/`STRF()` 키로 넣고 `STRINGS.ko`와 준비된 모든 언어 사전에 같이 등록한다 — 하드코딩 한글 리터럴 금지.
3. **개념(concepts)은 언어 공유 키.** 오버레이는 title·summary(+relations의 evidenceRef)만 바꾸고 concepts는 ko 것을 그대로 상속 — 연관 관계·stats·그래프 구조가 언어와 무관하게 동일해야 한다. 화면에 보이는 글자는 `tools/concepts.<lang>.json` 표시명이 담당한다(키 불변). 새 개념을 만들면 그 사전에도 라벨을 넣는다 — 라벨은 서로 유일해야 한다.
4. **내부 링크는 canonical(`#!문서명`) 유지.** 번역 파일 안에서도 링크를 언어별로 바꾸지 않는다(라우팅이 언어를 해석).
5. **본문 번역 규칙**: 내용 추가·수정·삭제 금지, HTML 구조·클래스·SVG 지오메트리 보존, SVG 텍스트 라벨은 번역(전문용어·코드는 원형), aria-label도 번역.

## 언어 하나를 추가/확장하는 순서

0. **`tools/build_prerender.py`의 `LANGS`에 `<lang>` 추가** — 여기가 언어 목록의 **정본**이다. `build_ai_export.py`(피드·사이트맵 hreflang·llms 링크)와 `validate_i18n.py`(미러·라벨·오버레이·STRINGS 패리티)는 이 목록 또는 `docs/` 실제 폴더에서 언어를 읽으므로 자동으로 따라온다. 같은 파일에서 손으로 채울 것: 스냅샷 chrome 문구(`STR`), `OG_LOCALE`, `EXTRA_PAGES`의 언어별 요약.
   - **자동으로 따라오지 않는 것이 있다** — 아래 표의 조각을 하나도 빠짐없이 훑을 것. 2026-07-28까지 이 자리에 "더 손댈 곳이 없다"고 적혀 있었고, 그래서 **개념 표시명 사전이 통째로 빠진 채 ja가 출시됐다**(모든 게이트는 초록이었다).
1. `docs/<lang>/`에 번역 파일 배치 — **한국어와 같은 상대 경로**(`list` 노드의 `path`)에 둔다 (부분 가능 — 나머지는 ko 폴백)
2. `i18n.js`: `LANGS_READY`에 `<lang>` 추가, `STRINGS.<lang>` 사전 채우기(키 목록은 `STRINGS.ko` 기준 — 빠진 키는 ko 폴백). **`LANGS_READY`에 넣는 것만으로 브라우저 언어 자동 감지가 그 언어로 분기한다**(`app.js`의 `detectLang`이 목록 기반 — 2026-07-27 이전에는 "한국어냐 아니냐"로만 갈려 ja/zh 본문을 넣어도 영어가 나가는 함정이 있었다)
3. 번역한 각 문서마다(원칙 1): `list`에 `label_<lang>`(+필요시 `tags_<lang>`), `tools/doc-entries.<lang>.json`에 `{name, title, summary}` 오버레이 추가
4. `tools/clusters.json`에 `<lang>` 배열 등록(새 클러스터가 생기면 **모든 언어**에 추가) → `python3 tools/build_index.py` 실행(`--check` 0)
5. **`tools/concepts.<lang>.json` 작성** — `concepts.en.json`과 같은 형태(`{note, labels}`), 같은 키 집합. **키는 한국어 canonical 그대로 두고 표시명만** 채운다(라틴 문자 개념은 매핑하지 않는다 — 그대로 보이는 게 맞다). 빠뜨리면 검색 칩·문서 하단·지식지도·2D/3D 그래프의 개념이 **그 언어에서만 한국어**로 보인다. `validate_i18n`의 `concept-dict-coverage`가 강제한다
6. 기능 JS 안에 **언어별 리터럴 사전**(예: `games.js`의 `G2048_LADDER`)이 있으면 그 언어 항목도 채운다 — `hidden-lang-dict`가 잡는다. 새 UI 문구는 애초에 이런 사전을 만들지 말고 `STRINGS`에 넣는다
7. `docs/<lang>/ai-map` 작성 — 본문 번역 + km-* id·정적 폴백 수치 유지, `data-topics` 키는 그 언어의 클러스터 라벨과 일치
8. 설정 select 표기: 콘텐츠가 충분해지면 `STRINGS`의 `lang<Xx>` 값에서 "준비 중/coming soon" 제거
9. Work Log 폴더 제목("07월"·"05일") 등 구조 라벨은 해당 언어 콘텐츠가 생길 때 `title_<lang>`으로

## 전면 병행 정책 — en(2026-07-26) · ja(2026-07-28)

- **신규 문서는 en·ja 본문 동반이 규칙**이다(워크로그 제외, 뉴스 포함). PR CI의 `tools/check_translation.py`가 `ENFORCED_LANGS = ('en', 'ja')`를 순회하며 기계 강제한다: ① `docs/<L>/<p>` 추가·수정 시 그 노드의 `label_<L>`과 (인덱스 문서면) `doc-entries.<L>.json` 오버레이 동반, ② 신규 ko 인덱스 문서에 `docs/<L>/<p>` 부재 시 실패. **다음 언어는 소급 번역이 끝난 뒤 `ENFORCED_LANGS`에 넣는다** — 끝나기 전에 켜면 모든 PR이 막힌다.
- **번역 도식의 글자 폭도 기계가 잰다** — `validate_design.py`는 문자별 하한 폭으로 박스 초과를 잡는데, 2026-07-27까지 **가나(히라가나·가타카나)가 폭 0으로 계산**됐다(`_is_cjk`에 없어 `fallback: 0.0`으로 떨어짐 — "ナレッジグラフ"가 0으로 측정). 지금은 가나·CJK 문장부호를 `cjk` 비율(실측 1.0~1.024)에 편입했고, **반각 가타카나만 따로**(실측 0.5) 둔다 — `cjk`로 묶으면 과대추정이 되어 실제로는 들어가는 글자를 ERROR로 막기 때문이다. 새 언어를 추가할 때 **그 문자 체계가 폭 계산에 잡히는지 먼저 확인**할 것.
- **번역 도식도 같은 게이트를 통과한다**: `validate_design.py`와 `check_diagram_bounds.mjs`가 `docs/` 아래 **모든 언어의** 본문(존재분)을 순회한다(2026-07-27 일반화 — 그전에는 `LANGS = ['ko','en']` 하드코딩이라 ja 도식이 한 번도 검사되지 않았다). 영어 라벨은 한글보다 길어지기 쉽고(대문자≈0.7·소문자≈0.5×폰트), 일본어는 가나가 전각이라 같은 뜻이라도 글자 수가 늘기 쉽다(레벨 2자 → `レベル` 3자) — 둘 다 번역 시 박스 폭을 선검토한다. 칸이 격자로 붙어 있어 넓히면 줄이 어긋나는 도식은 **부제를 줄이고**, 홀로 선 상자는 **중심 좌표를 유지한 채 넓힌다**.
- sitemap은 번역 본문이 있는 문서에 언어별 URL + `xhtml:link` hreflang(ko·en·ja·x-default=ko)을 싣고, llms.txt는 존재분에 `[EN]`·`[JA]` 링크를 단다 — 전부 `build_ai_export.py` 자동 생성이라 별도 손질 불요. 피드도 언어별(`feed.xml`·`feed.en.xml`·`feed.ja.xml`)이며 사이드바 RSS 링크가 읽는 언어의 피드를 가리킨다.
