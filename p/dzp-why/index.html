왜 지금인가 — 흩어지고 사라지는 개발 지식

프로젝트를 수행하면 Architecture와 설계 구조, 업무 Rule과 상태 전이, DB Table·Column의 의미, API 연계, 장애 원인과 해결 방법, 성능 개선 사례, 재사용 가능한 개발 패턴 같은 지식이 계속 만들어진다. 그러나 이 지식의 대부분은 Source Code · Commit · Merge Request · Issue · 메신저 · 이메일 · 회의 · 개인 기억에 분산된 채 남고, 조직 지식으로 축적되지 못한다.

비용은 이미 수치화되어 있다

  • 개발자의 62%가 매일 30분 이상을 답을 찾는 데 쓰고, 68%는 주 1회 이상 지식 사일로에 부딪힌다 — Stack Overflow Developer Survey 2022
  • 개발자의 69%가 주 8시간 이상(근무시간의 약 20%)을 비효율로 잃고, 주요 원인으로 "불충분한 문서"를 지목한다 — Atlassian, State of Developer Experience 2024
  • 지식노동자는 근무시간의 19%를 정보 검색·수집에 사용한다 — McKinsey, The Social Economy (2012)
  • 직무 지식의 42%는 그 사람에게만 있는 고유 지식이라, 퇴사하면 동료가 그 업무의 42%를 수행할 수 없다. 대형 기업 기준 비효율적 지식공유의 손실은 연 4,700만 달러로 추산된다 — Panopto Workplace Knowledge Report (2018)
  • 신규 개발자가 온전한 생산성에 도달하기까지는 평균 3~9개월이 걸린다 — DX, Developer Onboarding Research

그 결과 조직에서는 같은 문제의 반복 분석, 설계 의도와 변경 배경의 소실, 프로젝트 간 경험 재사용 부족, 담당자 이동·퇴사에 따른 지식 손실, 신규 개발자의 높은 온보딩 비용, AI 개발 도구 사용 시 반복적인 Context 재설명이 되풀이된다.

"문서를 잘 쓰자"는 답이 되지 못한다

오픈소스 설문에서 93%가 "불완전하거나 오래된 문서"를 만연한 문제로 꼽으면서도 60%는 문서에 거의 기여하지 않았고(GitHub Open Source Survey 2017), Stack Overflow는 사내 위키·문서 DB가 방치되고 신뢰를 잃는 구조적 이유를 일찍이 분석한 바 있다(Why Your Wikis … Don't Work, 2019). 일정과 우선순위에 밀리는 개발 현장에서 사람의 성실함에 의존하는 문서화는 지속되지 않는다.

문제의 재정의 부족한 것은 개발자의 성실함이 아니라 구조다. 지식은 이미 GitLab에 쌓이고 있다 — 그것을 읽어 정리할 주체가 사람일 필요가 없을 뿐이다. 그리고 그 구조의 절반(지식을 담아 잇고 검증하는 엔진)은 Reference Wiki로 이미 운영 중이다 — 없는 것은 GitLab과의 연결뿐이다. 다음 편 제안의 핵심에서 그 구조를 다룬다.
