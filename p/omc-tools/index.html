실전 시나리오별 워크플로우

모드·에이전트·도구를 실제 상황에 어떻게 엮어 쓰는지 8가지 시나리오로 정리했습니다. 아래 번호 버튼이나 이전·다음 버튼으로 시나리오를 하나씩 확인하세요.

시나리오 1 — 새 프로젝트 킥오프

빈 프로젝트를 처음 시작할 때 — 문서화 → 설계 합의 → 요구사항 명확화 → 팀 구현 순으로 진행합니다.

# 1. 프로젝트 구조 문서화
/oh-my-claudecode:deepinit
# 2. 아키텍처 합의 (전문가 합의 기반)
ralplan: 전체 시스템 아키텍처 설계 (Next.js, PostgreSQL, Redis)
# 3. 핵심 요구사항 명확화
/deep-interview "소셜 로그인이 있는 SaaS 앱"
# 4. 팀으로 기본 기능 구현
team ralph: 기본 CRUD 기능 전체 구현

시나리오 2 — 기능 추가

요구사항이 명확하면 곧바로 autopilot, 모호하면 deep-interview로 다듬은 뒤 구현합니다.

# 요구사항이 명확할 때
autopilot: 이메일 알림 기능 추가 (가입 환영, 비밀번호 재설정, 주문 확인)
# 요구사항이 모호할 때 — 먼저 명확화
/deep-interview "알림 기능 추가"
# → 명확해진 요구사항으로 구현
autopilot: [명확해진 요구사항]으로 구현

시나리오 3 — 레거시 코드 리팩토링

현황 파악 → 계획 → 병렬 변환 → 검증의 네 단계로 안전하게 진행합니다.

# 1. 현황 파악 (기술 부채 분석)
deep-analyze: 이 코드베이스의 기술 부채 파악
# 2. 마이그레이션 계획
/oh-my-claudecode:plan JavaScript → TypeScript 마이그레이션
# 3. 여러 파일 병렬 변환
ulw: 이 15개 파일 전부 TypeScript로 변환
# 4. 검증
review code
fix build

시나리오 4 — 버그 추적 및 수정

에러 메시지를 그대로 붙여넣으면 debugger가 스택을 분석해 근본 원인을 찾습니다.

# 에러 메시지를 그대로 붙여넣기
deep-analyze:
  Error: Cannot read property 'user' of undefined
  at AuthMiddleware (middleware.ts:45)
# → debugger가 스택 분석 → 근본 원인 파악 → 수정안 제시
# 수정 적용
fix build

시나리오 5 — 배포 전 코드 리뷰

품질·보안 리뷰를 차례로 돌리고, 발견된 문제를 ralph로 한 번에 수정합니다.

# 1. 종합 코드 리뷰 (로직·안티패턴·성능)
review code
# 2. 보안 취약점 점검
security review
# 3. 발견된 모든 문제 일괄 수정
ralph: 코드 리뷰에서 발견된 모든 문제 수정

시나리오 6 — TDD 개발

테스트를 먼저 만들고 구현하는 흐름(Red → Green → Refactor)을 자동으로 반복합니다.

# 테스트 먼저, 구현은 나중
tdd: 사용자 인증 서비스 개발
# → 1) 테스트 케이스 작성  2) 실패 테스트(Red)
# → 3) 구현 위임  4) 통과 확인(Green)  5) 리팩토링

시나리오 7 — 데이터 분석 작업

여러 분석 에이전트가 병렬로 Python(pandas·matplotlib)을 돌려 종합 보고서를 만듭니다.

# 로그·CSV 데이터 분석
/sciomc 이 CSV 파일 분석:
  - 사용자 행동 패턴
  - 이탈 원인 분석
  - 매출 기여도 높은 기능

시나리오 8 — Git 작업 자동화

git-master에게 커밋 정리, PR 설명 작성, 브랜치 전략까지 위임할 수 있습니다.

# 변경 파일을 의미 단위로 커밋 정리
git-master에게 위임: 변경된 파일들 의미있는 단위로 커밋 정리
# PR 설명 작성 (한국어, 이유·내용·테스트 포함)
git-master: 이 변경사항 PR 설명 작성
# 브랜치 전략
git-master: feature/auth 브랜치 작업 후 main에 squash merge 준비

Windows 주의

Windows PowerShell 환경에서는 별도 주의가 필요합니다. 핵심은 tmux 의존 기능은 psmux로 해결(WSL 불필요), WSL2는 대안 경로라는 점입니다.

  • v4.14.4에서 Native Windows Hook manifest 관련 수정(sh 호출 제거)이 있었고, 이후 Native Windows Hook은 그대로 사용할 수 있습니다. 과거 문서의 "WSL2 권장" 안내는 구식으로, 현행 공식 README는 WSL2를 대안 경로로만 안내합니다.
  • tmux 가 필요한 기능(omc team CLI, 일부 외부 AI 워커 병렬 실행)은 Native Windows PowerShell만으로는 제약이 있을 수 있습니다. 공식 README는 Windows용 네이티브 tmux 호환 도구인 psmux(winget install psmux)를 제시하며, psmux 사용 시 WSL이 필요 없습니다.
  • 플러그인 설치·setup·doctor·세션 내 스킬 사용은 Native Windows에서 그대로 가능합니다. 문제가 반복되는 환경이라면 WSL2로 전환하는 대안 경로도 있습니다.
  • PowerShell에서 npm view·npm ping 이 정상이어도, Claude Code 플러그인 설치 흐름과 npm CLI 설치 흐름은 별개입니다.
사전 확인 사항 1. 실제 사용 환경이 Windows Native PowerShell인지 WSL2인지
2. OMC를 Claude Code 플러그인으로 쓸지, npm CLI/runtime으로 쓸지
3. /omc-teams 처럼 tmux가 필요한 멀티 AI 기능까지 사용할 계획인지

마지막으로 비용·성능과 명령어 참조 편이 알뜰하게 쓰는 법과 전체 명령어 표로 시리즈를 마무리합니다.
