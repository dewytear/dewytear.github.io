Claude Ship — PR을 머지까지 데려가는 세 에이전트, 쓰는 법과 장점

세 줄 요약

  • Claude Ship은 풀 리퀘스트(PR)가 열린 뒤의 일을 맡는 에이전트 묶음이다. Code Review가 문제를 찾고, PR Steward가 실패한 검사·충돌·리뷰 코멘트를 고쳐 커밋하고, Claude Approvals가 팀이 파일로 적은 정책대로 "누가 더 승인해야 하는가"를 판정한다. 2026년 11월 23일 Team·Enterprise 플랜 베타로 나왔다.
  • 개인 개발자는 Claude Code에서 /ship 한 줄로 커밋·푸시·PR 생성·리뷰까지 하고, 그 뒤 "지켜보기(watch)"가 시작돼 검사 실패와 리뷰 답변을 Claude가 처리한다. 머지는 사람이 누른다.
  • 장점은 리뷰가 코드를 쓰는 속도를 따라오게 만드는 데 있다. Anthropic은 자사 Claude Code 팀에서 6~9월 머지 PR이 두 배 넘게 늘고 되돌린 비율이 40% 넘게 줄었다고 밝혔다. 대신 정책 파일 한 줄이 사람 없는 머지를 허용할 수 있으니, 관찰 모드와 브랜치 규칙을 먼저 두는 순서가 중요하다.

코딩 에이전트가 코드를 쓰는 속도는 빨라졌는데, 그 코드를 리뷰하고 승인하는 쪽은 여전히 사람의 시간에 묶여 있다. PR을 열고 다른 일로 넘어갔다가, 며칠 뒤 리뷰가 오면 옛 코드로 돌아가 고치고, 검사를 다시 기다리고, 승인해 줄 사람을 찾는다. Anthropic이 Claude Ship을 소개하며 든 문제가 이것이다. 이 글은 공식 문서와 발표를 바탕으로 세 에이전트의 역할, 개인과 조직 각각의 사용법, 실제로 어떤 이득이 있는지와 어디서 조심해야 하는지를 정리한다. 이 위키는 Claude Code로 문서를 쓰고 PR로 머지하는 저장소라, 마지막에 이 위키의 흐름에 비춰 본 판단도 적었다.

Code Review는 2026년 10월 15일 정식 출시된 기존 제품이고, PR Steward와 Claude Approvals가 이번에 베타로 더해졌다. 셋은 따로따로 켤 수 있고 저장소 단위로 켠다.

Code Review의 네 단계는 눈여겨볼 만하다. 여러 에이전트가 병렬로 후보를 찾고(Find), 후보를 코드에 대조해 오탐을 거르고(Verify), 중복을 합쳐 심각도로 줄 세운 뒤(Rank), 인라인 코멘트와 검사 결과로 올린다(Post). 찾은 것을 그대로 쏟지 않고 한 번 더 검증하는 단계가 들어 있어서, 리뷰 봇의 흔한 불만인 "소음"을 줄이는 쪽으로 설계됐다. 심각도는 🔴 Important(머지 전에 고칠 것), 🟡 Nit(사소), 🟣 Pre-existing(이 PR이 만든 문제가 아님) 셋이고, 다시 리뷰할 때는 지난 리뷰 이후 바뀐 부분만 보며 Nit과 Pre-existing은 덜 올린다.

2. 개인 사용법 — /ship 한 줄

조직 관리자가 아무것도 켜지 않아도 개인 개발자는 터미널의 Claude Code에서 /ship을 쓸 수 있다. 사용량은 본인의 일반 Claude Code 사용량으로 잡힌다. 전제는 Claude Code 2.1.330 이상, GitHub CLI 2.63 이상(gh auth login 완료), git 2.38 이상이다.

  1. 변경을 만든 그 세션에서 /ship을 친다. 커밋 메시지를 대화에서 뽑기 때문이다(다른 세션에서 치면 "Update greet.py and 1 more" 같은 제목이 나온다).
  2. 확인 창은 없다. 커밋 직전과 푸시 직전에 "Esc to cancel"로 끝나는 줄이 몇 초 떠 있다가 진행된다. 기본 브랜치에 있으면 새 브랜치를 만들어 옮기고, 이미 다른 브랜치에 커밋돼 있으면 그 브랜치를 푸시해 PR을 연다.
  3. /code-review로 리뷰한다. 노력 수준은 /ship low처럼 앞에 붙인다(기본 high).
  4. "지켜보기"가 시작된다. 오토 모드에서 Claude는 묻지 않고 리뷰 지적을 고치고, 기본 브랜치를 머지해 충돌을 풀고, 실패한 검사를 손보고 재실행하며, 리뷰 코멘트에 답하고 스레드를 해결하고 재리뷰를 요청한다. GitHub에는 사용자 본인의 이름으로 올라간다.
  5. 검사가 통과하고 코멘트가 정리되면 Claude가 알린다. 머지는 사용자가 한다.

이미 PR이 열려 있으면 /steward가 커밋·푸시·리뷰를 건너뛰고 지켜보기만 시작한다. 지켜보는 동안 Claude Code는 사용자의 메시지 없이 움직일 때 PR 머지·승인·자동 머지 켜기·강제 푸시를 하는 gh·git 명령을 막고, 커넥터·WebFetch·WebSearch도 거부한다. git stash·git reset·git checkout·git add -A·git commit -a도 거부 목록에 있다. 지켜보기는 PR이 머지·닫힘, 7일 경과, Esc 한 번, 브랜치 전환, /clear·/resume·/branch, 세션 종료 가운데 하나로 끝난다. 저장소에 .claude/skills/steward/SKILL.md를 두면 지켜보기와 PR Steward가 같은 규칙을 읽는다.

자동으로 안 하는 것도 분명하다. PR이 이미 열린 브랜치의 미커밋 변경, 공개 저장소의 미커밋 변경, 이름이 비밀처럼 보이는 파일(.env 등)은 커밋하지 않는다. .gitignore·CLAUDE.md·.github/ 아래를 고쳤으면 직접 커밋하라고 한다. GitHub Enterprise와 포크에서는 PR을 열지 않으니 먼저 열고 /ship을 친다. 네이티브 Windows와 bypassPermissions 모드에서는 지켜보기가 시작되지 않는다.

3. 조직 사용법 — 하나씩, 한 저장소부터

관리자(Claude 조직 Owner)는 Organization settings › Claude Ship에서 켠다. 공식 문서가 권하는 순서는 에이전트 하나씩, 저장소 하나부터다.

공식 설정 문서의 순서를 그대로 옮겼다. 끌 때는 Approvals → PR Steward → Code Review 순이어야 한다. 정책 파일이 꺼진 Code Review를 다시 부를 수 있기 때문이다.

정책 파일은 "더 똑똑한 CODEOWNERS"

Claude Approvals의 핵심은 저장소 루트의 .claude/approvals.yml이다. 규칙마다 경로 패턴, 조건, 그리고 판정(verdict)을 적는다. 판정은 Claude가 어디까지 하는가(comments·approves·blocks)와 사람 몇 자리(seats)가 필요한가로 이뤄진다. 공식 문서의 시작 예시 둘을 그대로 옮긴다.

# .claude/approvals.yml — A안: 리뷰가 통과하면 한 사람이면 되고 Claude가 승인
version: 1
mode: observe
rules:
  - purpose: "A change takes two people. When Claude's review passes, one is enough and Claude approves."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    override:
      - { if: "claude/code_review = pass", verdict: { claude: approves, seats: 1 } }
  - purpose: "A change to the review rules takes two people."
    paths: ["**/.claude/**"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }
# .claude/approvals.yml — B안: 모든 변경에 사람 둘, Claude는 조언만
version: 1
mode: observe
rules:
  - purpose: "A change takes two people."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    advisory: [claude/code_review]
  - purpose: "A change to the review rules takes two people."
    paths: ["**/.claude/**"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }

읽는 법은 이렇다. seats: 2는 사람 두 자리인데 작성자가 한 자리를 채울 수 있으니 "작성자 + 한 명"이다. 작성자를 빼려면 seats: [{ count: 1, from: [humans, "!pr/authors"] }]처럼 쓴다. override는 조건이 맞을 때 판정을 바꾸는 자리이고, 분류기가 답을 못 내면 규칙 본래의 엄격한 판정으로 돌아간다. 여러 규칙이 겹치면 가장 엄격한 쪽이 이긴다(blocks > comments > approves). 조건에는 pr/files_changed > 50 같은 PR 사실과 분류기 답을 쓸 수 있다. 분류기는 Anthropic이 주는 둘(claude/code_review는 Important 지적이 남았는지로 pass/fail, claude/diff는 푸시 뒤 변화가 trivial·same_intent·different 중 무엇인지)에 더해, .claude/classifiers/<이름>/def.yml에 자연어 프롬프트와 출력 값을 적어 직접 만든다. 예컨대 "로그인·결제·마이그레이션을 건드리면 high"라는 위험도 분류기를 만들고 repo/change_risk = low일 때만 한 사람으로 줄이는 식이다.

정책 파일·분류기 폴더·REVIEW.md·CODEOWNERS·.gitmodules 같은 파일은 보호 파일이라 Claude가 승인하지 않고, 개발자는 PR 댓글로 @claude approve(본인 승인 등록), @claude approvals rerun(재평가), @claude approvals resolve f-…(정책이 허용한 사람이 지적 닫기)를 쓴다. 검사 제목이 곧 상태다. "Waiting on human review from any person (1/2)", "Held by Code Review's findings", "Passed; no approval from Claude"처럼 읽힌다.

4. 장점 — 무엇이 실제로 좋아지나

  • 리뷰가 코드 속도를 따라온다. Anthropic은 Claude Code 팀에서 2026년 6월부터 9월 사이 머지된 PR이 두 배 넘게 늘고 되돌린(revert) 비율은 40% 넘게 줄었다고 밝혔다. 같은 글이 그 팀에서는 Code Review가 더 넓은 절차의 한 층이라고 덧붙였으니, 수치를 에이전트 셋만의 효과로 읽지는 말아야 한다.
  • 오탐을 거르는 단계가 설계에 들어 있다. 찾은 후보를 코드에 대조해 검증한 뒤에만 올리고, 재리뷰는 바뀐 부분만 본다. 리뷰 봇을 꺼 버리게 만드는 소음 문제를 제품 구조로 다룬다.
  • 승인권이 분리돼 있다. 고치는 에이전트(PR Steward)는 승인·머지를 못 하고, Anthropic 서비스가 그 요청 자체를 거부한다. 판정하는 에이전트(Approvals)는 팀이 쓴 파일대로만 움직이고, 머지를 막을 권한은 GitHub 필수 검사 설정에서 온다. "AI가 AI 코드를 승인한다"는 걱정에 대한 답이 이 분리다.
  • 정책이 코드로 남는다. 누가 몇 명, 어떤 경로에, 어떤 조건에서 승인해야 하는지가 approvals.yml에 적히고, 그 파일 자체가 보호 파일이라 바꾸려면 다시 사람 둘이 필요하다. 관찰 모드로 먼저 돌려 보고 강제로 넘어가는 길이 기본 절차다.
  • 비용에 천장이 있다. Code Review 월 한도, PR Steward 월 한도와 저장소별 상한, 분류기 실행 한도를 따로 둔다. 한도에 닿으면 리뷰를 건너뛰고 PR에 그 사실을 적는다.
  • 기존 규칙 위에 얹힌다. 브랜치 보호, 필수 검사, CODEOWNERS, 자동 머지와 함께 동작한다. 사용자가 올린 고객 사례에서 TELUS 엔지니어링 디렉터는 "사람을 루프에 두되 사람의 시간은 판단이 필요한 변경에만 쓰게 됐다"고 했고, Carvana 엔지니어링·분석 SVP는 파일럿에서 리뷰 피드백 처리 시간이 줄었다고 했다.
  • Claude Code 없이도 쓴다. Code Review·Steward·Approvals는 GitHub App으로 돌므로 다른 도구로 쓴 코드에도 붙는다. Claude Code는 PR 전, Claude Ship은 PR 후를 맡는다는 것이 Anthropic의 구분이다.

5. 조심할 것

  • 정책 한 줄이 사람 없는 머지를 허용한다. seats: 0이면 봇이 쓴 PR이 아무도 안 본 채 머지될 수 있고, seats: 1은 작성자가 채울 수 있다. GitHub 브랜치 규칙이 승인 한 개를 요구할 때 Claude의 승인 리뷰가 그 하나가 될 수 있다. 자동 머지나 머지 큐를 켜 둔 저장소에서는 Claude의 수정 푸시가 머지를 촉발한다. 공식 문서가 모두 경고하는 항목이다.
  • 분류기는 PR 작성자가 쓴 글을 읽는다. 제목·설명·코멘트가 분류기 답을 흔들 수 있다고 문서가 명시한다. 분류기에 라벨·리뷰어 쓰기 권한을 줄 때는 라벨이 배포를 여는 저장소를 피하라고 한다.
  • 지켜보기는 내 자격증명으로 내 컴퓨터에서 코드를 돌린다. 기본 브랜치를 머지해 들어오는 스크립트, 다른 사람이 내 브랜치에 푸시한 것, 훅, SKILL.md가 모두 실행될 수 있다. 머지 권한자와 브랜치 푸시 권한자를 모두 믿을 수 있는 저장소에서만 켜라는 것이 공식 권고다.
  • 셀프호스트 환경에서는 승인 거부가 안 된다. PR Steward를 자체 러너에서 돌리면 Anthropic 서비스가 승인 요청을 막지 못하고, GitHub는 그 승인을 필수 승인으로 셀 수 있다. CLAUDE.md도 읽지 않는다.
  • 관찰 모드도 돈이 든다. 정책이 claude/code_review를 조건으로 쓰면 푸시마다 리뷰가 돌고, 분류기는 답이 없어도 과금된다. 분류기 실행당 예산(budget: { cost: 5 }, 기본 10달러, 상한 10달러)과 월 한도를 먼저 둔다.
  • 경쟁 제품과의 차이는 "승인"에 있다. 정리 글들은 GitHub Copilot 코드 리뷰, Cursor Bugbot, Codex 리뷰가 조언형이라 스스로 머지를 막거나 승인하지 않는다고 분류한다. Claude Ship은 정책이 허용하면 승인까지 간다. 그래서 더 편한 만큼 정책 파일의 책임이 무겁다.

6. 이 위키의 PR 흐름에 비추어

이 위키는 Claude Code 세션이 문서를 쓰고 PR을 열면 운영자가 "머지해"라고 답해야 스쿼시 머지가 된다. CI는 검증 게이트 네 개(파이썬 9단계·도식 경계·다국어 렌더·빌드)를 돌린다. Claude Ship에 옮겨 적으면 B안에 가깝다. 모든 경로에 사람 한 자리, CI는 별도 필수 검사, Code Review는 advisory로 두어 문서 PR에 코드 리뷰가 과금되지 않게 하는 구성이다. 콘텐츠 저장소라 Code Review의 "논리 오류" 기준이 맞지 않으니 REVIEW.md로 범위를 좁혀야 하고, PR Steward가 처리할 "실패한 검사"는 대부분 도식 글자 넘침이나 번역 누락이라 수정 커밋보다 사람 판단이 맞다. 지금은 /ship의 지켜보기가 Claude Code 세션 쪽 CI 실패를 재실행·수정해 주는 부분만 바로 쓸 만하다.
