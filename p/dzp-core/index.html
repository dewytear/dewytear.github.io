제안의 핵심과 아키텍처

본 제안의 목적은 단순한 회사 Wiki 구축이 아니다. GitLab에 축적되는 개발 결과를 AI가 지속적으로 분석해 지식을 추출하고, 기존 지식과 비교해 신규 생성·갱신·폐기를 판단하는 플랫폼을 만드는 것이다. 직원의 업무 흐름은 지금과 완전히 같다 — Wiki 작성, Markdown 편집, Tag 등록, 문서 분류, 지식 정리를 아무것도 추가로 요구하지 않는다. 직원은 최종 생성된 지식을 검색하고 읽기만 한다.

직원의 역할은 위 행에서 끝난다. 아래 행 전체가 AI의 몫이다.
핵심 개념 — Event Stream과 Knowledge State GitLab은 개발 변경의 Event Stream이고, Wiki는 현재 시점에 유효한 Knowledge State다. GitLab에는 Commit·MR·Release가 시간 순서로 계속 쌓이지만, Wiki는 "7/1 수정사항, 7/2 수정사항…" 같은 이력의 나열이 아니라 조직이 지금 알아야 하는 지식 구조(Architecture · Rule Engine · 상태 체계 · 채널 정책 · Troubleshooting …)로 정제되어 유지된다.

Knowledge State의 실체 — 결정적으로 빌드되는 인덱스

"현재 유효한 지식 상태"는 추상적 구호가 아니라 기계적으로 재현 가능한 산출물이어야 한다. Reference Wiki가 이를 이미 실증했다: 모든 문서의 메타데이터(제목·요약·개념·관계)는 큐레이션 파일 하나에서 결정적 빌드로 지식 인덱스 JSON이 되고, 같은 입력은 언제나 같은 출력을 낸다. 그래서 --check 한 번으로 "저장된 상태가 소스와 어긋났는가"를 바이트 단위로 판정할 수 있고, 어긋난 채로는 머지가 불가능하다(드리프트 게이트). Knowledge State가 Event Stream보다 뒤처지거나 소스와 모순되는 것을 규율이 아니라 기계가 막는 구조 — 이것이 회사 플랫폼이 물려받을 상태 관리의 실체다.

업계가 이미 가고 있는 길

  • 문서를 코드 곁에 — Spotify는 문서를 코드와 같은 저장소에 두고 CI로 빌드하는 Backstage TechDocs로 5,000개 이상의 문서 사이트를 운영하고, GitLab은 2,700페이지가 넘는 공개 핸드북의 handbook-first 문화로 유명하다. docs-as-code는 대규모 조직에서 이미 검증된 접근이다.
  • 문서 동기화의 자동화 — Swimm은 모든 PR마다 코드 변경과 문서를 대조해 자동 갱신하는 Auto-sync로 "Continuous Documentation"을 상용화했다.
  • 코드에서 지식 자동 추출 — Cognition의 DeepWiki(2025)는 저장소를 분석해 아키텍처 다이어그램과 모듈 문서가 포함된 위키를 자동 생성하며 상위 공개 저장소 5만 개 이상을 인덱싱했다. GitHub은 저장소 지식을 상시 주입하는 Copilot Spaces를 GA했고, Claude Code의 CLAUDE.md·AGENTS.md는 "저장소 안의 기계가 읽는 지식 파일"을 업계 관례로 만들었다.
  • 지식 검색 시장의 급성장 — 전사 AI 지식 검색의 Glean은 ARR $200M을 넘겼고, Atlassian은 Rovo를 클라우드 요금제에 기본 탑재했다.

즉 "GitLab 개발 결과의 AI 자동 지식화"는 docs-as-code의 검증된 토대 위에, 2025년 이후 상용화된 자동 추출 기술을 조직 지식 관리에 적용하는 것이다.

플랫폼 아키텍처

전체 플랫폼은 GitLab을 원천으로 하는 단방향 파이프라인으로 구성한다.

개발 결과가 아래로 흐르며 지식이 된다. 직원이 개입하는 층은 맨 위(개발)와 맨 아래(읽기)뿐이다.

지식 생성 Trigger — 완료로 인정된 변경만

모든 Commit을 즉시 지식화하지 않는다. 개발 중에는 미완성 구현, 실패한 시도, 임시 수정이 섞여 있기 때문이다. 조직이 완료로 인정하는 관문 — Review를 거쳐 기준 Branch에 Merge되고 Pipeline이 성공한 변경 — 만 분석 대상으로 삼는다. 완료된 변경 안에서 무엇이 지식이고 무엇이 아닌지(기계적 Refactoring·오타 등 제외 기준)는 지식 관리 체계의 가치 판정이 담당한다.

증분 분석 — 전체를 다시 읽지 않는다

프로젝트별로 마지막 처리 Commit SHA를 관리하고, GitLab Compare로 그 이후의 변경 파일만 수집해 관련 Context를 확장 분석한다. AI Token 사용량 절감, 처리시간 단축, 중복 분석 방지, 장애 시 재처리가 모두 이 상태 관리에서 나온다.

# 프로젝트별 knowledge trigger·sync 상태 (예시)
{
  "project": "scm/sales-order",
  "knowledgeBranches": ["master", "release/*"],
  "lastProcessedSha": "abc123def456",
  "lastProcessedAt": "2026-07-06T14:32:00+09:00",
  "status": "success"
}

단순 Diff가 아닌 Context 기반 분석

if ("CREDIT_HOLD".equals(soStatus)) 한 줄만 보고는 업무 정책을 판단할 수 없다. 변경 Diff에 더해 전체 Class · 호출자 · 관련 Mapper와 SQL · 관련 Test · 관련 Config · 기존 Wiki를 함께 읽는 Impact Expansion을 거쳐, 단순 코드 요약이 아닌 실제 개발 지식을 추출한다.

지식 무결성 게이트 — Trigger와 별개의 층

Pipeline 성공은 입구의 게이트다 — "이 변경을 분석할 자격이 있는가"만 판정한다. 지식 저장소 자신의 무결성은 별개의 게이트 층이 지키며, 이 층은 Reference Wiki가 이미 CI로 운영 중인 것을 그대로 물려받는다(위키는 어떻게 스스로를 지키는가):

  • 상태 검증 — 끊어진 링크·중복 ID·고아 문서·인덱스 미등재·도식 경계 초과를 커밋마다 전수 검사(ERROR 0가 머지 조건).
  • 드리프트 검증(--check) — 인덱스·그래프·llms.txt·sitemap이 결정적 재빌드 결과와 바이트 단위로 일치하는지 판정. AI Curator가 문서만 고치고 인덱스 반영을 빠뜨리는 사고를 기계가 차단한다.
  • 동반 게이트 — "문서를 바꿨으면 기록(Work Log)도, 지식 체계 반영도 같은 변경 단위에" 규칙을 diff 기반으로 강제. 회사 KPI의 "Merge 대비 지식 반영률"이 바로 이 게이트의 통과율이다(로드맵).
  • 리뷰 신호(비차단) — 기계가 강제할 수 없는 판단 영역(예: 지식관계를 다각도로 검토했는가)은 차단 대신 체크리스트를 띄워 사람의 검토를 유도한다.

Wiki Repository 층의 Index와 Provenance가 구체적으로 어떤 구조인지 — 어떤 필드가 이미 실증됐고 어떤 필드를 회사용으로 확장하는지 — 는 다음 편 지식 관리 체계가 다룬다.

운영 안정성 — 실시간과 보정의 이중화

Webhook(Merge → Queue → Curator) 실시간 처리에만 의존하지 않고, 정기 Batch가 Project Registry의 현재 SHA와 sync-state를 비교해 누락 변경을 재처리한다. Webhook 실패, Network 오류, Queue 누락, Curator 장애, 일시적 API 실패에 대응하는 구조다.

지식이 어떻게 판정·구조화·연결·추적되는지는 지식 관리 체계가 따로 깊게 다룹니다.
