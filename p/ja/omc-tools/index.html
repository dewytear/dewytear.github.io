高度な活用 — ツール・ワークフロー・Windows

OMC は、コードをより正確に扱うためのツール群を用意しています。テキスト検索より精密な分析が必要なときに役立ちます。

ツール群代表的な機能使いどころ注意点
LSPlsp_hover、lsp_goto_definition、lsp_find_references、lsp_diagnostics正確なシンボルの探索、型エラーの確認、参照の検索typescript-language-server、pyright、rust-analyzer など言語ごとのサーバーが必要
AST Grepast_grep_search、ast_grep_replace構文の構造にもとづく検索・置換テキストの grep より精密だが、パターンを書く力が要る
Python REPLpandas、numpy、matplotlib による分析CSV・ログ・統計の分析データファイルへのアクセス権限とパッケージの有無の確認が必要
Ask / Team CLIomc ask、omc team、omc session search外部の CLI ワーカーとセッションの検索プラグインのインストールの流れと CLI/runtime の経路の区別が必要
LSP の補足 LSP（Language Server Protocol）は、コードエディタが「この変数の定義はどこ？」「ここに型エラーはある？」を正確に突き止められるようにする標準です。ただし、その言語のランゲージサーバーが入っていないと正常に動きません。

実戦のシナリオ別ワークフロー

モード・エージェント・ツールを実際の場面でどう組み合わせて使うのかを、8 つのシナリオにまとめました。下の番号のボタンか、前へ・次への ボタンでシナリオをひとつずつ確認してください。

シナリオ 1 — 新しいプロジェクトのキックオフ

空のプロジェクトを始めるとき — 文書化 → 設計の合意 → 要件の明確化 → チームでの実装、の順に進めます。

# 1. プロジェクト構造の文書化
/oh-my-claudecode:deepinit
# 2. アーキテクチャの合意（専門家の合意にもとづく）
ralplan: システム全体のアーキテクチャ設計 (Next.js, PostgreSQL, Redis)
# 3. 中心となる要件の明確化
/deep-interview "ソーシャルログインのある SaaS アプリ"
# 4. チームで基本機能を実装
team ralph: 基本 CRUD 機能をすべて実装

シナリオ 2 — 機能の追加

要件が明確ならそのまま autopilot、あいまいなら deep-interview で磨いてから実装します。

# 要件が明確なとき
autopilot: メール通知機能の追加 (登録の歓迎、パスワード再設定、注文の確認)
# 要件があいまいなとき — まず明確化
/deep-interview "通知機能の追加"
# → 明確になった要件で実装
autopilot: [明確になった要件]で実装

シナリオ 3 — レガシーコードのリファクタリング

現状の把握 → 計画 → 並列の変換 → 検証、の四段階で安全に進めます。

# 1. 現状の把握（技術的負債の分析）
deep-analyze: このコードベースの技術的負債を把握
# 2. マイグレーションの計画
/oh-my-claudecode:plan JavaScript → TypeScript のマイグレーション
# 3. 複数ファイルの並列変換
ulw: この 15 ファイルを全部 TypeScript に変換
# 4. 検証
review code
fix build

シナリオ 4 — バグの追跡と修正

エラーメッセージをそのまま貼り付ければ、debugger がスタックを分析して根本原因を見つけます。

# エラーメッセージをそのまま貼り付ける
deep-analyze:
  Error: Cannot read property 'user' of undefined
  at AuthMiddleware (middleware.ts:45)
# → debugger がスタックを分析 → 根本原因を把握 → 修正案を提示
# 修正の適用
fix build

シナリオ 5 — リリース前のコードレビュー

品質・セキュリティのレビューを順に回し、見つかった問題を ralph で一度に直します。

# 1. 総合的なコードレビュー（ロジック・アンチパターン・性能）
review code
# 2. セキュリティの脆弱性の点検
security review
# 3. 見つかったすべての問題を一括で修正
ralph: コードレビューで見つかったすべての問題を修正

シナリオ 6 — TDD での開発

テストを先に作ってから実装する流れ（Red → Green → Refactor）を自動でくり返します。

# テストが先、実装はあと
tdd: ユーザー認証サービスの開発
# → 1) テストケースの作成  2) 失敗するテスト(Red)
# → 3) 実装の委任  4) 通過の確認(Green)  5) リファクタリング

シナリオ 7 — データ分析の作業

複数の分析エージェントが並列で Python（pandas・matplotlib）を回し、総合的なレポートを作ります。

# ログ・CSV データの分析
/sciomc この CSV ファイルを分析:
  - ユーザーの行動パターン
  - 離脱の原因の分析
  - 売上への貢献が大きい機能

シナリオ 8 — Git 作業の自動化

git-master にコミットの整理、PR の説明の作成、ブランチ戦略まで任せられます。

# 変更したファイルを意味の単位でコミットに整理
git-master に委任: 変更したファイルを意味のある単位でコミットに整理
# PR の説明を作成（日本語で、理由・内容・テストを含めて）
git-master: この変更の PR の説明を作成
# ブランチ戦略
git-master: feature/auth ブランチの作業後、main への squash merge を準備

Windows での注意

Windows PowerShell の環境では別途の注意が要ります。要点はtmux に依存する機能は psmux で解決できる（WSL は不要）、WSL2 は代替の経路ということです。

  • v4.14.4 で Native Windows Hook の manifest に関する修正（sh 呼び出しの除去）があり、それ以降 Native Windows Hook はそのまま使えます。過去の文書の「WSL2 推奨」という案内は古く、現行の公式 README は WSL2 を代替の経路としてのみ案内しています。
  • tmux が必要な機能（omc team CLI、一部の外部 AI ワーカーの並列実行）は、Native Windows PowerShell だけでは制約が出ることがあります。公式 README は Windows 向けのネイティブな tmux 互換ツールである psmux（winget install psmux）を挙げており、psmux を使えば WSL は不要です。
  • プラグインのインストール・setup・doctor・セッション内でのスキルの利用は、Native Windows でもそのまま可能です。問題がくり返される環境なら、WSL2 へ切り替えるという代替の経路もあります。
  • PowerShell で npm view・npm ping が正常でも、Claude Code のプラグインのインストールの流れと npm CLI のインストールの流れは別ものです。
事前に確認すること 1. 実際に使う環境が Windows Native PowerShell なのか WSL2 なのか
2. OMC を Claude Code のプラグインとして使うのか、npm CLI/runtime として使うのか
3. /omc-teams のように tmux が必要なマルチ AI の機能まで使う予定があるか

最後にコスト・性能とコマンドリファレンスの章が、賢く使うコツと全コマンド表でシリーズを締めます。
