提案概要 — なぜ今、何を

開発者はいまと同じように GitLab へ開発の成果を反映するだけで、AI がその成果を分析して組織の知識へ自動で変換し積み上げる Read-Only Engineering Knowledge Platform を提案する。人が文書を書くウィキではなく、開発の成果物がそのまま知識の源になる構造だ。

一文の要約 GitLab に積み上がる開発の成果物を AI が継続して分析し、組織のいま有効な開発の知識へ変換し蓄積する Read-Only Engineering Knowledge Platform。

そしてこれは白紙からの設計ではない。この提案の知識の保存・索引・連結のエンジンは、事前の検証のために運用している Reference Wiki ですでに実装され検証されたものだ — 2026-07 時点の実測で、文書 115 編 · 固有の概念 370 個 · 自動の関連エッジ 364 本 · 人が宣言した型つきの知識の関係 114 件が決定的な登録のパイプラインの上で回っている。このシリーズの知識の管理の体系・資産の活用の編が、そのエンジンをどう会社の規模へ広げるかを扱う。つまり本提案は「作れるもの」の想像ではなく、「運用中の検証されたエンジンを GitLab につなぐ方法」の記述である。

最終の絵 — 好循環

目標はウィキそのものではない。開発の成果が知識になり、積み上がった知識がまた次の開発の生産性を上げる好循環の構造だ。人が書くウィキは「開発 → 文書の作成 → Wiki への登録」という追加の労働を求めるので続かなかったが、この構造では開発の経験が組織の資産になり、くり返しの分析が減り、プロジェクトのあいだで経験が再利用され、オンボーディングが速くなり、設計の意図が保たれ、Claude Code のような AI の道具が組織の知識を Context として使えるようになる。

開発するほど組織が賢くなる構造 — これが本提案の最終の方向だ。

このシリーズの構成

  • なぜいまか — 散らばり消えていく開発の知識、その費用の根拠
  • 提案の要 — 開発の流れはそのまま、知識化は AI が。Event Stream と Knowledge State
  • プラットフォームのアーキテクチャ — 7 階層の構成、知識の生成の Trigger、増分の分析、知識の無矛盾のゲート、運用の安定性
  • 知識の管理の体系 — 価値の判定 · 知識の原子の構造（実証のスキーマ + 拡張） · 二重の連結 · Identifier の検索 · 出典の追跡 · 信頼の等級 · 寿命の管理
  • 資産の活用とセキュリティ — 検証された Reference Wiki のエンジン（wiki-plugin）の再利用、AI の消費の層、知識の等級とアクセスの分離
  • 付加価値と活用のシナリオ — API の仕様書の自動の更新、社員・パートナー・顧客・AI の対象別のビュー、AI コーディングの事前の知識、非開発の職種での活用
  • 推進のロードマップ — 4 つの Phase、1 次の PoC（OmniEsol ERP · SCM のドメイン）、ゲートで計測する検証の KPI

なぜいまか — 散らばり消えていく開発の知識

プロジェクトを進めれば、Architecture と設計の構造、業務の Rule と状態の遷移、DB の Table・Column の意味、API の連携、障害の原因と解決の方法、性能の改善の事例、再利用できる開発のパターンといった知識が次々に生まれる。しかしこの知識のほとんどは Source Code · Commit · Merge Request · Issue · メッセンジャー · メール · 会議 · 個人の記憶に散らばったまま残り、組織の知識として積み上がらない。

費用はすでに数字になっている

  • 開発者の 62% が毎日 30 分以上を答え探しに使い、68% は週に 1 回以上、知識のサイロにぶつかる — Stack Overflow Developer Survey 2022
  • 開発者の 69% が週に 8 時間以上（勤務時間のおよそ 20%）を非効率で失い、主な原因として「不十分な文書」を挙げる — Atlassian, State of Developer Experience 2024
  • 知識労働者は勤務時間の 19% を情報の検索・収集に使う — McKinsey, The Social Economy (2012)
  • 職務の知識の 42% はその人にしかない固有の知識なので、退職すれば同僚はその業務の 42% を行えない。大企業の基準で、非効率な知識の共有による損失は年に 4,700 万ドルと推計される — Panopto Workplace Knowledge Report (2018)
  • 新しい開発者が十分な生産性に達するまでには、平均で 3〜9 か月かかる — DX, Developer Onboarding Research

その結果として組織では、同じ問題のくり返しの分析、設計の意図と変更の背景の喪失、プロジェクトのあいだでの経験の再利用の不足、担当者の異動・退職にともなう知識の損失、新しい開発者の高いオンボーディングの費用、AI の開発の道具を使うたびの Context の説明のくり返しが、何度も起きる。

「文書をきちんと書こう」は答えにならない

オープンソースの調査では 93% が「不完全あるいは古い文書」を蔓延する問題として挙げながら、60% は文書にほとんど貢献しなかった（GitHub Open Source Survey 2017）。Stack Overflow は、社内のウィキや文書の DB が放置され信頼を失う構造的な理由を早くに分析している（Why Your Wikis … Don't Work, 2019）。日程と優先順位に押される開発の現場では、人の真面目さに頼る文書化は続かない。

問題の定義しなおし 足りないのは開発者の真面目さではなく構造だ。知識はすでに GitLab に積まれている — それを読んで整理する主体が人である必要がないだけである。そしてその構造の半分（知識を収めてつなぎ検証するエンジン）は Reference Wiki としてすでに運用中だ — ないのは GitLab とのつながりだけである。次の編の提案の要でその構造を扱う。

問題意識と提案の輪郭をつかんだところで、中核とアーキテクチャが「開発フローはそのまま、知識化は AI が」という設計を具体化します。
