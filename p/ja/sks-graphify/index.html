graphify — コードベースを知識グラフに変え、grep の代わりに問い合わせさせるスキル

3行要約

  • graphify は /graphify . 一行でフォルダ内のコード・文書・PDF・画像・映像を一つの知識グラフにし、以後エージェントがファイルを丸ごと読む代わりに graphify query・path・explain で必要な部分グラフだけ受け取るようにするスキルだ。コードは tree-sitter（構文木パーサー）でローカルに LLM なしで解析し、すべてのエッジに EXTRACTED・INFERRED・AMBIGUOUS の信頼タグを付ける。
  • 2026年4月4日の PyPI 初公開から11月23日の 0.9.118 まで284回リリースされ、Claude Code・Cursor・Codex・Gemini CLI など20余りのアシスタントに対応する。リポジトリのスター数は集計サイトごとに7.6万から15万まで割れており、この記事は「10万前後」とだけ記す。開発元は Graphify Labs（Y Combinator S26）、ライセンスは Apache-2.0 と MIT の二重。
  • 公式ベンチマークは LOCOMO 記憶検索で recall@10 0.497（mem0 0.048）、グラフ構築の LLM 費用0を掲げる。よく引用される「トークン71.5倍削減」は52ファイルのコーパスで質問1回あたりの値で、実際のセッション単位の独立測定では7〜8%の削減や品質同率（44対45点）だった。大きなリポジトリの道案内・影響分析に強く、小さなプロジェクトと集中編集では利得が少ない。

コーディングエージェントが見知らぬリポジトリで最初にするのは grep とファイル読みだ。質問が「このエンドポイントはどこでストレージに届くか」のように構造を問うものなら、ファイルを一つずつ読んでコンテキストに積む方式はトークンを多く使い、全体像を取りこぼす。graphify はその場所にグラフを置く。一度作ればセッションが変わっても残り、質問ごとに関連ノード数十個だけを返す。この記事は公式リポジトリ（README・ARCHITECTURE・BENCHMARKS・skill.md）と外部の検証記事をもとに、動作原理、導入と使い方、ベンチマークの実際の意味、限界とセキュリティを整理する。このウィキも文書グラフの上で動くリポジトリなので、最後に二つのグラフを並べた。

1. どう作られるか — 三つのパス

公式の how-it-works 文書と ARCHITECTURE.md のパイプラインを写した。第1パスは33言語を tree-sitter 文法で、7言語（Dart・Apex・COBOL・Razor・Blade・Pascal・Robot Framework）は独自の抽出器で処理する。

核心は「コードは LLM に送らない」という原則だ。関数・クラス・import・呼び出し関係は構文木から決定的に取り出されるので、同じ入力に同じグラフが出て、費用は0で、何も外に出ない。文書と画像だけが意味抽出のためにモデルを通り、Claude Code の中ではそのセッションのモデルがサブエージェントを並列に立てて処理し、ターミナルで graphify extract を回すときは設定した API キー（Gemini・Kimi・Claude・OpenAI・DeepSeek・Azure・Bedrock・Ollama の順に自動検出）を使う。コミュニティ検出は Leiden アルゴリズム（エッジ密度でノードをまとめるグラフクラスタリング）で、埋め込みもベクトルストアも使わない。モデルが抽出した semantically_similar_to エッジがすでにグラフ内にあり、その構造自体が類似度の信号になるという説明だ。コミュニティ名は LLM なしでハブノードの名前から付ける。

2. すべての線にタグ — 信頼度の体系

how-it-works 文書の規則表。スキルファイルの「正直ルール」はエッジをでっち上げず、分からなければ AMBIGUOUS にせよと釘を刺す。同じ関係が複数箇所で見えれば最も高いタグ一つだけを残し、残りは also_seen に記録する。

このタグが graphify を「もう一つの検索インデックス」と分ける点だ。graphify explain "APIRouter" を打つとソース位置、コミュニティ、次数とともに接続47本が [uses] [INFERRED]、[imports] [EXTRACTED] のようにタグ付きで出て、graphify path "FastAPI" "ModelField" は3ホップの経路とその経路全体の信頼度（最も弱いホップ）を返す。リポジトリの BENCHMARKS.md は FastAPI の本番パッケージ内の INFERRED クロスファイルエッジ12本を手で全数検査してすべて正しかったと記しつつ、日付付きの一回限りの点検であり常時指標ではないと断る。解決器は「間違ったエッジより無いエッジ」を選ぶ。

3. 導入と使い方

Python 3.11.5〜3.14 と uv（または pipx）があれば二行だ。PyPI のパッケージ名が graphifyy（y が二つ）である点だけ注意する。他の graphify* パッケージは無関係だ。

uv tool install graphifyy      # CLI の導入 (pipx install graphifyy でも可)
graphify install               # Claude Code が既定。スキル + CLAUDE.md ブロック + PreToolUse フック
graphify install --project     # リポジトリ内 .claude/skills/graphify/ に導入 (git add の案内を表示)
graphify cursor install        # Cursor
graphify install --platform codex    # Codex ($graphify で呼ぶ)

そのあとアシスタントの中で /graphify . を打つ。スキルはまず graphify-out/graph.json があるか見て、あれば作り直さず問い合わせに移る（速い道）。なければファイル検出 → 抽出 → グラフ → クラスタリング → 命名 → 出力の順に進み、コーパスの大きさとトークン費用を報告する。スキルファイル自体が「API キーを決して尋ねず、キーなしで進めよ」と書いてあるので、コードのリポジトリでは何も設定せずに終わる。

スクリプトで使いやすいよう終了コードが決まっている。0 は回答、3 は名前が複数ノードに当たって候補を列挙した場合、4 はノードなし。名前が重なれば推測せず拒否する側だ。プロジェクト設定はスキャンルートの .graphifyrc に置く。拡張子が曖昧なファイル（.inc が PHP か Pascal か、.h が C か C++ か）は language.inc=php のように固定しないとグラフが粗くなる。

4. エージェントに本当にグラフを使わせる仕掛け

README の「Make your assistant always use the graph」節と install.py のフック定義を写した。フックのコマンドは導入時点の絶対実行パスを埋め込むので、アップグレード後は graphify install と graphify hook install を再実行する。

グラフがあってもエージェントが使わなければ意味がない。graphify がこの問題を扱う方法が、他のコードインデックス系ツールと違う点だ。graphify install はスキルファイルを置くだけでなく、CLAUDE.md に案内ブロックを書き、Claude Code の PreToolUse フック（ツール呼び出し直前に割り込むフック）を .claude/settings.json に登録する。フックは Read・Glob・Grep はもちろん Bash の cat・head・tail・sed -n のような読み取りコマンドの前でも発動し、「先にグラフを見よ」と勧める。--strict（または GRAPHIFY_HOOK_STRICT=1）で導入するとセッション最初の原本読みを一度拒否してグラフへ送り返し、直近30分以内にグラフ質問があればそのまま通す。拒否はセッションあたり一度なので、エージェントが永久に塞がれることはない。グラフが古ければ（最後のコミット後に変化）フックがそれも知らせる。

5. ベンチマーク — 公式数値と外部の測定

BENCHMARKS.md（2026-07-05 更新）の表。すべてのシステムを同じハーネスで同じモデル（Kimi K2.6）・同じ予算で回し、審判を第二審判と照合（一致 90.6%、カッパ 0.81）したと述べる。supermemory の recall は独自の埋め込み器を使う制約のため直接比較が難しいと脚注にある。コード知能の項目は n=6 で標本が小さい。

ベンチマークを読むときは二つを分けなければならない。第一に、上の表は graphify 自身のハーネスの結果だ。公平性ルール（単一モデル、共有埋め込み器、支出台帳）を公開し再現コマンドを記している点は評価できるが、自社測定という事実は残る。第二に、最も広まった数値「トークン71.5倍削減」はベンチマーク表ではなく how-it-works 文書のトークン比較から来ている。そのコーパスは Karpathy のリポジトリ三つ + 論文5本 + 画像4枚（52ファイル）で、質問1回あたり約1,700トークン対原本全体約123,000トークンだ。同じ文書が4ファイルでは5.4倍、6ファイルのライブラリでは約1倍と記す。小さなコーパスはどのみちコンテキストに入るので、圧縮ではなく構造把握が価値だという意味だ。

公式数値は how-it-works 文書、独立測定は検索で確認した整理記事（Zero-to-Hero ガイドが引用した Exchangepedia・Medium・KubeBlogs の値）に基づく。原文の多くはこの記事を書いた環境で開けず、ガイドの引用をそのまま写した。

6. 利点と限界

強いところ弱いところ
大きなリポジトリに初めて入るとき。ハブとコミュニティで構造を先に掴み、「このエンドポイントからストレージまで」を経路で見る小さなプロジェクト。ファイルがコンテキストに全部入るなら質問のオーバーヘッドがむしろトークンを増やす
影響分析とオンボーディング。共有コンポーネントの呼び出し元・依存を一度に列挙し、# WHY: コメントや ADR がノードとしてコードにつながる集中編集。数ファイルを直す作業ではエージェントがそのまま rg に行く方が速く、実際にそうする
文書の多いリポジトリ。PDF・論文・映像まで同じグラフに入り「コードと設計文書のつながり」が見える古いグラフ。pull・merge はフックが拾わず、graphify update . を忘れると誤った地図を持ち歩く（新ディレクトリ未検出 #1837 など）
検証可能性。エッジごとにタグと file:line が付き、答えを原本と照合できるグラフの答えは「文脈であって検証済みの答えではない」。INFERRED エッジは誤りうるし、テストコードの同名ヘルパーがノイズを作る
費用。コードグラフは無料・オフラインで、再実行はハッシュで飛ばす意味パスは文書・画像を設定したモデルに送る。Kimi を選べば Moonshot のサーバーへ行く。ログ ~/.cache/graphify-queries.log が質問を残す（無効化可能）

セキュリティ面では、2026年11月21日の 0.9.115 が、Windows でリポジトリ内のパス（.sh の source \\host\share\x のような UNC パス）がスキャンルート外に触れて SMB 認証を誘発していた問題を修正した（GHSA-g6c9-j4vm-mwq4）。見知らぬリポジトリをグラフにするツールなのでこの種の入力処理問題が起こりうるということで、最新版の維持が答えだ。スキルファイル自体もスキャンパスをシェルに置換せず引用 heredoc で渡し、パスに混ざったシェルコードが実行されないよう組まれている。共有 HTTP MCP サーバーを立てるときは --api-key を置き、graphify-out/cache/・manifest.json・cost.json は gitignore に入れる。

7. このウィキのグラフと並べると

このウィキは文書79編を概念共有・引用バックリンク・宣言された型付き関係の三層でつなぐ独自の知識グラフを持つ（接続の三層）。材料が違う。このウィキは人がキュレーションした概念と本文リンクからエッジを作り、graphify は構文木から呼び出し・import・継承を機械で取り出す。だが運用原則は似ている。このウィキの「本文に実在する関係だけ」は graphify の「エッジをでっち上げず、分からなければ AMBIGUOUS」と同じ場所にあり、どちらも埋め込みなしで構造そのものから隣人を見つける。違うのは用途だ。このウィキのグラフは人と AI が文書を行き来する地図で、graphify のグラフはエージェントがコードを読む前に立ち寄る索引だ。このリポジトリの app.js・tools/*.py に graphify を回せば文書グラフの隣にコードグラフがもう一つできるわけだが、今は文書側のグラフしかないので次の実験として残しておく。
