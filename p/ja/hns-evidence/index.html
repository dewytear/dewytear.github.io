ハーネスがスコアを動かす証拠 — Microsoft の白書と RHO・HarnessPro 研究を重ねて読む

3行要約

  • Microsoft は2026年11月9日の白書で、同じモデル・同じタスクのままハーネスだけを入れ替えて測定した。通過率は GPT-5.5 Chat で10.8ポイント、Claude Opus 4.8 で22.1ポイント上がり、モデルを替えた側はほとんど動かなかった。
  • 学界は同じ結論に別の道でたどり着いた。RHO（香港城市大学・Microsoft Research Asia、EMNLP 2026）は正解ラベルなしに過去の実行記録だけでハーネスを直し、SWE-Bench Pro の通過率を59%から78%へ上げた。後続の HarnessPro はそのループを再帰的に回し、性能と費用を同時に最適化してライト・ミディアム・ヘビーの三つのハーネスを出す。
  • 三つの資料に共通する結論は一つだ。モデルを固定したとき、結果を二桁ポイント動かす変数はハーネスであり、費用は呼び出しが増えてもキャッシュと出力圧縮でむしろ減らせる。この記事はその三資料を数値・構造・限界まで一か所に並べる。

ハーネス（harness）はモデルを取り囲む実行環境だ。モデルに渡す指示文、使えるツール、ツールが失敗したときの規則、出力をどこまで切って戻すかといった運用方針がすべてハーネスに属する。定義と構成はハーネスとはで扱ったので、ここでは繰り返さない。この記事の関心は別のところにある。2026年後半、「ハーネスはモデルと同じくらい、あるいはそれ以上に結果を左右する」という主張が、産業界の白書と学術論文の両方から数値付きで出た。ニュースとして一度消費するには惜しい資料なので、三編を重ねて読む形で書き留めておく。

三つの流れが同じ年に集まった。学界はハーネスが自らを直す方法を、Microsoft はハーネスを入れ替えたときの効果を、評価研究はハーネスがベンチマークスコアの隠れた変数であることを、それぞれ数値で示した。

1. Microsoft の白書 — 同じモデル、別のハーネス

Microsoft Copilot Studio にはハーネスが二つある。トピック・変数・ツールを作成者が一つずつ配線する Standard ハーネスと、モデルが計画を立ててツールを選び、失敗したら再試行するエージェントループ型のハーネスだ。後者は GitHub Copilot のコーディングエージェントから持ち込まれたため GitHub Copilot ハーネスと呼ばれていたが、10月28日に Microsoft 全体の共通基盤にするとして Microsoft Copilot ハーネスへ改名された。改名の告知は機能や課金に変更はないとしている。

11月9日のブログとともに公開された白書は、二つのハーネスを同じタスク・同じモデルで回した社内評価（2026年10月）の結果だ。主要な数値は次のとおり。

Microsoft のブログと白書（2026年11月9日）の数値を写した。モデルを替えた効果は「ほとんどなかった」としか書かれていないため棒にしていない。

この数値で読むべきは上昇幅そのものより、その非対称性だ。同じハーネス交換が Claude Opus 4.8 では二倍近く大きく効いた。白書は理由を長く説明しないが、公開されている構造だけで説明がつく。新しいハーネスはツール呼び出しが失敗したとき84~91%のケースで再試行し、Standard ハーネスは7%未満にとどまった。長いタスクで一度のツール失敗がそのままタスク失敗につながっていた損失が消えたわけだ。モデルがツールを上手に扱うほど「もう一度試す機会」の価値は大きいので、上昇幅がモデルごとに違って出るのは自然だ。

費用の項目も直感とは逆だ。モデル呼び出しは約二倍に増えたのに、入力処理の費用は15~21%減った。白書が挙げる理由はキャッシュである。長い会話で入力の83~88%がキャッシュから処理されれば、呼び出しが増えても新しく読むトークンは少ない。呼び出しあたりの遅延も10~36%減った。つまり「エージェントループは高い」という通念は、キャッシュを前提にしない計算だった。

2. RHO — 正解なしにハーネスを直す方法

Microsoft の実験は人が設計した二つのハーネスを比べた。学界の問いはもう一歩先に進む。ハーネスをエージェント自身が直せるか、それも正解ラベルなしで。従来の方法（プロンプト最適化、スキル・ツール合成、エージェント探索）はラベル付きの検証セットに対して繰り返し採点する必要があったが、実際の運用環境にそんなセットはない。代わりにエージェントが毎日吐き出すラベルのない実行記録（軌跡）がある。

RHO（Retrospective Harness Optimization、回顧的ハーネス最適化）は香港城市大学と Microsoft Research Asia の研究者が2026年6月に arXiv へ投稿し、EMNLP 2026 Findings に掲載した論文だ。方法は三段階からなる。

DPP（行列式点過程）は「難しい」と「互いに異なる」を同時に満たす部分集合を選ぶ確率的手法。自己選好は、エージェントが二つの実行結果を並べて見て、どちらが良いかを自分で選ぶことを指す。

第1段階で過去タスクのうち難しく互いに異なるものだけを少数選ぶ理由は費用だ。すべてのタスクを解き直すことはできないので、失敗が集まる場所を代表する標本を抜く。第2段階はそのタスクを何度も並列で解き直して二種類の信号を得る。一つの実行の中で「テストが通ったか」のような自己検証の信号、複数の実行の間で「同じ答えになるか」のような自己一貫性の信号だ。第3段階でエージェントはこの診断を見てハーネスの修正案を複数書き、各修正案で解き直した結果を元の結果とペアで比べ、自分でより良いと判断したものだけを採用する。どこにも人の採点や正解は入らない。

結果は1ラウンド基準だ。比較対象は同じ呼び出し予算を使うラベル不要の方法である。

ラベルを使う方法とも比べている。検証セットに対して採点する Meta-Harness を同じ1ラウンド予算で回すと SWE-Bench Pro で0.62、RHO はラベルなしで0.78だった。RHO がハーネスに書き込むものは三種類ある。タスクに依存しない一般指示、過去の失敗の背後にある環境の癖を記したスキル、そして実行可能なツールだ。それぞれが元の軌跡で観察された失敗類型の一つを狙う。

限界も論文自身が書いている。自己選好は保守的な選択器であって完璧な順位付けではない。SWE-Bench Pro では選好度の低かった候補の一つが実際には0.85で、採用されたもの（0.78）より高かった。ただし採用されたハーネスが基準値より悪化したベンチマークはなかった。また、コーディングエージェントでこの方法がうまく効く理由の一つは「テストが通ったか」が信頼できる自己信号であることなので、実行で確かめられない領域では自己選好が揺らぎうる。このウィキが上級ティップで扱った自己承認バイアス（モデルが自分の成果物を甘く評価する傾向）と同じ根だ。

コードは公開されており、Claude Code 用の動的ワークフロー（retrospection.js）としても束ねられている。そのワークフローはプロジェクトの CLAUDE.md、自動メモリ、補助スクリプトをハーネスとみなし、過去のセッション記録だけで1ラウンドを回す。論文の言うハーネスは Claude Code 利用者にとってすでに手元にあるファイル群だ、ということになる。

3. HarnessPro — 再帰で回し、費用まで軸に入れる

HarnessPro は2026年10月に arXiv へ投稿された後続研究だ。公開リポジトリのパッケージ名が src/rho/ で、環境変数も RHO_ で始まることから、RHO のコードの上に築かれた研究で間違いない。報道は清華大学の研究として紹介したが、arXiv 側の著者情報では所属を確認できず、論文自体も「査読中」の表記を付けている。この記事では所属を断定せず「RHO の後続研究」と呼ぶ。

RHO と違う点は二つ。第一に、一度振り返って終わりにせず、診断・進化・選択を再帰的に繰り返す。第二に、目的関数に費用を入れる。性能だけを見るとハーネスは「もっと考え、もっと呼び出せ」の方向にしか育たない。費用を第二の軸に置いてパレート選択（一方の軸を犠牲にしなければ他方を良くできない候補だけを残すこと）をすれば、フロンティア上に複数の運用点が残る。HarnessPro はそのうち三つを選び、ライト（費用優先）、ミディアム（均衡）、ヘビー（性能優先）として出す。

右側の点の位置は論文が報告した相対値を図式化したもの。ヘビーは RHO よりわずかに通過率が高く費用が4分の1ほど低い。ミディアムは通過率を1ポイント譲る代わりに費用を半分以上減らす。

数値は Codex + GPT-5.5 基準で、比較基準は RHO ハーネスだ。ヘビーは通過率 +2.0ポイントで費用26.1%減、ミディアムは通過率 -1ポイントで費用53%減。ベンチマーク別では Terminal-Bench 2 でヘビーが3回平均80.8%と RHO より4.5ポイント高く、費用は31.7%低かった（論文の版によって33.9%とも書かれている）。SWE-Bench Pro ではヘビー80.7%対 RHO 80.0%で費用26.5%減だ。実験は GPT-5.5 + Codex と GLM-5.2 + Claude Code の二つの組み合わせ、ベンチマークは Terminal-Bench 2、SWE-Bench Pro、ProgramBench の三つである。

進化したハーネスが実際に何を含むかはリポジトリで読める。Terminal-Bench 2 用のハーネスを開くと次のものが入っている。

  • プロファイル選択器: タスク説明だけを見て compact・lean・standard・deep・research の五つのプロファイルから一つを選ぶ規則文書。プロファイルごとに推論強度（low・medium・high）と「何回目のツール呼び出しから節約モード、何回目から仕上げ」という呼び出し予算が付く。ライトは compact タスクに小さいモデル（GPT-5.4-mini）を割り当て、ヘビーは standard タスクを high 推論に上げて仕上げ検証の余裕を増やす。
  • 出力圧縮: ツール出力を4,000文字、先頭2,400文字・末尾900文字だけ残し、履歴トークンに上限を置く方針。費用削減のかなりの部分はここから出る。
  • 機能の無効化リスト: ブラウザ利用、マルチエージェント、プラグイン、画像生成など、タスクに不要な機能を切っておくリスト。
  • セッション指示文: 「要求された実装をモックやプロキシに置き換えないこと」「仕上げ前にタスクを読み直し、成果物を独立した根拠と照合すること」のような一般規則。タスク ID や過去のスコアといったタスク固有の情報は入れていないと明記している。
  • 検証補助ツール: SWE-Bench Pro 用ハーネスには、要件台帳を書いてスモークテストを回す repair-verify スクリプトと契約検証チェックリストが含まれる。

つまりエージェントが自分で書いたハーネスの実体は長いプロンプト一枚ではなく、推論強度の割当表と呼び出し予算、出力の切り詰め規則、切る機能のリスト、検証スクリプトの束だ。このウィキが動作原理でハーネスの3要素として整理したのと同じ場所に、数値付きで収まっている。

三つの資料が異なる方法で同じ方向を指しているというのが、この記事を書いた理由だ。モデルを固定したままハーネスだけ替えても通過率は二桁ポイント動き、その利得のかなりの部分は「失敗したら再試行」「必要なだけ推論」「出力を切って戻す」のような、モデル能力とは無関係の運用規則から出ている。費用は呼び出し回数ではなくキャッシュと圧縮が決める。

反対方向の証拠も並べておくべきだ。7月の Scaffold Effect 論文は公開ハーネス三つ（Goose、OpenCode、OpenHands）にモデル二つを入れて Terminal-Bench Pro 50問を回したところ、解けた問題あたりのトークン消費がハーネスによって最大40倍違った一方、通過率の差は0~8ポイントにとどまった。モデルを上げてもトークン費用は1.0~1.3倍しか動かなかった。この論文の結論は、評価の単位を「モデル」ではなく「ハーネス・モデルの組」として書き、費用を併記せよというものだ。同じ月の「ハーネスが買うのは、おおむねトークンだ」という題の論文も、同じモデル・同じタスクでハーネスによりタスクあたり費用が最大3倍開くと報告した。ハーネスがスコアを上げるという主張と、ハーネスは主に費用を分けるという主張は矛盾しない。どのハーネス同士を比べるかによって差がスコアに出ることも費用に出ることもある、という意味であり、だからこそ二軸を併せて報告する HarnessPro 方式の報告が基準になりうる。

5. Claude Code 利用者に残るもの

これらの資料を Claude Code 側に移して読むと三つが残る。第一に、CLAUDE.md・スキル・フック・自動メモリはそれ自体がハーネスであり、RHO のリポジトリはこれらのファイルを過去のセッション記録だけで直すワークフローを実際に出した。第二に、HarnessPro が進化させた項目（推論強度の割当、ツール出力の切り詰め、不要機能の無効化、仕上げ検証の規則）はすべて Claude Code の設定とフックで表現できるものだ。第三に、効果を主張するには Scaffold Effect 論文の言うとおり通過率とトークンを同時に測らねばならない。このウィキの活用と拡張が扱った性能測定の項目がまさにその場所だ。
