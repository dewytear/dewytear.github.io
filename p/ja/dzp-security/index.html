資産の活用とセキュリティ

はじめから作り直さない

事前の検証のために運用している Reference Wiki（知識はどう積み上がるのかのシリーズが解説する、あのウィキ）がすでに備えている機能を複製して PoC を始め、検証された機能を会社のプラットフォームへ育てる。2026-07 の時点で実証されている範囲: HTML Fragment の文書、SPA の Web UI、JSON の Navigation Tree（不変の ID と物理の経路の分離）、統合／Tag／Concept の検索、Knowledge Index（決定的なビルド + --check のドリフトのゲート）、自動の関連の推薦（related）と型つきの知識の関係 5 種（relations）、Knowledge Map · 3D/2D の知識グラフ、AI の消費の層（llms.txt · 自己完結のグラフ JSON）、4 層の CI の検証のゲート、Work Log、Git History にもとづく文書の履歴。

再利用は「コードを参考にする」の水準ではない。このエンジンはすでに wiki-plugin（v0.7.0）としてパッケージされている — 登録・索引・検証の道具 18 種とスキル 4 種（add-doc · index · validate · wiki-init）を収め、新しいリポジトリに入れれば同じ知識の体系をすぐに立ち上げる（ウィキのエンジンのプラグイン化）。Reference Wiki 自身がこのプラグインの最初のドッグフーディングの利用者として運用しているので、「はじめから作り直さない」はスローガンではなくインストールの手順である。

とくにこの Reference Wiki では、AI が文書を作成・修正するときに知識の体系への反映が規則として義務づけられている（リポジトリの AI 向けの指針の文書で強制）。文書が一編加われば、ナビゲーションへの登録 → 知識の索引のエントリ（概念と関係の 5 型の多角的な検討を含む — 検討の抜けは、遮らないレビューの信号が知らせる） → 決定的な索引のビルド → 知識の地図・グラフ・検索への自動の反映 → Work Log への記録、までが同じ変更の単位（PR）で一緒に動く。会社のプラットフォームの「知識の反映率」という運用の規律が、すでに小さな規模で検証されているわけだ。

文書が増えれば知識の体系も一緒に更新される — 規則として義務づけられているので、人が気をつけなくても壊れない。
  • Reference Wiki → 機能の実験 → 検証 → 会社の PoC → 安定化 → 組織への展開という経路をとり、検証されていないものを組織へいきなり入れない。
  • 文書は HTML を中心に運用し、表 · Dashboard · SVG の Diagram · <details> · 状態の Badge · Warning Box · Architecture Flow · DB の構造の可視化を活かす。
  • HTML による AI の Token の増加は、文書の全体を読まない Knowledge Index にもとづく Retrieval で最小にする。これは CLAUDE.md の階層と MCP の連携で組織の知識を AI の文脈にする Anthropic 公式の推奨のパターンとも地続きだ。

AI の消費の層 — 機械が読む三つの扉

「AI が組織の知識を Context として活かす」という約束にも、Reference Wiki にはすでに実物がある（AI はこのウィキをどう読むのか）。外部の AI は三つの扉から入ってくる: ① llms.txt — 知識の全体の表紙（何がどこにあるか）を llmstxt.org の慣例で見せる → ② knowledge-graph.json — たった一度の fetch でグラフの全体（ノード・関連・型つきの関係・概念・各文書の URL）を受け取る自己完結のファイル → ③ 必要な文書だけを選んで個別に fetch。コーパスの全体を埋め込んだり毎回クロールしたりせずに、AI が関係をたどって必要なぶんだけ読む構造であり、これらのファイルは索引から自動で生成され、--check のゲートが古いまま配備されるのを止める。会社のプラットフォームの Claude Code や AI Agent との連携は、この契約を社内網の URL の上へそのまま移す仕事だ。

セキュリティとアクセスの構造

会社の開発の知識には、内部の Architecture、顧客のプロジェクトの情報、DB の構造、障害の分析、セキュリティの設定、認証に関わる情報が含まれうる。したがって知識の等級を分け、保管庫とアクセスを分離する。

  • PUBLIC — 全社員が閲覧できる一般の知識
  • INTERNAL — 開発の組織の範囲の技術の知識
  • CONFIDENTIAL — 顧客・プロジェクトの機微な情報を含む知識
  • RESTRICTED — 限られた組織だけがアクセスするセキュリティの知識
ひとつの公開の Wiki に混ぜない 勧める構造は General Wiki（全社員） · Engineering Wiki（開発の組織） · Restricted Knowledge（限られた組織）という保管庫とアクセスの分離だ。すべてのセキュリティの等級をひとつの公開の Wiki に混ぜず、社員は自分の権限の範囲の中だけで検索し閲覧する。
