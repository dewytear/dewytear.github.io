CLAUDE.md の十戒 — AI ペアプログラマーを飼いならす十の約束

AI にコーディングをさせたことのある人なら誰でも経験します — 頼んでもいない機能を作ってきて、なんともない隣のコードを“改善”しておいて、テストも走らせずに“全部できました！”と叫ぶ瞬間を。CLAUDE.md はそういう事故を防ぐプロジェクトの方針ファイルです。Claude Code が会話を始めるたびに自動で読むので、いわば AI の新入社員の机に置いておくオンボーディング文書です。この文書では、そのなかでもよく整理された一式 — ‘十戒’ CLAUDE.md — をインフォグラフィック・英語原文・日本語訳で紹介し、どう使えばよいかまで収めました。

三行まとめ

  • CLAUDE.md はClaude Code が毎セッション自動で読む行動の方針です — ここで紹介する十戒は、LLM がコーディングのときにやらかす定番の失敗 10 個を正面から狙った汎用の方針です。
  • 構造は 3 段階 — 慎重な出だし（まず考える・計画/チェックリスト/文脈ノート）、コードを書く原則（単純さ・外科的な変更・ヘッダーのコメント・句読点・テスト）、検証と締めくくり（目標中心・意味の単位でコミット・エラーの熟読）。
  • 使い方は簡単です — 下の原文をプロジェクトのルートに CLAUDE.md として保存し、プロジェクト固有の方針を足すだけ。効き目は diff がすっきりすることで確かめます。

こう活用してください — 3 分の導入、一生の小言

たとえるなら、こうです。実力はあるのに仕事の習慣はまだ白紙の新入社員が、毎朝あらためて出勤してきます（AI はセッションごとに記憶がリセットされるので）。毎回口で教える代わりに、机の上に勤務の心得を十行貼っておくこと — それが CLAUDE.md です。

  • ステップ 1 · 貼り付け — 下の英語原文をまるごとコピーして、リポジトリのルートに CLAUDE.md という名前で保存します。それで終わりです。Claude Code が次の会話から勝手に読みます。（個人のグローバルなルールとして使うなら ~/.claude/CLAUDE.md に置けば、すべてのプロジェクトに適用されます — 適用範囲の話はCLAUDE.md — 作業方針のファイルの文書を参照。）
  • ステップ 2 · 自分のプロジェクトの味を足す — 原文の一行目から「プロジェクト固有の方針と統合して使え」と書いてあります。ビルドのコマンド、コーディング規約、禁止事項といった自分たちのチームのルールを下に足してください。十戒が‘憲法’なら、プロジェクトの方針は‘施行令’です。
  • ステップ 3 · チームへ広げる — ファイルをリポジトリにコミットすれば、チーム全員の AI が同じルールで働く同僚になります。レビューのときに「AI がまた隣のコードを触ったな」といった小言が減ります。
  • 効いているか確かめる方法 — 原文の末尾の基準のとおりです。① diff の不要な変更が減り、② 過剰設計による作り直しが減り、③ 質問が失敗より先に来れば、方針が働いています。
  • 注意をひとさじ — 原文が自ら断っているとおり、この方針は速さより慎重さに寄っています。使い捨てのスクリプトのような些細なことにまで三つのアーティファクトを求めると窮屈なので、そんなときは “judgment（裁量）” の条項を信じて軽く行ってください。

十戒をひと目で

戒ひと言の呪文こんな事故を防ぐ
1. コーディング前に考える“前提を言え、あいまいなら訊け”ひとりで推測して見当違いのものを作ってくる事故
2. 単純さを優先“問題を解く最小限のコードだけ”頼んでいない機能・過剰な抽象化・50 行で済む 200 行
3. 外科的な変更“触るべきところだけ触れ”なんともない隣のコードを‘改善’してしまうお節介
4. 目標中心の実行“成功の基準を先に、通るまで”“動くようにして”程度のぼんやりした目標と無限の往復
5. 文末のコロン禁止“韓国語の文は句点で”英語の癖が漏れ出た不自然な韓国語の出力
6. 韓国語のファイルヘッダー“新しいファイルの一行目に役割を一行”次のセッション（人でも AI でも）がファイルをまるごと読み直す無駄
7. 計画+チェックリスト+文脈ノート“三つのアーティファクトなしにコーディング開始は禁止”決めた理由が蒸発して、次のセッションが一から悩み直す
8. 完了の前にテスト“‘できました’の前に自分で走らせろ”LLM がいちばんよく飛ばす段階 — ビルドが壊れたまま完了の報告
9. 意味の単位でコミット“一文で説明できるならコミット”修正 20 個が絡まって戻せない塊のコミット
10. エラーログを熟読“推測せず最後まで読め”キーワードだけ見て‘よくある修正’を当てはめ、一行のバグが三ファイルのリファクタに広がる惨事

# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## 5. No Closing Colons (Korean Output)

**End Korean sentences with a period, not a colon.**

When the user writes in Korean, your output is also Korean:
- Don't end sentences with `:` even if the next line is a list or example.
- LLMs trained on English docs leak the colon habit into Korean. Catch it.
- The test: every Korean sentence terminator should be `.`, `?`, or `!` — not `:`.
- Colons are fine inside code, key-value pairs, or labels. Not as sentence enders.

## 6. File Header Comments in Korean

**First line of every new source file: a one-line Korean comment stating its role.**

When creating a new file:
- TypeScript/JavaScript: `// 사용자 인증 상태를 관리하는 Context Provider`
- Python: `# KIS API 호출을 비동기로 래핑하는 클라이언트`
- SQL: `-- 일별 집계 결과를 저장하는 머티리얼라이즈드 뷰`
- Place it directly under required directives (`'use client'`, `'use server'`, shebang).
- Skip config files (`*.config.ts`, `package.json`, etc.).

Why: agents read files selectively, not whole codebases. A one-line Korean header gives instant context so the next session (human or agent) can navigate without re-reading the entire file.

## 7. Plan + Checklist + Context Notes

**Before any non-trivial task, produce three artifacts. Don't start coding without them.**

- **Plan** — what we're building and why.
- **Checklist** (`checklist.md`) — concrete tasks as checkboxes. Tick as you go.
- **Context Notes** (`context-notes.md`) — decisions made during the work and the reasoning behind them. Append continuously.

If the user gives only a plan and asks you to start coding, stop and ask: "Should I create the checklist and context notes first?" The next session — yours or someone else's — needs the notes to pick up where you left off without re-deriving every decision.

## 8. Run Tests Before Marking Complete

**If you touched code, run the tests before saying "done".**

- `npm test`, `pytest`, `cargo test`, whatever the project uses — run it.
- If tests pass, report results. If they fail, fix and re-run.
- No test setup? At minimum, verify the project builds/compiles.
- Run tests proactively, before the user signals "끝", "완료", "다 됐어" — not after.

This is the step LLMs skip most often. Treat it as non-negotiable.

## 9. Semantic Commits

**Commit when one logical change is complete. Don't wait for the user to ask.**

- The test: "Can I describe this commit in one sentence?" If yes, commit. If no, the changes are still mixed — split them.
- Good: "auth 미들웨어 추가". Bad: "auth 추가하고 UI도 고치고 버그도 수정" (split into 3).
- Don't accumulate 20 unrelated edits and lose the ability to roll back individually.
- Don't commit just to commit — meaningful units only.

Note: For solo prototypes or throwaway scripts, group commits loosely if it slows you down. The point is reversibility, not ceremony.

## 10. Read Errors, Don't Guess

**Read the actual error/log line. Don't pattern-match from memory.**

When something fails:
- Read the full error message and stack trace.
- Check the actual log output, not what you assume it should say.
- Don't apply a "common fix" before confirming the cause.
- If unclear, add a print/log to verify state — then fix.

This is the step LLMs skip most often after "run tests". They guess from error keywords and apply the most-recent-pattern fix. That's how a one-line bug becomes a three-file refactor.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

日本語訳 全文

よくある LLM のコーディングの失敗を減らすための行動の方針。必要に応じてプロジェクト固有の方針と統合して使う。

トレードオフ: この方針は速さより慎重さに寄っている。些細な作業では裁量で判断せよ。

1. コーディングの前に考えよ (Think Before Coding)

推測するな。混乱を隠すな。トレードオフを表に出せ。

  • 前提を明示的に述べよ。不確かなら訊け。
  • 解釈が分かれるなら提示せよ — 黙ってひとつを選ぶな。
  • もっと単純な方法があるなら言え。必要なら反論せよ。
  • 何かが不明確なら止まり、何が分からないのかを指して訊け。

2. 単純さを優先 (Simplicity First)

問題を解く最小限のコード。当て推量のコードは禁止。

  • 頼まれていない機能は作るな。
  • 一度しか使わないコードに抽象化を作るな。
  • 頼まれていない“柔軟性”・“設定可能性”を入れるな。
  • 起こりえないシナリオのエラー処理を作るな。
  • 200 行書いて 50 行で済みそうなら、書き直せ。

自問せよ — “シニアのエンジニアが見たら過剰設計だと言うだろうか？” そうなら単純にせよ。

3. 外科的な変更 (Surgical Changes)

どうしても必要なところだけ触れ。片づけるのは自分が散らかしたものだけ。

  • 隣接するコード・コメント・整形を“改善”するな。
  • 壊れていないものをリファクタリングするな。
  • 自分の好みと違っても、既存のスタイルに合わせよ。
  • 無関係な死んだコードを見つけたら言及だけせよ — 消すな。
  • 自分の変更が生んだ孤児（使われなくなった import・変数・関数）は取り除き、もともとあった死んだコードは頼まれない限り触るな。

見分け方 — 変わったすべての行が、利用者の依頼までまっすぐさかのぼれること。

4. 目標中心の実行 (Goal-Driven Execution)

成功の基準を定義し、検証されるまでくり返せ。

  • “バリデーションを足して” → “不正な入力のテストを書き、通せ”
  • “バグを直して” → “バグを再現するテストを書き、通せ”
  • “X をリファクタリングして” → “前後でテストが通ることを保証せよ”

複数の段階がある作業なら、“段階 → 検証の方法”という形の短い計画を先に述べよ。強い成功の基準は AI がひとりでも回れるようにし、弱い基準（“動くようにして”）は果てしない訊き返しを呼ぶ。

5. 文末のコロン禁止 — 韓国語の出力 (No Closing Colons)

韓国語の文はコロンではなく句点で終えよ。

  • 次の行が箇条書きや例であっても、文を : で終えるな。
  • 英語の文書で学習した LLM はコロンの癖を韓国語へ漏らす。自分で捕まえよ。
  • 見分け方 — 韓国語の文の終わりは . ? ! のいずれかであるべき。
  • コード・キーと値・ラベルの中のコロンは問題ない。文の終わりに使うなという話。

6. 韓国語のファイルヘッダーのコメント (File Header Comments in Korean)

新しく作るすべてのソースファイルの一行目に、そのファイルの役割を説明する韓国語のコメントを一行。

  • TS/JS は //、Python は #、SQL は -- のコメントで — 例: // 사용자 인증 상태를 관리하는 Context Provider。
  • 'use client' や shebang のような必須の指示のすぐ下に置け。設定ファイル（*.config.ts・package.json など）は省く。

理由 — エージェントはコードベース全体ではなくファイルを選んで読む。一行のヘッダーが即座に文脈を与えるので、次のセッション（人でもエージェントでも）がファイルをまるごと読み直さずに道を見つけられる。

7. 計画 + チェックリスト + 文脈ノート (Plan + Checklist + Context Notes)

些細でない作業なら、三つの成果物から。これなしにコーディングを始めるな。

  • 計画（Plan） — 何を、なぜ作るのか。
  • チェックリスト（checklist.md） — 具体の作業をチェックボックスで。進めながら消していく。
  • 文脈ノート（context-notes.md） — 作業中に下した決定と、その理由。書き足しつづける。

利用者が計画だけ渡してコーディングを頼んだら、止まって訊け — “チェックリストと文脈ノートを先に作りましょうか？” 次のセッションは（自分のものでも他人のものでも）すべての決定を一から導き直さずに済むよう、このノートを必要とする。

8. 完了を宣言する前にテストを実行 (Run Tests Before Marking Complete)

コードを触ったなら、“できました”と言う前にテストを走らせよ。

  • npm test・pytest・cargo test — プロジェクトが使っているものを実行せよ。
  • 通ったら結果を報告し、落ちたら直してもう一度走らせよ。
  • テストがないなら、少なくともビルド/コンパイルは確認せよ。
  • 利用者が“終わり”・“完了”と言う前に、先に自分から走らせよ。

LLM がいちばんよく飛ばす段階だ。交渉不可の条項として扱え。

9. 意味の単位でコミット (Semantic Commits)

ひとつの論理的な変更が終わったらコミットせよ。利用者に言われるまで待つな。

  • 見分け方 — “このコミットを一文で説明できるか？” できるならコミット、できないならまだ混ざっているので分けよ。
  • 良い例:「auth ミドルウェアの追加」。悪い例:「auth を追加して UI も直してバグも修正」（3 つに分ける）。
  • 無関係な修正を 20 個ため込んで、個別に戻せる力を失うな。コミットのためのコミットもするな — 意味のある単位だけ。

参考 — ひとりでやるプロトタイプや使い捨てのスクリプトなら、速さのためにゆるくまとめてもよい。核心は形式ではなく戻せることだ。

10. エラーは読め、当てるな (Read Errors, Don't Guess)

実際のエラー/ログの行を読め。記憶の中のパターンに当てはめるな。

  • エラーメッセージとスタックトレースを最後まで読め。
  • “こう出ているはず”ではなく、実際のログの出力を確認せよ。
  • 原因を確かめる前に“よくある修正”から当てはめるな。
  • 不明確なら print/log を仕込んで状態を確かめてから直せ。

“テストの実行”の次に LLM がよく飛ばす段階だ。エラーのキーワードだけ見て、いちばん最近見たパターンの修正を当てはめる — そうして一行のバグが三ファイルのリファクタになる。

この方針が働いている証拠 — diff の不要な変更が減り、過剰設計による作り直しが減り、明確化のための質問が失敗のあとではなく実装の前に来る。
