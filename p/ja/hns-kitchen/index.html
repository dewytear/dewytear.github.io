動作原理 — 厨房のたとえ・チーム・三要素

ハーネスエンジニアリングを厨房の運営にたとえると、理解しやすくなります。

一人シェフ vs マルチエージェント

一人シェフは速いけれどボトルネックが生まれ、マルチエージェントの厨房は役割を分けて品質を保ちながら長く働きます。
  • 一人シェフ — 注文・調理・検品・皿洗いをひとりで。最初は速いのですが、注文が立て込むとボトルネックが生まれ、長くは働けません。
  • マルチエージェント — 注文・仕込み・調理・検品と役割を分ける。同時に並列で、それぞれ得意なことに集中 → 品質を保ちながら長く働きます。
構成長所短所
単一エージェント速くて経済的拡張性・安定性に限界
マルチエージェント安定していて拡張性が高いコストがより掛かる

万能ではありません。一人の厨房で足りる作業もあれば、マルチが光る作業も別にあります。

ハーネス = 厨房運営の全体

誰が・いつ・何をするかが事前に設計され、エージェント・スキル・オーケストレーションがタイトにつながります。そのワークフローとルールを全体としてうまく管理することがハーネスエンジニアリングです。

品質は磨きつづける

材料が新鮮か（中間の成果物）、最後の料理が大丈夫か、中間も最終も検討・フィードバックする必要があります。ハーネスを使っても一度で完成品は出てきません。出てくる成果物は下書きと見て、エージェントたちを磨きつづけて高品質へ引き上げます。

トークンの使用量 マルチで回すぶんトークンの使用量は増えます。とくにエージェントどうしが会話するときに多くなり、計測では約 30% 多く使われたケースもありました。

エージェントチームとコンテキスト管理

複数のエージェントをどう協業させるか、そしてコンテキストをどう管理するかが、ハーネスの品質を左右します。

隔離型サブエージェント → 会話するチームへ

隔離サブエージェントは結果を返すだけですが、エージェントチームは互いを呼び起こして協業します。
  • 従来のやり方 — サブエージェントたちが隔離された環境でそれぞれ働き、結果だけを返す（並列）。互いに会話する手段がありませんでした。
  • エージェントチーム — エージェントたちがコミュニケーションしながら働くので、より賢く動きます。

たとえば、リサーチのエージェントが調査を終えて終了したあと分析のエージェントがスポーンされ、分析中にリサーチの足りない部分を見つけたとします。このとき自分で調べるのではなく、リサーチのエージェントをもう一度呼び起こして追加の調査を依頼します。

エージェントチームの有効化

この機能は実験版なので、既定では無効です。ユーザーフォルダの ~/.claude/settings.json で環境変数をオンにします。

# ~/.claude/settings.json の env
"CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  • この値をオンにして初めて、エージェントたちが会話しながらチームとして動きます。
  • エージェントが動的ロードに成功するとチームモードがきちんと入り、失敗すると隔離された通常のサブエージェントとして立ち上がることがよくあります。（実験版のバグ）
  • ちなみに Gemini の Antigravity CLI にも、エージェント間のコミュニケーション機能が追加されました。

コンテキスト = 厨房の作業台

コンテキストは料理を作る作業台のようなものです。その料理に関係するものだけが載っていればすっきりしますが、関係のないものが混ざると失敗の余地が生まれます（塩の容器に砂糖が入っているようなもの）。実際、会話が長くなると前後の考えが矛盾することがあり、その状態で仕事をさせると AI は「A が正しいのか B が正しいのか」と混乱します。だからコンテキストの管理が大切なのです。

核となる 3 要素と動作の構造

ハーネスの構成要素は多いのですが、講師はこの三つさえそろえばマルチエージェントの協業はうまく起きると見て、ここに集中します — エージェント・スキル・オーケストレーター。

1）エージェント — 自然言語の文書

エージェントはコードではなく自然言語で書かれた文書です。次のものを入れます。

  • 役割と原則
  • 入力プロトコル・出力プロトコル（結果をどんな形式で出すか）
  • 協業 — ほかのエージェントと何をやり取りするか
  • 再呼び出しやエラーが起きたときのふるまい

2）スキル — くり返し作業の標準化

スキルは name + description に、決められたプロセス・知識・チェックリストを自由に入れたものです。

  • プロセスが決まっているので一貫性が保たれます。
  • 小さなスキルを組み合わせてより大きなシステムを構成できます。
  • 標準化のおかげでくり返しの作業が速くなります。

スキル設計のコツ: くり返し作業を見つけ → 単一の責務に分け → 入力／出力を定義 → 例外を処理 → エージェントにつなぐ。

3）オーケストレーター — マイクロマネジメントしない PM

ワークフロー全体がきちんと回っているかに責任を持つ PM です。ダメな PM のように細かく口を出さず、「ワークフローをうまくこなしているか」くらいだけをチェックします。

プラグインの 6 ステップ

⑥ の検証まで終わればチーム編成は完了し、続いて運用のループが回りはじめます。

/harness は依頼を全部で六つのステップで処理します。

  1. 依頼の分析
  2. エージェントチームの設計
  3. エージェントの生成
  4. スキルの生成
  5. オーケストレーターの生成・ワークフローの策定
  6. ハーネス構成の検証
チームの動きの 6 パターン エージェントチームの協業パターンは六つが明示されています — 順次実行、並列してから統合、レビューの工程など。これらのパターンをハイブリッドに組み合わせて状況に合わせて動きます。

構造まで理解したら、残るのは応用です — 活用と拡張の章で実際の事例とハーネス 100、他のツールとの組み合わせを見ます。
