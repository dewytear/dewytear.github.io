知識の管理の体系 — 判定 · 構造 · 連結 · 追跡 · 信頼 · 寿命

パイプラインが知識を作るのだとすれば、この編はその知識がどんな構造に収まり、どうつながり、どう信頼を保つのかを扱う。ここに出てくる構造は想像ではない — 事前の検証のための Reference Wiki が、2026-07 の時点で文書 115 編 · 固有の概念 370 個 · 自動の関連エッジ 364 本 · 型つきの知識の関係 114 件の規模で実際に運用して検証したスキーマを核とし、会社の開発の知識に要るフィールドだけを後方互換（additive）に広げる。

価値の判定 — 変更の量ではなく再利用の価値

  • 知識にする対象 — 新しい Architecture・業務の Rule、DB の Table・Column の意味の変更、API の追加・変更、状態の遷移の変更、外部のシステムとの連携、くり返せる障害の解決、共通の開発のパターン、性能の改善の事例、セキュリティの方針・Dependency の変化、既存の設計の方針の変更
  • 既定で除外 — 変数名の変更、単純な Null Check、誤字・コメント・Formatting、単なる Log の追加、Test Data、一度きりの Debug、機械的な Refactoring

知識の原子の構造 — 実証されたスキーマの上に広げる

知識の一編は三重の属性として存在する。第一の重ねがノードの属性だ — Reference Wiki のナビゲーションのツリーで、すべての文書のノードは name（不変の論理 ID であり経路でもある）と path（物理の経路）を分けて持つ。ファイルがドメインのツリーの中で動いても path だけが変わり name は不変なので、積み上がったリンク・関係・検索がファイルの置き直しで壊れない。ここに表示のための label（+言語ごと）・tags・著作の model が載る（知識はどう積み上がるのか）。第二の重ねが索引のエントリ — 下の例の上の部分が実証された核、下の部分が会社向けの拡張だ。第三の重ね（連結）は次の節で扱う。

# Knowledge Index のエントリ — 実証された核 + 会社の拡張（例）
{
  // ── 実証の核: Reference Wiki が 115 編の規模で運用中のフィールド ──
  "name": "dz-erp-so-status-transition",   // 不変の論理 ID = 経路
  "title": "受注の状態の遷移の方針",
  "summary": "販売オーダーの状態の体系と、出荷・売上への遷移の条件",
  "concepts": ["受注状態遷移", "与信チェック", "分割出荷"],  // 本文に実在する概念だけ
  "section": "Douzone · OmniEsol · SCM",   // ツリーの位置から自動で計算
  "related": [ … ],                        // 自動で計算 — 手で編集しない
  "relations": [ … ],                      // 宣言された型つきの関係（次の節）

  // ── 会社の拡張（提案）: スキーマ v2 の additive の規則に従う — フィールドの追加は後方互換 ──
  "kind": "policy",  "status": "active",  "trust": "DECISION",
  "product": "OmniEsol",  "domain": "SCM",  "project": "sales-order",
  "identifiers": ["SD_SO_HDR", "SD_SO_ITEM", "SO_STS_CD", "CREDIT_CHK_YN"],
  "sources": [{
    "project": "scm/sales-order",
    "commit": "abc123",  "mergeRequest": 382,
    "paths": ["src/.../SalesOrderService.java", "mapper/.../SalesOrderMapper.xml"]
  }]
}

拡張が核を侵さないことが要点だ。Reference Wiki のスキーマの契約は「フィールドの追加は後方互換、意味の変更はバージョンの引き上げ」を明記しているので、identifiers・sources・trust のような会社のフィールドを足しても、検証器・ビルド・グラフ・検索といった既存の消費者は修正なしでそのまま動く。新しく作るのはフィールドと、そのフィールドを読む検索の層だけである。

二重の連結 — 計算された関連と、宣言された関係

知識は孤立したカードではなくグラフであるべきだ。Reference Wiki は連結を二重に実証しており、会社のプラットフォームはこれをそのまま受け継ぐ（文書はどうつながるのか）:

  • ⓐ 計算された関連（related） — 機械が共有された概念から自動で計算する対称の連結。ありふれた概念ほど低く、まれな概念ほど高く重みづけし（希少性・idf）、概念を 2 つ以上共有するか、まれな概念（全体で 3 編以下）を 1 つ共有するときだけつなぐ。連結が足りなければ同じフォルダ（System）で補い、すべての文書が 2〜4 の連結を持ち、孤立は 0 を保証する。人がリンクを張らなくてもグラフが保たれる層 — AI が大量に生成する会社の知識ではとくに大事だ。
  • ⓑ 宣言された関係（relations） — 方向と種類のある型つきの関係が 5 種: 先行知識（prerequisite） · 実装（implements） · 事例（example-of） · 根拠（evidence-for） · 置換（supersedes）。それぞれの関係は方向（A→対象）と一行の根拠（evidenceRef）、そして宣言の主体（source）を持つ。保存は正方向の一度だけで、逆方向（「この文書へ入ってくる関係」）は消費する側が自動で導く。

ここで会社のプラットフォームとスキーマがぴたりと噛み合うのが source のフィールドだ。実証されたスキーマは、宣言の主体の語彙として human · ai-proposed · imported · rule-derived をすでに予約している（Reference Wiki の 114 件はすべて human）。会社のプラットフォームではAI Curator が関係を ai-proposed として提案し、人が承認すれば human へ昇格する — 自動化の速さと「本文に実在する関係だけを張る」という正直さの原則を、ひとつのフィールドで両立させる構造だ。無矛盾は機械が守る: 存在しない対象を指す関係と、5 つの語彙の外の型は ERROR としてマージが遮られ、根拠の欠落や食い違う宣言は検討の信号（WARN）として浮かび上がる。

積み上げる更新 — 知識の密度を増やす

新しい知識が見つかったからといって、いつも新しい文書を作りはしない。まず Knowledge Index を検索して関連する文書があれば既存の文書を広げる。たとえば「受注の状態の遷移の体系」の文書がある状態で分割出荷の状態が加わったなら、新規の文書より先に既存の文書の拡張を判断する。Wiki が変更の履歴の集まりではなく継続して精製された、いまの知識の状態として保たれる理由だ。

既存の文書の拡張をいつも先に判断する — 文書の数より密度を増やす方向に。

開発の Identifier での検索

開発者は自然言語より Table 名 · Column 名 · Rule ID · Class 名 · Method 名 · API 名 · Mapper ID · Error Code で探すことが多い。上の拡張のフィールド identifiers がこの検索の一次のキーになり、検索の優先の順は① Identifier の完全一致（拡張のフィールド） → ② 題 → ③ 概念（concepts） → ④ 要約 → ⑤ タグ → ⑥ 関連する文書（related） → ⑦ 同じプロジェクトで構成する — ②〜⑥ はすべて実証された核のフィールドの上で動くので、会社が新しく作る検索のロジックは ① と ⑦ だけだ。ソースで出会った SO_STS_CD ひとつだけで、関連する方針の文書に届けるようでなければならない。

出典の追跡（Provenance）

すべての知識は、拡張のフィールド sources のようにどのプロジェクト → どの Commit → どの MR → どの Source File から来たのかを逆にたどれねばならない。Reference Wiki では文書の作成日・更新日を Git の履歴から導くことでこの原則を小さく実証しており、会社のプラットフォームは追跡の単位を GitLab の座標（commit・MR・paths）へ広げる。検索で知識を足しつつ出典を一緒に保つやり方は RAG の研究が確立したもので、外部の知識を結びつけるとより事実に即し出典をたどれる生成になり（Lewis et al., NeurIPS 2020）、ハルシネーションが大きく減る（Shuster et al., 2021）ことが実証されている。

信頼の水準 — FACT · INFERRED · DECISION

コードで見つかったというだけの理由で、公式の方針として確定はしない。最新の研究でも、最高の性能の LLM でさえコードの要約の品質と正確さを見誤る場合が報告されており（arXiv 2507.16587, 2025）、NIST の生成 AI のプロファイルはコンテンツの出典の追跡（Content Provenance）と「自信たっぷりに述べられる誤り（confabulation）」の管理を、中心のリスクの統制として求めている（NIST AI 600-1）。信頼の水準は拡張のフィールド trust に記録する。

区分意味例掲載の方針
FACTコードから直接に確かめられるTable · Column · API · Class の関係自動での掲載の可能性が高い
INFERREDコードの構造にもとづく推論再試行の目的の推定、重複の防止の推定推論であることを明示して掲載
DECISION業務・Architecture の決定GUID を選んだ理由、与信のチェックの時点の決定MR・設計の文書など追加の根拠を確かめてから掲載

寿命の管理 — 削除せず置き換える

方針が変わったからといって過去の知識を削除しない。たとえば「与信のチェック → 受注の保存の時点」が「受注の保存 + 出荷の時点で再検証」に変わったなら、既存の文書を superseded へ移して新しい方針の文書とつなぎ、いまの方針と変更の履歴を同時にたどれるようにする。このつながりこそ、関係の 5 種の置換（supersedes）の型だ — 新しい文書 -[supersedes]-> 古い文書。興味深いことに Reference Wiki では文書をその場で改訂するため、この型は正直に 0 件のまま空いている（語彙・検証・UI は備えつつ、無理な組を作らなかった）。方針の変更が実在する会社の開発の知識はこの型がはじめて実戦に投入される環境であり、下の状態機械の「置換」の遷移が、そのまま supersedes の関係の生成である。

superseded の文書は、新しい文書と supersedes の関係でつながったまま残る — 「なぜ変わったのか」が一緒に保たれる。
受け継ぐ原則 — 正直さ 概念（concepts）と関係（relations）は本文に実在するものだけを張る。連結を増やそうとして、ない概念を入れたり無理な関係を作ったりすることはグラフをゆがめる — Reference Wiki が規則として打ち込み運用してきた原則であり、検証器の WARN は「直すべき一覧」ではなく「人が一度見る一覧」だ。AI が大量に知識を生成する会社の規模では、この原則がいっそう大事になる — ai-proposed → 人の承認という流れと、遮らないレビューの信号がその安全装置である。
