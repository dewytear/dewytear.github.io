intent.md — コードより先に残す意図と、AI ネイティブ SDLC

コードレビューをしていると、こういう瞬間が来ます。何を変えたのかは diff にすべて書いてあるのに、なぜ変えたのかはどこにもない。 だからレビューがコードを検査する作業ではなく、意図を推し量る作業になってしまう。エージェントが一日にプルリクエストを十件も上げはじめると、この推測のコストがそのまま十倍になります。Anthropic が2026年8月21日に公開した AI ネイティブ SDLC プレイブックは、まさにその地点を狙っています。そして出発点に置かれたファイルが intent.md です。

三行まとめ

  • intent.md は、何を望むのか・なぜ望むのか・どんな制約の下でかをコードより先に書いてリポジトリにコミットするマークダウンファイルです。五つの節が推奨の書式です。
  • これは規則ファイルではありません — CLAUDE.md が「どう働くか」なら、intent.md は「今回はなぜこれをやるのか」です。そして Claude Code が自動では読んでくれないので、両者をつなぐ配線は自分でやる必要があります。
  • ファイル一つに見えますが、背後には六段階の絵があります — intent.md → spec.md → plan.md → diff → レビュー記録 → 障害記録 → ふたたび意図と回る輪であり、各段階の成果物がそのまま監査証跡になります。

intent.md には何を書くのか

プレイブックが示す書式は五つの節です。文書というより、答えを埋めないと先へ進めない質問票に近いものです。

Intent: [機能または問題の名前]
Author: [名前]
Status: draft

## Problem
- いま誰がどんな問題を抱えているか。そう判断した根拠は?

## Proposed outcome
- 解決したら何が変わるか?

## Affected users and systems
- ユーザー: / システム:

## Constraints
- 必ず守ること: / 範囲の外:

## Open questions
- まだ決めていないこと:

プレイブックに載る実例を見ると、抽象的な文書でないことがはっきりします。問題の節には「顧客が請求の進み具合を訊くためにコールセンターへ電話する — 対応者の通話時間のおよそ三分の一が状況確認だけに費やされる」が入り、成果の節には「顧客がポータルで請求の状況・次の手順・見込み日を見られる」が、影響の節には「請求担当者、ポータルチーム、請求コア API」が入ります。根拠のついた問題と、確かめられる成果と、これから触ることになるシステムの名前が一枚に集まります。

最後の節であるまだ決めていないことが、実務でとりわけ効きます。この種の項目はたいてい文書から消され、誰かの頭の中にだけ残り、実装の途中で「あれはどうすることにしましたっけ」と再び顔を出します。書いておけば、わからないという事実そのものが成果物になります。

CLAUDE.md とは何が違うのか

名前が似ていて紛らわしいのですが、二つのファイルは層が違います。一方はつねに真である規則で、もう一方はこの変更にだけ真である理由です。

CLAUDE.mdintent.md
収めるものビルドコマンド、規約、触ってはいけない場所 — つねに当てはまる指針この変更一つの問題・成果・制約
寿命プロジェクトが生きているあいだ機能一つが終わるまで
書く人主に開発者意図を持つ人なら誰でも — 企画・サポート・運用
承認とくになし(レビューで代える)プロダクトオーナーが承認
読まれ方セッションごとに自動でコンテキストに入る自動では入らない — 配線が要る

最後の行が、この文書でいちばん実用的な箇所です。Claude Code が起動時に自分で読み込むのは CLAUDE.md・CLAUDE.local.md・.claude/rules/ と自動メモリの索引であり、intent.md はその一覧に入っていません。 フォルダにきれいに積んでおけばエージェントが勝手に参照してくれる、という期待は外れます。つなぐ方法は四つあり、コストと確実さがそれぞれ違います。

  • CLAUDE.md に一行の指示 — 「変更を計画する前に intent/<スラッグ>/intent.md を読め」。コンテキストの費用がほぼなく最初に試す価値がありますが、指針は強制ではなく確率です。
  • @ インポート — CLAUDE.md に @intent/現在の作業/intent.md のように書けば中身は確実に入ります。ただしインポートはセッション開始時にすべて読み込まれるので、意図が溜まるほど誰も触っていない分までコンテキストを食います。いま作業中の一つにだけ使う手です。
  • スキル — 「意図を読んで仕様を書く」をスキルに包めば必要なときだけ読み込まれます。組織の intent.md の書式そのものをスキルにしておくのも、プレイブックが直接すすめる方法です。
  • フック — 必ず守らせたいなら指針ではなくフックです。承認済みの意図ファイルがないときに編集を止めるようにすれば、モデルの判断とは無関係に掛かります。

まとめると、指針は確率を上げ、フックは決めます。 どちらが要るかは、その規則を破ったときの被害の大きさが決めてくれます。

なぜいまこのファイルなのか

プレイブックの前提は一文です — コードはもはやボトルネックではない。 従来の開発ライフサイクルは、実装がいちばん長くいちばん高くついた時代に、その区間を節約するために設計されたものです。要求文書もスプリント計画も段階ごとの承認も、これから何週間もかかる仕事の向きを先に合わせるための装置でした。

エージェントが実装の区間を数時間に縮めた途端、その前提が崩れました。ところが前後の区間 — 要求の確定、レビュー、リリース — はいまも人の速度で回ります。開発者三人が一日にプルリクエストを何十件も上げ、レビューするのも同じ三人なら、起きることは二つに一つです。待ち行列が積み上がるか、ざっと見てマージされるか。 縮めて浮いた時間が後ろで淀むわけです。

ここから出る結論は「もっと熱心にレビューしよう」ではありません。人が一行ずつ打っていた時代には行単位のレビューが正しかったのであって、diff の大半をエージェントが書くいまは、人の注意を diff からその上の層へ移すべきだという方向です。何をなぜ作るのかが正確なら、間違ったコードが5,000行生まれることはありません。

六段階と成果物の鎖

プレイブックはライフサイクルを六段階に置きますが、一方向に流れる線ではなく輪として見ます。段階ごとに次の段階が読める成果物を一つコミットし、そのコミットが集まればそのまま監査証跡になります。

六つの段階がそれぞれ読める成果物を一つ残し、そのコミットが集まって監査証跡になります。
段階残るもの草案承認
計画intent.md — なぜ作るのかエージェントプロダクトオーナー
設計spec.md — 何をどんな要求・設計でエージェントプロダクトオーナー
ビルドplan.md — どこをどの順で、何で検証するかエージェント開発者
テストコードとテスト、そして通過の証拠エージェントゲート(自動)
デプロイREVIEW.md に書いたレビュー方針と、その記録エージェント人(危ない箇所だけ)
運用障害記録 — そこから出てくる新しい意図エージェント人

段階の継ぎ目を守る装置は三つに整理されます。スキルは規則違反をまれにし、フックはほぼ不可能にし、評価(eval)は設定そのものが古びていないかを回帰検査します。三つめが耳慣れないところで、プレイブックが力を入れる箇所です — コードだけをテストするのではなく、規則・スキル・フックが変わったときにエージェントが同じ水準で働けているかを検査せよ、というものです。実際に最近終えた作業を20〜50件そろえて評価の束とし、設定を触るたびに通過率を測るやり方が示されています。

テスト段階でよく踏む落とし穴も挙げておく価値があります。失敗するテストを先に書かせておくと、エージェントがときどきテストのほうを直して通してしまいます。これは指針では防ぎにくく、実装中はテストファイルの編集を拒むフックが確実です。先に述べた「指針は確率、フックは決定」の具体例です。

フォルダはこう置きます

プレイブックが定めているのはリポジトリ内の intent/ フォルダまでです。コードの隣に置くことに意味があり、成果物の鎖とそこから生まれたコードが一つのリポジトリで一緒に動きます。その内側をどう分けるかはチームに委ねられていて、変更一つにフォルダ一つという構成が無難です。

intent/
  README.md              # フォルダの規則、何がどこにあるか
  ship-tracking/         # 変更一つ = フォルダ一つ
    intent.md            # なぜ作るのか (プロダクトオーナー承認)
    spec.md              # 何をどんな要求・設計で (プロダクトオーナー承認)
    plan.md              # どこをどの順で (開発者)

規則は二行で足ります。フォルダごとに intent・spec・plan を一つずつ置き、プルリクエスト一つに成果物一つを入れて、マージがそのまま承認になるようにします。仕様が二つ必要になったら仕様を割るのではなく、そもそも意図が二つだったと見てフォルダを分けるほうがよいでしょう。機能が大きすぎて割れないなら、それはたいてい機能がまだ大きすぎるという合図です。

承認をわざわざプルリクエストで受けるのは、新しい道具を持ち込まないためです。意図だけを載せたプルリクエストを上げれば、レビュー画面も承認記録も取り消しの道も、すでにある仕組みで片づきます。チャットでエージェントを呼んで草案を作らせ、その草案がプルリクエストとして上がり、責任者がマージすれば次の段階が起動する、という流れを一つのリポジトリの中で終えられます。

軽く始める

あらゆる変更に意図の文書を求めれば、すぐに形式だけが残ります。誤字の修正や明らかなバグのように何をすべきかがすでに明確な仕事は、そのまま直すほうがよいです。一人で使うリポジトリなら、機能の単位に育ったときだけ書けば十分です。

導入はこの順序が無難です。まず書式を一枚決めてチームに配る。次に、コードベースを知らない人でもエージェントと話しながら草案を作れるように開いておく — 意図を持つ人がそのまま作成者なので、開発者にだけ開くとこのファイルの意味が消えます。三つめに、草案はプルリクエストとして上げ、プロダクトオーナーがマージで承認する。四つめに、ここまで回りはじめたら、チケットの登録や指標の逸脱といった出来事が草案を自動で作るところまで広げます。

すでに別の道具に要求が溜まっているなら、一度に移す必要はありません。成果物ごとに原本がどこにあるかのリンクを一行差しておくだけでも鎖は始まります。

批判的に読む — まだ空いている枠

このプレイブックは標準ではありません。Anthropic の企業導入支援チームが顧客と実際にやってきたやり方をまとめたガイドであり、公開直後から空白を指摘する反応がつきました。そのまま倣う前に知っておくほうがよいでしょう。

  • 測定の層がありません。 どの信号がどこにあるかは教えてくれますが、その信号を段階をまたいで集め、基準線を引き、時間に沿って追う方法が空いています。指標の名前を挙げることと、ダッシュボードを持つことは別の仕事です。
  • 要求工学が薄いです。 意図から仕様へ渡る区間が事実上「intent.md を読んで spec.md を書け」の一行です。コードが安くなるほど残る梃子は要求の品質なのに、悪い仕様を渡されたエージェントは5,000行の正確に間違ったコードを作り上げます。
  • 決定論的な統制はフックだけです。 鎖の継ぎ目のうち実際に何かを止めてくれるのは三箇所だけ — 計画モードが承認まで編集を押さえる箇所、PreToolUse フックがツール呼び出しを拒む箇所、評価の束が通過率を下回るとパイプラインを落とす箇所。残りの継ぎ目では、誤った翻訳が非の打ちどころのない成果物の姿をして下流へ流れていきます。

三つめがこの構造の本当の危うさです。鎖は各枠が埋まったことは保証しますが、枠と枠のあいだが正しく訳されたことは保証しません。 承認の判が六つ押してあっても、二つめと三つめのあいだで意味がずれていたなら、残るのはよく整理された監査証跡と、間違った製品です。

このウィキではどうしているか

このウィキは成果物の鎖ではなくゲートのほうに寄っています。文書を一つ登録すると索引・地図のフォールバック・翻訳の同伴物・作成日・プラグインの同梱物がすべて揃っている必要があり、その検査を人の記憶ではなく八段階のゲートが代わりに行います。規則は CLAUDE.md に書いてありますが、破ったときに実際に止めるのは CI です — 上で述べた「指針は確率、ゲートは決定」をそのまま選んだかたちです。

逆に意図のほうは事後に残します。 作業が終わると作業ログに何をなぜそう決めたのかを書き、それが次の作業の根拠になります。プレイブックの言い方をすれば、鎖の前ではなく後ろに意図を置く方式であり、一人あるいは少人数が一つの主題を最初から最後まで引き受けるあいだはこちらのほうが煩わしくありません。ただし承認を要する人が複数になった瞬間、順序を逆にする価値が生まれます — 後から書かれた意図は、反対する機会をすでに逃したあとだからです。

事実確認ノート

プレイブックの公開日(2026年8月21日)、六段階の構成、成果物の鎖(intent.md → spec.md → plan.md → diff → レビュー記録 → 障害記録)、intent.md の五つの節と請求ポータルの実例、デプロイ段階の REVIEW.md、20〜50件の評価の束は、いずれも Anthropic の公式プレイブックとその無料コースに従いました。「Claude Code が intent.md を自動で読む」と書いた二次的なまとめがありますが、セッション開始時に自動で読み込まれるのは CLAUDE.md・CLAUDE.local.md・.claude/rules/ と自動メモリの索引であり、任意のファイルはここに含まれません(公式のメモリ文書) — この文書では公式の記述に従い、つなぐ方法を四つに整理しました。欠けた測定の層・薄い要求工学・決定論的な統制がフックだけだという指摘は、公開後に出た外部の分析であって Anthropic の記述ではありません。intent/ の内側のスラッグ構造と「プルリクエスト一つに成果物一つ」は公式の規定ではなく、実務で使われている推奨案です。
