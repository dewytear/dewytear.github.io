最初の実行と動作構造

実際に一度回してみます。例は ERP の営業・受注モジュールに顧客からの要望（CR）を反映する場面です。核心はひとつだけ — 「命令」ではなく「意図」を渡すということです。

今日の例（CR） 顧客からの要望: 「取引先の信用等級ごとの与信限度（信用限度）を超える注文は自動で保留（hold）にし、営業担当者へ通知を送ってほしい。」標準パッケージに手を入れるカスタマイズなので、影響範囲の分析と回帰テストが必ず要ります。

実行のライフサイクル — 何が順に起きるのか

人が関わる地点は①の意図と④の承認のふたつだけです。

ステップ 1 — 意図の文を書く

いちばん大事な習慣です。「〜して」（命令）ではなく「〜したいと思っています」（意図）と書きます。そうしてはじめて、ハーネスが自分でチームを設計する余地が生まれます。/harness と入力してから Tab で補完し、依頼を続けて書きます。

/harness ERP の営業・受注モジュールで、取引先の信用等級ごとの与信限度を
超える注文を自動で保留にし、営業担当者へ通知を送る顧客向けカスタマイズを
進めたいと思っています。標準ソースの影響範囲の分析と
回帰テストまで含めてください。
意図をうまく渡すコツ（初級の必須） ①目標（何を）·②対象モジュール（どこを）·③制約（標準の毀損を最小化・アップグレード互換）·④ほしい成果物（影響範囲・テスト）をひとつの文に入れると、チーム編成が正確になります。詳しい背景はエージェント・スキルの設計を参照。

ステップ 2〜3 — ドメイン分析 & チーム案

Enter を押すとハーネスがドメインを分析し、途中で「ハーネスをフル構築 / ハーネスだけ構築」のような選択を尋ねてきます。参考にする標準仕様や要件の文書があれば、このときに渡せます（数百ページの PDF も処理できます）。ほどなくエージェントチームの草案を提案します。例:

提案されたエージェント役割
営業の標準ソース分析担当与信・注文の流れとカスタムの影響範囲を把握
カスタマイズ設計担当標準を直接いじらない拡張の方式（例: アドオン）を設計
開発エージェント保留処理・通知のロジックを実装
回帰 QA エージェント標準の注文・与信の機能が壊れていないかを検証

ステップ 4 — 検討して「進めて」

ここで人が関わります。提案されたチームが適切かを見て、足りなければ修正を頼みます。よければひと言で承認します。

進めて

この瞬間から作業は人の手を離れ、オーケストレーターの立てた順序どおりに進みます。

ステップ 5 — 並列の自律実行（観察）

  • エージェントたちが並列で働きます。Shift + 方向キーで、それぞれのエージェントが何をしているかをのぞけます（作業中のエージェントは色で表示）。
  • ほかの作業も同時に回したいときは、新しいターミナル窓をもうひとつ開いて別のハーネスを実行します。
  • 開発 → QA →（問題が見つかれば）手戻り、というループが自動で回ります。

ステップ 6 — 成果物の確認

終わるとプロジェクトに _workspace フォルダができ、下のような文書が積み上がります（名前は理解を助けるための例で、実際はハーネスが計画どおりに命名します）。

  • 要件の整理 — CR を開発できる仕様に整理
  • 標準ソースの影響範囲 — どの標準機能・画面に影響が及ぶか
  • カスタマイズの設計 — 標準を直接いじらない拡張の方式、アップグレード互換への配慮
  • 実装した変更の一覧 — 何をどう変えたか
  • 回帰テストの結果 — クリティカル / メジャー / マイナーに分類
  • 移行ガイド — 本番反映の手順・注意事項
覚えておいてください — これは下書きです ハーネスの結果は完成品ではなく、よく準備された下書きです。とくに ERP のカスタムは標準への影響範囲と回帰の結果を人が必ず検討したうえで反映してください。検証をより固くする方法は検証・品質で扱います。中で何が起きていたのかは動作の構造で確認してください。

動作の構造と 6 ステップ

進めて を押したあと、ハーネスの内部で何が起きているのかをのぞいてみます。大きくは6 ステップでチームを組み、そのあと運用のループを回します。

プラグインの 6 ステップ — チームを作る過程

ここまでが「チーム作り」。⑥ の検証を通れば、実際の作業（運用のループ）が始まります。

運用のループ — チームの働き方

チームができると、オーケストレーターが下のループを回します。核心は「分けて並列にやり、テストで検証し、間違っていればやり直す」です。

  1. 分解 — 目標を作業の単位に切り分けます。例: 影響範囲の分析・保留ロジック・通知・回帰テスト
  2. 分担 & 並列実行 — 各エージェントが同時に担当の作業を進めます。
  3. 検証 — QA が結果を突き合わせて確認（標準機能の回帰、数値の整合性）。
  4. フィードバックのループ — 問題があれば担当のエージェントへ戻してやり直し。通るまでくり返します。

エージェントチーム vs 隔離サブエージェント

Claude Code の標準のサブエージェントは互いに隔離されていて会話できません。エージェントチームは互いに通信します — たとえば開発のエージェントが「標準ソースの情報が足りない」と気づけば、分析のエージェントを呼び起こして追加の調査をさせられます。

実験機能 — オンにする方法 エージェントチームは実験機能です。~/.claude/settings.json の環境変数でオンにします: 
"env": {
  "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
}
動的ロードに失敗すると隔離サブエージェントとして立ち上がるバグがあるので、エージェントが見えないときは /exit してから入り直し、/agents で確認してください。
ファイルはどこにできるのか 生成されたエージェント・スキルの定義はプロジェクトの .claude の下に残るので、Git でチームと共有できます。ただしプラグイン自体はマシンごとに個別インストールが必要です。構成の変更履歴は CLAUDE.md に記録されます。チーム設計そのものをさらに深く扱うエージェント・スキルの設計へ続きます。

動くところを見たら、今度は手を入れる番です — 設計と検証の章で、エージェントとスキルを設計し、_workspace で品質を守ります。
