初級 — コンテキストを節約する習慣9つ

Claude Code をうまく使う第一歩は、派手な機能ではなくコンテキストを節約する習慣です。コンテキストとは、モデルが一度に覚えていられる会話とコードの総量のこと。これが埋まってくると、先に合意した内容を忘れて的外れな答えを出し始めます。この文書は、公開講座の28のコツのうち初級の9つを選び、それぞれを Anthropic の公式ドキュメントと突き合わせて整理したものです。コツごとに公式ドキュメントへのリンクを付けたので、深掘りしたいときはそこから辿ってください。

文書情報（出典） · 骨組み: 公開講座の動画 — Claude Code のコツ28の初級編（1〜9）
· 検証・補強: Claude Code 公式ドキュメントとの突き合わせ（2026-08-14 時点）— 機能はバージョンにより変わることがあります

1. どのプロジェクトも /init から

すでにコードが積み上がったプロジェクトに Claude Code を投入するとき、最初のコマンドは /init です。Claude がコードベースを読み、ビルドコマンド・テスト方法・プロジェクトの慣習をまとめた CLAUDE.md を作ってくれます — このファイルはセッション開始のたびに自動で読まれるプロジェクト案内書なので、毎回「このプロジェクトが何か」を説明する手間が消えます。すでに CLAUDE.md があれば、上書きせず改善案を出します。

公式ドキュメント: How Claude remembers your project — この wiki の CLAUDE.md 実習と CLAUDE.md 十戒も同じ主題を扱っています。

2. ステータスラインを点ける

ターミナルで使うなら /statusline で状態表示を設定しましょう。いま使っているモデル、git のブランチ、そして何より残りコンテキストの割合が入力欄の下に常時表示されます。どれだけ埋まったかが目に見えると、下の 3〜5 番の習慣が自然と身につきます。デスクトップアプリは最初から表示されるので設定不要です。

公式ドキュメント: Status line configuration — 表示項目はスクリプトで自由に変えられます。

3. コンテキストを小さく保つ

「コードベース全体を確認して」のような命令は、一度でコンテキストを何十%も燃やします。大きな問題はまず分割から頼みましょう — 「決済システムを直して」ではなく「決済システムの修正を小さなステップに分けて」から始め、ステップごとに別々に進めます。モデルがどれだけ賢くても、コンテキストが足りなくなれば前の話を忘れます。

4. /context でトークンを食う犯人を探す

コンテキストの減りが早すぎるときは /context と打ちましょう。どのファイル・ツール・メッセージがどれだけ占めているかを可視化してくれます。犯人はたいてい三つのどれかです — 丸ごと読んだ大きなファイル、ツール定義を全部積んだ MCP サーバー（上級編の22番）、長くなった会話履歴。

公式ドキュメント: Slash commands リファレンス

5. 60%あたりで /compact、作業の切れ目には /clear

二つの違いが肝心です。/compact は会話履歴を要約して圧縮します — 「決定事項は残して」のように残すものを指定でき、文脈は続きます。/clear は完全な初期化で、新しい会話を開くのと同じです。一つの作業が終わって次に移るときは、圧縮より初期化 — 前の作業の残りかすが新しい作業を汚しません。

文脈がまだ要るなら圧縮、作業が変わるなら初期化。迷ったらステータスラインの残量を見る。

6. プランモードで始める

プランモードはファイルに一切触れず、読む・分析する・計画するだけのモードです（ターミナルでは Shift+Tab で切り替え）。何も変えないので安心して任せられ、計画の途中で Claude のほうから質問を投げて意図を絞り込んでくれます。要望を具体的に書きにくいときほど、プランモードの値打ちが上がります。

一つ背景を — 2026年8月14日から、新規セッションの既定値は毎回承認を求めない auto モードです（尋ねない既定値）。だから「触る前にまず計画」というこの習慣は、むしろ前より大事になりました — 実行が速くなったぶん、方向は先に合意しておくのが安全です。モードの詳細: Permissions and modes

7. ジュニア開発者のように接する

「パディングを画面幅で調整する関数を書いて」と言った時点で、いちばん大変な仕事 — 問題を定義し解き方を考える仕事 — をあなたが全部やったことになります。代わりに「機種によって映像が切れるんだけど、どう解決すべきかな？」のように問題を渡しましょう。Claude はプロジェクト全体を読んで解決策を提案できるので、構想から一緒にやって、その案を Claude 自身に実行させるのが道具をいちばん大きく使う方法です。

8. Claude に聞き返させる

要望が曖昧なときは、プロンプトの最後にこう付けましょう — 「私が何を望んでいるか95%理解できるまで質問し続けて」。Claude が具体化の質問を次々と投げ、その問答が終われば最初から正しい方向へ進みます。曖昧な指示で三回やり直させるより、質問五つに答えるほうが安いのです。

9. ToDo に自己点検を植える

作業リストを任せるとき、最後に点検項目を明示しましょう — 「Chrome の開発者ツールを開いてコンソールエラーを確認しろ」「全部通るまでは先に進むな」、そして何より「現在の項目が完了した・正しいと95%以上確信するまで次の ToDo に移るな」。自己点検なしに ToDo を10個回すと、それぞれ60%の完成度で終わって隙間が積もり、あとで原因も見つからずトークンだけ燃やす羽目になります。点検を植えれば最初の成果物の完成度が変わります。
