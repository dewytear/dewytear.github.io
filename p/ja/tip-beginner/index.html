初級 — コンテキストを節約する習慣9つ

Claude Code をうまく使う第一歩は、派手な機能じゃありません。コンテキストを節約する習慣が先です。コンテキストとは、モデルが一度に覚えていられる会話とコードの総量のこと。これが埋まってくると、Claude がさっき合意したことを忘れて、的外れなことを言い始めます。「さっき言ったのに、なんでまた？」と思ったことがあるなら、犯人はたぶんコンテキストです。この文書は Tip シリーズ28のうち初級の9つ。コツごとに公式ドキュメントへのリンクを付けてあるので、深掘りしたくなったらそこから辿ってください。

文書情報（出典） · 根拠: Claude Code 公式ドキュメント（2026-08-14 時点）— 機能はバージョンにより変わることがあります

1. どのプロジェクトも /init から

コードがすでに積み上がったプロジェクトに Claude Code を投入するなら、最初のコマンドは迷わず /init です。Claude がコードベースをざっと読んで、ビルドコマンド・テスト方法・プロジェクトの慣習をまとめた CLAUDE.md を作ってくれます。このファイルはセッション開始のたびに自動で読まれるプロジェクト案内書なので、毎回「このプロジェクトはですね…」と説明する手間が消えます。すでに CLAUDE.md があれば上書きせず改善案を出すだけなので、気軽に回してみてください。

公式ドキュメント: How Claude remembers your project — この wiki の CLAUDE.md 実習と CLAUDE.md 十戒も同じ主題です。

2. ステータスラインを点ける

ターミナル派なら /statusline で状態表示を点けておきましょう。いま使っているモデル、git のブランチ、そして何より大事な残りコンテキストの割合が入力欄の下に常時表示されます。残量が目に見えるようになると、下の 3〜5 番の習慣は勝手に身につきます。デスクトップアプリは最初から表示されているので設定不要です。

公式ドキュメント: Status line configuration — 表示項目はスクリプトで自由に変えられます。

3. コンテキストを小さく保つ

「コードベース全体を確認して」のような命令は、一発でコンテキストを何十%も燃やします。大きな問題はまず分割から頼みましょう — 「決済システムを直して」ではなく「決済システムの修正を小さなステップに分けて」から始めて、ステップごとに別々に進めるんです。モデルがどれだけ賢くても、コンテキストが底をつけば前の話は忘れます。

4. /context でトークンを食う犯人を探す

コンテキストの減りが妙に早い？ そんなときは /context と打ってみてください。どのファイル・ツール・メッセージがどれだけ占めているか、ひと目で見えます。犯人はたいてい三つのどれか — 丸ごと読んだ大きなファイル、ツール定義を全部積んだ MCP サーバー（上級編の22番で扱います）、伸びに伸びた会話履歴。

公式ドキュメント: Slash commands リファレンス

5. 60%あたりで /compact、作業の切れ目には /clear

この二つ、混同しないでください。/compact は会話履歴を要約して圧縮します — 「決定事項は残して」のように残すものを指定でき、文脈は続きます。/clear は完全な初期化で、新しい会話を開くのと同じ。一つの作業が終わって次へ移るときは、圧縮より初期化です — 前の作業の残りかすが新しい作業を汚しません。

文脈がまだ要るなら圧縮、作業が変わるなら初期化。迷ったらステータスラインの残量を見る。

6. プランモードで始める

プランモードはファイルに一切触れず、読む・分析する・計画するだけのモードです（ターミナルでは Shift+Tab で切り替え）。何も変えないから安心して任せられるし、計画の途中で Claude のほうから質問を投げて意図を絞り込んでくれます。プロンプトを細かく書くのが面倒なときほど、プランモードが効きますよ — どうせ向こうから聞いてくれますから。

知っておきたい背景をひとつ — 2026年8月14日から、新規セッションの既定値は毎回承認を求めない auto モードです（尋ねない既定値）。だから「触る前にまず計画」というこの習慣は、むしろ前より大事になりました — 実行が速くなったぶん、方向は先に合意しておくのが安全です。モードの詳細: Permissions and modes

7. ジュニア開発者のように接する

「パディングを画面幅で調整する関数を書いて」と言った瞬間、いちばん大変な仕事 — 問題を定義して解き方を考える仕事 — をあなたが全部やったことになります。AI を1割しか使っていないんです。代わりに問題を渡しましょう。Claude はプロジェクト全体を読んで解決策を提案できるので、ブレインストーミングから一緒にやって、向こうが出した案を向こうに実行させる — これが道具をいちばん大きく使う流れです。

# こうじゃなくて（解き方を自分で決めて指示）
パディングを画面幅に応じて動的に調整する関数を書いて

# こう（問題を渡して、解き方を一緒に考える）
いま機種によって映像が切れることがあるんだ。原因は何だと思う？
どう直すのがいいか、案を二つ三つ比べて見せて。

8. Claude に聞き返させる

要望が曖昧なときは、プロンプトの最後にこの一行を足してみてください — 「私が何を望んでいるか95%理解できるまで質問し続けて」。Claude が具体化の質問を次々と投げ、その問答が終われば最初から正しい方向へ進みます。曖昧な指示で三回やり直させるより、質問五つに答えるほうがずっと安いんです。

いまあるものと全然違う雰囲気のモーショングラフィックを作りたい。
私が何を望んでいるか、95%理解できるまで質問し続けて。
質問が終わるまでは作業を始めないで。

9. ToDo に自己点検を植える

作業リストを任せるときは、点検項目もセットで明示しましょう。これがないと ToDo 10個がそれぞれ60%の完成度で終わって隙間が積もり、あとになって原因も見つからずトークンだけ燃やす羽目になります。点検を植えると、最初の成果物の完成度が目に見えて変わりますよ。

ランディングページを作って。ただし次のルールを守って:
1. 各 ToDo が終わったら Chrome の開発者ツールでコンソールエラーを確認
2. エラーが全部消えるまでは次の ToDo に進まない
3. 現在の項目が完了したと95%以上確信するまで完了マークを付けない

初級コマンドをひと目で

コマンドやることこう使ってみて
/initコードベースを読んで CLAUDE.md を生成・改善既存プロジェクトへの投入時は必ず最初に。ファイルがあれば上書きしないので安心
/statuslineモデル・ブランチ・コンテキスト残量を常時表示設定は一度きり — 「モデルと残量を見えるようにして」と言ってもOK
/context何がどれだけコンテキストを占めているか可視化残量の減りが妙に早いとき — 大きなファイル・MCP・長い履歴のどれかが見えます
/compact会話履歴を要約して圧縮（文脈は継続）60%あたりで。/compact 決定事項は残してと残すものを指定
/clear会話を完全初期化（新しい会話と同じ）一つの作業が終わるたびに — 残りかすが次を汚しません
Shift+Tabplan・auto などモード切り替え慣れない作業はプランモードから — ファイルに触れないので安心して任せられます
