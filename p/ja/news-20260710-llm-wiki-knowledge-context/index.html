LLM Wiki とナレッジコンテキスト — 書き込みの時点でコンパイルするチームの知識

LLM Wiki を主題にしたセミナーの発表を分析した文書です。発表はカルパシー（Andrej Karpathy）の LLM Wiki の提案から出発し、発表者のチームが実際に運用している“ナレッジコンテキスト”（Obsidian のボールト + Git リポジトリ）の実装、規模が大きくなって出会った索引の膨張の問題と OpenViking の導入、そして人とエージェントの役割を分けたガバナンスまでを扱います。発表の内容をそのまま移す代わりに、言及された道具・提案の元の出典（カルパシーの gist・GitHub リポジトリ・公式の文書）をウェブで確認して根拠を補い、中心の過程を図に整理しました。

扱った内容と根拠の確認 · 素材: 社内セミナーの発表“LLM Wiki とナレッジコンテキスト”（2026-07）
· 根拠の補強: カルパシーの LLM Wiki の gist、volcengine/OpenViking（GitHub・公式の文書）、kepano/obsidian-skills（GitHub）を直接確認 — リンクは文書の末尾の出典の節に。
· このウィキの LLM Wiki — 概要の講義シリーズ、セカンドブレイン レベル 2 と同じ主題の系譜の文書です。

① 問題 — 知識はあるのに、毎回また説明する

発表が挙げた出発点はよく見る風景です。チームの知識がチャットのログ・文書・個人のメモに散らばっていて、新しいメンバーが来るたび、エージェントに仕事をさせるたびに同じ文脈を最初から説明し直します。共有の文書は“最終”、“本当に最終”の写しが増えてどれが現行かわからなくなり（Google ドキュメント式の写しの増殖）、いちばん値打ちのある暗黙知 — なぜそう決めたのか、どんな試みが失敗したのか — は記録されないまま人の頭の中だけに残ります。LLM の時代には、この費用はトークンでも請求されます: エージェントを呼ぶたびに同じ背景の説明を文脈へ注ぎ直すことになるからです。

② RAG と LLM Wiki — 読みの時点の検索 vs 書き込みの時点のコンパイル

この問題への通常の答えが RAG（検索拡張生成）です。文書を断片（チャンク）にして埋め込んでおき、質問が来た瞬間に似た断片を探して文脈へ差し込むやり方 — つまり知識の整理を読み（質問）の時点へ先送りします。カルパシーが提案した LLM Wiki は方向をひっくり返します。資料が入ってくる時点で LLM が読んで整理・統合し、人が読めるウィキの文書にしておけば、質問の時点では検索のパイプラインなしにただその文書を読めばよいのです。カルパシーはこれをコンパイラにたとえます — 元の資料がソースコード、LLM がコンパイラ、ウィキが実行の成果物であり、RAG が実行のたびにソースを探し直すインタプリタだとすれば、LLM Wiki はあらかじめコンパイルしておくほうです。

同じ知識、違う時点 — RAG は質問のたびに探し、LLM Wiki は入ってきたときに一度整理する。
RAG（読みの時点の検索）LLM Wiki（書き込みの時点のコンパイル）
整理の時点質問の瞬間（そのつど）資料が入るとき（あらかじめ一度）
質問の費用検索のパイプライン + 断片の注入のくり返し文書を読む（パイプラインは不要）
知識の形断片（チャンク） — 人には読みにくい統合された文書 — 人と LLM の共用
一貫性断片どうしの矛盾に気づきにくいコンパイル・lint の段階で統合・点検
合う場所膨大で頻度が低く、原文の引用が大事な資料チームがくり返し使う生きた知識

ふたつは排他的ではありません — 発表も“よく使う中心の知識はウィキへコンパイル、膨大な原文は検索で”という併用を前提にしています。

③ カルパシーの LLM Wiki — 3 層の構造と index.md・log.md

カルパシーが gist で公開した提案の骨組みは3 層の構造です。いちばん下に元のソース（入ってきた資料を原文のまま、不変で保管）、その上に LLM が元を読んで概念の単位のマークダウンとして保守するウィキのレイヤー（人は読み取り専用 — 直したければ元の層に資料を入れてまたコンパイルさせる）、そしてこのすべての動作を定めるスキーマのレイヤー（CLAUDE.md・AGENTS.md 類の規約: 文書の形式、命名、連結の規則）です。ここに管理のファイルがふたつ付きます — 全項目の目次である index.md、そしてすべての変更を ## [日付] 動作 | 対象 の形式で追記していくだけの log.md。運用の動作は ingest（新しい資料のコンパイル） · query（質問への応答） · lint（ウィキ全体の矛盾・壊れたリンクの点検）の三つに整理されます。

3 層の構造: 元は不変、ウィキは LLM が管理、スキーマが規約を強制 — index.md・log.md が目次と履歴を担う。
このウィキとの接点 いま見ているこのウィキが、まさにこの構造の変形です — 本文（HTML のフラグメント）がウィキのレイヤー、list・知識インデックスが index.md の役、Work Log が log.md の役、CLAUDE.md の規則 + validate のゲートがスキーマと lint の役をします。講義シリーズ LLM Wiki — 概要で同じ概念を段階ごとに扱います。

④ ナレッジコンテキスト — Obsidian のボールト + Git でチームへ移す

発表の中心は、カルパシーの個人向けの提案をチームの規模へ移した実際の実装です。リポジトリひとつがそのままチームの知識の文脈であり、物理的には Obsidian のボールトであり Git のリポジトリです — 非開発者は Obsidian の画面でノートを書き、開発者は Git で PR を送ります。同じファイルをふたつの窓口で扱うだけです。フォルダの構造がそのまま権限の構造です:

  • context/ — チームの共有層。検証を通った知識だけが入る、チームの公式の文脈。
  • members/<名前>/ — 個人の作業層。各自の下書き・実験・メモ。ここまでは自由。
  • agents/ — エージェントの設定とスキル。共有層と個人層の両方に存在し、個人が作ったスキルが検証を経てチームのスキルへ昇格します。AGENTS.md がチームの公式のシステムプロンプトの役。
  • _private/ — 同期から外れる領域。昇格の経路そのものがありません。

中心の過程は、個人の知識がチームの知識になる昇格（promotion）のフローです。個人層のノートを共有層へ上げるには PR を開き、自動の検証（形式・リンク・frontmatter）と AI のレビュー（重複・規約の違反・既存の文書との衝突）を経て、最後に人が承認してはじめて context/ に合わさります。frontmatter（メタデータ）は Obsidian の Templates で入力の時点に強制し、すべての履歴は Git のヒストリが自動で残します。

知識だけでなくスキルも同じ関門を通る — よくできた個人のスキルがチームの資産になる経路。

発表が挙げた効果は四つです。(1) 背景の説明の代わりにノートのリンクひとつで文脈が伝わり、(2) エージェントに同じ説明をくり返し注ぎ込まないのでトークンが節約され、(3) 個人のスキル・プロンプトが昇格のフローに乗ってチーム全体へ広がり、(4) 公式の文脈が単一のリポジトリなので“最終_本当に最終”の写しの問題が構造的に消えます。決定の背景のような暗黙知も、PR の説明とノートとして残り積み上がります。

⑤ スケールの壁 — マークダウンの膨張と OpenViking

運用が根づくと別の問題が来ました。ノートが数千枚に増えて索引のファイルが 1,000〜3,000 行のものが 20〜30 個にふくらみ、エージェントが文脈をつかもうと索引を読むだけで文脈のかなりの部分が消費されました — 書き込みの時点のコンパイルで節約したトークンを探す費用が食い返す状況です。発表のチームが導入した解が、バイトダンスが公開した OpenViking です: エージェントのメモリ・知識（RAG）・スキルをひとつのファイルシステムのパラダイムに統合した“コンテキストデータベース”で、すべての知識が viking:// のパスを持ちます。要は階層の読み込みです — すべてのノードが L0（一行の要約） · L1（概要） · L2（全文）の三段階の要約を持ち、エージェントは L0 で全体を安く見渡し、候補の L1 で計画を立て、本当に必要な文書だけを L2 で読み込みます。ディレクトリ単位の再帰的な検索（フォルダの L0・L1 で位置を絞ってから下位へドリルダウン）が巨大な索引を置き換えます。

全部を読むのではなく要約のはしごを降りていけ — L0 → L1 → L2 の段階的な読み込みが索引の膨張を置き換える。

発表は、既存のフォルダを OpenViking の型に対応づけるマッピングも紹介しました — 参考の資料は resources、決定の根拠や議事録は evidence、エージェントのスキルは skills、会話や作業の記憶は memory、まだ分類前のものは unindexed に置いて少しずつ編入。検索と読み込みがどの経路をどれだけ読んだかが観測できる（observability）点も導入の理由に挙げました。

⑥ ガバナンス — 人が握るもの、エージェントに任せるもの

“エージェントがウィキを管理する”は“全部任せる”という意味ではありません。発表のチームの原則は既定はエージェント、例外を人が明示するという、ホワイトリストの逆転です:

主体担当理由
人だけ_private/ の領域同期・昇格の経路そのものがない — 機械が触れる理由がない
削除知識を消すことは戻しにくく、文脈の判断が要る
敏感な権限・最終の承認共有層へのマージの責任の所在は人に
エージェントそのほかのすべて整理・統合・リンク・要約・レビューなどのくり返しの作業は機械のほうが誠実だ

これを支える仕掛けが三つあります — frontmatter は Obsidian の Templates で入力の時点に強制して事後の手直しを減らし、Git のヒストリが誰が（人であれエージェントであれ）何をいつ変えたかを漏れなく残し、昇格のフローの人の承認のゲートが共有層の品質の下限を守ります。このウィキの Douzone ナレッジプラットフォームの提案が採った“開発の流れはそのまま、知識化は AI が”と同じ思想です。

⑦ 道具の生態系 — エージェントが Obsidian を扱いはじめた

発表が最後に挙げた合図は道具の側です。Obsidian の CEO ステフ・アンゴ（Steph Ango, kepano）が obsidian-skills を公開しました。これは Claude Code のようなコーディングエージェントが Obsidian のファイル形式（.md のウィキリンク・コールアウト、.base のデータベース、.canvas のキャンバス）を正しく読み書きできるよう教える Agent Skills 規格の SKILL.md 五つです。Obsidian が CLI も提供しはじめたので、“人は Obsidian の画面で、エージェントはファイル・CLI・スキルで”同じボールトを扱うというこの記事の構図が公式の道具に支えられることになります。ナレッジコンテキストのようにマークダウン + Git を選んだチームには、エージェント側の窓口が標準化されつつあるという意味です。

まとめ — 三つの文で

  • 知識の整理を質問の時点（RAG）から書き込みの時点（ウィキへのコンパイル）へ移せば、チームとエージェントが同じ文書を読む単一の文脈が生まれる。
  • チームの規模では構造がそのままガバナンスだ — 個人層／共有層／非公開層の分離と昇格の PR フローが品質と責任を作る。
  • 知識が大きくなると探す費用がボトルネックになる — 階層の要約（L0・L1・L2）と再帰的なドリルダウンが巨大な索引の次の段階だ。
