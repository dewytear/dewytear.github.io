設計と検証 — エージェント・スキル・_workspace

ハーネスがチームを自動で組んでくれますが、原理が分かればより正確に指示できますし、生成されたチームを自分で手直しすることもできます。核心はふたつ — エージェント（誰が）とスキル（どうやって）です。

エージェント = 自然言語で書いた「職務記述書」

エージェントはコードではなく文章です。次の四つを入れます。

  • 役割・原則 — 何に責任を持ち、どんなルールを守るか。
  • 入力・出力 — 何を受け取り何を出すか（プロトコル）。
  • 協業 — どのエージェントと何をやり取りするか。
  • 再呼び出し・エラー時のふるまい — 詰まったらどうするか。
# 例: 営業の標準ソース分析担当（エージェント定義の抜粋）
役割: ERP 営業・受注の与信・注文の流れを分析し、
      今回のカスタムが標準機能に及ぼす影響範囲を特定する。
原則: 標準の毀損を最小化 · アップグレード互換をつねに優先する。
入力: 顧客要望(CR)、標準仕様/ソースの参照
出力: 影響範囲レポート(影響する画面·機能·データの一覧)
協業: 設計担当へ影響範囲を渡し、情報が足りなければ再調査を依頼
エラー: 根拠が見つからなければ「要確認」と記し、素通りさせない

スキル = くり返し作業を収めた「マニュアル」

スキルは 名前 + 説明 + 手順・チェックリストでできています。よくできたスキルは複数のエージェントが再利用します。

# 例:「回帰テストのチェックリスト」スキル
name: regression-checklist
description: カスタム反映後、標準の営業・受注機能が壊れていないか点検
手順:
  1. 標準の注文の作成/修正/取消が正常に動くか確認
  2. 与信限度の正常な範囲の注文がブロックされないか確認
  3. カスタム(限度超過で保留)の動作を確認
  4. 通知の送信とログを確認
  5. 数値の整合性(注文金額·限度)をクロスチェック
スキル設計の 5 ステップ（初級のコツ） ① よくくり返される作業を見つける → ②ひとつの責務だけを持つように切り分ける → ③ 入力／出力を決める → ④ 例外処理を書く → ⑤ どのエージェントが使うかをつなぐ。

営業・受注のチーム — データの流れの例

各エージェントは自分のスキルを使い、QA で止まれば開発担当へ戻ります。

チームをうまく組む初級の原則

原則理由ERP での例
役割は狭くひとつのエージェントが何役もやると品質が落ちる「分析」と「開発」を分ける
入出力を明確に次の人がそのまま引き継げるように影響範囲レポート → 設計の入力
QA は別に作った人が自分のものを検収すると見落とす回帰 QA を独立したエージェントに
詰まったら印を付けて止まる知らないことを作り話にしないため「要確認」のフラグ
生成されたチームの手直し ハーネスが作ったエージェントが気に入らなければ、自然言語で修正を頼むだけです。例: /harness QA エージェントは標準の注文取消のシナリオも必ず検証するように修正。検証をどれだけ固くするかが、結果の信頼度を左右します → 検証・品質。

検証・品質と _workspace

ERP のカスタムは標準の機能を壊してはいけないので、検証が命です。ハーネスは QA エージェントと根拠の記録でそれを支えます。

QA は何を確認するのか

誤字脱字の検査ではなく、内容の整合性を見ます。

  • 主張 ↔ 根拠の整合 — 結論が実際の資料・ソースに根拠を持つか。
  • 数値の一貫性 — 注文金額・与信限度・精算金額が前後で合っているか。
  • 標準の回帰 — カスタムのせいで標準の注文・与信の機能が壊れていないか。

見つけた問題はクリティカル / メジャー / マイナーに分類してレポートします。

検証のループ — 通るまで

欠陥がなくなるまで開発↔QA を回り、必要なら別のツールで二次検証します。

なぜ間違いが減るのか — 根拠の記録

  • 出典ベース — _workspace に根拠の出典が一緒に残ります。「もっともらしい嘘（ハルシネーション）」が減り、あとから「なぜこうしたのか」を追えます。
  • 履歴の記録 — 構成の変更履歴が CLAUDE.md に積み上がり、次の人が文脈を引き継げます。
  • 中間成果物の蓄積 — 一次分析 → 設計 → 実装 → QA レポートが段階ごとに残るので、どの段階が間違っていたかを指摘しやすくなります。

二重の検証 — 別のツールで交差させる

ひとつのツールだけで検証すると偏ることがあります。QA エージェントに別の CLI（例: Codex CLI）でもう一度確認させられます。

/harness QA エージェントは Codex CLI を使って回帰の結果を交差検証するように修正
トークンのコスト — 分かって使う マルチエージェントは便利なぶんトークンを多く使います。とくにエージェントどうしが会話するときに約 30% ほど多く消費されるケースもあります。簡単なカスタムまで重く回す必要はありません — 難易度に合わせてチームの規模を決めてください。
厨房のたとえ — 結果は「下書き」 一人シェフ（単一のツール）は速いけれどボトルネックがあり、マルチエージェント（厨房のチーム）は役割を分けて品質を保ちながら長く働きます。ただし一度で完成品が出るわけではありません — よく準備された下書きと見て、ERP へ反映する前には標準への影響範囲・回帰の結果を人が必ず確認してください。さまざまな適用事例はシナリオ集で見ます。

最終章シナリオ・ハーネス 100・コマンドが、実戦の掲示板と性能、クイックリファレンスでシリーズを締めます。
