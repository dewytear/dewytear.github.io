提案の中核とアーキテクチャ

本提案の目的は、単なる会社の Wiki の構築ではない。GitLab に積み上がる開発の成果を AI が継続して分析して知識を取り出し、既存の知識と比べて新規の生成・更新・破棄を判断するプラットフォームを作ることだ。社員の業務の流れはいまとまったく同じである — Wiki の作成、Markdown の編集、Tag の登録、文書の分類、知識の整理を何ひとつ追加で求めない。社員は最終的に生成された知識を検索して読むだけだ。

社員の役割は上の行で終わる。下の行の全体が AI の受け持ちだ。
中心の概念 — Event Stream と Knowledge State GitLab は開発の変更の Event Stream であり、Wiki はいまの時点で有効な Knowledge State だ。GitLab には Commit・MR・Release が時間の順に積まれ続けるが、Wiki は「7/1 の修正、7/2 の修正…」といった履歴の羅列ではなく、組織がいま知っておくべき知識の構造（Architecture · Rule Engine · 状態の体系 · チャネルの方針 · Troubleshooting …）へ精製されて保たれる。

Knowledge State の実体 — 決定的にビルドされる索引

「いま有効な知識の状態」は抽象的なスローガンではなく、機械的に再現できる成果物でなければならない。Reference Wiki がこれをすでに実証した: すべての文書のメタデータ（題・要約・概念・関係）はキュレーションのファイル一つから決定的なビルドで知識インデックスの JSON になり、同じ入力はいつも同じ出力を出す。だから --check 一回で「保存された状態がソースとずれていないか」をバイトの単位で判定でき、ずれたままではマージできない（ドリフトのゲート）。Knowledge State が Event Stream より遅れたり、ソースと矛盾したりするのを規律ではなく機械が止める構造 — これが会社のプラットフォームが受け継ぐ状態の管理の実体だ。

業界がすでに歩んでいる道

  • 文書をコードのそばに — Spotify は文書をコードと同じリポジトリに置いて CI でビルドする Backstage TechDocs で 5,000 以上の文書サイトを運用し、GitLab は 2,700 ページを超える公開のハンドブックの handbook-first の文化で知られる。docs-as-code は大きな組織ですでに検証されたアプローチだ。
  • 文書の同期の自動化 — Swimm は、すべての PR ごとにコードの変更と文書を突き合わせて自動で更新する Auto-sync で「Continuous Documentation」を商用化した。
  • コードから知識を自動で抽出 — Cognition の DeepWiki（2025）はリポジトリを分析してアーキテクチャの図とモジュールの文書を含むウィキを自動生成し、上位の公開のリポジトリ 5 万以上を索引した。GitHub はリポジトリの知識を常時注入する Copilot Spaces を GA し、Claude Code の CLAUDE.md・AGENTS.md は「リポジトリの中の、機械が読む知識のファイル」を業界の慣行にした。
  • 知識の検索の市場の急成長 — 全社の AI 知識検索の Glean は ARR $200M を超え、Atlassian は Rovo をクラウドの料金プランに標準で載せた。

つまり「GitLab の開発の成果の AI による自動の知識化」は、docs-as-code という検証された土台の上に、2025 年以後に商用化された自動の抽出の技術を組織の知識の管理へ当てはめることである。

プラットフォームのアーキテクチャ

プラットフォームの全体は、GitLab を源とする一方向のパイプラインとして構成する。

開発の成果が下へ流れながら知識になる。社員が関わる層は、いちばん上（開発）といちばん下（読むこと）だけだ。

知識の生成の Trigger — 完了と認められた変更だけ

すべての Commit をすぐ知識にはしない。開発の途中には、未完成の実装、失敗した試み、一時の修正が混じっているからだ。組織が完了と認める関門 — Review を経て基準の Branch に Merge され、Pipeline が成功した変更 — だけを分析の対象にする。完了した変更のなかで何が知識で何がそうでないか（機械的な Refactoring や誤字などの除外の基準）は、知識の管理の体系の価値の判定が受け持つ。

増分の分析 — 全体を読み直さない

プロジェクトごとに最後に処理した Commit の SHA を管理し、GitLab の Compare でそれ以後に変わったファイルだけを集めて、関連する Context を広げて分析する。AI の Token の使用量の削減、処理の時間の短縮、重複した分析の防止、障害のときの再処理は、すべてこの状態の管理から出てくる。

# プロジェクトごとの knowledge trigger・sync の状態（例）
{
  "project": "scm/sales-order",
  "knowledgeBranches": ["master", "release/*"],
  "lastProcessedSha": "abc123def456",
  "lastProcessedAt": "2026-07-06T14:32:00+09:00",
  "status": "success"
}

単なる Diff ではなく Context にもとづく分析

if ("CREDIT_HOLD".equals(soStatus)) の一行だけを見ても業務の方針は判断できない。変更の Diff に加えてClass の全体 · 呼び出し元 · 関連する Mapper と SQL · 関連する Test · 関連する Config · 既存の Wiki をあわせて読む Impact Expansion を経て、単なるコードの要約ではない実際の開発の知識を取り出す。

知識の無矛盾のゲート — Trigger とは別の層

Pipeline の成功は入口のゲートだ — 「この変更に分析する資格があるか」だけを判定する。知識の保管庫そのものの無矛盾は別のゲートの層が守り、この層は Reference Wiki がすでに CI で運用しているものをそのまま受け継ぐ（ウィキはどう自分を守るのか）:

  • 状態の検証 — 切れたリンク・重複した ID・孤立した文書・索引への未登録・図の境界の超過を、コミットごとに全数で検査する（ERROR 0 がマージの条件）。
  • ドリフトの検証（--check） — 索引・グラフ・llms.txt・sitemap が、決定的な再ビルドの結果とバイトの単位で一致するかを判定する。AI Curator が文書だけを直して索引への反映を落とす事故を、機械が遮る。
  • 同伴のゲート — 「文書を変えたなら記録（Work Log）も、知識の体系への反映も同じ変更の単位で」という規則を diff にもとづいて強制する。会社の KPI の「Merge に対する知識の反映率」が、まさにこのゲートの通過率だ（ロードマップ）。
  • レビューの信号（非遮断） — 機械が強制できない判断の領域（たとえば知識の関係を多角的に検討したか）は、遮る代わりにチェックリストを出して人の検討を促す。

Wiki Repository の層の Index と Provenance が具体的にどんな構造なのか — どのフィールドがすでに実証されていて、どのフィールドを会社向けに広げるのか — は、次の編の知識の管理の体系が扱う。

運用の安定性 — 実時間と補正の二重化

Webhook（Merge → Queue → Curator）の実時間の処理だけに頼らず、定期の Batch が Project Registry のいまの SHA と sync-state を比べて、漏れた変更を再処理する。Webhook の失敗、Network のエラー、Queue の取りこぼし、Curator の障害、一時的な API の失敗に対応する構造だ。

知識がどう判定・構造化・連結・追跡されるかは、知識管理体系が別途深く扱います。
