知識はどう積み上がるのか — 4 階層の知識階層と登録パイプライン

このパートはこのウィキそのものを説明します。ウィキの目標は単なる記事の寄せ集めではなく、文書が増えるほどつながりも一緒に育つ知識グラフになることです。そのためには知識がどこにでも積まれてはならず、決められた構造（どこに）と決められた手順（どうやって）で積まれる必要があります。この文書では、その構造と手順を実際の文書ひとつ（はじめに）を例に最後まで追いかけて説明します。

構造 — World → Domain → System → Document

すべての文書は 4 段階の知識階層の中に居場所を持ちます。最上位の World は知識の世界（学習知識 AI・業務知識 Douzone）、Domain はその中の領域、System は具体的な主題体系、Document が個々の文書です。たとえば はじめに 文書の住所はこう読めます:

「はじめに」（welcome）の 4 階層の住所 — section 文字列では AI · Claude · Code · Introduction。

この階層は別のデータベースではなく、ナビゲーションツリー（list ファイル）の入れ子そのものから導かれます。サイドバーに見えるフォルダ構造がそのまま知識階層なので、「メニューは別・分類は別」というズレが原理的に起きません。同じ System（末端フォルダ）にある文書たちは読む順序のあるシリーズとして扱われ、このフォルダ所属は後で見る関連文書の計算のセーフティネット（フォルダ補完）としても使われます。

文書のふたつの名前 — 不変 ID と物理パス

ツリーの葉（文書）ノードはふたつの重要なフィールドを持ちます:

  • name — 不変の論理 ID: ハッシュルート（#!welcome）であり、知識グラフのノードキー。いちど決めたら変わらないので、文書を別のフォルダへ移しても既存のリンクやエッジが壊れません。
  • path — 物理パス: docs/ko/ 以下の実際のファイル位置（例: ai/claude/code/introduction/welcome）。ドメインツリーをたどるので、フォルダを見るだけで知識階層が分かります。

文書の本文は静的な HTML 断片（骨組みのない <h2>…<p>…）です。ビルドツールもサーバーも JS レンダリングも要らず、URL でそのまま fetch されるので、人間のブラウザも AI も同じ原文を読みます — この性質が AI 消費レイヤーの土台になります。

三つの標識 — ラベル・タグ・概念の役割分担

文書ひとつが登録されるとき、名前のほかに三つの標識が一緒に残ります。三つは似て見えますが、記録される場所も、使われる場所もまったく違います — この分担を知っていれば「タグを付けたのに、なぜグラフに反映されないのか」といった混乱がありません。

標識どこに記録どこで使う「はじめに」（welcome）の実例
ラベル（label）list ノードサイドバー・一覧の表示名（言語別 label_en）「はじめに」
タグ（tags）list ノード入っていく扉 — 文書下部のチップ、Tags 索引、検索の補助claude-code · 紹介 · インストール · スラッシュコマンド · CLAUDE.md
概念（concepts）doc-entries（キュレーション）つなぐ材料 — 知識グラフのエッジ計算の原料、検索で最大の重みClaude Code · ターミナル · CLI · 自然言語 · インストール · 認証 · スラッシュコマンド など 10 個

タグはブラウジングの装置です。文書本文の下部にチップとして表示され、チップを押すとそのタグの付いた文書一覧へ移動します（文書がひとつだけならその文書へ直接）。Tags 索引はタグ全体を辞書のように広げます — ハングルは初声（ㄱ・ㄴ・ㄷ…）、英字はアルファベットのバケットにまとまり、よく使われた上位 10 個がバンドとして先に出ます。統合検索でもタグが一致すればスコアを得ますが、重みは概念より低めです（タグ 3 < 概念 5）。言語を変えると tags_en のような言語別タグが代わりに表示されます。なお Work Log 文書はわざと tags: [] にしています — 作業記録が知識タグの索引を散らかさないようにするためです。

概念はグラフの装置です。人（または AI）が文書を読み、本文に実在する中心概念だけをキュレーションして残し、次の編で見る関連文書（related）の計算はすべてこの概念から出発します。つまりタグをいくら付けてもグラフのエッジはひとつも生まれません — 3D 知識グラフと 2D ビューが読むのは概念だけです。逆に概念は索引ページには出てきません。同じ文書に対する「探す扉」と「つなぐ材料」が分かれているので、ブラウジングの利便のためにタグを増やしても、知識グラフの正直さ（本文実在の原則）は揺らぎません。

手順 — 文書ひとつが登録されるパイプライン

新しい知識が入るときは必ず同じ手順を通ります。手順の核心は人（または AI）が文書を実際に読んでキュレーションした要約・概念を残す段階（③）です — ここで知識グラフの材料が作られます。

登録パイプライン — 人がやるのは ①〜③、④ からは機械が同じ結果を再現します。
  1. 本文の作成 — ドメインツリーの位置に HTML 断片として保存。
  2. list 登録 — name・path・ラベル・タグをツリーに追加。この瞬間にナビゲーションと知識階層の中に居場所ができます。
  3. キュレーション — 文書を読んで doc-entries に要約 1 行 + 中心概念（平均 6 個）を記録。概念は本文に実在するものだけを書くのが原則です（次の編の正直さの原則）。
  4. インデックス再生成 — ビルドツールが ② の階層と ③ の概念から関連文書（related）を計算し、知識インデックスを作り直します。このビルドは決定論的（同じ入力 → いつも同じ出力）なので、CI の --check が「インデックスがソースと食い違えばマージ不可」を機械的に強制します。

結果として文書をひとつ入れれば — ナビゲーション・知識マップ・3D 知識グラフ・検索・AI 用グラフファイルまですべての表面が自動でいっしょに更新されます。知識管理でありがちな「整理はしたのに見つけられない」状態が構造的に起きない理由です。

現在の規模 この手順で積み上がった知識は現在文書 115 編・固有概念 370 個・つながり 236 本（文書あたり平均 3.2 本）、さらにキュレーションで宣言した型付き関係 114 件が重なっています。孤立文書（つながり 0）は 0 編 — すべての文書がグラフの中にあります。数値は知識マップでライブ集計されます。
