ウィキはどうやって自分を守るのか — ゲートと自動化の体系

前の五編は、知識が積み上がり、つながり、読まれ、AI に消費され、プラグインとしてパッケージされる構造を説明してきました。最後の問いが残ります — この構造がずれていないことを、誰が保証するのか？ 文書を追加してインデックスの再生成を忘れたら？ ツールを直してプラグインの写しを忘れたら？ この編では、その保証を担うゲート（gate）と自動化の体系を、実際の事故の事例とともに説明します。

原則 — 判断のいらない労働は機械が、判断は人が

このウィキの自動化は生成ではなく検証が中心です。要約・概念・関係・本文は、人（または AI の作業者）が文書を読んでキュレーションします — ここには判断が必要で、判断を機械に渡すとグラフの正直さが崩れるからです。代わりに機械はふたつを担います: ① キュレーションの結果どうしが食い違っていないかを判定し（ゲート）、② 判断のいらない復元労働を代行します（--fix）。ルールを散文でだけ書いておくと忘れられます — 実際に忘れられて事故になり、そのたびにルールがゲートとして機械化されてきました。

つねに同じ結果 — 決定論的ビルドとドリフトのゲート

知識インデックス・グラフ JSON・llms.txt・sitemap・文書の日付 — サイトが読む生成物はすべてツールが生成し、手では編集しません。ビルドは決定論的（同じ入力 → いつも同じ出力）なので、CI の --check モードが「いまリポジトリにある生成物」と「ソースから作りたての生成物」をバイトで比較できます。食い違えば（＝文書を直して再生成を忘れれば）マージが止まります。だから AI が読むグラフファイルが実際の知識と違う瞬間は、構造的に存在しません。

PR を守る同伴ゲート — 「A を変えたなら B も一緒に」

あるルールは生成物の比較では捕まえられません。「アセットを直したならキャッシュバスターも上げよ」のような同伴ルールは、PR の変更一覧（diff）を見て片割れも一緒に来たかを検査する必要があります。こうしたゲートが四つあり、すべて実際の事故や運用の必要から生まれました:

ゲート守るルール生まれたきっかけ
check_worklog実質的な変更のある PR には Work Log を同伴（既存ログの更新も認める）「小さくても記録」のルールが散文にしかなく忘れられていた問題
check_cachebuster?v 付きアセット（app.js など）を直したら同じ PR で ?v を上げる2026-07-09 の実事故 — 直したのに再訪ブラウザで「反映されない」
check_plugin_syncプラグイン同梱のツールはルートの tools/ とバイト一致 + バンドル変更時はバージョン上げ2026-07-10 の実事故 — 検証機 190 行が古いまま配布された
diagram-bounds図の文字が箱・viewBox を1px もはみ出さないことをヘッドレスブラウザの実レンダーで検査フォント幅の推定だけでは境界値のはみ出しを取りこぼしていた問題

すべての同伴ゲートが遮断なのではありません。check_relations_review は新しく登録された文書を選び、その知識の関係の型の分布と 5 型（先行知識・実装・事例・根拠・置き換え）のチェックリストを出す非遮断のレビュー信号です — 関係は本文に実在するときだけ正直に付けるものなので（無理なリンクは禁止）、機械が「関係を入れろ」と強制できないからです。だからこれはマージを止めず、関係を先行知識だけで埋めるなというルールを人／AI に一度見せる信号としてだけ働きます（上の知識グラフの WARN と同じ「人が一度見る一覧」の思想）。

すべての PR は四層のゲートを通らなければなりません — ひとつでも ERROR ならマージ不可。

自分で直すゲート — --fix

ゲートが「ずれている」と判定したあとの復元は、ほとんどが判断のいらない労働です: バンドルの写しはルートからコピーすればよく、キャッシュバスターは数字を+1 すればよい。だからふたつのゲートに --fix モードがあります — check_plugin_sync --fix はずれたスナップショットを自動で復元し、check_cachebuster --fix は古い ?v を自動で上げます。境界は明確です: 復元は機械、判断は人。 プラグインのバージョンをどれだけ上げるか（内容更新＝minor、バグ修正＝patch）、機能変更が解説文書を古くしたかどうかは、--fix は触りません。

変更タイプの宣言 — ゲートが捕まえられないもののための規律

機械のゲートには限界があります。関係タイプの機能を入れた PR はすべてのゲートを通ったのに、肝心のこのシリーズの文書が新機能を説明していないという記述のギャップは、別の検討でようやく見つかりました — 「説明が古いか」は誤検知なく機械が判定できないからです。だから最後の装置はゲートではなく宣言の規律です。作業を始めるときに変更タイプを宣言し、タイプ別の影響表に目を通します:

  • ENGINE ビューアの動作 — 自己記述文書の検討 · ?v 上げ  /  STYLE デザイン・図 — デザイン規則 · ?v 上げ
  • TOOL ビルド・検証ツール — バンドル同期 + バージョン  /  SCHEMA 生成物の契約 — schema.md を同伴 · 後方互換の判断 · 解説文書の検討
  • PLUGIN スキル・メタ — バージョン上げ  /  CONTENT 本文・一覧 — 登録の 5 段階 · プラグインへの反映は禁止

宣言はプランや PR 本文に一行あれば十分です（例: 「変更タイプ: TOOL + PLUGIN」）。複数の宣言が普通です — 関係タイプの機能は五つのタイプを貫いており、始めに宣言していれば SCHEMA 行の「解説文書の検討」が実装 PR の中で引っかかっていたはずです。これはゲート（強制）ではなく判断の補助です — 判断が必要な領域を機械化する代わりに、判断する時点を前へ引き寄せます。

ひと目でまとめ 生成物は決定論的ビルドでのみ生成（直接編集は禁止）→ --check がドリフトを遮断 → 同伴ゲート 4 種が「片割れも一緒に来たか」を検査 → ERROR 0 がマージの条件。復元の労働は --fix が代行し、機械が判定できない記述やバージョンの判断は変更タイプの宣言で人が開始時点に押さえます。ゲートはすべて、実際の事故の再発防止として生まれました。
