21. ワークツリーでセッションを並列に回す

同じプロジェクトで二つのセッションが同時にファイルを直すと — 片方はログイン機能、片方はグラフィックのロジック — 同じファイルに触れた瞬間に衝突します。ワークツリー（worktree）は git が提供する独立した作業コピー。リポジトリの履歴は共有しつつファイルは別々に持つので、セッションごとに自分のワークツリーで働けば、そもそも重なりようがありません。終わったら git のマージで合わせるだけ。

git worktree コマンドを手で打ってもいいんですが、いまは Claude Code が寿命管理までやってくれます — claude --worktree（-w）で始めれば作成・命名・後片付けが自動で、デスクトップアプリは新しいセッションごとに勝手にワークツリーを作ります。.env のような git が追跡しないファイルはコピーに存在しないので、自動で持ち込みたければプロジェクトのルートに .worktreeinclude ファイルを置いてください。

# ターミナル1 — ログイン機能（独立ワークツリーで）
claude --worktree login-feature

# ターミナル2 — グラフィックのロジック（別のワークツリーで、同時に）
claude -w motion-logic

# それぞれ終わったらブランチをマージ — 衝突の心配なし
コピーが物理的に分かれているから、衝突はそもそも起きない — 管理するのは合わせる瞬間だけ。

22. MCP サーバーの代わりに API を直接呼ぶ

MCP（Model Context Protocol）は外部ツールをつなぐ標準ですが、サーバーをつなぐとそのツール定義の一式がコンテキストに載る費用があります。要る機能が一つ二つなら、その API エンドポイントを直接呼ばせるほうがトークンもコンテキストも安い。ツールをほぼ全部使うなら MCP、一つ二つなら直接呼ぶ — この区別だけ覚えておいてください。ちなみに、いまはツール検索（Tool Search）が標準で入って、必要なツール定義だけをその都度読み込むのでこの費用は大きく減りました。でも「使う分だけ載せる」という原則そのものは変わらず有効です。

公式ドキュメント: Connect Claude Code to tools via MCP — この wiki の MCP 紹介もどうぞ。MCP 仕様そのものの大改訂は尋ねない既定値で扱いました。

23. /loop で予約作業を仕掛け、セッションの外はルーティンに任せる

/loop 5分ごとにデプロイの状態を確認してのように繰り返し作業を仕掛けておくと、セッションが生きている間、Claude が定期的に自分で確認してくれます。デプロイの監視、定期点検、「8時にうちの Slack を確認して」のような時刻指定もOK。人が見張らなくていい監視系の仕事を丸ごと渡せるので、使い道は広いですよ。

ただし /loop が動くのはセッションが開いている間だけ。セッションやパソコンと無関係に動くべき仕事はルーティン（Routine）の出番です — プロンプト・リポジトリ・コネクタを一つの構成として保存しておくと、Anthropic のクラウド上でスケジュール（最短1時間間隔、cron 式に対応）や API 呼び出し・GitHub のイベントで実行されます。ノートパソコンが閉じていても動きます。整理すると三つ — いまのセッション内の繰り返しは /loop、自分のマシンに固定する予約はデスクトップの予約タスク、パソコンなしでも動くべきならルーティン。この wiki の朝のブリーフィングもルーティンで動いています。

公式ドキュメント: Run prompts on a schedule

24. スマホから遠隔で操縦する

ターミナルでclaude remote-controlを実行するとリンクが一つ出ます。それをスマホで開くと — コードはあなたのローカルマシンでそのまま動いたまま — 操作だけがスマホに移ります。地下鉄で進み具合を確かめて次の指示を出す、そんな使い方です。条件は一つだけ、ローカルマシンを点けておくこと — 操縦する相手はそのマシンですから。長い作業が終わったときや承認が要るときはスマホに通知も来ます。

公式ドキュメント: Remote Control — continue local sessions from your phone

25. データベースに自然言語で聞く

PostgreSQL・Supabase など主要なデータベースは MCP サーバーで Claude Code とつながります。つないでおけば「先週の登録者のうち離脱した人の共通点は？」みたいな質問を SQL なしの自然言語で投げられます — スキーマの探索、集計、条件検索まで、Claude がデータアナリストのようにこなします。どのデータベースを使っていても、まず「この DB をつないで」と聞くのがいちばん速い始め方です。

26. 深く考えさせるときは ultrathink

ターミナルでプロンプトに ultrathink を添えると（入力欄が虹色になったら適用済み）、Claude が思考（thinking）の予算を最大まで使ってから答えます。そのぶんトークンをたくさん燃やすので、日常使いには向きません — プロンプトをいくら変えてもいい答えが出ない難問や、構造設計の判断みたいな場面に取っておく切り札です。

公式ドキュメント: Model configuration — effort。執筆時点では思考の深さを effort 設定でも調節できます。

深く考えさせる別の道もあります — 一つのモデルの思考予算を増やす代わりに、複数のエージェントが合意するまで計画を練らせるやり方です。OMC プラグインの ralplan がそれで、planner・architect・critic の三役が合意に至るまで計画を検討します（--deliberate で高リスクの審議モード）。アーキテクチャ・DB・セキュリティのような判断の重い設計なら、ultrathink よりこちらが合うことも — 詳細は OMC 実行モード。

27. 権限を編集して安全に自律走行させる

settings.json でコマンドごとに無条件で許可／必ず確認を決められます。全部を自動承認すると、rm（ファイル削除）や git push --force（衝突を無視する強制プッシュ）みたいな危険なコマンドまで通りかねないので、「こういう危険なコマンドは私に聞くようにして」と頼んで拒否ルールを作らせておきましょう。2026年8月14日から既定値になった auto モードでは、このルールの重みがさらに増しました — 狭く書いた拒否ルールは席を外している間も働き続け、広すぎる許可ルールはむしろ無視されます。ルールが実際に執行される方針になったわけです。

# .claude/settings.json — 危険なコマンドは必ず確認
{
  "permissions": {
    "ask": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)"
    ]
  }
}
# 手で書くのが不安ならこの一行で:「rm や強制プッシュみたいな
# 危険なコマンドは必ず私に聞くよう権限を設定して」

公式ドキュメント: Permissions — 背景は尋ねない既定値の記事をどうぞ。

28. エージェントチーム — 互いに会話するエージェントたち

サブエージェントと混同しやすいんですが、構造が違います。サブエージェントは並列で働くものの互いに会話せず、メインに報告するだけ。エージェントチームは独立したセッション同士が会話して、作業リストを共有し、仕事を分け合います — 各メンバーとあなたが個別に話すこともできます。企画・マーケティング・デザインのエージェントを置いて互いに相談させながら働かせる絵なら、サブエージェントじゃなくエージェントチームです。トークンは余計にかかりますが、メンバー同士が互いの結果に反論し補い合うべき課題では、成果がはっきり違います。

報告の構造が違えば使い道も違う — 独立した調査はサブエージェント、協業の課題はエージェントチーム。

自分でフラグを立ててチームを設計する代わりに、パッケージ化されたチームモードを使う道もあります。OMC プラグインの team は N 人のエージェントに役割を与えて段階型のパイプラインで協業させるモードで、完了まで繰り返す ralph と組み合わせた team ralph が OMC で最も強い実行強度。チームの構成と役割の割り当てをプラグインが代わりにやってくれるので、エージェントチームを実務ですぐ試したいならこちらの入口が速いです — OMC 実行モード・エージェントとスキルを参照。

公式ドキュメント: Orchestrate teams of Claude Code sessions — 執筆時点では実験的な機能で、環境変数 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 で有効化します。方法論が気になるなら、この wiki のハーネスエンジニアリング講義がエージェントチームの運用を12編で扱っています。

この wiki に当てはめると

  • ルーティン（使用中） — この wiki の朝のブリーフィングがルーティンで動いています。毎朝 KST 7時に AI ニュースをさらって登録候補をまとめて報告する仕事を、人がパソコンを点ける前にクラウドが済ませておくんです。
  • 試してみたい: DB への自然言語クエリ — この wiki のお気に入り・閲覧数は Cloudflare D1 データベースに積まれています。MCP でつなげば「今週いちばん閲覧が伸びた文書は？」を SQL なしで聞けます — 次のネタをデータで選ぶ道です。
  • 試してみたい: ワークツリー — いまは一つのブランチで順番に作業しています。長い翻訳バッチと急ぎのバグ修正が重なる日は、ワークツリー二つに分ければ互いに待つ必要がありません。
  • 試してみたい: 拒否ルール — このリポジトリは master がそのままデプロイなので、git push --force が特に危険。拒否ルールの筆頭候補です。
  • 試してみたい: ralplan — 知識グラフのモデル改編や文書の統合みたいに一度決めたら戻しにくい構造の決定には、planner・architect・critic の合意を通すほうが安全です。

むすび

28のコツは三つの原則に縮みます。コンテキストは予算（初級）— 節約して、分割して、見えるようにする。繰り返しは仕組みへ（中級）— うまくいったプロンプトはスキルと CLAUDE.md に固める。並列は隔離から（上級）— ワークツリーと権限ルールを先に置いてから自律を広げる。道具は変わり続けても、この三つは長持ちするはずです。
