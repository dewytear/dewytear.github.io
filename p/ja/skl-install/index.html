スキルの導入・セキュリティ・作成

スキルの実習は拍子抜けするほど簡単です — 「このスキルを入れて」のひと言で終わります。ただし、さきほど学んだ動作の原理を思い浮かべながら使うと、ずっと面白くなります。

インストールする

  • スキルの配布ページの 「Get this skill」のボタンを押すと、git のアドレスがコピーされます。
  • そのアドレスを Claude Code に貼り付けて「このスキルを入れて」と言えばインストールされます。（手動なら該当のフォルダにコピー）
  • 既定ではグローバル（全体）のフォルダに入ります。（プロジェクト／グローバルの選択もできますが、はじめは気にしなくて大丈夫です）
  • インストール後に見えなければ /reload（プラグインのリロード）するか、Claude Code を落として立ち上げ直せばスキルを咥えてきます。（/clear はコンテキストを空にするだけなので別ものです）

スマートフォンでは Claude アプリ（サンドボックスで動く）からもスキルを試せます。

使う

# 使えるスキルの一覧を確認
私が使えるスキルには何がありますか?
# 明示的な呼び出し
/スキル名 <命令>

実習 — 組織のブランドのスキル

機関のウェブサイトのスタイルをもとに作ったブランドガイドラインのスキルを入れてから、こう頼みます。

<ブランド> のブランドガイドラインのスキルを使って
夏季ワークショップのページを作って

すると、でたらめにではなく組織のブランドのスタイルでページが作られます。核心はきれいさではなく — 同じスキルを使えばみんな似たスタイルになり、組織の中で一貫した、再利用できる成果物が出てくる、という点です。同じやり方で PPT テンプレートのスキル（発表資料）、Finder のスキル（組織内の専門家を探す）などを使います。

発動の原理のおさらい 「組織のスタイルで作って」と言うだけでスキルが発動するのは、メタデータの description に「このスタイルを使うときはこのスキルを使え」と書いてあるからです。ただし確実にしたいならスキル名を明示するほうがよいです。

セキュリティ上の注意

スキルは強力なぶん、セキュリティのリスクも大きくなります。必ず押さえておくべきところです。

他人のスキルを軽々しく使わない

スキルの中にはスクリプトが入っていて、このスクリプトは自分の PC（ノート）を実行させる権限をそのまま持ちます。だから、他人が作ったスキルを検証なしに持ってきて使うのは危険です。

  • スキルの中に危険なコードが隠れていることがあり、実際に API キーの漏洩・セキュリティ事故の事例が多くあります（MCP のハブから取ったものなど）。
  • 認証・検証されたスキルだけを使い、できれば社内で検証されたスキルだけを使います。
  • 検査のツールもありますが、そのツールをどこまで信頼するかがまた問題です。結局、コードやガイドラインを自分で確かめる慎重さが要ります。
  • 危険なスキルを「上からかぶせて」補うより、参考にして自分で作るほうが安全です。

権限とサンドボックス

  • スキルごとに読み取りのみ／書き込み・編集も可など、権限の制約を設けられます。
  • ノート PC で何気なく「はい」と答えるとシステムが壊れることもあるので、危険な作業はサンドボックス（VM）で別に回すほうが安全です。
  • 機関の内部なら閉域網・オンプレミスの環境で動かすことを勧めます。（モデルも社内／オープンなモデルを選ぶ）
ひと言でいうと スキルは自分のコンピュータを実行する権限を持ちます。出どころのはっきりしないスキルは、絶対に軽々しく入れないでください。

スキルをつくる（スキルエンジニアリング）

うまく使えるようになると、自然と「自分で作りたい」と思うようになります。スキルをつくることをスキルエンジニアリングと呼び、それを助けるスキルをつくるスキル（skill-creator）が標準で備わっています。

skill-creator — メタなスキル

A/B テストのループを回しながら磨き、ベンチマークを通れば完成です。

スキルをつくるためのスキルで、次の流れとサブエージェントを備えています。

  • create → evaluate → improve → benchmark のループ。
  • 内部に evaluator · grader · 比較 · 分析のサブエージェントを搭載。
  • スクリプトを入れて「これをスキルにして」と言えば、自前のループとテスト（A/B）を経て、しっかりしたものに仕上げてくれます。

ふたつのカテゴリ

区分内容モデルが進歩したら
能力を伸ばすスキルPDF の操作・文書の生成・複雑なファイル変換など。スクリプトにして決定論的・安定的に使う。モデルが上手になれば不要になることも
組織に根づくスキル組織の責任・業務の流れ・担当者など。エージェントが知らない社内の知識。どれだけ進歩しても代替できない — 作りつづける必要がある
強調 — 組織に根づくスキルを作りつづけよう 能力を伸ばすスキルは、いまはうまく活用しつつ「一生もの」とは思わず、モデルが進歩したら畳めるものとして見ます。いっぽう組織に根づくスキルは、LLM がどれだけ進歩しても自分たちの組織の責任・流れ・担当者を代わりにはできないので、継続的に築いていくことがエージェントのガバナンスの核心です。
配布が簡単 スキルの大きな長所のひとつが配布です。共有のリポジトリ／サーバー／コミュニティに登録しておけばバージョン管理と共有がしやすく、「Get this skill」をコピー →「入れて」の一度で組織全体へ広がります。現場でファイルを直して再配布するのも、すぐにできます。

まとめ — エンジニアリングの階層と Q&A

エンジニアリングの階層

ここまで学んだものを目的で分けると、「全部エンジニアリングだな」ではなく、それぞれの筋が見えてきます。

エンジニアリング目的
プロンプトエンジニアリングLLM を賢くする
コンテキストエンジニアリング文脈の当たる確率を上げる
エージェンティックエンジニアリングAI が仕事をうまくこなすようにする
ハーネスエンジニアリング信じて任せられるようにする

ハーネスはスキル + サブエージェントを搭載したメタなスキルと見ることができます。スキルの概念をつかんでおけば、ハーネスが表向きは簡単そうに見えても内部は複雑だ、と理解しながら見られます。

MCP vs スキル

MCP はプロトコルです — 外部のツールとエージェントをつなぐための規約なので、読み込み方も使い方もスキルとは違います。競合の関係ではありません: スキルの中で外部との接続が必要なら MCP を使えるので、スキルの中に MCP があってもよいのです。ただしスキルがあまりに強力なので、MCP の代わりにスキルで置き換えるケースも増えています。

Q&A の要点 · 公開されたスキルを軽々しく受け取るのは安全ではない — 検証されたものだけを。
· 同じ名前の MCP の関数とスキルがあると状況によって変わるので、「このスキルを使え」のように明示するか、ネームスペースで区別する。
· スキルの性能評価 — トリガーがきちんと効くか／結果が役に立つか、といった指標を先に決めてから LLM judge と目視で確認する。
· トークン — 一般の Claude より Claude Code のほうが多く使うが、望む結果が一度で得られるならより有用なこともある。トークンだけを見ず、総合的に選ぶ。
