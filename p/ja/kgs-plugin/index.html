ウィキエンジンのプラグイン化 — wiki-plugin と同期の規律

この知識体系はこのサイト専用ではありません。構造・パイプライン・検証ゲートを Claude Code プラグイン（wiki-plugin）としてパッケージし、どのリポジトリでも同じ知識体系をブートストラップできるようにしました。この文書では、何をなぜプラグインにしたのか、そして原本と写しがずれないようにどんな規律を置いたのかを説明します。

なぜ — エンジンとコンテンツの分離

このウィキはふたつの層でできています。エンジン（4 階層の構造、登録パイプライン、インデックスビルダー、検証ゲート、ビューア）とコンテンツ（文書たち、キュレーションされた概念、クラスター名）。前の四編が説明した原理はすべてエンジンの性質なので再利用できます — 新しいプロジェクトの知識管理を始めるときにこのエンジンを入れれば、文書を入れた瞬間から同じ知識グラフが育ちます。逆にコンテンツ（このサイトの doc-entries・クラスターラベル）はサイト固有の資産なのでバンドルから除外されます。

構成 — スキル 4 種 + ツールのスナップショット

プラグインはマーケットプレイスから二行でインストールします（/plugin marketplace add → /plugin install）。入れると、ウィキ運用の四つの局面がスキルとして入ってきます:

スキルやること
wiki-init新しいウィキプロジェクトのブートストラップ — 構造・ナビツリー・インデックスのパイプライン・検証ゲート・CI までいっぺんに。
add-doc文書追加の全ワークフローを強制 — ファイル → ツリー登録 → キュレーション → インデックス → Work Log → 検証。
index知識インデックス・文書の日付・AI 消費レイヤーの再生成 + スキーマ契約の順守。
validate品質検証の一括実行と ERROR/WARN の解釈 — 「何が欠陥で何が検討の合図か」まで。

スキルとともに、インデックスビルダーや検証機などの運用ツールのスナップショットが同梱されます。プロジェクトに自前の tools/ があればそちらを優先して使い（ドッグフーディングの経路）、なければプラグイン同梱のものを使います。SPA ビューア（画面）は、マーケットへの追加がリポジトリ全体をクローンする仕組みなので、別バンドルなしでつねに最新の実物がローカルにあります。

規律 — スナップショットは必ず原本と同じでなければならない

同期の規律 — 人の記憶ではなく CI が原本と写しの一致を保証します。

スナップショット方式の弱点はドリフト（原本だけ直して写しを忘れること）です。そこで専用のゲートが原本の tools/ とバンドルをバイト単位で比較し、違えば CI を失敗させます。さらにバンドルが変わる PR はプラグインのバージョン上げを同伴しなければ通りません — 入れる側が「いつ何が変わったか」をバージョンで追えるようにするリリースの規律です。このゲート自体と、サイト固有のデータ（クラスターラベル・キュレーションのエントリ）はバンドルの除外リストに入っています。

ドッグフーディング — 最初の利用者はこのウィキ自身

このウィキが wiki-plugin の最初の利用者でありリファレンス実装です。文書の追加・インデックスの再生成・検証まで、このサイトの日々の運用がそのままプラグインの統合テストになり、運用で見つかったギャップ（抜けたガイド、ゲートの穴）はプラグインの改善へ還流します。前の四編で見た原理 — 積む構造、つなぐルール、読む眼、AI の消費 — がすべてこのプラグインの中に入っているので、このシリーズはそのまま wiki-plugin の設計解説でもあります。

インストール /plugin marketplace add dewytear/dewytear.github.io → /plugin install wiki-plugin@dewytear-wiki。スキルの詳細と同期のポリシーはリポジトリの plugins/wiki-plugin/README.md にあります。この同期がずれないよう守るゲート・自動化の体系は次の編で扱います。
