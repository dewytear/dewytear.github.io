グラフデータベースとGraphRAG — 関係を保存すると答えが変わる

表の代わりに関係を保存するグラフデータベースから出発し、その上にナレッジグラフを築き、そのグラフでAIの回答品質を引き上げるGraphRAGまで — 概念と例を軸に一気につなぐ入門解説です。

まず、なじみのない言葉を三つ

  • グラフデータベース(グラフDB) — データを表(テーブル)ではなく点(ノード)と線(エッジ)で保存するデータベース。「誰が何をした」という関係そのものが保存の基本単位です。
  • RAG — AIに質問するたび、資料の山から関連する断片をその場で探して添える方式(Retrieval-Augmented Generation、検索拡張生成)。オープンブック試験のように、答える前に根拠を広げさせます。
  • GraphRAG(グラフRAG) — その「資料の山」をバラバラの断片ではなく互いにつながったグラフとして保存し、検索時に周辺の文脈まで一緒に引き寄せるRAGです。

この三つは一本の鎖でつながります。関係を保存すると(グラフDB) → 知識が網になり(ナレッジグラフ) → 網ごと検索して答えの根拠が豊かになる(GraphRAG)。以下、この鎖を先頭から一つずつ解いていきます。

グラフDB — JOINの代わりに道探し

私たちに馴染み深いのはリレーショナルデータベース(RDB)です。会員表・評価表・映画表のように表単位でデータを積み、表と表の関係は照会の瞬間にJOIN(共通の列で二つの表をつなぎ合わせる演算)で復元します。表が二つならJOIN一回、五つなら四回 — 関係が深くなるほど、つなぎ合わせるコストが膨らみます。

グラフDBは逆を行きます。関係を最初から矢印(エッジ)として保存しておくのです。「Aという人が高評価をつけたアクション映画は?」という質問が来たら、表をつなぐのではなく、Aのノードから出発して評価エッジをたどり、ジャンルエッジをもう一歩歩けば答えに着きます。人が頭の中で関係を思い浮かべる過程をほぼそのままデータ構造に移した格好で、描いてみれば文章のように読めます — 人物A →(評価 5.0)→ 映画X →(ジャンル)→ アクション。

同じデータ、違う保存 — RDBは関係を計算し、グラフDBは関係を保存します。「Aが高評価したアクション映画」は右側なら矢印二歩で届きます。

この保存モデルの正式名称がプロパティグラフです。ノードとエッジの双方にラベル(種類: 人、映画…)とプロパティ(名前、点数、日付…)を付けられるので、現実の「主語–動詞–目的語」をほぼそのまま収められます。代表的な実装がNeo4jで、このウィキのナレッジグラフモデルも同じプロパティグラフ系です。

Cypher — グラフへの尋ね方

RDBにSQLがあるように、グラフDBにはCypher(サイファー)という問い合わせ言語があります。面白いのは、文法が絵に似ていること — ノードは丸括弧 ( )、エッジは角括弧 [ ]、方向は矢印で書きます。先ほどの質問をCypherにするとこうなります。

// Aが4点以上をつけたアクション映画 — パターンがそのまま絵
MATCH (a:Person {name: 'A'})-[r:RATED]->(m:Movie)-[:GENRE]->(:Genre {name: 'Action'})
WHERE r.score >= 4.0
RETURN m.title, r.score

(a:Person)-[r:RATED]->(m:Movie) を声に出して読めば「人物aが映画mを評価した」。JOINを頭の中で組み立てる必要はなく、探したい関係の形をそのまま描いて尋ねるのがグラフ問い合わせの感覚です。

RAGの復習 — オープンブック試験

RAGはAIの回答に根拠を付ける標準手法です。質問が来ると①資料庫から関連する断片を検索し(Retrieval)、②質問に添えて増強し(Augmented)、③その中から答えを生成させます(Generation)。モデルが記憶に頼ってもっともらしい作り話(ハルシネーション)をする代わりに、出典のある答えを返すようになります。ウェブ検索との違いは自分だけのデータ — ウェブにない社内文書、個人ノート、設備マニュアル — を根拠に使える点。組織の専門家の暗黙知(文書化されていない経験知)を、いつでも引き出せる引き出しにする仕事に近いのです。

ふつうのRAGは資料をベクトルデータベースに入れます。文書は長いので一定の長さのチャンク(断片)に切り、各断片を意味を担う数値の列(埋め込み)に変えて保存し、質問と意味の近い断片を拾ってきます。ここまでは立派です。問題は切った瞬間に文脈が切れること — 断片同士は他人になり、「この断片がどの文書のどの章に属し、どの断片とつながるのか」を検索は知り得ません。

GraphRAG — 断片をつなぎ、網ごと持ってくる

GraphRAGはこの断絶をグラフで縫い合わせます。チャンクをノードにし、チャンク同士の関係 — 同じ文書への所属、前後の順序、同じ実体(人・製品・出来事)への言及 — をエッジとして保存します。検索は二段階になります。まずベクトル検索で質問に近い断片を見つけ(広く網を打つ)、続いてその断片からエッジをたどって隣の文脈を一緒に引き寄せる(深く歩く)。断片一つではなく、断片の属する街区が丸ごと根拠になるのです。

左は断片を一つずつ拾い、右は断片の属する街区ごと持ってくる — 答えの説得力の差はここで生まれます。

効果は三つの筋で現れます。

  • マルチホップ推論 — 「政治カテゴリの最新ニュース」という質問は、ベクトル検索だけでは不器用です(「政治」という語に似た断片を探す話ではないので)。グラフならカテゴリノード → 所属記事 → 各記事の本文チャンクと歩いて、まさにその集合を集めてきます。集まった記事がそのまま答えの根拠一覧です。
  • 階層と所属が見える — 断片がどの文書・どの章に属し、どの文書と関連するかが構造として残るため、モデルは「文脈の切れた断片一つ」ではなく構造を知った状態で答えます。
  • 根拠の可視化 — 答えがどのノードを踏んで作られたかをグラフの絵として一緒に見せられます。「答え+答えの地図」が同時に出るので、検証と信頼が容易になります。

まとめると、モデルは同じまま、モデルに手渡す文脈の織り方が変わるのです。答えが一、二段落におとなしく収まる質問ならベクトルRAGで十分。答えが複数文書に散った関係にまたがるときにGraphRAGが真価を出します。実務ではベクトルで拾い、グラフで歩くハイブリッド構成が一般的です。

オントロジーとグラフスキーマ — 網の設計図

グラフを積む前に決めるべきことがあります。どんな種類のノードと、どんな種類の関係を認めるのか。この規則体系がオントロジー(知識を整理する標準の枠)であり、それをグラフDBのラベル・プロパティとして具体化したものがグラフスキーマです。日常や業務で暗黙のうちに使っている概念とその関係規則を仕様書として書き出し、AIにも人と同じ地図を見せる作業です。

教育ドメインの例が直感的です。概念と概念の間に先行関係を記した知識マップ — 「二次関数を学ぶには方程式が先」 — があれば、二次関数でつまずき続ける生徒に二次関数の問題ばかり繰り返す代わりに、一歩手前の方程式の問題を一緒に薦めることができます。オントロジーが推論の基準線になるのです。プロダクトチームがデータ分析のためにページ–サブページ–クリックイベントの名前と階層を設計するタクソノミー(分類体系)の仕事も同じ系譜 — オントロジーは関係の意味まで記す、より大きな枠だという点が違うだけです。

順番に並べるとこうなります。オントロジー(どの関係を認めるか) → グラフスキーマ(それをラベル・プロパティでどう書くか) → ナレッジグラフ(実データで満たした網) → GraphRAG(その網を検索に使う)。GraphRAGの品質はほとんどこの設計段階で決まります。

名前が似た他人 — LangGraph

名前に「グラフ」が入るためよく混同されるのがLangGraph(ラングラフ)です。これは知識を入れるグラフではなく、AIエージェントの作業フローを組むフレームワーク — 質問意図の分析、情報検索、回答生成といった作業ステップ一つひとつをノードとして定義し、どの順序・条件で実行するかをエッジでつなぎます。つまりGraphRAGのグラフは知識の地図、LangGraphのグラフは仕事の順序図。二つはよく一緒に使われます — LangGraphで組んだエージェントの「検索」ノードの中でGraphRAGを呼ぶ、という具合です。組んだフローが意図どおり動くかは、可視化ツールのLangGraph Studioで段階ごとの実行を目で確かめられます。

どこで使われるか

製造・スマートファクトリーが好例です。工程から溢れる故障履歴を設備 → 部位 → 症状 → 原因 → 対処のグラフとして書いておけば、新しい故障が起きたとき、同じ症状の過去事例と検証済みの対処まで関係をたどって即座に届きます。ニュースサービスならカテゴリ → 記事 → 本文チャンク、教育なら概念 → 先行概念 → 問題 — ドメインごとに網の形は違っても、「関係が答えの半分」である場所ならどこでも同じ方法が通ります。組織や個人の暗黙知をエージェントに移す超個人化の流れと噛み合うのもここです: 自分が暗黙に知っているつながりをグラフとして明示して初めて、AIも自分と同じように歩けるのです。

始め方 — 描いて、書き出して、自動で抽出する

第一歩はただ描いてみることです。Neo4j Labsの無料ウェブツールarrows.appは、マインドマップを描く感覚でノードをドラッグしてグラフをスケッチできるホワイトボードです。頭の中の考えや自動化したい業務を、とにかくノードと矢印で広げてみる — これが事実上のオントロジーの下書きです。描き上げた図はPNG・SVGはもちろんCypher文としてエクスポートでき、そのままグラフDBに流し込んで本物のナレッジグラフにできます。

第二歩は文書を自動でグラフに変えることです。Neo4j公式のPythonパッケージneo4j-graphragにはナレッジグラフ構築パイプライン(SimpleKGPipeline)が入っており、PDFを与えるとチャンク分割 → 実体・関係抽出 → 埋め込み → グラフ格納を一度にやってくれます。

# PDF一本をナレッジグラフに — 実質この一行
pipeline = SimpleKGPipeline(
    llm=llm, driver=neo4j_driver,
    embedder=embedder, from_pdf=True,
)
await pipeline.run_async(file_path="document.pdf")

回し終えると文書中の実体と関係がグラフとして抽出されており、同じパッケージの検索器(リトリーバー)で、ベクトル検索とグラフ探索を混ぜたGraphRAG問い合わせへと続けられます。「文書をどうグラフに変えるのか」が漠然としているときの、最速の初実験です。作って終わりではなく、望む答えが返るかの評価まで付けて初めて使い物になるRAGになる、という点も覚えておく価値があります。

このウィキとの接点

このウィキがGraphRAGを回しているわけではありません。しかし素材は同じ系譜です — 文書ごとに概念を抽出してつなぐ知識体系、その結果として立っているプロパティグラフモデル、そして機械が丸ごと持っていけるknowledge-graph.jsonのエクスポートまで。この記事の語彙で言えば、このウィキはオントロジー(kgs文書セット)とナレッジグラフ(インデックス)をすでに備えた、GraphRAG-readyなコーパスなのです。グラフを手で触ってみたければ、このウィキのグラフスタジオでノードとエッジを置いてみるのも、arrows.appと同じ感覚の練習になります。

ファクトチェックノート 概念説明と例(映画の評価、ニュースカテゴリ、教育の知識マップ、製造の故障履歴)は提供された対談の書き起こしを再構成したもので、話者の身元は扱わない。技術的事実は一次資料で照合した — neo4j-graphrag-python ドキュメント(SimpleKGPipeline・from_pdf)、arrows.app(Neo4j Labs)のCypherエクスポート、openCypherのパターン文法、LangChainのLangGraphドキュメント(ノード・エッジ・状態)。ベクトルRAGのチャンク断絶とGraphRAGのマルチホップの利点は、GraphRAGサーベイ(arXiv 2501.00309)とHybridRAG(arXiv 2408.04948)の整理と一致する。Cypher例のラベルは説明用であり、実務のスキーマではない。
