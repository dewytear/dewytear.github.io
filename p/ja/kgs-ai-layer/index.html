AI がこのウィキを読む方法 — 機械可読レイヤーとグラフ巡回

このウィキの最終目標のひとつは、AI に仕事を渡すときここを真っ先に見に行かせること、そして単票の検索ではなく関連をたどって分析させることです。だから人間向けの画面とは別に、外部の AI が自分で見つけて巡回できる機械可読レイヤーがあります。文書本文が JS なしに URL でそのまま fetch される静的断片であること（1 編）が、このレイヤーの土台です。

三つの扉 — 表紙・グラフ・契約

  • llms.txt（表紙） — サイトルートにある AI 向けの玄関。ウィキの目的、機械向けファイルの場所、そしてすべての文書のタイトル・要約・URL が System ごとに整理されています。AI エコシステムの慣例（llms.txt）に従うので、初めて来たエージェントが最初に読むファイルです。
  • data/knowledge-graph.json（自己完結グラフ） — このファイルひとつを fetch するだけでグラフ全体を巡回できます。各ノード（文書）にタイトル・要約・概念・関連エッジ（related）と向きのある型付き関係（relations）はもちろん原文 URL までインラインされているので、ほかのファイルと結合する必要がありません。
  • AI 巡回ガイド（契約） — 「ノードとは何で、エッジをどう解釈し、どの順で fetch するか」を明文化した文書。スキーマとルールがここに固定されているので、どのエージェントも同じやり方で読みます。

ここに三つの扉を補助する入り口もいっしょに生成されます。llms-full.txt はすべての文書の本文プレーンテキストを 1 ファイルにまとめた全コーパスのダンプなので、fetch 一度でウィキ全体をコンテキストに載せられます。feed.xml（Atom フィード）は最新の文書 30 編を時系列で知らせ、人の RSS リーダーやクローラーが新しい記事を購読できるようにします。robots.txt は主要な AI クローラー（GPTBot・ClaudeBot・PerplexityBot など）を名指しで明示的に歓迎し、上の入り口を広告します。コンテンツのライセンスは CC BY 4.0 — 「出典を示せば自由に引用・再利用してよい」という法的な合図を robots.txt・llms.txt・フィード・サイトのフッターが一貫して宣言し、AI システムが安心してこのウィキを引用できるようにしています。

JS を実行しない客のための扉 — 静的スナップショット

ここまでの入り口は機械にデータを渡す道でした。ところが一般の検索エンジンはデータではなくページを索引します。このウィキはハッシュルーティングの SPA なので、JS を実行しないクローラーが #!welcome に来ると空の抜け殻を見ます。文書断片（docs/ko/…）は本文ではあるものの、タイトル・説明・正規アドレスのない HTML の破片なので、ページとするには足りません。

そこで文書ごとに静的スナップショットもいっしょに出します — /p/<name>/（英語は /p/en/<name>/、日本語は /p/ja/<name>/）。本文をそのまま入れつつ <title>（最初の h2）・説明（要約）・canonical・言語の相互リンク（hreflang）・Article JSON-LD（ライセンス・作成日を含む）を載せた本物のページです。本文中の #! リンクもスナップショットどうしでつないであるので、JS のないクローラーがリンクをたどるだけでウィキ全体を巡回でき、/p/・/p/en/・/p/ja/ の全体一覧ハブがその巡回の出発点になります（ホームは JS でナビゲーションを描くので、元の HTML には文書リンクがひとつもありません — ハブへのリンクを <noscript> に埋め込んで、その行き止まりをなくしました）。

スナップショットは人が到着してもよいページです。最初は人が開くとすぐ SPA へ送っていたのですが、それではこのスナップショットが存在する理由である文書ごとの固定アドレスが消えてしまいます — 検索結果や共有リンクから来た人はアドレスが /#!name に変わるのを見ることになり、ブックマークしたり再共有したりしてもその文書を指せません。いまは送らず、いちばん上に「ウィキで開く」リンクだけを置いています。スナップショットにはOpen Graph・Twitter カードも載っているので、リンクを展開して見せる場所（X・Slack・Discord など）でタイトル・要約・画像がいっしょに出ます — そのプレビューを作る側は JS を動かさないので、SPA では作れず、静的ページだけができることです。

同じ知識の三つの表面 ひとつの文書は三つのアドレスを持ちます — url（原文の断片、機械のパース用）・route（SPA、人間用）・page（静的スナップショット、検索エンジン・JS のないクローラー用）。グラフのノードに三つとも入っているので、消費者は目的に合う表面を選べます。サイトマップが広告するのは page です。

巡回はこう流れる

単一 fetch の巡回 — グラフファイル一枚で計画を立て、原文は必要なものだけ取ってきます。

実際の 2 ホップ巡回を例にすると: ハブのハーネスの構成と効果から出発すると、1 ホップで隣の 4 編、2 ホップなら13 編に届きます。AI はこうして到達した文書の集合について、共有概念（shared）を根拠に「これらの文書がなぜひとまとまりなのか」を説明しながら分析できます — 単票の検索では不可能な、関係ベースの読み方です。ここに relations が加われば、単に「関連がある」を超えて先行・実装・根拠といった関係の種類と向きまで読み、「何を先に読むべきか」「どの文書がどの主張の根拠か」を押さえて分析できます。

絶対にずれないように — ドリフトのゲート

機械可読ファイルが実際の知識とずれてしまえば、ないほうがましです。だからこれらのファイルは手で書かず知識インデックスから自動生成され（robots.txt もフィードもすべて生成物）、CI の --check ゲートが「文書を追加・修正して再生成しなければマージ不可」を強制します。フィードの時刻さえビルド時刻ではなく git 履歴（doc-dates.json）から来るので、再生成しても結果が揺れません。結果: 文書が増えた瞬間に llms.txt・llms-full.txt・フィード・グラフ JSON・sitemap・静的スナップショットがつねに一緒に最新になります。スナップショットのゲートはもう一歩進んで、もう生成されない古いスナップショット（stale）まで捕まえます — 文書の名前が変わると古いページが幽霊のように残り、検索エンジンに露出しつづけるからです。検証の時点で 97 ノードの URL がすべて実ファイルと一致し、切れた参照（dangling）が 0 であることを機械的に確認しました。

AI に仕事を頼むとき プロンプトに一行あれば十分です — 「dewytear.github.io/llms.txt をまず読み、knowledge-graph.json の関連（related・relations・concepts）をたどって分析せよ。」 スキーマの詳細と巡回のルールは AI 巡回ガイドが契約として保証します。こうした知識管理の構造のおかげで、ウィキが大きくなるほど AI の分析半径も自動で一緒に大きくなります。
