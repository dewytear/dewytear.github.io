実習と哲学 — オンボーディングから運用まで

スターターキットにはオンボーディングのスキルが入っていて、/onboard（または「オンボーディングして」）のひと言で個人向けのセットアップが始まります。

リリースの入手からグラフビューでボルトを開く瞬間まで — /onboard ひとつで個人向けのセットアップ。

準備 — リリースを入手する

  • 講義で案内された LLM Wiki のページ（GitHub リポジトリ）から、最新のリリース（例: 1.7.0）のファイルをダウンロードします。
  • zip を解くとフォルダがひとつ（= ウィキボルト、すなわち Obsidian のボルト）できます。
  • 実際に使うパス（ドキュメント・デスクトップなど）へ、このフォルダを先に置いておきます。

オンボーディングの実行

# フォルダのパスをコピー — Windows: Ctrl+Shift+C / Mac: Cmd+Option+C
# そのフォルダで Claude Code を実行してから
/onboard        # または「オンボーディングして」

決められた質問が続きます — どんな目的で使うのか、なんと呼べばよいか、メインボルトとつなぐか、など。コンテキストを多く渡すほど賢くなるので、誠実に答えます。（およそ 5 分）

  • メインボルトがあればつなぐ — 人工知能がウィキを作るときに自分が書いたノートを参照します。
  • なければ単独で始めても大丈夫です。

Obsidian でボルトを開く

  1. Obsidian の左下 → ボルトの管理 → Open folder as vault でそのフォルダを開きます。
  2. 左下に自分のフォルダ名が出ているか確認します。
  3. Ctrl/Cmd + G でグラフビューを開くと、埋め込まれたノートの関係が見えます。
きれいに始めたいなら サンプルのデータなしで始めたいときは、concept・entity・article のフォルダのサンプルファイルだけ消せば大丈夫です。Codex 用のファイルも用意されていますが、Claude Code で使うほうが有利です。

三つの中心的な動作 — Ingest · Query · Lint

LLM ウィキの重要な三つの動作です。（Karpathy が示した考え方）

三つの動作が循環し、クエリは BM25 → ベクトル → 仮説検証へと段階的に強くなります。

1）Ingest — 消化・吸収

ひとつの記事／概念をチャンクに分けて、人工知能にも人にも読みやすいカードにする作業です。生の資料を渡せば出典ベースのウィキカードが生成されます。

/ingest        # 生ソースをウィキカードへ

2）Query — 取り出して使う

集めるだけでは意味がないので、クエリで取り出して使います。一般のエージェントは正規表現（語の頻度・マッチ）でしか検索しませんが、ここでは QMD（マークダウンのクエリ）MCP で三つの検索を段階的に使います。

方式いつ
BM25（レキシコン）利用者がはっきりした語を挙げているとき — 頻度の高い語で検索。
ベクトル検索あいまいなとき — 似た概念まで持ってくる（「水が飲みたい」→ コップ）。
仮説検証（hypothetical）利用者の水準が知識の水準より低いとき — LLM が問いを読み替えてキーワードを作り、検索し直す。

後ろへ行くほど時間がかかります。ファイルを正確に分かっている状況なら、その住所を直接渡すのがいちばん速いです。結果は query フォルダに整理され、どんな目的で作った文書かを取り出し直せるように出典ベースで残ります。

3）Lint — 保守

メンテナンスの作業です。新しくインジェストしたときに、既存のノート（例: A という概念）が新しいノート（A′）と関係していて古くなっていれば一緒に更新します。/lint で全体的な保守を回し、いつでも引用できる新しさを保ちます。（監査 audit・検証 verify のスキルも一緒に）

まとめ Ingest（生の資料 → カード）·Query（BM25・ベクトル・仮説検証で取り出す）·Lint（新しさを保つ）— この三つの軸で、生きた知識ベースを回します。

ウェブクリッパーとインボックス、Query の実戦

ウェブ記事をクリッパーでインボックスに集め、/inbox で仕分けし、インジェストしてから /query で取り出して使います。

Obsidian のウェブクリッパー

Chrome 拡張の Obsidian Web Clipper でウェブの記事をクリップし、ボルトのインボックスに入れます。講師はキャプチャのルール（JSON のテンプレート）をウィキボルトに入れてあります。

  • 設定 → 一般オプションのボルトの保存先にボルト名を登録すれば、どのボルトへ送るか指定できます。
  • テンプレート（JSON）をインポートし、Web Article のテンプレートをいちばん上に上げます（先に発動）。x.com・youtube など、アドレスによってトリガーされるテンプレートもあります。
  • キャプチャすると、あらかじめ指定した 0.2 inbox/article のようなフォルダに保存されます。

インボックスのスキル — 集めて分析

/inbox        # インボックスに集めた資料を分析し、主題ごとにまとめて提案

いくつかを先に集めておいて /inbox を回すと、「5 つのうち 3 つは同じ筋なので、一緒にインジェストしますか？」のように主題ごとに分けて提案します。

トークンのコツ — 原文のスクレイピング

インジェストのときにリンクだけ渡すと、AI が原文を取ってくるところから始めることになり、トークンが余分にかかります。ウェブクリッパーで先にスクレイピングして原文を確保してから始めれば、トークンを節約できます。

Query の実戦

/query LLM ウィキボルトの学術的な価値を整理して。
あとでリファレンスマネージャーで書誌情報を引用するつもり。

ウィキボルトで足りなければメインボルトまで検索して持ってくるようになっていて、自分がどう質問したかも一緒に記録されます。結果には答えだけでなく、Obsidian のメタデータをどう設計すればよいか（author・created・source・category など）まで薦めてくれます。

論文はまるごと入れないこと 論文の原文をすべてインジェストするより、要旨（abstract）くらいで基本の概念だけ分からせ、原文の場所を残しておくのがよいです。重要なキーペーパーだけフルで読ませ、自分のコメンタリーや実験の文脈も一緒に入れると、さらに役立ちます。

活用と哲学 — 読む力とふたつのボルトの運用

ウィキは材料の置き場

LLM ウィキは材料の置き場です。ここから出来上がった料理（成果物） — カリキュラムや講義案など — はメインボルトへ移ります。成果物が大きすぎて配信がつらいときは、別の dev（開発）フォルダで管理します。（HTML や node_modules などの重いファイルはボルトの外で管理 — レンダリングの低下を防ぐため）

いちばん大事な力 — 読む力

AI の時代にいちばん大事な力は読む力です。エージェントにやらせておいて読まないのは簡単ですが、自分が読んでこそ、まともに任せられます。講師は人工知能をセットアップする目的そのものを「自分が読む時間を確保すること」に置いています。ウィキの concept・entity・guide・query のカードは、すべて人にも読みやすく組まれています。

なぜふたつのボルトに分けるのか

著者の明示や .claude のルールが、メインボルト（自分が管理）と LLM ボルト（AI に任せる）で互いに違います。ひとつにまとめるとエラーと汚れた情報が増えるので、分けるほうがましです。既存のボルトの一部をウィキへ移したいなら、スターターキットのボルトでエージェントを立ち上げ、既存のボルトの住所を渡して「ウィキにする価値のあるものを移して」とマイグレーションできます。

締めくくり — AI の知識に直接くっついていよ

リーダーはふた通りに分かれます —「もっと教えて」と、「メンバーにやらせればいい、なぜ自分が学ぶのか」。ところが自分のメンバー（パートナー）の知識の上限が、そのまま自分の上限になります。だから私たちはAI の知識に直接くっついて（attach）いなければならず、そのための自分の知識の置き場が要ります。講師はそのなかで Obsidian をいちばん良い道具に挙げています。

Q&A の要点 · 共同のボルト — 公式の Sync、または osync でセルフホスト（NAS・クラウド・Docker）。同時編集も 1〜2 秒あければおおむね安全。
· PDF のスクラップ — 整合性が大事なら変換、コンテキストだけ要るなら Python でマークダウン化するほうがトークンを節約。
· メタデータのフィールドはその知識を取り出して使う人が決める — どんな分類で取り出すかに合わせてキーと値を設計する。
· ボルトの規模 — メタデータ（type など）でフィルタすれば、1 万ノートでも問題なくインデックス化・アクセスできる。
