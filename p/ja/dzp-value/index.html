付加価値と活用のシナリオ — 開発の組織を越えて

ここまでの編は開発の組織の内側の視点 — 知識がどう作られ管理されるか — を扱った。この編は、そうして積み上がったひとつの Knowledge State が、いくつもの顔で消費されうることを扱う。付加価値の源は文書をもっと書くことではなく、すでに積み上がった保管庫に対象ごとのビューをもうひとつ足すことだ — 一度積み上げれば、社員・パートナー・顧客・AI がそれぞれの範囲で同じ知識を取り出して使う。

API の仕様書の自動の更新 — 最初の派生の製品

いちばんすぐに効く付加価値は、API の仕様書がコードとともに生き続けるようになることだ。手で書く仕様書の持病はよく知られている — 最初に書いたあと更新が後回しになり、コードとずれた仕様が連携する開発者や顧客を誤らせる。このプラットフォームでは API の仕様は別の成果物ではなく、知識のパイプラインの自然な出力になる:

  • 抽出 — Merge された Controller・Mapper・Config の変更から、Endpoint · Parameter · 応答の構造 · Error Code を読み取る。コードから直接に確かめられる事実なので、ほとんどが FACT の等級 — 信頼の水準の体系で自動の掲載の可能性がいちばん高い知識だ。
  • 更新 — API が変われば、同じ Merge のトリガーが仕様の文書を更新する。「仕様書は別、コードは別」という二重の管理が構造的に消える。
  • 検索 — identifiers の拡張のフィールドに API 名や Error Code が載るので、連携する開発者がエラーのコードひとつで、その仕様と方針の文書へすぐ届く。
  • 履歴 — インタフェースの方針が変われば、旧の版の仕様を supersedes で置換としてつなぎ、「いまの仕様」と「なぜ変わったのか」をあわせて保つ。

ひとつの保管庫、対象ごとのビュー

セキュリティの 4 等級はアクセスの統制の仕掛けであると同時に、掲載のチャネルの選別器でもある。同じ保管庫から等級のフィルタだけを変えて、対象ごとの Read-Only のビューを作る — 保管庫を複製したり、文書を書き写したりはしない。

保管庫はひとつ、ビューは対象の数だけ — 等級のフィルタが掲載のチャネルになる。
  • 社員 · 開発の組織 — すべての等級の範囲で Identifier の検索、AI の道具の文脈、オンボーディングの経路。なぜいまかが数字にした損失（週 8 時間の非効率・オンボーディング 3〜9 か月）を直接に減らす基本のビュー。
  • パートナー · 協力会社 — INTERNAL のうち選ばれた連携開発のガイド・API の仕様・カスタマイズの知識。パートナーがぶつかる「担当者に聞かないと分からない」連携の知識がセルフサービスになり、くり返しの問い合わせへの対応の費用が減る。
  • 顧客 — PUBLIC の等級の製品の技術の文書・API のガイド・リリースの影響の案内。顧客向けの文書サイトを別に作ってまた古びさせる二重の管理が消える — コードが変われば顧客の文書も同じパイプラインで更新されるからだ。
  • AI Agent — AI の消費の層の llms.txt とグラフ JSON の契約をそのまま使い、社内のアシスタントと顧客サポートのボットが同じ知識を根拠（出典つき）として答える。人向けのビューと機械向けのビューが、ひとつの保管庫から出てくる — そしてこの機械向けのビューのいちばんの消費者が、下の AI コーディングだ。

AI コーディングの事前の知識 — 好循環が閉じる地点

いちばん戦略的な活用は知識グラフを AI コーディングの事前の知識として使うことだ。いまは開発者が Claude Code のような AI の道具に、毎回ドメインの背景を説明し直している — 「受注の状態はこう遷移して、与信のチェックはあの時点で行って…」（なぜいまかが指した、Context をくり返し説明する費用）。このプラットフォームでは、AI が作業を始める前に知識グラフを先に読む:

  • 入口 — llms.txt で知識の全体の地形をつかみ、knowledge-graph.json の一度の fetch でノード・関係・概念・URL を手に入れる。
  • 選別 — 作業する対象のソースで出会った identifiers（Table・Rule ID・API 名）で関連する方針の文書に届き、型つきの関係をたどって必要なぶんだけ広げる — 先行知識で背景を、supersedes で「いま有効な方針」を、DECISION の等級で設計の決定の理由を。
  • 作業 — ドメインの Rule・状態の遷移・過去の障害・設計の意図をすでに知った状態でコードを読み書きする。CLAUDE.md や MCP との連携で、この手順をプロジェクトの慣行として固定できる。

これが概要の好循環の図の四つ目の箱（「次の開発 — Claude Code · Agent」）の実体だ — 開発の成果が知識になり、その知識が次の開発の AI へ事前の知識として注入され、また開発の成果の品質を上げる。知識が積み上がるほど AI コーディングの正確さが組織の単位で複利のように上がる構造であり、Reference Wiki の巡回の契約がこの消費のしかたをすでに小さく実証している。

非開発の職種まで — 信頼の等級が読者を広げる

開発の知識は開発者だけのものではない。技術支援・CS は障害の事例や Troubleshooting を検索して一次の対応の品質を上げ、営業・PM は製品の機能・方針・用語の知識で顧客との会話の正確さを上げ、新しく入った人は職務にかかわらず組織の知識の地図をオンボーディングの経路として使う。非開発の読者がコードを読めなくても安全なのは、信頼の等級が文書ごとに付くからだ — FACT（コードで確かめられた事実）と INFERRED（推論）・DECISION（決定）が分かれていて、読者が知識の確からしさを取り違えない。

要点 このプラットフォームの付加価値は、部署ごとに文書のチャネルを新しく作ることから来るのではない。一度積み上げた Knowledge State に、等級のフィルタでビューを増やすこと — API の仕様書、パートナーのガイド、顧客の文書ポータル、そして AI コーディングの事前の知識は、すべて同じ保管庫の違う断面だ。積み上げる費用は一度、消費は多角的に。
