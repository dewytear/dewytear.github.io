ノートの構造 — メタデータ・リンク・カード

ウィキのノートを開くとタイトル → メタデータ → 本文の順に並んでいます。たとえば本文が 38 行目から始まるなら、その前の37 行はすべてメタデータです。

YAML フロントマターが肝

Obsidian がマークダウンのエディタとして価値が高いのは、まさにこの YAML フロントマターのメタデータのフィールドです。Claude Code で学んだ段階的な開示（progressive disclosure）と同じ原理で動きます。

エージェントはメタデータ（フロントマター）を先に読み、必要なときだけ本文を開きます。
  • コンテキストウィンドウには制限があり（多くて 100 万トークン）、すべての内容を開いて見ることはできません。
  • だから重要な内容だけを簡潔に（concise）いちばん上（メタデータ）に入れておきます。
  • Claude Code のようなエージェントは、このメタデータを先に読みます。全体に比べれば氷山の一角ですが、この一角だけをざっと見て、何に関する内容かを素早くつかみます。

タイトル・説明をうまく書く（英語で）

スキルの description と同じく、ノートのタイトルと説明（description）のフィールドをうまく書くことが大切です。私たちは日本語話者ですが、人工知能は英語のほうが速く・うまく読むので、メタデータは英語で書くほうが有利です。

コンテキストの最適化 Obsidian の大きな長所は、ひとつのファイルにすべてを詰め込まず、「好みは 好み.md を見よ」「専門のペルソナはここを見よ」のように別ファイルの住所を書けることです。仕事のときに必要なファイルだけ開かせてコンテキストを最適化します。講師は Karpathy のアイデアを借りて、こうしたメタデータの作成を自動化するコマンド・スキルのセットを用意しています。

つながり（Links）とボルト間の参照

Obsidian のいちばんの長所はノートどうしのつながりです。たとえば「BM25」のノートに、MOC（Map of Content、知識の地図）、ハーネスエンジニアリング、ログなど、さまざまなノートがつながっています。このつながりが核心です。

住所ひとつでつながった知識をまとめて読む

「BM25」のノートの住所だけを人工知能に渡せば、それとつながった残りのノートもソーセージのように連なって読まれます。ただしこの自動のつながりは同じボルトの中でだけ可能です。

ノートどうしがリンクでつながった小さな知識グラフ — 青い線（accent）はボルトを越えるつながりです。

ボルト間のつながり — マークダウンリンク

ボルトの内部で使うウィキリンク（[[...]]）はボルトの外のノートを指せないので、外部のボルトへのつながりはマークダウンリンクの方式（[テキスト](住所)）にする必要があります。講師はこのボルト間のリンクも自動で書かれるように、システムファイルに設定してあります。

  • オンボーディングのときに「あなたのメインボルトは何ですか？」と尋ねられます。
  • メインボルトの住所を渡すと、その URI の値をパースして、その住所へのつながりも一緒に作ってくれます。
例 — モバイルコマンドセンター 車に Starlink とバッテリーのシステムを入れる「モバイルコマンドセンター」のウィキカードを作ったとき、人工知能はウィキボルトの中の関連する概念（Related）だけでなく、メインボルトに整理してあった関連記事も見つけてつなぎました（メインボルト Related）。こうして自分の知識システム全体をつなぎ、Obsidian のボルトが生まれつき持つ限界（ボルト内のつながりしかできない）を越えます。

ウィキカードの種類と生ソース

研究者は知識の出典を明示しなければなりません。だから raw の資料を生ソース（raw source）として入れ、どこから知識を持ってきたかを示します。（Zotero や Bookends のようなリファレンスマネージャーをつないだインデックス化・引用の自動化も予定されています。）

生ソース → ウィキカード

記事・報道・論文・YouTube の書き起こしなどをボルトに入れると、LLM が読んで抽出しウィキカードにします。ひとつの記事から学べることが五つあれば五枚のカードができますし、複数のソース（記事 3 本 + YouTube 2 本）をいっぺんにインジェストして AI に勝手にコンパイルさせることもできます。

生ソースを LLM が読んで出典ベースのウィキカードへ — 概念・実体・ガイド・マップに分かれます。

カードの種類

種類内容
Concept基本の概念カード。
Entity固有名詞・サービス名・人の名前など。
GuideConcept・Entity を含むフレーズ —「これで何をする」といったやり方。
Maps / Labs全体を網羅する概念カード。
キャプチャのコツ — 目的を残す 知識をキャプチャするときは、つねに #（シャープ）のうしろに目的を書きます。あとで検索するためです。キャプチャしたきり二度と見ないことになりがちなので、未来の自分が検索でたどり着けるヒントを残しておくとよいです。インジェストを任せるときも「なぜ集めたのか / 何をしたいのか」を尋ねるようにしておけば、その意図を持ってメインボルトの過去の研究とつなげて推論してくれます。

システムファイルと rules

ボルトにはノートだけでなく、AI の動きを定めるシステムファイルも一緒に入ります。講師が念入りに削り出したこれらのファイルは、いちど通読してみる価値があります。

著者とモデルの明示

  • メインボルトの主な著者は人（自分）です。
  • LLM ウィキには自分の名前とともに、どのモデルが書いたのかも明示します。例:「Opus 4.8 · effort X-high」「Fable」「Codex Fugu · Ultra」など。
  • どのモデルが作ったウィキかを記録して品質を比較・最適化します。インジェストはトークンと時間を多く使うので、本当に重要な資料だけを集めるのがよいです。

メインボルトのシステムファイル

Claude が読む文書、ほかのエージェントが読む文書、CMDS（コンテキスト）に関する内容、ボルトのルール、執筆・フォーマットのルール、研究の主題、ペルソナ（brain dump）などが入ります。

LLM ウィキの core-context

LLM ウィキはどんな目的でウィキを使おうとしているのかを収めるコンテキストのファイルを使います。オンボーディングを始めると core-context.md を直しながら、名前・所属・部署・趣味・好みなどを埋めます。ここでもすべてを 1 ファイルに書かず、「好みは 好み.md、専門のペルソナはここ」のように住所を明示してコンテキストを最適化します。

.claude/rules — 憲法のように読まれるルール .claude フォルダの中の rules フォルダのマークダウンファイルは、Claude Code がセッション開始のすぐに先に読みます（憲法のように厳密に守る）。一方 CLAUDE.md はガイドとして参考にします。だから編集のルール・好み・重要な強制のルールは rules に入れておくとよいです。

構造が分かったら、自分で回してみる番です — 実習と哲学の章で、オンボーディングから Ingest・Query・Lint、ウェブクリッパー、そして二つのボルトを運用する哲学まで進みます。
