実行モード

OMC は作業の性格に合わせていくつもの実行モードを用意しています。各モードは「どう仕事を進めるか」を決めるやり方だと考えてください。モードは、軽い単発の作業から大きく自律的な作業までの強さのスペクトラムとして理解すると分かりやすくなります。

強さのスペクトラム（弱い → 強い）: 会話（単発の問い）→ plan（計画の策定）→ autopilot（自律実行）→ ralph（完了までくり返し）→ team ralph（チーム + くり返し）

左は軽い単発の作業、右へ行くほど自律的で強い実行モードです。

中心となる 4 モード — 詳しく見る

実務でいちばんよく使うことになる四つのモードです。どんな原理で動くのか、いつ使っていつ使ってはいけないのかを、公式のスキル定義にもとづいて解きました。下のモード名のボタンか、前へ・次へ のボタンでページを切り替えて見てください。

Autopilot — /oh-my-claudecode:autopilot <task>

2〜3 行のアイデアを渡すだけで、要件の分析 → 設計 → 並列の実装 → QA → 多角的な検証まで全工程を自律で終わらせる自律実行モードです。成果物は「動いて、検証されたコード」です。（なお、現行の公式 README は team を代表のモードとして掲げています — Team のページを参照。）

どう動くのか — 五つの段階（Phase 0〜4）を順に進み、前の段階が終わってから次の段階が始まります。拡張の段階で短い依頼を詳しい仕様（.omc/autopilot/spec.md）へ広げ、計画を critic が検証したあと、実行の段階では内部的に ralph + ultrawork を使って難易度別の executor が並列で実装します。

  • 向いている — 要件がある程度は明確で、計画・コーディング・テスト・検証といった複数の段階が必要な機能を、最初から最後まで任せたいとき。
  • 向いていない — 選択肢の探索やブレインストーミング（→ plan）、素早い単発の修正（→ 普通の会話）、要件があいまいな場合（→ deep-interview を先に）。入力があまりにあいまいだと、autopilot 自身が deep-interview を先に勧めることもあります。
  • 中断・再開 — /oh-my-claudecode:cancel でいつでも中断でき、進行の状況が保存されるので続きから再開できます。
# スラッシュコマンドでも、自然言語のキーワード("autopilot:"、「オートパイロット」)でも可能
/oh-my-claudecode:autopilot 注文キャンセル API の追加 (キャンセル理由の保存、在庫の戻しを含む)

Ralph — /oh-my-claudecode:ralph <task>

「終わりました」という嘘の報告を防ぐ、完了を保証するモードです。作業をユーザーストーリーの単位に構造化し、すべてのストーリーが通過してレビュアーの検証まで終わるまで、止まらずくり返します。

どう動くのか — 始めるときに作業を prd.json（ストーリーごとの完了条件の一覧）として自動で構造化し、ストーリーをひとつずつ通過（passes: true）するまでくり返します。くり返しのなかで分かったことは progress.txt に積み上がって次の反復で活かされ、完了を宣言する前にはレビュアー（既定は architect）が完了条件と照らした検証を必ず行います。セッションが勝手に終わらないよう persistent-mode の Hook が Stop イベントを遮り、内部の実行には ultrawork の並列エンジンを使います。

  • --critic=architect|critic|codex — 完了の検証を担うレビュアーを差し替えられます（既定は architect）。
  • 向いている — マイグレーションやレビュー指摘の一括修正のように「部分的な完了が許されない」作業。
  • 注意 — 検証に落ちると再試行がくり返され、そのぶんトークンのコストが増えます。完了条件を具体的に書くほど反復は減ります。
# マジックキーワード "don't stop"、"until done"、韓国語の「랄프」でも発動
/oh-my-claudecode:ralph コードレビューで出た指摘 12 件をすべて修正 (ビルド・テストの通過まで)

Ultrawork — /oh-my-claudecode:ultrawork <task> · ulw

互いに独立した作業を、複数のエージェントへ同時に配る並列実行のエンジンです。速さが最優先のときに使います。

どう動くのか — 作業の意図をまずつかみ、関連するコンテキストを並列で集めたあと、依存関係を見て同時に回せる作業のまとまり（並列ウェーブ）を組みます。独立した作業は絶対に順番待ちをさせず同時に発射し、それぞれの作業の難しさに合ったモデルのティアが自動で割り当てられます。30 秒以上かかるビルドやテストはバックグラウンドで回します。

  • ultrawork は継続性と検証のループを持たない「部品」です。完了したかどうかの管理は利用者の役目なので、完了の保証が必要なら ralph（ultrawork を内蔵）を使ってください。
  • 向いている — 互いに依存のない多数のファイルの一括変換・修正（例: 15 ファイルすべてを変換）。
  • 注意 — 同時に何人もの作業者が動くぶん、同じ時間に使うトークンがいちばん多くなります。
# 短いキーワード ulw / uw /「ウルトラワーク」
ulw: src/legacy フォルダの独立したユーティリティクラス 12 個すべてに単体テストを追加

Team — /oh-my-claudecode:team <N>:<agent> <task>

N 体のエージェントに役割を与え、段階型のパイプラインで協業させるモードです。ralph と組み合わせた team ralph が OMC でいちばん強い実行の強さです。現行の公式 README は team を OMC の代表（canonical）モードとして掲げています（リポジトリの説明も「Teams-first Multi-agent orchestration」）。

どう動くのか — チームの計画（team-plan）→ 要件の文書化（team-prd）→ 分担しての実行（team-exec）→ 検証（team-verify）→ 修正のループ（team-fix）という段階型のパイプラインで進みます。たとえば /team 3:executor "TypeScript のエラーをすべて修正" は executor 3 体が作業を分けて担当します。

  • 前提 — ~/.claude/settings.json に CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 の環境変数の設定が必要です。オフだと警告のうえ、可能な範囲で非チームの実行にフォールバックします。
  • 区別 — セッション内の /team（ネイティブのチームのワークフロー）と、ターミナルの omc team（tmux の窓に claude・codex・gemini の実際の CLI ワーカーを立てる）は別のランタイムです。
  • 注意 — いちばん強いモードなので、トークンのコストもいちばん大きくなります。作業の分解と役割の分担が本当に必要な大きい作業にだけ使ってください。
# 役割(agent)には executor、architect などエージェント名を指定
/oh-my-claudecode:team 3:executor ビルドを壊している TypeScript のエラーをすべて修正

三つのモードの包含関係 — autopilot ⊃ ralph ⊃ ultrawork ultrawork は並列の実行だけを担う部品で、ralph はその上に継続実行・ストーリーの追跡・完了の検証を載せたもの、autopilot はさらにその上に要件の分析・設計・QA・多角的な検証というパイプライン全体を載せたものです。だから「並列だけ要るなら ulw、完了の保証が要るなら ralph、最初から最後まで任せるなら autopilot」と選べば大丈夫です。
autopilot ⊃ ralph ⊃ ultrawork — 外側ほど多くの段階を包みます。

autopilot の 5 段階の進み方（詳細）

autopilot は依頼を受けると、次の五つの段階を自動でたどります。各段階は前の段階が終わってから始まり、実行と検証の段階の中では並列の処理が起きます。

  1. 拡張 — アナリストとアーキテクトが短い依頼を詳しい仕様（spec.md）へ広げます。あいまいなら deep-interview を先に勧めます。
  2. 計画 — アーキテクトが実装の計画を立て、critic が抜けと危険を検証します。
  3. 実行 — ralph + ultrawork で、難易度別の executor たちが並列で実装します。
  4. QA — ビルド・リント・テストを最大 5 回くり返します。同じエラーが 3 回くり返されたら根本的な問題と見て中断・報告します。
  5. 検証 — architect・security-reviewer・code-reviewer の 3 名全員の承認が必要で、差し戻された項目は修正してから再検証します。

補助のモード

中心となる 4 モードを補うモードです。計画の段階、要件の整理、原因の分析のように、実行の前後を支えます。

モード目的使用例おすすめの場面
Plan実行の前に計画を立てて利用者の承認を得る/oh-my-claudecode:plan <作業>実装の前に段階と範囲を確定したいとき（omc-plan は互換用のエイリアス）
Ralplan合意にもとづく計画の策定 — plan --consensus のエイリアスで、planner・architect・critic が合意するまで計画を磨く/oh-my-claudecode:ralplan <description>アーキテクチャ・DB・セキュリティなど、リスクの高い設計の検討（--deliberate で高リスクの審議モード）
Deep Interviewソクラテス式の問いであいまいな要件を明確にする/deep-interview <idea>要件が抽象的だったり範囲がはっきりしないとき — 出てきた仕様は autopilot が引き継いで使う
UltraQAビルド・リント・テストが通るまで診断と修正のサイクルをくり返す/oh-my-claudecode:ultraqa <goal>実装は終わっていて、品質のゲートだけをくり返し回したいとき
Trace複数の tracer が並列で仮説を立て、証拠にもとづいて原因を追跡する/oh-my-claudecode:trace障害・バグ・性能低下の原因の分析
CCGClaude・Codex・Gemini の三つのモデルの結果をまとめる/oh-my-claudecode:ccg <task>複数のモデルの視点が必要なレビュー・分析
実務での選び方 バグ 1 件や単一ファイルの修正なら普通の会話で十分です。複数のファイルを変える必要があるなら autopilot、独立した作業が多いなら ultrawork、完了の保証が大事なら ralph、要件そのものがあいまいなら deep-interview を先に使う、というのが現実的です。実装は終わっていて品質のゲートだけ回すなら ultraqa、役割の分担が必要な大きい作業なら team まで上げつつ、強さが上がるほどコストも一緒に大きくなることを覚えておいてください。
韓国語キーワードへの対応 最新のバージョンは韓国語のマジックキーワードも認識します。プロンプトに「랄프」「오토파일럿」「울트라워크」「코드 리뷰」「보안 리뷰」「딥 분석」のような韓国語の表現を使うと、英語のキーワードと同じモードが自動でオンになります。ただし韓国語のエイリアスは部分文字列として一致するので、意図せずモードがオンになることがあり、キャンセルのキーワード（stopomc / cancelomc）は英語でのみ動きます。
