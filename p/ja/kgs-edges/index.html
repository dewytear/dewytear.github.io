文書はどうつながるのか — 概念キュレーションと idf 重みつきエッジ

知識グラフの品質は、結局「ふたつの文書が関連している」を何で判定するかにかかっています。このウィキは埋め込みや統計抽出のようなブラックボックスの代わりに、人が読んで残した概念（concepts）を材料に検証できるルールでエッジを計算します。この文書では、そのルールを実際の数値と実際のエッジで最後まで解剖します。

材料 — 概念は抽出ではなくキュレーション

すべての文書は登録されるときに中心概念 5〜6 個をキュレーションされます（前編のパイプライン ③）。ここにひとつの原則があります: 概念は本文に実在するものだけを書く。つながりを作りたいからといって本文にない概念を入れると、グラフが「実際の知識の地図」であることをやめてしまうからです。だからこのグラフのエッジは数が少ない代わりに、ひとつひとつが根拠（共有した概念）を示せます。

はかり — まれな概念ほど強いつながり

ふたつの文書が概念を共有すると、つながりの候補になります。ところが、すべての概念が同じ重さであるはずはありません。66 編のうち 12 編に出てくる「スキル」を共有するのは偶然に近いですが、たった 3 編にしか出てこない「ベクトル検索」を共有するのは強い信号です。そこで概念ごとに希少性の重み（idf） — ざっくり「全文書数 ÷ その概念が出てくる文書数」の対数 — を与えます:

希少性のはかり — よくある概念の共有は軽く、まれな概念の共有は重く数えます。

実際のエッジを解剖する — Welcome ↔「Claude Code とは何か」

実際のグラフのエッジをひとつ開けてみると: はじめにと Tutorial 基礎の章は「ターミナル」（重み 3.51）・「CLAUDE.md」（2.01）・「Claude Code」（1.90）の三つの概念を共有しています。スコアは重みの合計 ≈ 7.42 — 同じ文書の第 1 位は概念 4 個を共有する Tip 初級編（≈ 9.68）なので、共有概念が多くまれであるほど上に来るわけです。文書下部の「関連文書」でこの根拠概念がそのままチップとして表示されるので、なぜつながったのかをいつでも確認できます。

判定ルール — System の中は密に、あいだは疎に

判定フロー — 2026年9月24日の精度の測定でエッジを判定した結果から生まれた規則です。「まれ」の基準(3編以下)は以前の規則のものをそのまま使います。
  • 同じ System の中 → 共有が2個以上ならつなぎ、1個だけでもその概念が3編以下にしか出なければつなぎます。実例:スキルとは ↔ スキルのインストールは「サンドボックス」一つだけを共有しますが、2編にしか出ないまれな概念なので認められます。連載の中の文書はたいてい同じ主題を続けるので、敷居を低く置きます。
  • System をまたぐとき → 共有が3個以上か、2個のうち一つがまれ(3編以下)な場合だけつなぎます。概念一つでは、どれほどまれでもまたぎません。実例:Tutorial の基礎編 ↔ CLAUDE.md の十戒は「CLAUDE.md」(11編)と「作業指針」(2編)を共有し、まれな方が錨になってつながります。逆にはじめに ↔ OMC の紹介は「インストール」「スラッシュコマンド」を共有しますが、どちらもありふれているのでつながらず、提案の概要 ↔ セルフホスティング公開ベータは「GitLab」一つで World までまたいでいたエッジなので切れました。
  • それ以外 → 概念ではつなぎません。概念のつながりが2個に満たない文書は同じ System の隣(例:基礎編 → 同じ Tutorial の前後の章)で補完します。ただし日付記事のフォルダは補完しません — 日付順に積まれたニュースは読む順序ではなく、隣にあることが関係があることを意味しないからです。そのため一部の文書はつながりが0〜1個のまま残ります — 日付記事と、フォルダに一つだけで補完する隣のない文書(送信エンジンの依頼・個別のスキル紹介の二編)です。無理に隣をつけなかった誠実な結果です。現在の比率は概念のつながり183個(88%)・フォルダ補完25個(12%)です。

以前の規則は System を問わず「異なる概念が二つ重なるのは偶然とは考えにくい」と見ていました。測ってみるとそうではありませんでした。エッジを一本ずつ判定すると、無駄足34本のうち20本が「インストール」「プラグイン」のようなありふれた概念二つで、10本が「メタデータ」「クエリ」のような意味の違う同じ語一つで System をまたいだエッジでした。同じ System の中では、ありふれた概念二つの共有もたいてい本当の関係なので規則をそのまま残し、境界をまたぐエッジにだけより多くの証拠を求めるように変えました。このウィキが World のあいだに望む構造 — 中は密に、あいだは疎に — を System の単位にも当てはめたものです。

境界値の波及 — なぜ概念を安易に増やせないのか

「3 編以下」ルールには微妙な波及があります。あるまれな概念がいま 3 編に出ているとして、新しい文書がその概念をもうひとつ使うと、4 編になった瞬間にその概念ひとつでつながっていた既存のエッジが資格を失って切れます。だからこのウィキのルール集（CLAUDE.md）は「孤立をなくすために本文にない概念を追加すること」を禁じています — 無理につないだひとつが、隣の文書の本物のつながりを切りかねないからです。つながりの薄い文書は欠陥ではなく検討の合図としてだけ扱います。これがこのグラフの正直さの原則です: エッジはつねに実際の本文に根拠を持ち、キュレーションはグラフをよく見せるための道具ではありません。

キュレーションでつなぐ関係 — 向きのある型付きエッジ

ここまでのエッジ（related）は機械が共有概念から自動計算した対称の関係です — A と B がつながっても、向きも種類もなく「互いに関連がある」だけです。ところが知識には向きと種類のある関係もあります: 「これを読むにはあれが先」「この概念をあの文書が実装する」「この記事があの主張の根拠だ」。こうした関係は概念の共有だけでは捉えられないので、このウィキは related とは別のコレクションとして、作業者がキュレーションで宣言する型付き関係（relations）を別に付けます。

向きのある型付きエッジ — キュレーションで「この文書を読むにはあの文書が先」と宣言します（逆方向は自動で導かれます）。

語彙は五つです — 先行知識（prerequisite）・実装（implements）・事例（example-of）・根拠（evidence-for）・置き換え（supersedes）。各関係は向き（A→対象）と一行の根拠（どこで成り立つのか）を一緒に付けます。保存は順方向の一度きりで、逆方向（「この文書に入ってくる関係」）は全文書を走査して自動的に導きます。文書下部の「知識の関係」ブロックで、出ていく関係と入ってくる関係を型バッジとともに見られます。

宣言はこんな形をしています — 実際のデータから 1 件をそのまま持ってくると（記事が知識文書の根拠になる関係）:

{ "target": "sb-level4",              // この関係が向かう文書
  "type": "evidence-for",             // 関係の種類: 根拠
  "evidenceRef": "Neo4j ジム・ウェバー原文（2024-06-04）のまとめ —
                  sb-level4 の知識グラフ的アプローチへの専門家の根拠",
  "source": "human" }                 // キュレーションの出所（人の承認 — 自動提案ではない）

現在ウィキに宣言された関係は 110 件で、すべてこの形式です。ほとんどは講義型の System と AI 2040 ニュースシリーズの読む順序の prerequisite チェーン（前の文書 → 次の文書）で、残りは System を横切る implements・example-of・evidence-for・交差 prerequisite です。型ごとの実例:

  • 先行知識（prerequisite） — このシリーズ自体がチェーンです: 積み上がるのか → この文書 → 7 つの眼 → AI が読む方法 → プラグイン化。各編が次の編の先行知識として宣言されているので、「何を先に読むべきか」をグラフが知っています。はじめに → 拡張機能も同じ型。
  • 実装（implements） — ウィキエンジンのプラグイン化が、このシリーズの説明したエンジンを実装します。ハーネスの概念文書 → プラグインアーキテクチャ文書も同じ系譜。World を横切る橋もあります — Douzone ナレッジプラットフォーム提案が「Reference Wiki（このウィキ）」を複製してこの登録パイプラインを実装すると宣言しています。
  • 事例（example-of） — LLM Wiki はセカンドブレイン レベル 2（主題でまとめる）が言う段階の実例です。最初のハーネス実行もハーネス実行講義の具体事例として付きます。
  • 根拠（evidence-for） — 上の JSON のように、外部の原文を確認した記事がSecond Brain 4 段階の主張の外部根拠として付きます。タリクの Fable フィールドガイドのまとめもハーネスエンジニアリングの「モデルより環境が結果を左右する」という主張を支えます — 記事 4 編がこの型で知識文書を支えています。

ここに三つ目のつながりの層がもうひとつあります — 引用バックリンク（citedBy）。文書本文から他の文書へ張った #! 内部リンクを、インデックスのビルドが逆方向に集めて、引用された文書の下部に「この文書を引用した文書」として自動表示します。概念の共有（related）でも宣言（relations）でもなく、書きながら実際に参照した痕跡から生まれるつながりなので、正直さのルールと自然に整合し — よく引用される文書がハブであることがおのずと見えてきます。引用元は知識インデックスに入った文書だけを数えるので、Work Log のようなジャーナルのリンクは混ざりません。

三つのレイヤーは性格が違います。related は機械・対称・概念ベースなので広く敷かれ、citedBy は機械・向きあり・本文リンクベース、relations はキュレーション・向きあり・型つきなので少ないけれど意味が濃いです。そして同じ正直さの原則に従います — 本文に実在する関係だけを付けます。実際、「旧版を残したまま新版が置き換える」置き換え（supersedes）の事例が今のウィキにはないので（文書をその場で直すため）、語彙・検証・UI は備えつつ、その型は空のままにしています — 関係を埋めるために無理な組を作りません。宣言された関係は検証機が守ります: 存在しない対象（relations-dangling-ref）と 5 語彙の外の型（relations-unknown-type）は ERROR でマージが止まり、根拠の欠落や食い違う宣言は WARN として検討の合図になります。

ひと目でまとめ 概念はキュレーション（本文実在のみ）→ エッジは希少性で重みづけした共有（System の中は 2 個↑ またはまれな 1 個、あいだは 3 個↑ かまれな錨を含む 2 個）→ 足りなければフォルダ補完(日付記事は除く) → ほとんどの文書が 2〜4 つながり、概念の届く隣がない文書は 0〜1 個のまま。その上に、本文 #! リンクの逆インデックスである引用バックリンク（citedBy）と、キュレーションで宣言する向きのある型付き関係（relations）を別に重ねます。よく参照される文書がハブとなってグラフの中心をつくります（次の編）。
