위키는 어떻게 스스로를 지키는가 — 게이트와 자동화 체계

앞의 다섯 편은 지식이 쌓이고, 이어지고, 읽히고, AI에게 소비되고, 플러그인으로 패키징되는 구조를 설명했습니다. 마지막 질문이 남습니다 — 이 구조가 어긋나지 않는다는 것을 누가 보장하는가? 문서를 추가하고 인덱스 재생성을 잊으면? 도구를 고치고 플러그인 사본을 잊으면? 이 편은 그 보장을 담당하는 게이트(gate)와 자동화 체계를 실제 사고 사례와 함께 설명합니다.

원칙 — 판단 없는 노동은 기계가, 판단은 사람이

이 위키의 자동화는 생성이 아니라 검증 중심입니다. 요약·개념·관계·본문은 사람(또는 AI 작업자)이 문서를 읽고 큐레이션합니다 — 여기엔 판단이 필요하고, 판단을 기계에 넘기면 그래프의 정직성이 무너지기 때문입니다. 대신 기계는 두 가지를 맡습니다: ① 큐레이션의 결과가 서로 어긋나지 않았는지 판정하고(게이트), ② 판단이 필요 없는 복원 노동을 대신합니다(--fix). 규칙을 프로즈로만 적어 두면 잊힙니다 — 실제로 잊혀서 사고가 났고, 그때마다 규칙이 게이트로 기계화됐습니다.

항상 같은 결과 — 결정적 빌드와 드리프트 게이트

지식 인덱스·그래프 JSON·llms.txt·sitemap·문서 일자 — 사이트가 읽는 산출물은 전부 도구가 생성하며, 손으로 편집하지 않습니다. 빌드는 결정적(같은 입력 → 언제나 같은 출력)이라, CI의 --check 모드가 "지금 저장소의 산출물"과 "소스에서 갓 만든 산출물"을 바이트로 비교할 수 있습니다. 어긋나면(= 문서를 고치고 재생성을 잊으면) 머지가 막힙니다. 그래서 AI가 읽는 그래프 파일이 실제 지식과 다른 순간이 구조적으로 존재하지 않습니다.

PR을 지키는 동반 게이트 — "A를 바꿨으면 B도 함께"

어떤 규칙은 산출물 비교로는 못 잡습니다. "자산을 고쳤으면 캐시버스터도 올려라" 같은 동반 규칙은, PR의 변경 목록(diff)을 보고 짝이 함께 왔는지를 검사해야 합니다. 이런 게이트가 여섯 있고, 전부 실제 사고나 운영 필요에서 태어났습니다:

게이트지키는 규칙태어난 계기
check_worklog실질 변경이 있는 PR엔 Work Log 동반 (기존 로그 갱신도 인정)"작아도 기록" 규칙이 프로즈로만 있어 잊히던 문제
check_cachebuster?v 자산(app.js 등)을 고치면 같은 PR에서 ?v 상향2026-07-09 실사고 — 고쳤는데 재방문 브라우저에 "반영 안 됨"
check_plugin_sync플러그인 동봉 도구는 루트 tools/와 바이트 일치 + 번들 변경 시 버전 상향2026-07-10 실사고 — 검증기 190줄이 낡은 채 배포됨
check_translation새 문서를 올리면 강제 언어의 본문·라벨·인덱스 오버레이 동반 (현재 en·ja)"신규 문서는 번역 동반" 규칙이 프로즈로만 있어 새던 문제 — 워크로그 게이트와 같은 뼈대로 옮겼습니다
i18n-render비한국어 언어의 주요 화면을 실제로 렌더해 한국어가 새는지 검사2026-07-28 실사고 — 파일 대조 게이트가 전부 초록인데 일본어 화면에 한국어가 나왔습니다
diagram-bounds도식 글자가 박스·viewBox를 1px도 넘지 않게 헤드리스 브라우저로 실렌더 검사폰트 폭 추정만으로는 경계값 삐짐을 놓치던 문제

모든 동반 게이트가 차단인 것은 아닙니다. check_relations_review는 새로 등재된 문서를 골라 그 지식 관계 타입 분포와 5타입(선행지식·구현·사례·근거·대체) 체크리스트를 띄우는 비차단 리뷰 신호입니다 — 관계는 본문에 실재할 때만 정직하게 다는 것이라(억지 링크 금지) 기계가 "관계를 넣어라"고 강제할 수 없기 때문입니다. 그래서 이것은 머지를 막지 않고, 관계를 선행지식으로만 채우지 말라는 규칙을 사람/AI가 한 번 보게 하는 신호로만 작동합니다(위 지식 그래프 WARN과 같은 "사람이 한번 볼 목록" 철학).

모든 PR은 네 층의 게이트를 지나야 합니다 — 하나라도 ERROR면 머지 불가.

스스로 고치는 게이트 — --fix

게이트가 "어긋났다"고 판정한 뒤의 복원은 대부분 판단이 필요 없는 노동입니다: 번들 사본은 루트에서 복사하면 되고, 캐시버스터는 숫자를 +1하면 됩니다. 그래서 두 게이트에 --fix 모드가 있습니다 — check_plugin_sync --fix는 어긋난 스냅샷을 자동 복원하고, check_cachebuster --fix는 낡은 ?v를 자동 상향합니다. 경계는 명확합니다: 복원은 기계, 판단은 사람. 플러그인 버전을 얼마나 올릴지(내용 갱신=minor, 버그픽스=patch), 기능 변경이 해설 문서를 낡게 했는지는 --fix가 건드리지 않습니다.

변경 유형 선언 — 게이트가 못 잡는 것을 위한 규율

기계 게이트에는 한계가 있습니다. 관계 타입 기능을 넣은 PR은 모든 게이트를 통과했지만, 정작 이 시리즈의 문서들이 새 기능을 설명하지 않는 서술 갭은 별도 검토에서야 발견됐습니다 — "설명이 낡았는가"는 오탐 없이 기계가 판정할 수 없기 때문입니다. 그래서 마지막 장치는 게이트가 아니라 선언 규율입니다. 작업을 시작할 때 변경 유형을 선언하고, 유형별 영향표를 훑습니다:

  • ENGINE 뷰어 동작 — 자기기술 문서 검토 · ?v 상향  /  STYLE 디자인·도식 — 디자인 규칙 · ?v 상향
  • TOOL 빌드·검증 도구 — 번들 동기 + 버전  /  SCHEMA 산출물 계약 — schema.md 동반 · 하위호환 판단 · 해설 문서 검토
  • PLUGIN 스킬·메타 — 버전 상향  /  CONTENT 본문·목록 — 등재 5단계 · 플러그인 반영 금지

선언은 플랜·PR 본문에 한 줄이면 됩니다(예: "변경 유형: TOOL + PLUGIN"). 복수 선언이 정상입니다 — 관계 타입 기능은 다섯 유형을 관통했고, 시작 때 선언했다면 SCHEMA 행의 "해설 문서 검토"가 구현 PR 안에서 걸렸을 것입니다. 이것은 게이트(강제)가 아니라 판단 보조입니다 — 판단이 필요한 영역을 기계화하는 대신, 판단할 시점을 앞으로 당깁니다.

한눈 요약 산출물은 결정적 빌드로만 생성(직접 편집 금지) → --check가 드리프트를 차단 → 동반 게이트 6종이 "짝이 함께 왔는지" 검사 → ERROR 0가 머지 조건. 복원 노동은 --fix가 대신하고, 기계가 판정 못 하는 서술·버전 판단은 변경 유형 선언으로 사람이 시작 시점에 챙깁니다. 게이트는 전부 실제 사고의 재발 방지로 태어났습니다.
