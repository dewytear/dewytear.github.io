고급 — 병렬·자율·예약의 8가지

마지막 편은 Claude Code를 여러 개, 오래, 손을 떼고 굴리는 이야기예요. 세션끼리 파일을 두고 충돌하지 않게 하는 워크트리부터 예약 작업, 폰 원격 조종, 그리고 서로 대화하는 에이전트 팀까지 — 시리즈의 팁 21~28번을 공식 문서와 대조해 정리했습니다.

문서 정보 (출처) · 근거: Claude Code 공식 문서 (2026-08-14 기준) — 실험 기능은 버전에 따라 달라질 수 있습니다

21. 워크트리로 세션을 병렬로 돌린다

같은 프로젝트에서 세션 두 개가 동시에 파일을 고치면 — 하나는 로그인 기능, 하나는 그래픽 로직 — 같은 파일을 건드리는 순간 충돌이 나요. 워크트리(worktree)는 git이 제공하는 독립된 작업 사본입니다. 저장소 이력은 공유하되 파일은 따로 가지니까, 세션마다 자기 워크트리에서 일하면 애초에 겹칠 수가 없어요. 끝나면 git 머지로 합치면 됩니다.

git worktree 명령을 손으로 쳐도 되지만, 지금은 Claude Code가 수명 관리까지 해 줘요 — claude --worktree(-w)로 시작하면 생성·이름·정리가 자동이고, 데스크톱 앱은 새 세션마다 알아서 워크트리를 만듭니다. .env처럼 git이 추적하지 않는 파일은 사본에 없으니, 자동 복사가 필요하면 프로젝트 루트에 .worktreeinclude 파일을 두세요.

# 터미널 1 — 로그인 기능 (독립 워크트리에서)
claude --worktree login-feature

# 터미널 2 — 그래픽 로직 (또 다른 워크트리에서, 동시에)
claude -w motion-logic

# 각자 끝나면 브랜치를 머지 — 충돌 걱정 없이
사본이 물리적으로 나뉘어 있으니 충돌 자체가 일어나지 않는다 — 합치는 시점만 관리하면 된다.

22. MCP 서버 대신 API를 직접 부른다

MCP(Model Context Protocol)는 외부 도구를 붙이는 표준인데, 서버를 연결하면 그 서버의 도구 정의 전체가 컨텍스트에 실리는 비용이 있어요. 필요한 기능이 한둘뿐이라면 해당 API 엔드포인트를 직접 호출하게 하는 편이 토큰·컨텍스트 모두 쌉니다. 도구 전부를 쓸 거면 MCP, 한두 개만 쓸 거면 직접 호출 — 이 구분만 기억하세요. 참고로 지금은 도구 검색(Tool Search)이 기본 제공돼서 필요한 도구 정의만 그때그때 불러오는 식으로 이 비용이 크게 줄었는데, "쓰는 만큼만 싣는다"는 원칙 자체는 그대로 유효합니다.

공식 문서: Connect Claude Code to tools via MCP — 이 위키의 확장 편의 MCP 절도 참고. MCP 스펙 자체의 큰 개정은 묻지 않는 기본값에서 다뤘어요.

23. /loop로 예약 작업을 걸고, 세션 밖은 루틴에 맡긴다

/loop 5분마다 배포 상태를 확인해 줘처럼 반복 작업을 걸어 두면 세션이 살아 있는 동안 Claude가 주기적으로 알아서 확인해요. 배포 감시, 정기 점검, "8시에 슬랙 확인" 같은 시간 지정도 됩니다. 사람이 지켜보지 않아도 되는 감시성 업무를 통째로 넘길 수 있어서 활용 폭이 넓어요.

다만 /loop는 세션이 열려 있는 동안만 돕니다. 세션·컴퓨터와 무관하게 돌아야 하는 일은 루틴(Routine)이 맡아요 — 프롬프트·저장소·커넥터를 묶어 저장해 두면 Anthropic 클라우드에서 스케줄(최소 1시간 간격, cron 표현식 지원)이나 API 호출·GitHub 이벤트로 실행됩니다. 노트북이 꺼져 있어도 돌아요. 정리하면 셋입니다 — 지금 이 세션 안의 반복은 /loop, 내 컴퓨터에 걸어 두는 예약은 데스크톱 예약 작업, 컴퓨터 없이도 돌아야 하면 루틴. 이 위키의 아침 브리핑도 루틴으로 돕니다.

공식 문서: Run prompts on a schedule

24. 폰에서 원격으로 조종한다

터미널에서 claude remote-control을 실행하면 링크가 하나 나와요. 그 링크를 폰에서 열면 — 코드는 여러분의 로컬 머신에서 그대로 돌고 — 조작만 폰에서 하게 됩니다. 지하철에서 진행 상황 확인하고 다음 지시 내리는 거죠. 조건은 하나, 로컬 머신이 켜져 있어야 합니다 — 조종하는 상대가 그 머신이니까요. 긴 작업이 끝나거나 승인이 필요할 때 폰으로 알림도 와요.

공식 문서: Remote Control — continue local sessions from your phone

25. 데이터베이스에 자연어로 물어본다

PostgreSQL·Supabase 등 주요 데이터베이스는 MCP 서버로 Claude Code와 연동됩니다. 연결해 두면 "지난주 가입자 중 이탈한 사람들의 공통점이 뭐야?" 같은 질문을 SQL 없이 자연어로 던질 수 있어요 — 스키마 탐색, 집계, 조건 검색까지 Claude가 데이터 분석가처럼 처리합니다. 쓰는 데이터베이스가 뭐든, 일단 "이 DB 연결해 줘"라고 물어보는 게 가장 빠른 시작이에요.

26. 깊게 생각시킬 땐 ultrathink

터미널에서 프롬프트에 ultrathink를 함께 쓰면(입력창이 무지개색으로 바뀌면 적용된 거예요) Claude가 생각(thinking) 예산을 최대치로 쓰고 답합니다. 그만큼 토큰을 많이 태우니까 아무 데나 쓸 건 아니고 — 프롬프트를 아무리 바꿔도 좋은 답이 안 나오는 어려운 문제, 구조 설계 판단 같은 곳에 아껴 쓰는 카드예요.

공식 문서: Model configuration — effort. 집필 시점 기준 생각 깊이는 effort 설정으로도 조절할 수 있습니다.

깊이 생각시키는 다른 길도 있어요 — 한 모델의 사고 예산을 키우는 대신 여러 에이전트가 합의할 때까지 계획을 다듬게 하는 겁니다. OMC 플러그인의 ralplan이 그 방식으로, planner·architect·critic 세 역할이 합의에 이를 때까지 계획을 검토해요(--deliberate로 고위험 심의 모드). 아키텍처·DB·보안처럼 판단이 무거운 설계라면 ultrathink보다 이쪽이 맞을 수 있습니다 — 상세는 OMC 실행 모드.

27. 권한을 편집해 안전하게 자율 주행한다

settings.json에서 명령별로 무조건 허용 / 무조건 확인을 정할 수 있어요. 전부 자동 승인하면 rm(파일 삭제)이나 git push --force(충돌 무시 강제 푸시)처럼 위험한 명령까지 통과할 수 있으니, "이런 위험한 명령은 나한테 물어보게 해 줘"라고 시켜서 거부 규칙을 만들어 두세요. 2026년 8월 14일부터 기본값이 된 auto 모드에서는 이 규칙이 특히 중요합니다 — 좁게 적은 거부 규칙은 자리를 비운 사이에도 일하고, 너무 넓게 열어 둔 허용 규칙은 오히려 무시돼요. 규칙이 곧 실제로 집행되는 정책이 된 셈입니다.

# .claude/settings.json — 위험한 명령은 반드시 확인받기
{
  "permissions": {
    "ask": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)"
    ]
  }
}
# 직접 쓰기 어려우면 이 한 줄로: "rm이나 강제 푸시 같은 위험한
# 명령은 꼭 나한테 물어보게 권한 설정해 줘"

공식 문서: Permissions — 배경은 묻지 않는 기본값 기사를 보세요.

왜 나눠야 하나 — 자기승인 편향과 검증의 분리

다음 팁으로 넘어가기 전에, 왜 굳이 역할을 갈라야 하는지부터 짚고 갈게요. 이유가 하나 있는데 이름이 붙어 있습니다 — 자기승인(self-approval) 편향, 연구 쪽 용어로는 자기 선호(self-preference) 편향이에요. LLM이 자기가 만들었거나 자기와 비슷한 방식으로 만들어진 결과를 더 타당하게 평가하는 경향입니다.

감이 아니라 측정된 현상이에요. 한 연구는 사람 평가자가 동등한 품질이라고 본 결과물을, LLM 평가자는 자기 것에 더 높은 점수를 준다는 걸 보였습니다. 더 인상적인 건 그다음입니다 — 자기 출력을 알아보는 능력(self-recognition)과 자기 선호의 강도가 선형으로 상관했어요. 우연히 자기 걸 좋아하는 게 아니라, 알아보기 때문에 편든다는 쪽을 가리킵니다.

여기서 문제가 생기는 구조가 하나 있습니다. 한 에이전트가 계획 → 실행 → 검증을 순서대로 다 하는 구조예요. 처음 세운 전제가 틀려도 같은 판단이 이어서 검증을 맡으니, 틀린 전제 위에 "통과" 도장이 계속 찍힙니다. 자기 출력을 자기가 채점하는 데다 앞선 맥락까지 그대로 들고 가니, 편향이 한 번으로 끝나지 않고 루프가 되는 거죠.

한쪽은 자기가 낸 답을 자기가 채점하고, 다른 쪽은 되돌릴 길이 있다. 차이는 에이전트 개수가 아니라 반려 경로.

그럼 모델을 바꿔서 교차 검토하면 해결될까요? 절반만 맞습니다. 다른 모델에게 맡기면 자기승인 편향 자체는 줄어드는 방향이 맞아요. 그런데 이번엔 다른 함정이 기다립니다 — 동조(conformity)와 아첨(sycophancy)입니다. 에이전트들이 서로의 논리를 받아들이면서 기존 결론이 반박되는 게 아니라 오히려 강화되는 현상으로, 멀티에이전트 토론 연구에서 잘 문서화된 실패 모드예요. 다수가 같은 답을 내면 소수 의견이 그쪽으로 따라가는 에코 챔버도 같은 계열입니다.

정리하면 대응은 두 겹이에요.

  • 역할을 나누고 반려 경로를 만든다 — 계획자 → 설계자 → 검증자로 갈라, 검증자가 문제를 찾으면 계획이나 설계 단계로 되돌립니다. 되돌릴 길이 없으면 나눠 놓은 의미가 절반으로 줄어요. 서브에이전트로 시작하고(중급 편 10번), 서로 대화가 필요해지면 다음 팁의 에이전트 팀으로 올라가면 됩니다.
  • 검증자에게 반박을 시킨다 — 여기가 진짜 갈림길입니다. "검토해 줘"라고 하면 동조가 일어나기 쉬워요. 대신 "이 계획이 틀렸다고 가정하고 반박해. 확신이 없으면 반려 쪽으로 판정해"처럼 반대를 기본값으로 세우세요. 26번의 ralplan이 critic 역할을 따로 두는 것도 같은 이유입니다.

결국 중요한 건 에이전트를 많이 만드는 게 아니라, 계획·실행·검증의 책임을 의도적으로 갈라 두는 것이에요. 하나가 다 하면 자기를 승인하고, 사이좋게 나누기만 하면 서로를 승인합니다.

28. 에이전트 팀 — 서로 대화하는 에이전트들

서브에이전트와 헷갈리기 쉬운데, 구조가 달라요. 서브에이전트는 병렬로 일하되 서로 대화하지 않고 메인에게 보고만 합니다. 에이전트 팀은 독립된 세션들이 서로 대화하고, 작업 목록을 공유하며 일을 나눠 가져요 — 각 팀원과 여러분이 개별 대화도 할 수 있습니다. 기획자·마케터·디자이너 에이전트를 두고 서로 소통시키며 일을 시키는 그림이라면 서브에이전트가 아니라 에이전트 팀이에요. 토큰은 더 들지만, 팀원끼리 서로의 결과를 반박·보완해야 하는 과제에서는 성과가 확실히 다릅니다.

보고 구조가 다르면 쓰임도 다르다 — 독립 조사엔 서브에이전트, 협업 과제엔 에이전트 팀.

직접 플래그를 켜고 팀을 설계하는 대신 포장된 팀 모드를 쓰는 길도 있어요. OMC 플러그인의 team은 N명의 에이전트에 역할을 주어 단계형 파이프라인으로 협업시키는 모드이고, 완료까지 반복하는 ralph와 결합한 team ralph가 OMC에서 가장 강한 실행 강도입니다. 팀 구성·역할 분배를 플러그인이 대신해 주니까, 에이전트 팀을 실무에 바로 써 보고 싶다면 이쪽 진입이 빨라요 — OMC 실행 모드·에이전트·스킬 참고.

공식 문서: Orchestrate teams of Claude Code sessions — 집필 시점 기준 실험 기능이라 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 환경 변수로 켜야 합니다. 방법론이 궁금하면 이 위키의 하네스 엔지니어링 강의가 에이전트 팀 운영을 12편으로 다뤄요.
