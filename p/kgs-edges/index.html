문서는 어떻게 이어지는가 — 개념 큐레이션과 idf가중치 엣지

지식그래프의 품질은 결국 "두 문서가 관련 있다"를 무엇으로 판정하느냐에 달려 있습니다. 이 위키는 임베딩·통계 추출 같은 블랙박스 대신, 사람이 읽고 남긴 개념(concepts)을 재료로 검증 가능한 규칙으로 엣지를 계산합니다. 이 문서는 그 규칙을 실제 수치와 실제 엣지로 끝까지 해부합니다.

재료 — 개념은 추출이 아니라 큐레이션

모든 문서는 등재될 때 핵심 개념 5~6개를 큐레이션받습니다(앞 편의 파이프라인 ③). 여기에 한 가지 원칙이 있습니다: 개념은 본문에 실재하는 것만 적는다. 연결을 만들고 싶다고 본문에 없는 개념을 넣으면 그래프가 "실제 지식의 지도"이기를 멈추기 때문입니다. 그래서 이 그래프의 엣지는 수가 적은 대신, 하나하나가 근거(공유 개념)를 제시할 수 있습니다.

저울 — 희귀한 개념일수록 강한 연결

두 문서가 개념을 공유하면 연결 후보가 됩니다. 그런데 모든 개념이 같은 무게일 수는 없습니다. 66편 중 12편에 나오는 '스킬'을 공유하는 것은 우연에 가깝지만, 단 3편에만 나오는 '벡터검색'을 공유하는 것은 강한 신호입니다. 그래서 개념마다 희소성 가중치(idf) — 대략 "전체 문서 수 ÷ 그 개념이 나오는 문서 수"의 로그 — 를 부여합니다:

희소성 저울 — 흔한 개념의 공유는 가볍게, 희귀한 개념의 공유는 무겁게 칩니다.

실제 엣지 해부 — Welcome ↔ "Claude Code란 무엇인가"

실제 그래프의 엣지 하나를 뜯어 보면: 시작하기와 Tutorial 기초 편은 '터미널'(가중치 3.51)·'CLAUDE.md'(2.01)·'Claude Code'(1.90) 세 개념을 공유합니다. 점수는 가중치의 합 ≈ 7.42 — 같은 문서의 1순위는 개념 4개를 공유한 Tip 초급 편(≈ 9.68)이니, 공유 개념이 많고 희귀할수록 위로 올라가는 셈입니다. 문서 하단의 "연관 문서"에서 이 근거 개념이 그대로 칩으로 표시되므로, 왜 이어졌는지를 언제나 확인할 수 있습니다.

판정 규칙 — System 안은 촘촘하게, 사이는 성기게

판정 플로우 — 2026-09-24 정확도 측정의 엣지 판정에서 나온 규칙입니다. 희귀의 기준(3편 이하)은 예전 규칙의 것을 그대로 씁니다.
  • 같은 System 안 → 공유 2개 이상이면 연결하고, 1개뿐이어도 그 개념이 3편 이하에만 나오면 연결합니다. 실례: 스킬 개요 ↔ 스킬 설치는 '샌드박스' 하나만 공유하지만, 2편에만 나오는 희귀 개념이라 인정됩니다. 연재 안의 문서는 대개 같은 주제를 이어 가므로 문턱을 낮게 둡니다.
  • System을 넘을 때 → 공유 3개 이상이거나, 2개 중 하나가 희귀(3편 이하)해야 연결합니다. 개념 하나로는 아무리 희귀해도 넘지 않습니다. 실례: Tutorial 기초 편 ↔ CLAUDE.md의 10계명은 'CLAUDE.md'(11편)와 '작업지침'(2편)을 공유해, 희귀한 쪽이 닻이 되어 연결됩니다. 반대로 시작하기 ↔ OMC 소개는 '설치'·'슬래시명령어'를 공유하지만 둘 다 흔해서 이어지지 않고, 제안 개요 ↔ 셀프호스팅 공개 베타는 'GitLab' 하나로 World까지 넘던 엣지라 끊겼습니다.
  • 그 외 → 개념으로는 연결하지 않습니다. 개념 연결이 2개가 안 되는 문서는 같은 System의 이웃(예: 기초 편 → 같은 Tutorial의 앞뒤 챕터)으로 보완합니다. 다만 날짜 기사 폴더는 보완하지 않습니다 — 날짜순으로 쌓인 뉴스는 읽는 순서가 아니어서, 옆에 있다는 것이 관련 있다는 뜻이 아니기 때문입니다. 그래서 일부 문서는 연결이 0~1개로 남습니다 — 날짜 기사, 그리고 폴더에 혼자 있어 보완할 이웃이 없는 문서(발송엔진 요청·개별 스킬 소개 두 편)입니다. 억지 이웃을 붙이지 않은 정직한 결과입니다. 현재 비율은 개념 연결 183개(88%) · 폴더 보완 25개(12%)입니다.

예전 규칙은 System을 가리지 않고 "서로 다른 개념 두 개가 겹치는 것은 우연이기 어렵다"고 보았습니다. 측정해 보니 그렇지 않았습니다. 엣지를 하나씩 판정했더니 헛걸음 34개 가운데 20개가 '설치'·'플러그인'처럼 흔한 개념 둘로, 10개가 '메타데이터'·'쿼리'처럼 뜻이 다른 같은 말 하나로 System을 넘은 엣지였습니다. 같은 System 안에서는 흔한 개념 둘의 공유도 대개 진짜 관련이라 규칙을 그대로 두고, 경계를 넘는 엣지에만 증거를 더 요구하게 바꿨습니다. 이 위키가 World 사이에 바라는 구조 — 내부는 촘촘, 사이는 성긴 — 를 System 단위에도 적용한 것입니다.

경계값의 파급 — 왜 함부로 개념을 못 늘리나

"3편 이하" 규칙에는 미묘한 파급이 있습니다. 어떤 희귀 개념이 지금 3편에 등장하는데, 새 문서가 그 개념을 하나 더 쓰면 4편이 되는 순간 그 개념 하나로 이어져 있던 기존 엣지가 자격을 잃고 끊어집니다. 그래서 이 위키의 규칙집(CLAUDE.md)은 "고립을 없애려 본문에 없는 개념을 추가하는 것"을 금지합니다 — 억지 연결 하나가 옆 문서의 진짜 연결을 끊을 수 있기 때문입니다. 연결이 옅은 문서는 결함이 아니라 검토 신호로만 다룹니다. 이것이 이 그래프의 정직성 원칙입니다: 엣지는 늘 실제 본문에 근거하고, 큐레이션은 그래프를 좋게 보이게 하는 도구가 아닙니다.

큐레이션으로 잇는 관계 — 방향 있는 타입 엣지

지금까지의 엣지(related)는 기계가 공유 개념으로 자동 계산한 대칭 관계입니다 — A와 B가 이어지면 방향도 종류도 없이 "서로 관련 있다"일 뿐입니다. 그런데 지식에는 방향과 종류가 있는 관계도 있습니다: "이걸 읽으려면 저게 먼저", "이 개념을 저 문서가 구현한다", "이 기사가 저 주장의 근거다". 이런 관계는 개념 공유만으로는 잡히지 않아, 이 위키는 related와 별개의 컬렉션으로 작업자가 큐레이션으로 선언하는 타입 관계(relations)를 따로 답니다.

방향 있는 타입 엣지 — 큐레이션으로 "이 문서를 읽으려면 저 문서가 먼저"라고 선언합니다(역방향은 자동 유도).

어휘는 다섯 가지입니다 — 선행지식(prerequisite)·구현(implements)·사례(example-of)·근거(evidence-for)·대체(supersedes). 각 관계는 방향(A→대상)과 한 줄 근거(어디서 성립하는지)를 함께 답니다. 저장은 정방향 한 번뿐이고, 반대 방향("이 문서로 들어오는 관계")은 전 문서를 훑어 자동으로 유도합니다. 문서 하단의 "지식 관계" 블록에서 나가는·들어오는 관계를 타입 뱃지와 함께 볼 수 있습니다.

선언은 이렇게 생겼습니다 — 실제 데이터에서 한 건을 그대로 가져오면(기사가 지식 문서의 근거가 되는 관계):

{ "target": "sb-level4",              // 이 관계가 향하는 문서
  "type": "evidence-for",             // 관계의 종류: 근거
  "evidenceRef": "Neo4j 짐 웨버 원문(2024-06-04) 정리 —
                  sb-level4 지식 그래프 접근의 전문가 근거",
  "source": "human" }                 // 큐레이션 출처 (사람 승인 — 자동 제안 아님)

현재 위키에 선언된 관계는 110건이고, 전부 이 형식입니다. 대부분은 강의형 시스템과 AI 2040 뉴스 시리즈의 읽기 순서 prerequisite 체인(앞 문서 → 다음 문서)이고, 나머지는 시스템을 가로지르는 implements·example-of·evidence-for·교차 prerequisite입니다. 타입별 실례:

  • 선행지식(prerequisite) — 이 시리즈 자체가 체인입니다: 쌓이는가 → 이 문서 → 7가지 눈 → AI가 읽는 법 → 플러그인화. 각 편이 다음 편의 선행지식으로 선언돼 있어 "무엇을 먼저 읽어야 하는지"를 그래프가 압니다. 시작하기 → 확장 기능도 같은 타입.
  • 구현(implements) — 위키 엔진의 플러그인화가 이 시리즈가 설명한 엔진을 구현합니다. 하네스 개념 문서 → 플러그인 아키텍처 문서도 같은 계보. World를 가로지르는 다리도 있습니다 — Douzone 지식 플랫폼 제안이 "Reference Wiki(이 위키)"를 복제해 이 등재 파이프라인을 구현하겠다고 선언합니다.
  • 사례(example-of) — LLM Wiki는 세컨드 브레인 레벨 2(주제로 묶기)가 말하는 단계의 실사례입니다. 첫 하네스 실행도 하네스 실행 강의의 구체 사례로 붙습니다.
  • 근거(evidence-for) — 위의 JSON처럼, 외부 원문을 확인한 기사가 Second Brain 4단계 주장의 외부 근거로 붙습니다. 타릭의 Fable 필드가이드 정리도 하네스 엔지니어링의 "모델보다 환경이 결과를 좌우한다"는 주장을 받칩니다 — 기사 4편이 이 타입으로 지식 문서를 받칩니다.

여기에 세 번째 연결층이 하나 더 있습니다 — 인용 백링크(citedBy). 문서 본문에서 다른 문서로 건 #! 내부 링크를 인덱스 빌드가 역방향으로 모아, 인용받은 문서 하단에 “이 문서를 인용한 문서”로 자동 표시합니다. 개념 공유(related)도 선언(relations)도 아닌, 글을 쓰다 실제로 참조한 흔적에서 나오는 연결이라 정직성 규칙과 자연히 정합하고 — 많이 인용되는 문서가 허브임이 저절로 드러납니다. 인용자는 지식 인덱스에 든 문서만 세므로 Work Log 같은 저널의 링크는 섞이지 않습니다.

세 레이어는 성격이 다릅니다. related는 기계·대칭·개념 기반이라 넓게 깔리고, citedBy는 기계·방향·본문 링크 기반이며, relations는 큐레이션·방향·타입이라 적지만 의미가 진합니다. 그리고 같은 정직성 원칙을 따릅니다 — 본문에 실재하는 관계만 답니다. 실제로 "구버전을 남긴 채 신버전이 대체"하는 대체(supersedes) 사례가 현 위키엔 없어(문서를 제자리에서 고치므로), 어휘·검증·UI는 갖추되 그 타입은 비워 두었습니다 — 관계를 채우려 억지 쌍을 만들지 않습니다. 선언된 관계는 검증기가 지킵니다: 존재하지 않는 대상(relations-dangling-ref)과 5어휘 밖 타입(relations-unknown-type)은 ERROR로 머지가 막히고, 근거 누락과 상충 선언은 WARN으로 검토 신호가 됩니다.

한눈 요약 개념은 큐레이션(본문 실재만) → 엣지는 희소성 가중 공유(System 안은 2개↑ 또는 희귀 1개, 사이는 3개↑ 또는 희귀한 닻을 낀 2개) → 부족하면 폴더 보완(날짜 기사 제외) → 대부분 2~4연결, 개념이 닿는 이웃이 없으면 0~1개로 둡니다. 그 위에 본문 #! 링크의 역인덱스인 인용 백링크(citedBy)와, 큐레이션으로 선언하는 방향 있는 타입 관계(relations)를 별도로 얹습니다. 많이 참조되는 문서가 허브가 되어 그래프의 중심을 이룹니다(다음 편).
