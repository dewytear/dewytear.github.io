하네스가 점수를 바꾼다는 증거 — Microsoft 백서와 RHO·HarnessPro 연구를 겹쳐 읽기

세 줄 요약

  • Microsoft는 2026년 11월 9일 백서에서 같은 모델, 같은 과제에 하네스만 바꿔 측정했다. 통과율은 GPT-5.5 Chat에서 10.8포인트, Claude Opus 4.8에서 22.1포인트 올랐고, 모델을 바꾸는 쪽은 거의 차이가 없었다.
  • 학계는 같은 결론을 다른 길로 냈다. RHO(홍콩성시대·Microsoft Research Asia, EMNLP 2026)는 정답 라벨 없이 과거 실행 기록만으로 하네스를 고쳐 SWE-Bench Pro 통과율을 59%에서 78%로 올렸고, 후속작 HarnessPro는 그 루프를 재귀적으로 돌리며 성능과 비용을 함께 최적화해 라이트·미디엄·헤비 세 하네스를 낸다.
  • 세 자료의 공통 결론은 하나다. 모델이 고정돼 있을 때 결과를 두 자리 포인트로 움직이는 변수는 하네스이고, 비용은 호출이 늘어도 캐싱과 출력 압축으로 오히려 줄일 수 있다. 이 글은 그 세 자료를 수치·구조·한계까지 한 자리에 놓는다.

하네스(harness)는 모델을 둘러싼 실행 환경이다. 모델에 주는 지시문, 쓸 수 있는 도구, 도구가 실패했을 때의 규칙, 출력물을 어디까지 잘라 다시 넣을지 같은 운영 정책이 모두 하네스에 속한다. 정의와 구성은 하네스란에서 다뤘으므로 여기서는 반복하지 않는다. 이 글의 관심은 다른 데 있다. 2026년 하반기에 "하네스가 모델만큼, 혹은 그 이상으로 결과를 좌우한다"는 주장이 산업계 백서와 학술 논문 양쪽에서 수치로 나왔다. 뉴스로 한 번 소비하기에는 아까운 자료라, 세 편을 겹쳐 읽는 형식으로 적어 둔다.

세 갈래가 같은 해에 모였다. 학계는 하네스를 스스로 고치는 방법을, Microsoft는 하네스를 바꿨을 때의 효과를, 평가 연구는 하네스가 벤치마크 점수의 숨은 변수라는 점을 각각 수치로 냈다.

1. Microsoft 백서 — 같은 모델, 다른 하네스

Microsoft Copilot Studio에는 하네스가 둘 있다. 토픽·변수·도구를 제작자가 하나씩 배선하는 Standard 하네스와, 모델이 계획을 세우고 도구를 고르고 실패하면 다시 시도하는 에이전트 루프형 하네스다. 후자는 GitHub Copilot의 코딩 에이전트에서 가져온 것이라 GitHub Copilot 하네스라고 불렸고, 10월 28일에 Microsoft 전체에 공통 기반으로 쓰겠다며 Microsoft Copilot 하네스로 이름을 바꿨다. 개명 공지는 기능이나 요금에 변화가 없다고 밝혔다.

11월 9일 블로그와 함께 공개한 백서는 두 하네스를 같은 과제, 같은 모델로 돌린 내부 평가(2026년 10월)의 결과다. 핵심 수치는 아래와 같다.

Microsoft 블로그·백서(2026년 11월 9일)의 수치를 옮겼다. 모델을 바꾼 효과는 "거의 없었다"고만 적혀 있어 막대로 그리지 않았다.

이 수치에서 읽을 점은 상승폭 자체보다 그 비대칭이다. 같은 하네스 교체가 Claude Opus 4.8에서 두 배 가까이 크게 작용했다. 백서는 이유를 길게 풀지 않지만, 공개된 구조만으로도 설명이 된다. 새 하네스는 도구 호출이 실패했을 때 84~91%의 사례에서 다시 시도했고 Standard 하네스는 7% 미만에서 그쳤다. 긴 과제에서 한 번의 도구 실패가 곧 과제 실패로 이어지던 손실이 사라진 셈이다. 모델이 도구를 잘 다룰수록 "다시 시도할 기회"의 가치가 커지므로, 상승폭이 모델에 따라 다르게 나타나는 것이 자연스럽다.

비용 항목도 직관과 반대다. 모델 호출은 약 두 배로 늘었는데 입력 처리 비용은 15~21% 줄었다. 백서가 꼽는 이유는 캐싱이다. 긴 대화에서 입력의 83~88%가 캐시에서 처리되면, 호출이 늘어도 새로 읽는 토큰은 적다. 호출당 지연도 10~36% 줄었다. 즉 "에이전트 루프는 비싸다"는 통념은 캐시를 전제하지 않은 계산이었다.

Microsoft 자신의 선택 가이드도 새 하네스를 만능으로 말하지 않는다. 커넥터나 MCP 서버를 쓴다는 것만으로는 에이전트 루프형이 필요하지 않고, 단순한 시나리오에 쓰면 결과는 그대로인데 추론과 지연, 크레딧 소비만 늘 수 있다고 적는다. 실무 사례로는 Microsoft 고객지원 부서가 이 하네스로 만든 해결 에이전트가 2026년 8월에 사람 개입 없이 처리한 비율 35%를 넘겼다는 수치가 있다.

2. RHO — 정답 없이 하네스를 고치는 법

Microsoft 실험은 사람이 설계한 두 하네스를 비교했다. 학계의 질문은 한 발 더 나간다. 하네스를 에이전트가 스스로 고칠 수 있는가, 그것도 정답 라벨 없이. 기존 방법(프롬프트 최적화, 스킬·도구 합성, 에이전트 탐색)은 라벨이 붙은 검증 세트에 대고 반복 채점을 해야 했는데, 실제 배포 환경에는 그런 세트가 없다. 대신 에이전트가 매일 쏟아내는 라벨 없는 실행 기록(궤적)이 있다.

RHO(Retrospective Harness Optimization, 회고적 하네스 최적화)는 홍콩성시대와 Microsoft Research Asia 연구진이 2026년 6월 arXiv에 올리고 EMNLP 2026 Findings에 실은 논문이다. 방법은 세 단계다.

DPP(행렬식 점과정)는 "어렵다"와 "서로 다르다"를 동시에 만족하는 부분집합을 고르는 확률 기법이다. 자기선호는 에이전트가 두 실행 결과를 나란히 보고 어느 쪽이 나은지 스스로 고르는 것을 말한다.

첫 단계가 과거 과제 중 어렵고 서로 다른 것만 소수 고르는 이유는 비용이다. 모든 과제를 다시 풀 수는 없으니, 실패가 몰린 자리를 대표하는 표본을 뽑는다. 두 번째 단계는 그 과제들을 여러 번 병렬로 다시 풀어 두 가지 신호를 얻는다. 한 실행 안에서 "테스트가 통과했는가" 같은 자기검증 신호, 여러 실행 사이에서 "같은 답이 나오는가" 같은 자기일관성 신호다. 세 번째 단계에서 에이전트는 이 진단을 보고 하네스 수정안을 여러 개 쓰고, 각 수정안으로 다시 푼 결과를 원래 결과와 쌍으로 비교해 스스로 더 낫다고 고른 것만 채택한다. 어디에도 사람의 채점이나 정답이 들어가지 않는다.

결과는 한 라운드 기준이다. 비교 대상은 같은 호출 예산을 쓰는 라벨 불필요 방법들이다.

라벨을 쓰는 방법과도 비교했다. 검증 세트에 대고 채점하는 Meta-Harness를 같은 한 라운드 예산으로 돌리면 SWE-Bench Pro 0.62였고, RHO는 라벨 없이 0.78이었다. RHO가 하네스에 써 넣는 것은 세 종류다. 과제와 무관한 일반 지시, 과거 실패의 환경 특이점을 적어 둔 스킬, 그리고 실행 가능한 도구다. 각각이 원래 궤적에서 관찰된 실패 유형 하나를 겨냥한다.

한계도 논문이 직접 적는다. 자기선호는 보수적인 선택기이지 완벽한 순위기가 아니다. SWE-Bench Pro에서 덜 선호된 후보 하나가 실제로는 0.85로 채택된 것(0.78)보다 높았다. 다만 채택된 하네스가 기본값보다 나빠진 벤치마크는 없었다. 또 코딩 에이전트에서 이 방법이 잘 먹히는 이유 가운데 하나는 "테스트가 통과했는가"가 믿을 만한 자기신호라는 점이라, 실행으로 확인할 수 없는 영역에서는 자기선호가 흔들릴 수 있다. 이 위키가 고급 팁에서 다룬 자기승인편향(모델이 자기 결과물을 후하게 평가하는 경향)과 같은 뿌리다.

코드는 공개돼 있고 Claude Code용 동적 워크플로(retrospection.js)로도 묶여 있다. 그 워크플로는 프로젝트의 CLAUDE.md, 자동 메모리, 보조 스크립트를 하네스로 보고 지난 세션 기록만으로 한 라운드를 돈다. 논문이 말하는 하네스가 Claude Code 사용자에게는 이미 손에 있는 파일들이라는 뜻이다.

3. HarnessPro — 재귀로 돌리고 비용까지 축으로 넣기

HarnessPro는 2026년 10월 arXiv에 올라온 후속 연구다. 공개 저장소의 패키지 이름이 src/rho/이고 환경변수도 RHO_로 시작하는 것을 보면 RHO의 코드 위에 세운 연구가 맞다. 보도는 칭화대 연구로 소개했으나 arXiv 쪽 저자 정보로는 소속을 확인하지 못했고, 논문 자체가 "심사 중" 표기를 달고 있다. 이 글에서는 소속을 단정하지 않고 "RHO 후속 연구"로 부른다.

RHO와 다른 점은 둘이다. 첫째, 한 번 회고하고 끝내지 않고 진단·진화·선택을 재귀적으로 반복한다. 둘째, 목적 함수에 비용을 넣는다. 성능 하나만 보면 하네스는 "더 많이 생각하고 더 많이 호출하라"는 쪽으로만 자란다. 비용을 두 번째 축으로 두고 파레토 선택(한 축을 희생하지 않고는 다른 축을 더 좋게 할 수 없는 후보들만 남기는 것)을 하면, 프런티어 위에 여러 운영점이 남는다. HarnessPro는 그중 셋을 골라 라이트(비용 우선), 미디엄(균형), 헤비(성능 우선)로 내놓는다.

오른쪽 점의 위치는 논문이 보고한 상대 수치를 도식화한 것이다. 헤비는 RHO보다 통과율이 약간 높으면서 비용이 4분의 1가량 낮고, 미디엄은 통과율을 1포인트 양보하는 대신 비용을 절반 넘게 줄인다.

수치는 Codex + GPT-5.5 기준이며 비교 기준은 RHO 하네스다. 헤비는 통과율 +2.0포인트에 비용 26.1% 감소, 미디엄은 통과율 -1포인트에 비용 53% 감소다. 벤치마크별로는 Terminal-Bench 2에서 헤비가 3회 평균 80.8%로 RHO보다 4.5포인트 높고 비용은 31.7% 낮았다(논문 판본에 따라 33.9%로도 적혀 있다). SWE-Bench Pro에서는 헤비 80.7% 대 RHO 80.0%에 비용 26.5% 감소다. 실험은 GPT-5.5 + Codex와 GLM-5.2 + Claude Code 두 조합, 벤치마크는 Terminal-Bench 2, SWE-Bench Pro, ProgramBench 세 개다.

진화한 하네스가 실제로 무엇을 담고 있는지는 저장소에서 읽을 수 있다. Terminal-Bench 2용 하네스를 열어 보면 다음이 들어 있다.

  • 프로필 선택기: 과제 설명만 보고 compact·lean·standard·deep·research 다섯 프로필 중 하나를 고르는 규칙 문서. 프로필마다 추론 강도(low·medium·high)와 "몇 번째 도구 호출부터 절약 모드, 몇 번째부터 마무리"라는 호출 예산이 붙는다. 라이트는 compact 과제에 작은 모델(GPT-5.4-mini)을 배정하고, 헤비는 standard 과제를 high 추론으로 올리고 마무리 검증 여유를 더 준다.
  • 출력 압축: 도구 출력을 4,000자, 앞 2,400자·뒤 900자만 남기고 기록 토큰 한도를 두는 정책. 비용 감소의 상당 부분이 여기서 나온다.
  • 기능 차단 목록: 브라우저 사용, 멀티 에이전트, 플러그인, 이미지 생성 등 과제에 불필요한 기능을 꺼 두는 목록.
  • 세션 지시문: "요청된 구현을 목업이나 프록시로 바꾸지 말 것", "마무리 전에 과제를 다시 읽고 산출물을 독립 근거로 대조할 것" 같은 일반 규칙. 과제 ID나 과거 점수 같은 과제 특정 정보는 넣지 않았다고 명시한다.
  • 검증 보조 도구: SWE-Bench Pro용 하네스에는 요구사항 장부를 쓰고 스모크 테스트를 돌리는 repair-verify 스크립트와 계약 검증 체크리스트가 포함된다.

즉 에이전트가 스스로 쓴 하네스의 실체는 긴 프롬프트 한 장이 아니라, 추론 강도 배정표와 호출 예산, 출력 자르기 규칙, 끄는 기능 목록, 검증 스크립트의 묶음이다. 이 위키가 동작 원리에서 하네스의 3요소로 정리한 것과 같은 자리에, 수치가 붙은 형태로 들어 있다.

세 자료가 서로 다른 방법으로 같은 방향을 가리킨다는 점이 이 글을 쓴 이유다. 모델을 고정한 채 하네스만 바꿔도 통과율이 두 자리 포인트로 움직이고, 그 이득의 상당 부분은 "실패 뒤 다시 시도", "필요한 만큼만 추론", "출력을 잘라 넣기"처럼 모델 능력과 무관한 운영 규칙에서 나온다. 비용은 호출 수가 아니라 캐시와 압축이 결정한다.

반대 방향의 증거도 같이 두어야 한다. 7월의 Scaffold Effect 논문은 공개 하네스 셋(Goose, OpenCode, OpenHands)에 모델 둘을 넣어 Terminal-Bench Pro 50문제를 돌렸는데, 풀린 문제당 토큰 소비가 하네스에 따라 최대 40배 차이 난 반면 통과율 차이는 0~8포인트에 그쳤다. 모델을 올려도 토큰 비용은 1.0~1.3배밖에 움직이지 않았다. 이 논문의 결론은 평가 단위를 "모델"이 아니라 "하네스·모델 쌍"으로 적고 비용을 같이 보고하라는 것이다. 같은 달 "하네스가 사는 것은 대개 토큰이다"라는 제목의 논문도 같은 모델·같은 과제에서 하네스에 따라 과제당 비용이 최대 3배 갈린다고 보고했다. 하네스가 점수를 올린다는 주장과 하네스가 주로 비용을 가른다는 주장은 모순이 아니다. 어느 하네스끼리 비교하느냐에 따라 차이가 점수로 나타나기도, 비용으로 나타나기도 한다는 뜻이고, 그래서 두 축을 함께 보고하는 HarnessPro 방식의 보고가 기준이 될 만하다.

5. Claude Code 사용자에게 남는 것

이 자료들을 Claude Code 쪽으로 옮겨 읽으면 세 가지가 남는다. 첫째, CLAUDE.md·스킬·훅·자동 메모리는 그 자체가 하네스이고, RHO 저장소는 이 파일들을 지난 세션 기록만으로 고치는 워크플로를 실제로 내놓았다. 둘째, HarnessPro가 진화시킨 항목(추론 강도 배정, 도구 출력 자르기, 불필요한 기능 끄기, 마무리 검증 규칙)은 전부 Claude Code의 설정과 훅으로 표현 가능한 것들이다. 셋째, 효과를 주장하려면 Scaffold Effect 논문이 말한 대로 통과율과 토큰을 같이 재야 한다. 이 위키의 활용과 확장이 다룬 성능 측정 항목이 바로 그 자리다.

사실검증 노트

Microsoft 수치 가운데 통과율 상승폭(10.8·22.1포인트), 도구 실패 뒤 재시도 비율(84~91% 대 7% 미만, 7배 이상), 호출 약 2배와 입력 처리 비용 15~21% 감소, 고객지원 에이전트의 자율 해결률 35%, 개명 공지의 "기능·요금 변화 없음"은 10월 28일 개명 공지와 11월 9일 블로그를 직접 읽어 옮겼다. 캐시 처리 비율 83~88%, 호출당 지연 10~36% 감소, 비즈니스 프로세스 벤치마크 65% 대 36%는 백서 소개 글의 검색 발췌 기준이며, 이 글을 쓴 환경은 네트워크 정책 때문에 백서 PDF(aka.ms/MCSQuality/Whitepaper)와 Microsoft Learn의 하네스 비교 문서를 직접 열지 못했다. 백서는 경쟁 제품 이름과 과제 세트 규모를 밝히지 않았고, 모든 수치는 Microsoft 자체 측정이다. 두 하네스의 구조 비교(배선 방식·Bash 컨테이너·하위 에이전트 역할·단순 과제 경고)는 Microsoft 공식 가이드를 인용한 정리 글들의 일치하는 범위만 적었다. 8월 정식 출시 시점은 한 보도 기준이다. RHO의 저자·소속·학회(Findings of EMNLP 2026, 부다페스트)·세 단계 구조·결과 표·Meta-Harness 비교는 공개 저장소를 받아 README·인용 파일·프로젝트 페이지에서 확인했고, "덜 선호된 후보가 0.85" 분석은 논문 본문 발췌 기준이다. HarnessPro의 세 모드·벤치마크·모델 조합·Terminal-Bench 2 수치(80.8%, +4.5포인트, 31.7% 또는 33.9%)는 arXiv 초록과 검색 발췌, 하네스 내용물은 공개 저장소의 README와 정책 파일을 직접 읽어 적었다. RHO 대비 +2.0/-26.1%, -1/-53%와 SWE-Bench Pro 80.7 대 80.0은 보도와 초록 발췌가 일치하는 범위다. 칭화대 소속은 보도에만 있고 논문 메타데이터로 확인하지 못해 본문에서 단정하지 않았다. arXiv 본문은 직접 열지 못했다. Scaffold Effect 논문(arXiv 2607.22585, 40배·0~8포인트·1.0~1.3배)과 "What Does a Harness Buy? Tokens, Mostly."(arXiv 2610.04433, 최대 3배)는 초록 발췌 기준이며, 전자의 저자 소속 Sentient Labs는 2차 정리 글 기준이라 본문에 적지 않았다.
