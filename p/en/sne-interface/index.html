Interface · Scale · Alignment · Expected Benefits

Interface — request to finalize it first (top priority)

Priority request Implementing the whole engine takes time, so we ask that the interface (the specification of what is exchanged) be finalized and provided before the engine itself. Only then can AI Notification implement in parallel the parts that publish send requests and receive results.

Proposed order of work

  1. Present the preferred option — we prefer the direction in which AI Notification publishes send requests to the queue and the engine consumes them.
  2. Agree on the direction — discuss this direction at the highest priority.
  3. Finalize the interface first — as soon as we agree, lock the interface down first → start parallel development.

Interfaces needed (direction · information exchanged)

#InterfaceDirectionInformation exchanged (conceptual)
①Send request deliveryAI Notification → engineRequest identifier, company, send target, message content, recipient list, channel, timing type and parameters
②Finalization at send time (lookup · resolution)Engine → AI Notification → engineWhen the timing arrives, request finalization of "the final targets and content to send now" → the finalized result is returned
③Send result · status returnEngine → AI NotificationRequest mapping, success/partial failure/failure per channel, failure reason, delivered · read
④(Optional) status · history integrationTo be discussedHow the status screen links to AI Notification data if the engine provides it

The concrete fields and formats are settled through discussion. This document presents only the direction and the kinds of information exchanged.

Scale · SLA · priority

Scale and SLA (daily/peak send volume, the delay allowed for "immediate", history retention period, granularity of result returns) are settled through discussion. The minimum scale (order of magnitude) needed for effort estimation is decided together at the kickoff.

Priority (phases)

Phase 1 · essential

  • Notification, note, and mail sending + idempotency and delivery guarantee
  • Timing for the four timing types + finalizing with the latest data at send time
  • Recurring batch lifecycle management
  • Result and status returns + the send status screen
  • Finalizing the interface first

Later phases

  • Advanced scheduling/recall features, expansion to the KakaoTalk and chat channels
  • Read confirmation, advanced statistics and analytics

Items that need discussion

  • The interface direction (preferred option → fast finalization)
  • The real-time criterion for "immediate" sending (allowed delay)
  • The order and priority of channel expansion
  • The scope of delivery and read confirmation (how much is returned)
  • The concrete integration for finalizing targets at send time (finalization request and response)
  • Who holds and manages the channel credentials
  • Rough figures for send volume and SLA (for effort estimation)

Expected benefits · schedule

  • Delivery reliability — sending without loss or duplication, with delivery confirmation.
  • Scalability — coping with high volume, many channels, and new channels.
  • Operability — status views and reprocessing reduce the operational burden.
  • Shared asset — turning the send engine into a shared asset.

We intend to start the discussion in early August, aim to finalize the interface in early August if possible, and then move on to implementing the send engine.
