Finding a Movie by Its Story — Your First Vector Retriever on a Neo4j Sandbox

The previous piece unfolded the map; this one laces up the boots. We borrow a graph database in the browser — nothing to install — turn movie plots into numbers, and build, end to end, a search engine that answers “got anything with a story like this?” with actual movies.

The goal fits in one sentence: throw in a plot, get back movies whose plots feel like it. It sounds grand, but there are only three parts, and each does something humble behind its unfamiliar name.

  • Embedding — turning a sentence into a list of numbers that carries its meaning (a vector). Sentences that mean similar things end up with numbers that sit close together. An embedding model does the converting; here we use OpenAI's.
  • Vector index — a lookup tab for finding those numbers fast. Like the thumb notches on a dictionary's edge, it takes you to “nearby vectors” without scanning everything.
  • Retriever — the searcher itself: it takes your question, embeds it, asks the index for the nearest matches, and hands back results.
Today's five steps. At the last one, “plot in → similar movies out” actually runs.

Step one — borrow a graph database

You don't install anything to try a graph DB. Neo4j lends you a Sandbox — a free cloud instance, in the same spirit as running a Python notebook on Google Colab: open the browser and a graph database appears. Log in, and when it asks which project to spin up, pick Recommendations — a movie-recommendation dataset of the MovieLens family, preloaded and ready.

Open it and the pictures from the previous piece are suddenly standing there in the flesh. Five kinds of nodes — Movie, Genre, Actor, Director, User. Click a movie node and its properties spill out: title, runtime, and the plot. Kung Fu Panda 3 has Jack Black attached by an ACTED_IN arrow, and some user attached by a RATED arrow — and inside that arrow sit a rating of 4 and a timestamp. Relationships that carry data of their own: this is where you first see, with your own eyes, the property-graph trait the previous piece kept talking about.

The skeleton of the Recommendations data. The RATED arrow keeps a rating and a timestamp inside itself — in a property graph, relationships hold data too.

Step two — a stroll with Cypher

Before the real construction, a few lines of Cypher (the graph query language — see the previous piece) to say hello to the data. The skeleton is three words: MATCH draws the shape of the relationship you want, RETURN names what you want back, LIMIT trims the count.

// who rated what — browse 25 of them
MATCH (u:User)-[r:RATED]->(m:Movie) RETURN u, r, m LIMIT 25

// titles and plots of Tom Hanks movies — comes back as a table, not a graph
MATCH (a:Actor {name: 'Tom Hanks'})-[:ACTED_IN]->(m:Movie)
RETURN m.title, m.plot LIMIT 10

The first query paints itself as a graph on screen; the second, returning bare properties instead of nodes, comes back as a table. Same data, drawn or tabulated on demand — once you've seen that, the stroll has done its job.

Step three — turn plots into numbers and plant them back

Now the core work. From Python, connect to the sandbox with the Neo4j driver (the connection snippet is sitting right on the sandbox page under Connect via drivers — copy, paste, done), pull each movie's plot text, pass it through the embedding model, and plant the resulting vector back onto the node as a new property. Embedding everything would take a while, so — as befits an exercise — we cut it at 100 movies.

# 100 movies with plots → embed → store as plotEmbedding
movies = tx.run("""
    MATCH (m:Movie) WHERE m.plot IS NOT NULL
    RETURN m.title AS title, m.plot AS plot LIMIT 100""")
for row in movies:
    vec = generate_embedding(row["plot"])   # call the OpenAI embedding
    tx.run("""
        MATCH (m:Movie {title: $title})
        SET m.plotEmbedding = $vec""", title=row["title"], vec=vec)

A few dozen seconds later, click any movie in the sandbox again: next to plot there is now a plotEmbedding property packed with 1,536 real numbers. To a human eye it's noise — but the distance between these numbers is the likeness of the stories. The demo used OpenAI's text-embedding-ada-002 (1,536 dimensions); starting fresh today you'd take its successor in the same slot (the text-embedding-3 family) — the procedure is identical.

Step four — add the tabs

Vectors planted; time to care about speed. With 100 movies a full scan is fine, but at hundreds of thousands, re-measuring every vector per query is waste. So we build a vector index — like the thumb notches on a dictionary, a shortcut to the nearby vectors, dug in advance. One Cypher statement:

// create a vector index over plotEmbedding on Movie nodes
CREATE VECTOR INDEX moviePlots
FOR (m:Movie) ON m.plotEmbedding
OPTIONS {indexConfig: {
  `vector.dimensions`: 1536,          // must match the embedding model
  `vector.similarity_function`: 'cosine'
}}

The two options say something simple: the vectors this index handles are 1,536-dimensional, and “near” is judged by cosine similarity (likeness measured as the angle between vectors). The dimension count must match the embedding model's output — get this wrong and the index refuses your vectors.

Step five — assemble the retriever, and ask

All the parts are on the bench: a connection (driver), a tab system (index), a converter (embedder). Hand the three to VectorRetriever from the neo4j-graphrag package introduced in the previous piece, and the search engine is assembled. A fourth argument decides which properties come back in the results.

from neo4j_graphrag.retrievers import VectorRetriever

retriever = VectorRetriever(
    driver,                                # ① which DB
    index_name="moviePlots",               # ② which index
    embedder=embedder,                     # ③ how to vectorise the question
    return_properties=["title", "plot"],   # ④ what to hand back
)
result = retriever.search(query_text="toys that secretly come alive", top_k=3)

Now ask for real. Throw in a short summary of Toy Story's plot, and Toy Story comes back in first place — title, plot, and the cosine similarity score alongside. Describe a film about a shooting incident, and a movie with exactly that material surfaces at a score around 0.93. Notice what never happened: the query never mentioned a title. It was found not because words overlapped, but because the stories resembled each other — this is the fork in the road between keyword search and vector search.

One step further

What we built today is a pure vector searcher. It hasn't used half of the graph's power yet — the moment you walk from a found movie node along ACTED_IN to its actors, along IN_GENRE to its genre, along RATED to users with similar taste, that's where GraphRAG proper begins. But this order is the right one. Cast with vectors, then walk with the graph — today's retriever is the first of those two verbs. The search recognised the story because the story was planted with care. That is also why this wiki keeps each document's concepts and relations in a form machines can read.

Fact-check note The procedure and run results (100 plots embedded, Toy Story ranked first, ~0.93 similarity on the shooting-incident query) are reconstructed from an external demonstration; this wiki did not re-run the same environment. Code and syntax were cross-checked against primary sources — the neo4j-graphrag-python docs (VectorRetriever's driver, index_name, embedder, return_properties; search's query_text and top_k), Neo4j's CREATE VECTOR INDEX syntax (vector.dimensions, vector.similarity_function), and the Neo4j Sandbox Recommendations (MovieLens-family) dataset. The package was named neo4j-genai at the time of the demo and has since been renamed neo4j-graphrag; text-embedding-ada-002 is a legacy model, with the text-embedding-3 family recommended for new builds.
