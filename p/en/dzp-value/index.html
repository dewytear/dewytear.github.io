Added Value and Use Scenarios — Beyond the Development Organization

The previous parts dealt with the perspective inside the development organization — how knowledge is created and managed. This part deals with how many faces a single Knowledge State, once accumulated, can be consumed in. The source of added value is not writing more documents, but adding one more view per audience on the repository that has already been accumulated — accumulate once, and employees, partners, customers, and AI each pull the same knowledge within their own scope.

Automatic API specification updates — the first derivative product

The most immediate added value is that the API specification stays alive together with the code. The chronic problem of manual specifications is well known — updates fall behind after the first draft, and a specification that diverges from the code misleads integration developers and customers. On this platform, the API specification is not a separate deliverable but a natural output of the knowledge pipeline:

  • Extraction — endpoints · parameters · response structures · error codes are read out of merged Controller · Mapper · Config changes. Because they are facts confirmed directly in the code, most of them are FACT grade — the knowledge with the highest chance of automatic publication in the trust level system.
  • Update — when an API changes, the same merge trigger updates the specification document. The dual management of "specification here, code there" structurally disappears.
  • Search — because API names and error codes are carried in the identifiers extension field, an integration developer reaches the relevant specification and policy document directly from a single error code.
  • History — when an interface policy changes, the old specification is linked as superseded via supersedes, preserving both "the current spec" and "why it changed."

One repository, a view per audience

The four security grades are an access control mechanism and at the same time a publication channel selector. From the same repository, read-only views per audience are created simply by varying the grade filter — no repository is cloned and no document is copied over.

One repository, as many views as there are audiences — the grade filter becomes the publication channel.
  • Employees · development organization — identifier search, AI tool context, and onboarding paths across the full grade range. The basic view that directly reduces the losses quantified in Why Now (8 hours of inefficiency per week, 3–9 months of onboarding).
  • Partners · collaborating firms — integration development guides, API specifications, and customization knowledge selected from INTERNAL. The integration knowledge that partners can currently learn only "by asking the person in charge" becomes self-service, and the cost of handling repeated inquiries drops.
  • Customers — PUBLIC grade product technical documents, API guides, and release impact notices. The dual management of building a separate customer documentation site and letting it go stale again disappears — because when the code changes, the customer documents are updated through the same pipeline.
  • AI Agent — using the llms.txt and graph JSON contracts of the AI consumption layer as they are, the in-house assistant and the customer support bot answer from the same knowledge with evidence (sources included). The human view and the machine view come out of one repository — and the foremost consumer of this machine view is AI coding below.

Prior knowledge for AI coding — where the virtuous cycle closes

The most strategic use is using the knowledge graph as prior knowledge for AI coding. Today, a developer re-explains the domain background to an AI tool such as Claude Code every single time — "the sales order status transitions like this, the credit check happens at that point…" (the cost of repeatedly re-explaining context that Why Now pointed out). On this platform, AI reads the knowledge graph first, before starting the work:

  • Entry — it grasps the overall terrain of the knowledge through llms.txt, and secures nodes · relations · concepts · URLs with a single fetch of knowledge-graph.json.
  • Selection — it reaches the related policy documents via the identifiers (table, rule ID, API name) it meets in the source it is working on, and expands only as far as needed by following typed relations — background through prerequisites, "the policy valid now" through supersedes, the reasons behind design decisions through the DECISION grade.
  • Work — it reads and writes code already knowing the domain rules, status transitions, past incidents, and design intent. This procedure can be fixed as a project convention through CLAUDE.md and MCP integration.

This is the substance of the fourth box ("Next development — Claude Code · Agent") in the virtuous cycle diagram of the overview — development results become knowledge, and that knowledge is injected as prior knowledge into the AI of the next development, raising the quality of development results again. It is a structure in which, the more knowledge accumulates, the more the accuracy of AI coding rises at organizational scale like compound interest, and the Reference Wiki's traversal contract has already demonstrated this mode of consumption at small scale.

Reaching non-development roles too — trust grades widen the readership

Development knowledge does not belong to developers alone. Technical support and CS search incident cases and troubleshooting to raise the quality of first-line response, sales and PMs raise the accuracy of customer conversations with product feature, policy, and terminology knowledge, and new joiners use the organization's knowledge map as an onboarding path regardless of their role. The reason it is safe even when non-development readers cannot read code is that a trust grade is attached to every document — FACT (facts confirmed in the code) is distinguished from INFERRED (inference) and DECISION (decision), so readers do not misunderstand how certain the knowledge is.

Key point The added value of this platform does not come from creating a new documentation channel for every department. It comes from adding views with grade filters on top of a Knowledge State accumulated once — API specifications, partner guides, the customer documentation portal, and prior knowledge for AI coding are all different cross-sections of the same repository.
