The Core of the Proposal and the Architecture

The purpose of this proposal is not to build a simple company Wiki. It is to build a platform where AI continuously analyzes the development results accumulating in GitLab, extracts knowledge from them, and compares it with existing knowledge to decide whether to create, update, or retire. An employee's workflow stays exactly as it is today — writing wiki pages, editing Markdown, registering Tags, classifying documents, organizing knowledge: none of it is asked of them. Employees only search and read the knowledge that finally gets produced.

The employee's role ends with the top row. The entire bottom row is AI's share.
The core concept — Event Stream and Knowledge State GitLab is the Event Stream of development changes, and the Wiki is the Knowledge State that is valid at the present moment. Commits, MRs, and Releases keep piling up in GitLab in time order, but the Wiki is not a list of history like "changes on 7/1, changes on 7/2…" — it is refined and maintained as the knowledge structure the organization needs to know right now (Architecture · Rule Engine · state systems · channel policies · Troubleshooting …).

What Knowledge State Really Is — A Deterministically Built Index

"The currently valid state of knowledge" must not be an abstract slogan but a mechanically reproducible artifact. The Reference Wiki has already demonstrated this: the metadata of every document (title · summary · concepts · relations) becomes a knowledge index JSON through a deterministic build from a single curation file, and the same input always yields the same output. That is why a single --check can decide, byte for byte, whether "the stored state has diverged from the source", and a merge is impossible while it has diverged (drift gate). A structure where a machine, not discipline, prevents the Knowledge State from falling behind the Event Stream or contradicting the source — this is the substance of the state management the company platform will inherit.

The Road the Industry Is Already On

  • Documents next to the code — Spotify runs more than 5,000 documentation sites with Backstage TechDocs, which keeps documents in the same repository as the code and builds them in CI, and GitLab is famous for the handbook-first culture of its public handbook of more than 2,700 pages. docs-as-code is an approach already proven in large organizations.
  • Automating document synchronization — Swimm commercialized "Continuous Documentation" with an Auto-sync that compares code changes against documents on every PR and updates them automatically.
  • Automatic knowledge extraction from code — Cognition's DeepWiki (2025) analyzes a repository and automatically generates a wiki containing architecture diagrams and module documents, and has indexed more than 50,000 top public repositories. GitHub made Copilot Spaces, which injects repository knowledge at all times, generally available, and Claude Code's CLAUDE.md and AGENTS.md turned "machine-read knowledge files inside the repository" into an industry convention.
  • Rapid growth of the knowledge search market — Glean, an enterprise-wide AI knowledge search, passed $200M in ARR, and Atlassian bundled Rovo into its cloud plans by default.

In short, "AI-driven automatic knowledge generation from GitLab development results" is the application of automatic extraction technology commercialized since 2025 to organizational knowledge management, on top of the proven foundation of docs-as-code.

Platform Architecture

The entire platform is built as a one-way pipeline whose source is GitLab.

Development output flows downward and becomes knowledge. The only layers employees touch are the very top (development) and the very bottom (reading).

Knowledge Generation Trigger — Only Changes Accepted as Done

Not every Commit is turned into knowledge immediately. During development, unfinished implementations, failed attempts, and temporary fixes are all mixed in. Only what passes the gate the organization accepts as done — a change that has gone through Review, been Merged into a baseline Branch, and whose Pipeline succeeded — becomes a target for analysis. Deciding what inside a completed change is knowledge and what is not (the criteria that exclude mechanical Refactoring, typos, and the like) is handled by the value assessment in the knowledge management system.

Incremental Analysis — Never Reading Everything Again

Each project keeps the SHA of the last processed Commit, and GitLab Compare collects only the files changed since then, expanding the analysis to the related Context. Reduced AI Token usage, shorter processing time, no duplicate analysis, and reprocessing after a failure all come out of this state management.

# per-project knowledge trigger·sync state (example)
{
  "project": "scm/sales-order",
  "knowledgeBranches": ["master", "release/*"],
  "lastProcessedSha": "abc123def456",
  "lastProcessedAt": "2026-07-06T14:32:00+09:00",
  "status": "success"
}

Context-based Analysis, Not a Plain Diff

You cannot judge a business policy from the single line if ("CREDIT_HOLD".equals(soStatus)). On top of the change Diff, an Impact Expansion reads the entire Class · its callers · the related Mapper and SQL · the related Test · the related Config · the existing Wiki together, so what is extracted is real development knowledge rather than a plain code summary.

Knowledge Integrity Gates — A Layer Separate from the Trigger

Pipeline success is the gate at the entrance — it only decides "is this change qualified to be analyzed". The integrity of the knowledge repository itself is guarded by a separate gate layer, and that layer is inherited as-is from what the Reference Wiki already runs in CI (How the Wiki Guards Itself):

  • State validation — broken links, duplicate IDs, orphan documents, missing index entries, and diagram bounds overflow are checked exhaustively on every commit (ERROR 0 is the merge condition).
  • Drift validation (--check) — decides whether the index, graph, llms.txt, and sitemap match a deterministic rebuild byte for byte. The machine blocks the accident where the AI Curator fixes only the document and forgets to reflect it in the index.
  • Companion gates — enforce, from the diff, the rule that "if you changed a document, the record (Work Log) and the knowledge-system update belong in the same change unit". The company KPI "knowledge reflection rate per Merge" is exactly this gate's pass rate (Roadmap).
  • Review signals (non-blocking) — for judgment areas a machine cannot enforce (for example, whether knowledge relations were reviewed from multiple angles), a checklist is raised instead of a block, inviting human review.

What the Index and Provenance of the Wiki Repository layer look like in concrete terms — which fields are already proven in practice and which fields are extended for company use — is covered by the next part, the knowledge management system.

Operational Stability — Duplication of Real-time and Reconciliation

Rather than relying only on real-time Webhook processing (Merge → Queue → Curator), a periodic Batch compares the current SHA in the Project Registry against the sync-state and reprocesses missed changes. It is a structure that copes with Webhook failures, Network errors, Queue drops, Curator outages, and transient API failures.

How knowledge is judged, structured, linked, and traced is covered in depth separately by the knowledge management system.
