Installing, Securing, and Creating Skills

Practicing with skills is almost disappointingly simple — "install this skill" is all it takes. That said, it is far more interesting when you keep the mechanics you learned earlier in mind as you use them.

Installing

  • Pressing the "Get this skill" button on a skill's distribution page copies its git address.
  • Paste that address into Claude Code and say "install this skill" and it gets installed. (For a manual install, copy it into the corresponding folder.)
  • By default it is installed in the global folder. (You can also choose project or global, but you need not worry about it at first.)
  • If it does not show up after installing, run /reload (reload plugins) or quit and restart Claude Code and it will pick the skill up. (/clear is different — it only empties the context.)

On a smartphone you can also try skills out with the Claude app (which runs in a sandbox).

Using

# Check the list of skills available to you
What skills do I have available?
# Explicit invocation
/skill-name <command>

Hands-on — an organization brand skill

Install a brand guideline skill built from the style of an institution's website, then make a request like this.

Using the <brand> brand guideline skill,
make a summer workshop page

The page then comes out in the organization's brand style rather than any old way. The point is not prettiness — it is that everyone using the same skill gets a similar style, producing consistent, reusable deliverables across the organization. In the same way you use a PPT template skill (presentation decks), a Finder skill (finding experts in the organization), and so on.

Triggering recap The reason a skill fires even when you just say "make it in the organization's style" is that the metadata description states "when using this style, use this skill." Still, to be certain it is better to name the skill explicitly.

Security Precautions

Skills are as much of a security risk as they are powerful. This is a part you absolutely must address.

Do not carelessly use other people's skills

A skill contains scripts, and those scripts carry permission to run things on my PC (laptop) as-is. So taking a skill someone else made and using it without vetting is dangerous.

  • Dangerous code can be hidden inside a skill, and there have in fact been many cases of API key leaks and security incidents (from things downloaded off MCP hubs, for example).
  • Use only certified and vetted skills, and where possible only skills vetted internally.
  • Inspection tools do exist, but then how much to trust that tool becomes another problem. In the end you need the care to check the code and guidelines yourself.
  • Rather than patching over a dangerous skill "on top," building your own with it as a reference is safer.

Permissions and sandboxes

  • Each skill can carry permission restrictions such as read-only, or write and edit allowed.
  • Absent-mindedly saying "yes" on your laptop can damage the system, so it is more stable to run risky work separately in a sandbox (VM).
  • Inside an institution, running it in a closed-network or on-premises environment is recommended. (Choose an in-house or open model as well.)
In one line A skill holds permission to run things on my computer. Never carelessly install a skill of unclear origin.

Creating Skills (Skill Engineering)

Once you have used them well, the thought "I want to make one myself" comes naturally. Making skills is called skill engineering, and a skill-making skill (skill-creator) that helps with it comes built in.

skill-creator — the meta skill

It is refined by running an A/B test loop, and is finished once it passes the benchmark.

As a skill for making skills, it comes with the following flow and subagents.

  • A create → evaluate → improve → benchmark loop.
  • evaluator, grader, comparison, and analysis subagents built in.
  • Drop in a script and say "turn this into a skill," and it builds a solid one through its own loop and testing (A/B).

Two categories

TypeWhat it coversAs models advance
Capability-boosting skillsPDF manipulation, document generation, complex file conversion, and the like. Built as scripts so they run deterministically and reliably.Once the model gets good at it, they may become unnecessary
Organization-internalizing skillsThe organization's responsibilities, workflows, owners, and so on. Our internal knowledge, which the agent does not know.Irreplaceable no matter how much models advance — keep building them
Emphasis — keep building organization-internalizing skills Make good use of capability-boosting skills now, but do not assume they will "last forever" — view them as something you can retire as models advance. Organization-internalizing skills, on the other hand, cannot be replaced no matter how far LLMs advance, because they cannot stand in for our organization's responsibilities, flows, and owners, so building them continuously is the heart of agent governance.
Distribution is easy One of the biggest advantages of skills is distribution. Register one in a shared repository, server, or community and version management and sharing become easy: copy "Get this skill" → say "install it" once, and it spreads across the whole organization. Editing the file on the spot and redistributing it is possible immediately too.

Wrap-up — Engineering Layers and Q&A

The layers of engineering

Sort what we have learned so far by purpose and, instead of "it's all engineering," the distinct grain of each becomes visible.

EngineeringPurpose
Prompt engineeringMaking the LLM smart
Context engineeringRaising the odds that the context is right
Agentic engineeringMaking the AI do the work well
Harness engineeringMaking it something you can trust and delegate to

A harness can be seen as a meta skill loaded with skills + subagents. With the concept of skills in hand, you can look at a harness understanding that it is complex inside even though it looks easy on the surface.

MCP vs skills

MCP is a protocol — a convention for connecting external tools with agents, so its loading and usage differ from skills. They are not competitors: if a skill needs an external connection it can use MCP, so MCP can live inside a skill. That said, skills are so powerful that cases of replacing MCP with skills are increasing too.

Q&A takeaways · Downloading open skills carelessly is not safe — only vetted ones.
· When there is an MCP function and a skill with the same name, which one wins depends on the situation, so be explicit ("use this skill") or separate them with namespaces.
· Evaluating skill performance — decide metrics first, such as whether it triggers well and whether the result is useful, then check with an LLM judge and by eye.
· Tokens — Claude Code uses more than regular Claude, but it can be more useful if it gets you the result you want in one go. Do not look at tokens alone; choose holistically.
