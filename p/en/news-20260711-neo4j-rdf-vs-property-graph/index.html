RDF or Property Graph — Two Models for a Knowledge Graph (Neo4j)

A document that organizes Jim Webber's article “RDF vs. property graphs: Choosing the right approach for implementing a knowledge graph” (2024-06-04), written by Neo4j's chief scientist. As generative AI drives demand for knowledge graphs up again, it compares, following the author's argument, the fundamental choice you face when actually implementing a knowledge graph — RDF (triples) from the 1990s semantic web, or the property graph of modern graph databases. Why Knowledge Graphs Now

As the generative AI market exploded (3,600% year over year by O'Reilly's count), demand for knowledge graphs came back to life. Knowledge graphs are strong on highly connected, heterogeneous data, so they are a good fit for grounding LLMs in facts. Independent research from data.world and Microsoft also pointed out the benefits of using knowledge graphs for RAG. Yet building and operating a knowledge graph brings countless design decisions, and the first fork in the road is RDF or property graph.

What a Knowledge Graph Is — Entities · Relationships · Organizing Principle

A knowledge graph is a semantically rich data model for storing, organizing, and understanding connected entities. It consists of three elements.

  • Entities — the data of the organization or domain.
  • Relationships — how entities interact with and relate to each other. They give the data context.
  • Organizing principle — meta-information about the core concepts. It acts as a contract (meta layer) between the data and its users.

The key is picking the complexity of the organizing principle to fit the job. The author says that range is wide, going from simple labels (node labels + named relationships) → a product hierarchy (Product Line → Category → Product) → a full ontology (the entire business vocabulary) — a heavy ontology is not always the right answer.

A knowledge graph's “organizing principle” is a spectrum — from simple labels to a full ontology, only as much as you need.

RDF — Triples and the Semantic Web

RDF (Resource Description Framework) is a W3C standard for exchanging data on the web. Its basic unit is the triple — a sentence made of three parts, subject, predicate, and object, each identified by a URI. The subject is a resource (node) of the graph, the predicate is an edge (relationship), and the object is either another node or a literal value.

The dream of the semantic web, and triple stores RDF became known together with the semantic web — the dream of putting machine-readable data with well-defined meaning onto the public web so that software agents could treat the web like one enormous distributed data structure. The idea was to combine metadata (ontologies) with a query language (SPARQL) and infer knowledge from web data. That dream never came true, and the technology flowed into “triple stores” applied to local databases. Pushed aside back then because SQL was dominant, triple stores were re-marketed as “a kind of graph database” along with the rise of graph DBs. Their query language is SPARQL, which reasons over triples according to ontology rules.

RDF's Practical Limits

RDF was not designed with database systems in mind, so implementation is awkward. The essentials the author points out:

  • It cannot distinguish unique relationships of the same type — even when two nodes are connected several times by relationships of the same type, RDF collapses them into a single triple. Expressiveness is limited.
  • Relationships are not first-class citizens — relationships are hidden inside triples, so to attach properties to a relationship or express multiple relationships of the same type you have to create more nodes and triples (the same detour as a join table in a relational DB). Example: to store mutual-follow multiple relationships in a social network, triples keep multiplying. The model gets verbose and complex, and maintenance becomes a chore.
  • SPARQL is not guaranteed to terminate — an ontology makes the data “smart”, but there is no guarantee the query will finish, so a user may wait indefinitely for an answer.

There are three practical burdens of the ontology-driven approach itself, too.

BurdenDetail
Skill barrierAcquiring the expertise to build a standard ontology takes great time and effort, and it is so specialized that it is hard to transfer within an organization.
Resource intensiveBuilding an ontology takes a long time and you can only deploy once it is finished, so time to business value is greatly delayed.
Lagging realityThe business moves faster than the ontology is updated, so the ontology is always behind → the knowledge graph reflects “the business of the past”.

Even so, RDF does have places where it fits — an ontology as a bridge for exchanging information between two well-understood local domains. And the author adds: since an ontology is ultimately a graph, it can be used outside the semantic web stack as well.

The Property Graph — Store It the Way You Draw It

A property graph organizes information as nodes, relationships, and properties.

  • Node — marks its role with one or more labels and holds arbitrary properties (key-value).
  • Relationship — a directed, named connection between two nodes. It always has a direction, a type, a start node, and an end node, and like nodes it can have properties. Even though it is directed, it is traversed efficiently in both directions.
  • Property — a key-value attached to both nodes and relationships.

The design principle is to store it in a form as close as possible to the logical model — exactly the picture you drew on the whiteboard. In a native property graph like Neo4j, the physical storage model is isomorphic to the logical model: “what you draw is what you store”. The query language is GQL, the ISO standard for property graphs, and the most widely used implementation is Cypher. Unlike SPARQL, Cypher and GQL are declarative languages focused on pattern matching rather than inference, so queries usually finish in time proportional to the size of the graph.

The same “property on a relationship”: the property graph puts it on the relationship in one go, while RDF, where relationships are not first-class, expresses it by adding a new node and triples.

Advantages of the Property Graph

The property graph was designed not as a data exchange format but as a DB model for applications and analytics. Unlike RDF it handles many-to-many and multiple relationships of the same type with ease, and because it is not locked into a predetermined structure you can grow the knowledge graph incrementally. Four advantages the author lists:

AdvantageDetail
SimplicityStand it up and use it fast — low complexity for beginners and experts alike.
DetailedHolding data on both nodes and relationships so entities and connections reflect the business accurately.
InteroperableNeo4j consumes and produces RDF to work with existing triple stores, and also integrates with modern systems such as relational and document DBs.
StandardsWith ISO GQL, graphs get the same confidence relational DBs enjoyed with ISO SQL.

Cases — What the Property Graph Achieved

  • NASA — project data going back to the late 1950s lay buried in organizational silos, so it moved its DB to a property graph holding millions of historical documents. Engineers find trends and lessons in past projects to prevent disasters — saving millions of dollars and years of R&D in preparing the “Mars mission”.
  • Basecamp Research — built the world's largest knowledge graph of Earth's biodiversity with Neo4j. Linking biological, chemical, and environmental data, it expanded known proteins by 50% and recorded more than 5 billion biological relationships — an excellent resource for protein design and generative AI.
  • Novo Nordisk — drives StudyBuilder with a Neo4j-based knowledge graph to streamline clinical data collection and reporting. Navigating tangled data standards such as CDISC, SNOMED, and UCUM, it secured end-to-end consistency, compliance, automation, and reuse (released as open source).

Conclusion — Property Graph by Default, RDF's Organizing Principle Layered On When Needed

Model choice depends on the situation, but if you can choose freely, you will usually pick the property graph for its simplicity and agility — the ecosystem of tools, literature, training, people, and ISO standards is broad too. Graphs have advanced greatly since the semantic web era, and modern best practice takes from both schools. The author's recommendation is clear:

The author's recommendation Keep the property graph as the default, and when the system needs it, layer on the organizing principles of the RDF world (taxonomies and ontologies) — not as a technical precondition.
It is not either/or — the property graph as the default, RDF's organizing principle as a layer added when needed.

Glossary

TermMeaning
Knowledge graphA semantic data model that stores and makes sense of data connected by entities, relationships, and an organizing principle.
Organizing principleMeta-information about core concepts — from simple labels to an ontology. A contract between data and users.
RDF · triple · URIA W3C standard for exchanging data on the web. Subject–predicate–object triples, each element identified by a URI.
Triple storeA store applying RDF/semantic web technology to a local DB. Queried with SPARQL.
SPARQLThe W3C query language for RDF. Reasons on top of ontology rules — with no termination guarantee.
Property graphMade of nodes (labels), relationships (direction, type, properties), and properties. Logical = physical, isomorphic.
Cypher · GQLProperty graph query languages. GQL is the ISO standard, Cypher the representative implementation. Centered on pattern matching.
Ontology · taxonomySystems of concepts, vocabulary, and classification. Can be layered onto a property graph as an “organizing principle layer”.

Summary — In Three Sentences

  • A knowledge graph is made of entities, relationships, and an organizing principle, and the complexity of the organizing principle is chosen to fit the job.
  • RDF is strong on standards, interoperability, off-the-shelf ontologies, and semantic data, but relationships are not first-class (triples and nodes multiply for multiple relationships and relationship properties) and it carries the burdens of SPARQL's lack of a termination guarantee and the cost of maintaining ontologies.
  • The author's recommendation is to use the property graph as the default and, when needed, layer RDF's taxonomies and ontologies on as an organizing principle — not as a precondition.
