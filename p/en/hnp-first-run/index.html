First Harness Run — Sales/Order Customization

Let us actually run it once. The example is a situation where a client request (CR) is reflected into the ERP sales/order module. There is exactly one key point — you give an "intent", not a "command".

Today's example (CR) Client request: "Automatically put orders that exceed the credit limit for the account's credit grade on hold, and send a notification to the sales rep." Because it is a customization that touches the standard package, impact analysis and regression tests are essential.

The run lifecycle — what happens in order

The only points where a person steps in are ① the intent and ④ the approval.

Step 1 — writing the intent sentence

This is the most important habit. Write it not as "do this for me" (a command) but as "we would like to do this" (an intent). Only then does the harness have room to design the team itself. After typing /harness, autocomplete with Tab and then append your request.

/harness In the ERP sales/order module, we would like to proceed with a client
customization that automatically puts orders exceeding the credit limit per the
account's credit grade on hold and sends a notification to the sales rep.
Please include standard source impact analysis and regression tests as well.
Tips for giving a good intent (essential for beginners) If you pack ① the goal (what) · ② the target module (where) · ③ the constraints (minimize damage to the standard · upgrade compatibility) · ④ the deliverables you want (impact · tests) into a single sentence, the team composition comes out accurate. For detailed background see Agent · skill design.

Steps 2–3 — domain analysis & team proposal

When you press Enter, the harness analyzes the domain and along the way asks you to choose between things like "build the full harness / build only the harness". If you have a standard specification or requirements document to refer to, you can feed it in at this point (it handles even hundreds-of-pages PDFs). Right after that it proposes a draft agent team. For example:

Proposed agentRole
Sales standard-source analystGrasps the credit and order flow and the scope of impact of the customization
Customization designerDesigns an extension approach that does not modify the standard directly (e.g. an add-on)
Development agentImplements the hold handling and notification logic
Regression QA agentVerifies that the standard order and credit features are not broken

Step 4 — review, then "go ahead"

Here a person steps in. You look at whether the proposed team is appropriate, and if it falls short you ask for changes. If it is fine, you approve with one word.

go ahead

From this moment the work leaves human hands and proceeds in the order the orchestrator planned.

Step 5 — parallel autonomous execution (observing)

  • The agents work in parallel. With Shift + arrow keys you can peek into what each agent is doing (an agent that is working is marked with color).
  • If you want to run another task at the same time, open one more terminal window and run a separate harness.
  • The loop of development → QA → (when a problem is found) rework turns automatically.

Step 6 — checking the deliverables

When it finishes, a _workspace folder appears in the project and documents like the ones below pile up (the names are examples to aid understanding; in reality the harness names them as planned).

  • Requirements write-up — organizes the CR into a developable specification
  • Standard source impact — which standard features and screens are affected
  • Customization design — an extension approach that does not modify the standard directly, with upgrade compatibility considered
  • List of implementation changes — what was changed and how
  • Regression test results — classified as critical / major / minor
  • Migration guide — the procedure and cautions for applying it to production
Remember — it is a draft A harness result is not a finished product but a well-prepared draft. For ERP customization in particular, a person must always review the standard impact and the regression results before applying it. Ways to make verification more solid are covered in Verification · quality. For what happened inside, see how it works.
