Oracle Ontology and Property Graphs — Turning Tables into a Map of Knowledge

A document that organizes Oracle's ontology and property graph approach. It compares the two branches of graphs, RDF and the property graph, covers how to link scattered relational tables (RDB) by entities and relationships into a “map of knowledge” (an ontology in the broad sense), and follows the flow from querying that inside Oracle DB with PGQL and SQL/PGQ all the way to natural-language questions with Select AI. The technologies (Oracle Graph, PGQL, SQL/PGQ, Graph Studio, Select AI) were grounded by checking the official documentation, and terms you may be hearing for the first time are unpacked in each section and in the glossary at the end.

① Two Branches of Graphs — RDF vs the Property Graph

The starting point is putting RDF and the property graph side by side. Both are graphs that see data as “dots and lines” (entities and relationships), but they have different characters.

Term — RDF and the triple RDF (Resource Description Framework) is a standard that expresses every fact strictly as three pieces — subject–predicate–object, that is, a triple (e.g., “Wine1 – origin – France”). It is closer to a vocabulary or lexicon that defines rules and concepts, so it is strong at reasoning about meaning formally (inference).

The property graph is more flexible. It expresses data as three things: nodes, edges, and properties.

  • Node (= vertex) — a single subject. An entity such as a person, event, or thing. (e.g., ‘Lee Mong-ryong’, ‘Seong Chun-hyang’)
  • Edge — the relationship that connects one node to another. (e.g., ‘married’)
  • Property — an attribute attached to a node or edge. Unlike RDF, a flexible value that may or may not be present. (e.g., gender=male, age=20)
  • Label — a name tag (type) attached to a node or edge. (e.g., the node label ‘Person’)

The key difference is where you put the attributes. To express the same wine table, RDF pulls every single column — type, importer, vintage, origin, price — out as an edge, so five lines hang off one node; as the data grows it becomes sharply more complex and heavier. The property graph puts the values that need no traversal, such as vintage and price, inside the node as properties, and leaves only the values to be shared and traversed, such as origin and importer, as edges. As a result the number of lines (edges) drops, which is cleaner, and connection traversal gets faster for questions like “only French wines” or “only wines from the same importer”.

The difference is where the properties sit — RDF pulls them all out as edges, which is strict but heavy; the property graph leaves only what must be traversed as an edge and stays light.

② Why the Property Graph — Following Connections Instead of Joins

The usefulness of the property graph shows up in relationship traversal. Two representative examples:

  • Bank transfers — given an account table and a transfer table, to see “is account 1 connected to account 833?” in an RDB you have to follow the transfer records with repeated joins in SQL. With a graph, making accounts nodes and transfers edges lets you visualize the path as it is, so which accounts it passed through is intuitively visible.
  • Retail orders — asking “what else did customers who bought chocolate buy?” across customer, order, and product tables takes several joins in SQL, but a graph sweeps product→customer→product straight along the edges.

What they have in common is that they are “questions where connection matters”. Uses by industry: finance (fraudulent transfer and money-laundering detection), retail (purchase-pattern clustering and recommendation), hospitals (movement paths of similar patients), manufacturing (part hierarchies, failure propagation, supply-chain impact), networks (fault routing in telecom, traffic, and road networks; root-cause tracing of cloud outages). Anywhere data is connected and interdependent is a fit.

③ What Is an Ontology — Broadly, a ‘Map of Knowledge’

This is the conceptual center of the article: there is no need to view ontology in the difficult sense of “semantics and the OWL standard” only.

Term — ontology (broad sense vs narrow sense) Narrow sense: a system that formally defines the grammar, vocabulary, and semantics of concepts with the W3C standard OWL (Web Ontology Language) and even performs inference — the rigorous ontology of the RDF family.
Broad sense: the graph itself, which links the entities and relationships of scattered tables, is also seen as a “layer of knowledge” and called an ontology. (Much of what Palantir calls an “ontology” is this connectedness too.) What matters is not the formal standard but the fact that distributed business data becomes one map of knowledge.

In practice, then, the broad sense is the useful one. Most workflows and business tasks are managed as tables (entities), and if you explicitly link the relationships between those entities, what was fragmented table by table becomes a map of knowledge you can view as interconnected. If you do not need RDF/OWL's formal inference, a property graph alone gives you a practical “knowledge layer”. (When formal semantics and inference really are required, RDF/OWL has the advantage — the two approaches are not mutually exclusive.)

④ Building the Graph — With Metadata, Without Copying Data

The most practical part. A property graph does not physically copy the data. It lays a graph ‘view’ made purely of metadata on top of existing RDB tables. With a CREATE PROPERTY GRAPH statement, you:

  • designate the tables that will become nodes and pick the key (account number, etc.) and the properties you need (e.g., bank account → node, key=id, properties=name·balance).
  • designate the tables that will become relationships as edge tables (“H tables”) and decide, via source key and destination key, which node connects to which node (e.g., bank transfer → edge, source=sending account, destination=receiving account).
Term — the edge table (H table) and “no FK needed” A separate table that holds relationships is commonly called an H table (edge table). A traditional RDB expresses relationships between tables with a foreign key (FK), but the source/destination keys of a property graph can be designated even without a PK–FK constraint in place. In other words, you can lay a graph on top even if FKs are not tidied up in the existing schema.

A practical tip: writing edge (H) tables by hand is tedious, but if you hand over the table information and the existing relationships, an AI such as ChatGPT or Claude will suggest “build it like this”. On Oracle Autonomous DB there is even a feature that, given schema (ERD) information, helps automatically generate the graph.

A graph is not a new store but a view over existing tables — designate the node tables plus the edge (H) tables and you are done.

⑤ Querying the Graph — PGQL, SQL/PGQ, and the ‘Hop’

There are two languages for putting questions to the graph you built. Both are SQL-based, so you use SELECT and WHERE as they are and write the graph pattern in a MATCH clause.

Terms — PGQL · SQL/PGQ · hop PGQL (Property Graph Query Language): an open graph query language created with Oracle's participation. Strong when running algorithms on the graph analytics engine (PGX).
SQL/PGQ: the graph query feature folded into the ISO SQL:2023 standard (Part 16). It uses the GRAPH_TABLE(...) operator plus a MATCH pattern. It runs directly on the SQL engine, so it is faster.
Pattern notation: nodes in (parentheses), relationships in [brackets], -> when directed and - when not.
Hop: crossing a relationship once. {1,3} means a path “connected even by way of 1 to 3 crossings” — it finds transfers that went through several intermediate accounts too.

Thanks to this ‘hop’, complex connection analysis is expressed in a single line. Three representative financial queries:

  • Direct transfer — return accounts that transferred even once (source→destination, 1 hop).
  • Multi-step transfer — {1,3} hops: even paths transferred through 1 to 3 intermediate accounts. Used for money-laundering detection.
  • Cycle (loop) detection — accounts where the start and the end are the same (e.g., money that came back to me after 5 hops). The core of detecting laundering rings.

Written in traditional SQL the same query balloons into countless joins and unions, but SQL/PGQ needs only one MATCH line — this is the core value of graph queries (expressing complex connections concisely and intuitively).

One hop notation opens up direct→multi-step→cycle analysis — money-laundering detection is the representative case.

⑥ Graph Algorithms — Some 80 Built-in Analytics

Graphs go beyond “finding” to “analyzing”. Oracle DB has about 80 graph algorithms built in, covering nearly all the famous ones. Four broad branches:

BranchWhat it findsUse
Community detectionTightly connected groups (clusters)Clustering retail customers with similar purchases
CentralityThe key, influential nodes of a networkIdentifying influencers and hub accounts
Structure identificationRecurring patternsDetecting fraud and money-laundering patterns
PathfindingConnecting paths between two nodesFund tracing · shortest path

Drawing out insights hidden inside patterns, beyond simple connections, is the greatest value of the property graph. That said, algorithmic analysis (especially at large volume) runs in parallel on a separately stood-up in-memory graph server (PGX), so it takes more time than a simple lookup.

⑦ Select AI — Asking the Graph in Natural Language

The key direction: rather than users writing PGQL or SQL/PGQ themselves, let AI generate it automatically. Oracle's Select AI provides this built into the DB. It turns natural language into a graph query, and the key to it is metadata.

Terms — Select AI · AI profile Select AI: a feature where you put in natural language, as in SELECT AI <natural language>, and the DB converts it to SQL (tables) or SQL/PGQ (graphs) and runs it.
AI profile: since Oracle does not provide its own LLM, you register in a profile which model to use and which schemas and objects to target. At query time that object's metadata (DDL for tables, the CREATE PROPERTY GRAPH statement for graphs) is passed to the LLM automatically so it produces an accurate query.

The flow is natural language → (AI profile: model + target metadata) → the LLM generates a GRAPH_TABLE query → the SQL engine executes → results. Supported actions: runsql (run it right away) · showsql (see the generated query) · explainsql (why it came out that way) · narrate (put the results into words) · showprompt (the prompt that actually went to the LLM — the CREATE PROPERTY GRAPH statement goes in there verbatim).

Feature scope and limits (mind the point in time) Natural-language generation supports SQL/PGQ only (PGQL is not covered) → another reason to go with SQL/PGQ. Generating synthetic (fake) test data, or combining graphs and tables in one query, is still limited. For natural language to produce good queries, tables and columns must carry comments (descriptions), and handling Korean and synonyms is supplemented with description properties and AI agents. (Select AI features are updated quickly, so re-check the latest docs when adopting.)
The user only throws natural language, and an LLM loaded with the metadata writes the graph query instead — the key to accuracy is “a schema with descriptions”.

Above all, defining “the business task (question) you want to solve” first is the starting point of graph design — because a graph is not a storage structure but a view you build per question.

Summary — In Three Sentences

  • A property graph links scattered tables by entities and relationships into a “map of knowledge” (an ontology in the broad sense), but lays it on as a metadata view without copying data.
  • Questions where connection matters (money laundering, recommendation, outage tracing) take one line of MATCH and hops instead of SQL joins — SQL/PGQ is both the standard and the fast path.
  • Do not write queries by hand; generate them from natural language with Select AI — the key is “metadata with descriptions”.
