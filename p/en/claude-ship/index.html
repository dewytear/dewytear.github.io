Claude Ship — Three Agents That Carry a PR to Merge: How to Use It and What You Gain

Three-line summary

  • Claude Ship is a bundle of agents for the work that starts after a pull request (PR) opens. Code Review finds problems, PR Steward pushes commits that fix failing checks, merge conflicts and review comments, and Claude Approvals reports "who still has to approve" according to a policy the team writes as a file. It launched on November 23, 2026 in beta for Team and Enterprise plans.
  • An individual developer types /ship in Claude Code and gets commit, push, PR creation and review in one go, followed by a "watch" in which Claude handles failing checks and review replies. A person still clicks merge.
  • The gain is review that keeps pace with how fast code is written. Anthropic says merged PRs on its own Claude Code team more than doubled from June to September while the share reverted fell by more than 40%. The flip side is that one line in the policy file can allow a merge no person looked at, so starting in observe mode and under branch rules is the order that matters.

Coding agents write code faster than before, but reviewing and approving that code is still tied to people's time. You open a PR and move on, a review arrives days later, you return to old code, push a fix, wait for checks again and look for someone to approve. That is the problem Anthropic names when it introduces Claude Ship. This page draws on the official docs and the announcement to set out what each of the three agents does, how an individual and an organization each use it, what the benefits are and where to be careful. This wiki is itself a repository where Claude Code writes documents and merges through PRs, so the end of the page reads the product against that flow.

Code Review is the existing product that reached general availability on October 15, 2026; PR Steward and Claude Approvals are the new beta agents. The three are switched on separately, repository by repository.

Code Review's four stages deserve a look. Several agents search for candidates in parallel (Find), candidates are checked against the code to drop false positives (Verify), duplicates are merged and ranked by severity (Rank), and the result goes up as inline comments and a check run (Post). Because a verification step sits between finding and posting, the design targets the usual complaint about review bots, noise. Severities are 🔴 Important (fix before merging), 🟡 Nit (minor) and 🟣 Pre-existing (not introduced by this PR). A re-review looks only at what changed since the last one and posts fewer Nits and Pre-existing findings.

2. For one developer: the /ship line

Even with nothing switched on by an administrator, a developer can use /ship in a terminal Claude Code session. It counts as ordinary Claude Code usage. Prerequisites: Claude Code 2.1.330 or later, GitHub CLI 2.63 or later signed in with gh auth login, and git 2.38 or later.

  1. Type /ship in the session where you made the change. The commit message is written from the conversation, so a different session yields a title like "Update greet.py and 1 more".
  2. There is no confirmation prompt. Before the commit and again before the push a line ending "Esc to cancel" shows for a few seconds, then it proceeds. On the default branch it creates a new branch and switches to it; work already committed on another branch is pushed as that branch and a PR opened.
  3. It reviews with /code-review. Put the effort level first, as in /ship low (default high).
  4. A watch starts. In auto mode Claude fixes review findings without asking, merges the base branch to resolve conflicts, works on failing checks and re-runs them, answers review comments, resolves threads and re-requests reviews. Everything appears on GitHub under your own name.
  5. When checks pass and comments are answered, Claude says so. You merge.

If a PR is already open, /steward skips commit, push and review and only starts the watch. While watching and acting without a message from you, Claude Code blocks gh and git commands that merge, approve, turn on auto-merge or force-push, and refuses connectors, WebFetch and WebSearch. git stash, git reset, git checkout, git add -A and git commit -a are refused as well. A watch ends when the PR merges or closes, after seven days, on one press of Esc, on a branch switch, on /clear, /resume or /branch, or when the session ends. A .claude/skills/steward/SKILL.md in the repo gives the watch and PR Steward the same house rules.

What it will not do automatically is equally clear. It does not commit uncommitted changes on a branch that already has a PR, in a public repository, or when a file's name looks like a secret (.env and the like). If you changed .gitignore, CLAUDE.md or anything under .github/, it asks you to commit yourself. It does not open PRs on GitHub Enterprise or from forks, so open the PR first and then run /ship. No watch starts on native Windows or in bypassPermissions mode.

3. For an organization: one agent at a time, one repository first

An Owner of the Claude organization switches it on at Organization settings › Claude Ship. The order the official docs recommend is one agent at a time, starting with one repository.

The order is taken from the official setup docs. Turning off must run Approvals → PR Steward → Code Review, because a policy file can start billed reviews on a repository where Code Review is off.

The policy file is "a smarter CODEOWNERS"

The heart of Claude Approvals is .claude/approvals.yml at the repo root. Each rule has path patterns, a condition and a verdict. The verdict says how far Claude goes (comments, approves or blocks) and how many people's seats (seats) are needed. The two starter examples from the official docs, verbatim.

# .claude/approvals.yml — A: one person is enough when the review passes, and Claude approves
version: 1
mode: observe
rules:
  - purpose: "A change takes two people. When Claude's review passes, one is enough and Claude approves."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    override:
      - { if: "claude/code_review = pass", verdict: { claude: approves, seats: 1 } }
  - purpose: "A change to the review rules takes two people."
    paths: ["**/.claude/**"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }
# .claude/approvals.yml — B: two people on every change, Claude only advises
version: 1
mode: observe
rules:
  - purpose: "A change takes two people."
    paths: ["**"]
    verdict: { claude: comments, seats: 2 }
    advisory: [claude/code_review]
  - purpose: "A change to the review rules takes two people."
    paths: ["**/.claude/**"]
    nested: inherit
    verdict: { claude: comments, seats: 2 }

How to read it: seats: 2 means two human seats, and the author can fill one, so it is "author plus one". To exclude authors, write seats: [{ count: 1, from: [humans, "!pr/authors"] }]. override changes the verdict when its condition holds, and if a classifier gives no answer the rule's own stricter verdict stands. When several rules overlap, the strictest wins (blocks > comments > approves). Conditions can use PR facts such as pr/files_changed > 50 and classifier answers. Two classifiers come from Anthropic: claude/code_review answers pass or fail depending on whether an Important finding is still open, and claude/diff says whether a push changed the PR trivial, same_intent or different. You write your own in .claude/classifiers/<name>/def.yml as a natural-language prompt with declared outputs, for instance a risk rating that says "high if it touches sign-in, billing or a migration", and then let repo/change_risk = low drop the requirement to one person.

Policy files, the classifier folder, REVIEW.md, CODEOWNERS and .gitmodules are protected files that Claude never approves. On a PR, developers use comments: @claude approve to register their own approval, @claude approvals rerun to re-evaluate, and @claude approvals resolve f-… to close findings when the policy's list names them. The check title is the status, read as "Waiting on human review from any person (1/2)", "Held by Code Review's findings" or "Passed; no approval from Claude".

4. What actually gets better

  • Review keeps up with code. Anthropic reports that on its Claude Code team merged PRs more than doubled between June and September 2026 while the reverted share fell by more than 40%. The same post adds that Code Review is one layer of a broader process on that team, so the numbers are not the three agents alone.
  • A false-positive filter is built in. Candidates are verified against the code before posting, and re-reviews look only at what changed. The noise that makes teams switch review bots off is handled in the product's structure.
  • The power to approve is separated. The fixing agent (PR Steward) cannot approve or merge, and Anthropic's service refuses the request itself. The judging agent (Approvals) follows only the file the team wrote, and its power to block comes from GitHub's required-check setting. That separation is the answer to "AI approving AI code".
  • Policy becomes code. Who, how many, on which paths and under what conditions is written in approvals.yml, and that file is itself protected, so changing it takes two people again. Observe first, enforce later is the default path.
  • Cost has ceilings. A monthly limit for Code Review, a monthly limit and per-repo cap for PR Steward, and a classifier limit are set separately. At the limit, reviews are skipped and the PR says so.
  • It sits on existing rules. It works with branch protection, required checks, CODEOWNERS and auto-merge. In the customer quotes Anthropic published, TELUS's director of engineering said they keep a human in the loop and the human's time now goes to the changes that need it, and Carvana's SVP of engineering and analytics said teams in their pilot spend less time working through review feedback.
  • No Claude Code required. Code Review, Steward and Approvals run as a GitHub App, so they attach to code written with any tool. Anthropic's split is that Claude Code works before the PR and Claude Ship after it.

5. Where to be careful

  • One policy line can allow a merge no one looked at. With seats: 0 a bot-written PR can merge unseen, and seats: 1 can be filled by the author. Where a GitHub branch rule requires one approval, Claude's approving review can be that one. In a repository with auto-merge or a merge queue, Claude's fix pushes can trigger the merge. The official docs warn about every one of these.
  • Classifiers read what the PR author wrote. The docs state that titles, descriptions and comments can steer a classifier's answer, and that classifiers should not get label or reviewer write access where a label gates a deploy.
  • A watch runs code on your machine with your credentials. Scripts that arrive when the base branch is merged in, other people's pushes to your branch, hooks and SKILL.md can all execute. The official advice is to run a watch only where you trust everyone who can merge to the base branch or push to yours.
  • Self-hosted runners cannot refuse approvals. If PR Steward runs on your own runner, Anthropic's service cannot block an approval request, and GitHub may count it toward required approvals. It also does not read CLAUDE.md there.
  • Observe mode costs money. A policy that uses claude/code_review as a condition starts a review on every push, and classifiers are billed even when they give no answer. Set per-run budgets (budget: { cost: 5 }, default and maximum 10 dollars) and monthly limits first.
  • The difference from rivals is approval. Comparison write-ups classify GitHub Copilot code review, Cursor Bugbot and Codex review as advisory tools that neither block nor approve on their own. Claude Ship goes as far as approval where the policy allows, so the convenience comes with a heavier policy file.

6. Read against this wiki's PR flow

In this wiki a Claude Code session writes documents and opens a PR, and the operator has to answer "merge" before a squash merge happens. CI runs four gates (nine Python checks, diagram bounds, multilingual render, build). Translated into Claude Ship, that is close to starter B: one human seat on every path, CI as a separate required check, and Code Review in advisory so document PRs do not bill code reviews. As a content repository, Code Review's "logic error" lens does not fit, so REVIEW.md would have to narrow its scope, and the "failing checks" PR Steward would handle are mostly diagram text overflow or missing translations, where a human judgment beats a fix commit. What is usable right away is the part of the /ship watch that re-runs and fixes CI failures on the Claude Code session's side.
