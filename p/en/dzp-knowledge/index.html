Knowledge Management System — Assessment · Structure · Connection · Tracking · Trust · Lifecycle

If the pipeline is what produces knowledge, this part covers what structure that knowledge is held in, how it is connected, and how it keeps its trustworthiness. The structure described here is not imagination — the Reference Wiki built for advance validation runs at a scale of 115 documents · 370 unique concepts · 364 automatic related edges · 114 typed knowledge relations as of 2026-07, and its schema, verified in real operation, is taken as the core, extended backward-compatibly (additive) with only the fields the company's development knowledge needs.

Value Assessment — Reuse Value, Not Change Volume

  • Turned into knowledge — a new Architecture or business Rule, a change in the meaning of a DB Table or Column, an API addition or change, a state transition change, an external system integration, a repeatable incident resolution, a common development pattern, a performance improvement case, a security policy or Dependency change, a change to an existing design policy
  • Excluded by default — variable renames, simple Null Checks, typos, comments and Formatting, plain Log additions, Test Data, one-off Debug code, mechanical Refactoring

The Atomic Structure of Knowledge — Extending a Proven Schema

A single piece of knowledge exists as three layers of attributes. The first layer is node attributes — in the Reference Wiki's navigation tree, every document node holds name (the immutable logical ID, which is also the route) and path (the physical location) as separate things. Even when a file moves inside the domain tree, only path changes while name stays immutable, so accumulated links, relations, and search do not break when files are rearranged. On top of that sit the display label (plus per-language variants), tags, and the authoring model (How Knowledge Accumulates). The second layer is the index entry — the upper part of the example below is the proven core, the lower part the company extension. The third layer (connections) is covered in the next section.

# Knowledge Index entry — proven core + company extension (example)
{
  // ── proven core: fields the Reference Wiki runs across 115 documents ──
  "name": "dz-erp-so-status-transition",   // immutable logical ID = route
  "title": "Sales order status transition policy",
  "summary": "The sales order status scheme and the shipment·revenue transition conditions",
  "concepts": ["order status transition", "credit check", "partial shipment"],  // only concepts really in the body
  "section": "Douzone · OmniEsol · SCM",   // computed automatically from the tree position
  "related": [ … ],                        // computed automatically — never hand-edited
  "relations": [ … ],                      // declared typed relations (next section)

  // ── company extension (proposed): follows schema v2's additive rule — adding fields is backward-compatible ──
  "kind": "policy",  "status": "active",  "trust": "DECISION",
  "product": "OmniEsol",  "domain": "SCM",  "project": "sales-order",
  "identifiers": ["SD_SO_HDR", "SD_SO_ITEM", "SO_STS_CD", "CREDIT_CHK_YN"],
  "sources": [{
    "project": "scm/sales-order",
    "commit": "abc123",  "mergeRequest": 382,
    "paths": ["src/.../SalesOrderService.java", "mapper/.../SalesOrderMapper.xml"]
  }]
}

The point is that the extension does not encroach on the core. The Reference Wiki's schema contract states that "adding a field is backward-compatible, changing a meaning requires a version bump", so even when company fields such as identifiers, sources, and trust are added, existing consumers — validators, build, graph, search — keep working unchanged. All that is newly built is the fields themselves and the search layer that reads them.

Two Layers of Connection — Computed Relatedness and Declared Relations

Knowledge should be a graph, not isolated cards. The Reference Wiki proved connections in two layers, and the company platform inherits them as they are (How Documents Connect):

  • ⓐ Computed relatedness (related) — symmetric connections the machine computes automatically from shared concepts. The more common a concept the lower its weight, the rarer the concept the higher (rarity · idf), and an edge is drawn only when two or more concepts are shared or when one rare concept (in three documents or fewer overall) is shared. Where connections are short, the same folder (System) fills the gap, guaranteeing 2–4 connections for every document and zero orphans. It is the layer that keeps the graph intact even when nobody adds links by hand — which matters especially for company knowledge that AI generates in bulk.
  • ⓑ Declared relations (relations) — five typed relations that carry a direction and a kind: prerequisite · implements · example-of · evidence-for · supersedes. Each relation has a direction (A→target), a one-line rationale (evidenceRef), and a declaring party (source). It is stored only once, in the forward direction; the reverse direction ("relations coming into this document") is derived automatically on the consuming side.

The exact point where the company platform and the schema mesh is the source field. The proven schema has already reserved human · ai-proposed · imported · rule-derived as the vocabulary for the declaring party (all 114 relations in the Reference Wiki are human). On the company platform, the AI Curator proposes a relation as ai-proposed, and once a person approves it, it is promoted to human — a structure that reconciles, in a single field, the speed of automation with the honesty principle of "declare only relations that really exist in the body". The machine guards integrity: a relation pointing at a target that does not exist, or a type outside the five-word vocabulary, blocks the merge as an ERROR, while a missing rationale or a conflicting declaration surfaces as a review signal (WARN).

Cumulative Updates — Growing the Density of Knowledge

Finding new knowledge does not always mean creating a new document. The Knowledge Index is searched first, and if a related document exists, the existing document is extended. For instance, when a document on the "sales order status transition scheme" already exists and a partial-shipment status is added, extending the existing document is considered before creating a new one. That is why the Wiki stays a continuously refined state of current knowledge rather than a collection of change history.

Extending an existing document is always considered first — toward more density rather than more documents.

Development Identifier Search

Developers search by Table name · Column name · Rule ID · Class name · Method name · API name · Mapper ID · Error Code more often than in natural language. The extension field identifiers above becomes the primary key of this search, and the search priority is built as ① exact Identifier match (extension field) → ② title → ③ concepts → ④ summary → ⑤ tags → ⑥ related documents (related) → ⑦ same project — ② through ⑥ all run on top of proven core fields, so the only search logic the company builds anew is ① and ⑦. A single SO_STS_CD encountered in the source should be enough to reach the relevant policy document.

Source Tracking (Provenance)

Every piece of knowledge must be traceable back to which project → which Commit → which MR → which Source File it came from, as in the extension field sources. In the Reference Wiki this principle was proven at small scale by deriving each document's creation and modification dates from Git history, and the company platform extends the unit of tracking to GitLab coordinates (commit · MR · paths). Growing knowledge through retrieval while keeping its sources is the approach established by RAG research: it is demonstrated that combining external knowledge produces more factual and source-traceable generation (Lewis et al., NeurIPS 2020) and greatly reduces hallucination (Shuster et al., 2021).

Trust Level — FACT · INFERRED · DECISION

Nothing is settled as official policy merely because it was found in code. Even recent research reports cases where the best-performing LLMs misjudge the quality and accuracy of code summaries (arXiv 2507.16587, 2025), and NIST's generative AI profile requires Content Provenance tracking and the management of "confidently stated errors (confabulation)" as core risk controls (NIST AI 600-1). The trust level is recorded in the extension field trust.

LevelMeaningExamplePublication policy
FACTDirectly verifiable in codeTable · Column · API · Class relationshipsHigh chance of automatic publication
INFERREDInferred from code structurePresumed retry purpose, presumed duplicate preventionPublished with the inference stated
DECISIONA business or Architecture decisionWhy GUID was chosen, deciding when the credit check runsPublished after extra evidence such as the MR or design docs is confirmed

Lifecycle — Superseded, Not Deleted

Past knowledge is not deleted just because a policy changed. For example, when "credit check → at sales order save" becomes "sales order save + re-verification at shipment", the existing document is switched to superseded and linked to the new policy document, so that the current policy and the change history are tracked at the same time. That link is exactly the supersedes type among the five relations — new document -[supersedes]-> old document. Interestingly, in the Reference Wiki documents are revised in place, so this type is honestly empty at zero instances (the vocabulary, validation, and UI are all in place, but no forced pairs were created). Company development knowledge, where policy changes really do happen, is the environment where this type goes into real use for the first time, and the "supersede" transition in the state machine below is precisely the creation of a supersedes relation.

A superseded document stays linked to the new one by a supersedes relation — "why it changed" is preserved along with it.
An Inherited Principle — Honesty Only the concepts and relations that really exist in the body are declared. Adding a concept that is not there, or forcing a relation, in order to increase connections distorts the graph — it is a principle the Reference Wiki has nailed down as a rule and operated by, and the validators' WARNs are not "a list of things to fix" but "a list for a human to look at once". At company scale, where AI generates knowledge in bulk, this principle matters even more — the ai-proposed → human approval flow and the non-blocking review signals are the safeguards.
