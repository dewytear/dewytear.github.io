Security Precautions

Skills are as much of a security risk as they are powerful. This is a part you absolutely must address.

Do not carelessly use other people's skills

A skill contains scripts, and those scripts carry permission to run things on my PC (laptop) as-is. So taking a skill someone else made and using it without vetting is dangerous.

  • Dangerous code can be hidden inside a skill, and there have in fact been many cases of API key leaks and security incidents (from things downloaded off MCP hubs, for example).
  • Use only certified and vetted skills, and where possible only skills vetted internally.
  • Inspection tools do exist, but then how much to trust that tool becomes another problem. In the end you need the care to check the code and guidelines yourself.
  • Rather than patching over a dangerous skill "on top," building your own with it as a reference is safer.

Permissions and sandboxes

  • Each skill can carry permission restrictions such as read-only, or write and edit allowed.
  • Absent-mindedly saying "yes" on your laptop can damage the system, so it is more stable to run risky work separately in a sandbox (VM).
  • Inside an institution, running it in a closed-network or on-premises environment is recommended. (Choose an in-house or open model as well.)
In one line A skill holds permission to run things on my computer. Never carelessly install a skill of unclear origin.
