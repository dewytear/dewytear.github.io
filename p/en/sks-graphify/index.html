graphify — A Skill That Turns a Codebase into a Knowledge Graph So Agents Query Instead of Grep

Three-line summary

  • graphify turns the code, docs, PDFs, images and video in a folder into one knowledge graph with a single /graphify ., and from then on the agent asks graphify query, path and explain for the relevant subgraph instead of reading whole files. Code is parsed locally with tree-sitter (a syntax-tree parser) and no LLM, and every edge carries an EXTRACTED, INFERRED or AMBIGUOUS confidence tag.
  • First published on PyPI on April 4, 2026, it reached 0.9.118 on November 23 after 284 releases and supports some 20 assistants including Claude Code, Cursor, Codex and Gemini CLI. Star counts differ by aggregator, from 76k to 152k, so this page says only "around 100k". The company is Graphify Labs (Y Combinator S26); the license is Apache-2.0 and MIT, dual.
  • Its official benchmark claims recall@10 of 0.497 on LOCOMO memory retrieval (mem0 0.048) and zero LLM credits to build the graph. The widely quoted "71.5x fewer tokens" is one query on a 52-file corpus; independent session-level tests found 7 to 8% savings or a quality tie (44 vs 45 points). It is strong for orientation and impact analysis in large repositories and offers little on small projects and focused edits.

The first thing a coding agent does in an unfamiliar repository is grep and read files. When the question is structural, such as "where does this endpoint reach storage", reading files one by one into context costs tokens and misses the big picture. graphify puts a graph in that spot. Built once, it survives across sessions, and each question returns a few dozen relevant nodes. This page draws on the official repository (README, ARCHITECTURE, BENCHMARKS, skill.md) and outside verification to set out how it works, how to install and use it, what the benchmarks actually mean, and its limits and security notes. This wiki itself runs on a document graph, so the end sets the two graphs side by side.

1. How it is built: three passes

Taken from the official how-it-works page and ARCHITECTURE.md. Pass 1 handles 33 languages with tree-sitter grammars and seven more (Dart, Apex, COBOL, Razor, Blade, Pascal, Robot Framework) with built-in extractors.

The core principle is "code never goes to the LLM". Functions, classes, imports and call relations come deterministically out of the syntax tree, so the same input gives the same graph, it costs nothing, and nothing leaves the machine. Only documents and images pass through a model for semantic extraction. Inside Claude Code, the session's own model dispatches parallel subagents for that; from a terminal, graphify extract uses a configured API key (auto-detected in the order Gemini, Kimi, Claude, OpenAI, DeepSeek, Azure, Bedrock, Ollama). Community detection is the Leiden algorithm (graph clustering that groups nodes by edge density), with no embeddings and no vector store. The semantically_similar_to edges the model extracts are already in the graph, so, the docs say, the structure itself is the similarity signal. Community names are derived from hub nodes without an LLM.

2. A tag on every edge: the confidence scheme

The rubric from the how-it-works page. The skill file's "honesty rules" say never invent an edge and use AMBIGUOUS when unsure. When the same relation appears in several places, the highest-tagged copy is kept and the others are recorded under also_seen.

These tags are what separate graphify from "one more search index". graphify explain "APIRouter" returns the source location, community and degree together with its 47 connections tagged like [uses] [INFERRED] and [imports] [EXTRACTED], and graphify path "FastAPI" "ModelField" returns a three-hop path with the path's overall confidence, its weakest hop. The repository's BENCHMARKS.md reports a manual audit of all 12 INFERRED cross-file edges inside FastAPI's production package, all correct, while noting that it is a dated one-off spot check rather than a continuous metric. The resolver prefers no edge over a wrong one.

3. Install and use

With Python 3.11.5 to 3.14 and uv (or pipx) it is two lines. The one thing to watch is the PyPI name graphifyy with two y's; other graphify* packages are unrelated.

uv tool install graphifyy      # install the CLI (pipx install graphifyy also works)
graphify install               # Claude Code by default: skill + CLAUDE.md block + PreToolUse hooks
graphify install --project     # into the repo's .claude/skills/graphify/ (prints a git add hint)
graphify cursor install        # Cursor
graphify install --platform codex    # Codex (invoke with $graphify)

Then type /graphify . inside the assistant. The skill first checks whether graphify-out/graph.json exists; if it does, it skips the build and goes to querying (the fast path). Otherwise it runs detection, extraction, graph build, clustering, labeling and export, reporting corpus size and token cost. The skill file itself says never to ask for an API key and to proceed without one, so a code repository needs no configuration at all.

Exit codes are fixed for scripting: 0 is an answer, 3 is a name that matches several nodes (candidates are listed), 4 is no matching node. An ambiguous name is refused rather than guessed. Project settings live in .graphifyrc at the scan root. Ambiguous extensions (is .inc PHP or Pascal, is .h C or C++) must be pinned, as in language.inc=php, or the graph comes out thin.

4. The machinery that makes the agent actually use the graph

From the README section "Make your assistant always use the graph" and the hook definitions in install.py. The hook command embeds the absolute executable path at install time, so after an upgrade run graphify install and graphify hook install again.

A graph nobody consults is useless, and how graphify handles that is what sets it apart from other code indexes. graphify install does not only drop a skill file. It writes a guidance block into CLAUDE.md and registers Claude Code PreToolUse hooks (hooks that run just before a tool call) in .claude/settings.json. The hook fires before Read, Glob and Grep, and also before Bash readers such as cat, head, tail and sed -n, nudging the agent to look at the graph first. Installed with --strict (or GRAPHIFY_HOOK_STRICT=1), it denies the session's first raw read once and redirects it to the graph, but lets it through if a graph query ran in the last 30 minutes. The denial happens once per session, so the agent is never stranded. If the graph is stale (changed since the last commit) the hook says so as well.

5. Benchmarks: official numbers and outside measurements

The table from BENCHMARKS.md (updated 2026-07-05). It states that every system ran on the same harness with the same model (Kimi K2.6) and budgets, with the judge validated against a second judge (90.6% agreement, kappa 0.81). A footnote says supermemory's recall is hard to compare because its self-hosted build locks in its own embedder. The code-intelligence row has n=6, a small sample.

Two things have to be kept apart when reading the benchmarks. First, the table above comes from graphify's own harness. Publishing fairness rules (one model, a shared embedder, spend ledgers) and reproduction commands counts for something, but it is still self-measurement. Second, the most widely circulated figure, "71.5x fewer tokens", comes not from the benchmark table but from the token comparison on the how-it-works page. That corpus is three Karpathy repositories plus five papers and four images (52 files), at about 1,700 tokens per query against about 123,000 for the raw files. The same page gives 5.4x on four files and about 1x on a six-file library: a small corpus fits in context anyway, so the value there is structure, not compression.

Official figures from the how-it-works page; independent measurements are the values cited in write-ups found by search (the Exchangepedia, Medium and KubeBlogs figures as quoted by the Zero-to-Hero guide). Most originals could not be opened from the environment this page was written in, so the guide's citations are carried over as given.

6. Strengths and limits

StrongWeak
Entering a large repository. Hubs and communities give the structure first, and "from this endpoint to storage" becomes a pathSmall projects. When the files fit in context anyway, query overhead can raise token use
Impact analysis and onboarding. A shared component's callers and dependencies in one list, with # WHY: comments and ADRs linked to the code as nodesFocused edits. Fixing a few files is faster with plain rg, and agents do exactly that
Doc-heavy repositories. PDFs, papers and video enter the same graph, so the link between code and design docs showsStale graphs. Hooks do not cover pull or merge, so forgetting graphify update . means carrying a wrong map (new directories not discovered, #1837, and others)
Verifiability. Every edge has a tag and a file:line, so an answer can be checked against the sourceGraph answers are "context, not verified answers". INFERRED edges can be wrong, and same-named helpers in test code add noise
Cost. The code graph is free and offline, and re-runs skip by hashThe semantic pass sends docs and images to the configured model. Choosing Kimi sends them to Moonshot's servers. A log at ~/.cache/graphify-queries.log keeps your questions (can be turned off)

On security, version 0.9.115 of November 21, 2026 fixed a Windows issue where a path inside the repository (such as source \\host\share\x in a .sh file, a UNC path) was stat'ed outside the scan root and could force SMB authentication (GHSA-g6c9-j4vm-mwq4). A tool that graphs unfamiliar repositories can hit this class of input-handling problem, and staying current is the answer. The skill file itself passes the scan path through a quoted heredoc rather than substituting it into the shell, so shell code hidden in a path does not execute. For a shared HTTP MCP server set --api-key, and gitignore graphify-out/cache/, manifest.json and cost.json.

7. Side by side with this wiki's graph

This wiki has its own knowledge graph linking 79 documents through three layers: shared concepts, citation backlinks and declared typed relations (the three layers of connection). The raw material differs. This wiki builds edges from human-curated concepts and body links; graphify extracts calls, imports and inheritance from syntax trees by machine. The operating principles are alike, though. This wiki's "only relations that exist in the text" sits where graphify's "never invent an edge, use AMBIGUOUS when unsure" sits, and both find neighbors from structure alone, without embeddings. What differs is the use. This wiki's graph is a map for people and AI moving between documents; graphify's graph is an index an agent visits before reading code. Running graphify over this repository's app.js and tools/*.py would put a code graph next to the document graph. Only the document graph exists today, so that stays a next experiment.
