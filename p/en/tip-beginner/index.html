Beginner — 9 Habits That Save Context

The first step to using Claude Code well isn't a fancy feature — it's the habit of conserving context. Context is the total amount of conversation and code the model can hold at once, and when it fills up, Claude starts forgetting things you already agreed on and saying odd stuff. If you've ever thought "I literally just told you this," context was probably the culprit. This document covers the beginner nine of this Tip series' 28, and every tip links to the official docs so you can dig deeper whenever you like.

About this document (sources) · Grounded in the official Claude Code docs (as of 2026-08-14) — features may change across versions

1. Start every project with /init

Bringing Claude Code into a project that already has code? Don't overthink it — the first command is /init. Claude reads through the codebase and writes a CLAUDE.md with build commands, test instructions, and project conventions. That file is a project guide read automatically at the start of every session, so you stop re-explaining "so, this project is…" every time. If a CLAUDE.md already exists it suggests improvements instead of overwriting, so run it without worry.

Official docs: How Claude remembers your project — this wiki's Basics-chapter CLAUDE.md hands-on and CLAUDE.md commandments cover the same ground.

2. Turn on the status line

Working in the terminal? Turn on the status bar with /statusline. The model in use, the git branch, and — the big one — the remaining context percentage stay visible under the input box. Once you can see the gauge, habits 3 through 5 below stick on their own. The desktop app already shows this, so nothing to set up there.

Official docs: Status line configuration — the displayed items are fully scriptable.

3. Keep the context small

A command like "review the entire codebase" burns tens of percent of your context in one shot. For big problems, start with the splitting — not "fix the payment system" but "break the payment system fix into small steps," then run each step separately. However smart the model is, once context runs dry it forgets what you said earlier.

4. Find the token hogs with /context

Context draining weirdly fast? Type /context. It shows you at a glance which files, tools, and messages are taking how much. The culprit is usually one of three: a large file read whole, an MCP server that loaded its full tool catalog (tip 22 in the advanced part), or a conversation history that grew and grew.

Official docs: Slash commands reference

5. Around 60%, run /compact; between tasks, run /clear

Don't mix these two up. /compact summarizes and compresses the history — you can say what to keep ("keep the decisions"), and the thread continues. /clear is a full reset, same as opening a new conversation. When one task ends and another begins, reset rather than compress — leftovers from the old task can't contaminate the new one.

Compress when the thread still matters; reset when the task changes. If unsure, check the status line.

6. Start in plan mode

Plan mode touches no files — it only reads, analyzes, and plans (switch with Shift+Tab in the terminal). Since nothing changes, you can hand over anything with peace of mind, and while planning Claude asks you questions that narrow your intent. The lazier you feel about writing a detailed prompt, the more plan mode earns its keep — it asks the questions for you.

One thing worth knowing — since 14 August 2026, new sessions default to auto mode, which no longer asks approval at every step (Defaults That Stop Asking). That makes "plan before touching anything" more important, not less — execution got faster, so agree on the direction first. Mode details: Permissions and modes

7. Treat it like a junior developer

The moment you say "write a function that adjusts padding by screen width," you've already done the hardest part yourself — defining the problem and picking the approach. That's using maybe 10% of the AI. Hand over the problem instead. Claude can read the whole project and propose an approach, so brainstorm together and let it execute its own plan — that's the flow that uses the tool at full size.

# Not like this (you already picked the solution)
Write a function that adjusts padding dynamically by screen width

# Like this (hand over the problem, design the fix together)
The video gets cut off on some devices. What do you think is causing it,
and how should we fix it? Compare two or three approaches for me.

8. Make Claude ask you back

When your requirement is fuzzy, tack this one line onto the prompt — "keep asking me questions until you understand what I want at 95%." Claude fires off clarifying questions, and once that exchange ends it heads in the right direction from the very start. Answering five questions is a lot cheaper than redoing vague instructions three times.

I want motion graphics with a completely different feel from what we have.
Keep asking me questions until you understand what I want at 95%.
Don't start working until the questions are done.

9. Plant self-checks into the to-dos

When you hand over a task list, spell out the checks too. Without them, ten to-dos each finish at 60% completeness, the gaps pile up, and later you burn tokens hunting causes you can't find anymore. Plant the checks and the first deliverable comes out at a visibly different level.

Build the landing page. But follow these rules:
1. After each to-do, open Chrome DevTools and check console errors
2. Do not move to the next to-do until all errors are gone
3. Do not mark an item done until you are 95%+ confident it is complete
