Beginner — 9 Habits That Save Context

The first step to using Claude Code well is not a fancy feature but the habit of conserving context. Context is the total amount of conversation and code the model can hold at once; when it fills up, Claude starts forgetting what you agreed on earlier and giving odd answers. This document takes the beginner nine out of a public tutorial's 28 tips and checks each one against Anthropic's official documentation. Every tip links to the official page, so follow the links when you want to go deeper.

1. Start every project with /init

When you bring Claude Code into a project that already has code, the first command is /init. Claude reads the codebase and writes a CLAUDE.md with build commands, test instructions, and project conventions — this file is a project guide that gets read automatically at the start of every session, so you stop re-explaining the project each time. If a CLAUDE.md already exists, it suggests improvements instead of overwriting.

Official docs: How Claude remembers your project — this wiki's CLAUDE.md hands-on and CLAUDE.md commandments cover the same ground.

2. Turn on the status line

If you work in the terminal, set up a status bar with /statusline. The model in use, the git branch, and — most importantly — the remaining context percentage stay visible under the input box. Once you can see how full the context is, habits 3 through 5 below come naturally. The desktop app already shows this, so no setup needed there.

Official docs: Status line configuration — the displayed items are fully scriptable.

3. Keep the context small

A command like "review the entire codebase" burns tens of percent of your context in one go. Have Claude split the problem first — not "fix the payment system" but "break the payment system fix into small steps," then run each step separately. However good the model is, it forgets earlier conversation once context runs short.

4. Find the token hogs with /context

If your context fills too fast, type /context. It visualizes which files, tools, and messages are taking how much of the window. The culprit is usually one of three things: a large file read whole, an MCP server that loaded its full tool definitions (tip 22 in the advanced part), or a long conversation history.

Official docs: Slash commands reference

5. Around 60%, run /compact; between tasks, run /clear

The difference matters. /compact summarizes and compresses the conversation history — you can say what to keep ("keep the decisions"), and the thread continues. /clear is a full reset, the same as opening a new conversation. When one task ends and another begins, resetting beats compressing — leftovers from the previous task cannot contaminate the new one.

Compress when the thread still matters; reset when the task changes. If unsure, check the status line.

6. Start in plan mode

Plan mode touches no files — it only reads, analyzes, and plans (switch with Shift+Tab in the terminal). Since nothing changes, you can hand over anything with peace of mind, and while planning Claude asks you questions that narrow down your intent. The harder your request is to spell out, the more plan mode is worth.

One piece of background — since 14 August 2026, new sessions default to auto mode, which no longer asks approval at every step (Defaults That Stop Asking). That makes "plan before touching anything" more important, not less — execution got faster, so agree on the direction first. Mode details: Permissions and modes

7. Treat it like a junior developer

If you say "write a function that adjusts padding by screen width," you have already done the hardest work yourself — defining the problem and choosing the approach. Give it the problem instead: "the video gets cut off on some devices — how should we fix this?" Claude can read the whole project and propose an approach, so ideating together and letting it execute its own plan uses the tool at full size.

8. Make Claude ask you back

When your requirement is fuzzy, end the prompt with: "keep asking me questions until you understand what I want at 95%." Claude fires off clarifying questions, and once that exchange ends it heads in the right direction from the start. Answering five questions is cheaper than redoing vague instructions three times.

9. Plant self-checks into the to-dos

When you hand over a task list, spell out the checks at the end — "open Chrome DevTools and check console errors," "do not move on until everything passes," and above all "do not move to the next to-do until you are 95%+ confident the current one is complete and correct." Without self-checks, ten to-dos each finish at 60% completeness, the gaps pile up, and later you burn tokens hunting causes you can no longer find. Plant the checks and the first deliverable comes out at a different level.
