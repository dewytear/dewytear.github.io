Asset Reuse and Security

We do not build it from scratch

We start the PoC by cloning the features already provided by the Reference Wiki that is running for pre-validation (the very wiki explained by the How Knowledge Accumulates series), and we grow the validated features into the company platform. Scope proven as of 2026-07: HTML Fragment documents, SPA Web UI, JSON Navigation Tree (immutable IDs separated from physical paths), unified/Tag/Concept search, Knowledge Index (deterministic build + --check drift gate), automatic related-document recommendation (related) and five typed knowledge relations (relations), Knowledge Map · 3D/2D knowledge graph, an AI consumption layer (llms.txt · self-contained graph JSON), a four-layer CI validation gate, Work Log, and Git History based document history.

Reuse here is not merely "referring to the code." This engine is already packaged as wiki-plugin (v0.7.0) — it carries 18 registration/index/validation tools and 4 skills (add-doc · index · validate · wiki-init), so installing it in a new repository instantly bootstraps the same knowledge system (Packaging the Wiki Engine as a Plugin). The Reference Wiki itself runs as the first dogfooding user of this plugin, so "we do not build it from scratch" is not a slogan but an installation procedure.

In particular, in this Reference Wiki, reflecting the knowledge system is mandated as a rule whenever AI writes or edits a document (enforced by the repository's AI guideline document). When a single document is added, navigation registration → knowledge index entry (including concepts and a multi-angle review of the five relation types — a missed review is surfaced by a non-blocking review signal) → deterministic index build → automatic reflection in the knowledge map, graph, and search → Work Log record all move together within the same unit of change (PR). In other words, the company platform's operating discipline of a "knowledge reflection rate" is already being validated at small scale.

As documents grow, the knowledge system is updated with them — mandated by rule, so it does not break even when nobody looks after it.
  • Along the path of Reference Wiki → feature experiment → validation → company PoC → stabilization → organizational rollout, nothing unvalidated is introduced to the organization directly.
  • Documents are operated HTML-first, making use of tables · dashboards · SVG diagrams · <details> · status badges · warning boxes · architecture flows · DB structure visualizations.
  • The increase in AI tokens caused by HTML is minimized by Knowledge Index based retrieval, which does not read whole documents. This also aligns with the pattern officially recommended by Anthropic, which turns organizational knowledge into AI context through the CLAUDE.md hierarchy and MCP integration.

The AI consumption layer — three doors machines read

The promise that "AI uses organizational knowledge as context" also already exists in physical form in the Reference Wiki (How AI Reads This Wiki). External AI comes in through three doors: ① llms.txt — exposes the cover page of the whole knowledge (what is where) following the llmstxt.org convention → ② knowledge-graph.json — a self-contained file that delivers the entire graph (nodes · related links · typed relations · concepts · each document's URL) in a single fetch → ③ fetching only the individual documents that are needed. It is a structure in which AI follows relations and reads only as much as it needs, without embedding the whole corpus or crawling every time; these files are generated automatically from the index, and the --check gate prevents them from being deployed stale. Connecting the company platform to Claude Code and AI agents is a matter of moving this same contract onto intranet URLs.

Security and access structure

Company development knowledge may include internal architecture, customer project information, DB structures, incident analyses, security settings, and authentication-related information. Knowledge grades are therefore separated, and repositories and access are separated as well.

  • PUBLIC — general knowledge readable by all employees
  • INTERNAL — technical knowledge within the scope of the development organization
  • CONFIDENTIAL — knowledge containing customer/project sensitive information
  • RESTRICTED — security knowledge accessible only to restricted organizations
Do not mix it all into one public wiki The recommended structure separates repositories and access into General Wiki (all employees) · Engineering Wiki (development organization) · Restricted Knowledge (restricted organizations). All security grades are not mixed into a single public wiki, and employees search and read only within the scope of their own permissions.
