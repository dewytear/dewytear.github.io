Design and Verification — Agents, Skills, _workspace

The harness forms the team automatically, but if you know the principles you can direct it more precisely, and you can also tune the generated team yourself. There are two key things — agents (who) and skills (how).

An agent = a "job description" written in natural language

An agent is not code but writing. It holds the following four things.

  • Role · principles — what it is responsible for, the rules it must keep.
  • Input · output — what it takes in and what it puts out (the protocol).
  • Collaboration — which agents it exchanges what with.
  • Re-invocation · behavior on errors — what to do when it gets stuck.
# e.g. sales standard-source analyst (excerpt from an agent definition)
Role: Analyze the credit and order flow of ERP sales/order, and
      identify the scope of impact this customization has on standard features.
Principles: Always put minimizing damage to the standard · upgrade compatibility first.
Input: client request (CR), standard specification/source references
Output: impact report (list of affected screens, features, data)
Collaboration: pass the impact to the designer, request re-investigation when information is lacking
Errors: if the evidence cannot be found, mark it "needs checking" and do not let it pass

A skill = a "manual" that holds a repetitive task

A skill consists of name + description + procedure · checklist. A well-made skill gets reused by several agents.

# e.g. the "regression test checklist" skill
name: regression-checklist
description: Check that the standard sales/order features are not broken after the customization is applied
procedure:
  1. Check that standard order creation/modification/cancellation works normally
  2. Check that orders within the normal credit limit range are not blocked
  3. Check the customization (hold on exceeding the limit) behavior
  4. Check the notification dispatch and the logs
  5. Cross-check numerical consistency (order amount · limit)
The 5 steps of skill design (beginner tip) ① Find a task that repeats often → ② split it so it carries only one responsibility → ③ decide the input/output → ④ write down the exception handling → ⑤ connect it to the agent that will use it.

The sales/order team — a data flow example

Each agent uses its own skills, and when it is blocked at QA it goes back to the developer.

How solid you make the verification is what decides how much you can trust the result → Verification · quality.

Verification · Quality and _workspace

For ERP customization, since the standard features must not be broken, verification is everything. The harness backs this up with a QA agent and evidence records.

What does QA check

It is not a typo check; it looks at the consistency of the content.

  • Claim ↔ evidence consistency — whether the conclusion is grounded in the actual materials and source.
  • Numerical consistency — whether the order amount, credit limit, and settlement amount match end to end.
  • Standard regression — whether the customization broke the standard order and credit features.

Problems found are reported classified as critical / major / minor.

The verification loop — until it passes

It loops between development and QA until there are no defects, and if needed runs a 2nd verification with another tool.

Why it gets things wrong less often — evidence records

  • Source-based — the evidence sources are left together in _workspace. "Plausible falsehoods (hallucinations)" are reduced, and later you can trace "why it was done this way".
  • History records — the history of configuration changes piles up in CLAUDE.md, so the next person picks up the context.
  • Accumulated intermediate deliverables — the first analysis → design → implementation → QA report are left stage by stage, so it is easy to pin down which stage went wrong.

Double verification — crossing with another tool

Verifying with only one tool can be biased. You can make the QA agent check once more with another CLI (e.g. Codex CLI).

/harness Modify the QA agent so that it cross-verifies the regression results using Codex CLI
Token cost — know it before you use it Multi-agent setups are convenient, and just as much they use more tokens. In particular, when the agents talk to each other, there are cases where about 30% more is consumed. There is no need to run even a simple customization in a heavyweight way — size the team to the difficulty.
The kitchen analogy — the result is a "draft" A one-person chef (a single tool) is fast but has bottlenecks, while multiple agents (a kitchen team) split the roles and work long while keeping quality. That said, a finished product does not come out in one go — see it as a well-prepared draft, and before applying it to the ERP, a person must always check the standard impact and regression results.
