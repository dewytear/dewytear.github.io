Designing Agents and Skills

The harness forms the team automatically, but if you know the principles you can direct it more precisely, and you can also tune the generated team yourself. There are two key things — agents (who) and skills (how).

An agent = a "job description" written in natural language

An agent is not code but writing. It holds the following four things.

  • Role · principles — what it is responsible for, the rules it must keep.
  • Input · output — what it takes in and what it puts out (the protocol).
  • Collaboration — which agents it exchanges what with.
  • Re-invocation · behavior on errors — what to do when it gets stuck.
# e.g. sales standard-source analyst (excerpt from an agent definition)
Role: Analyze the credit and order flow of ERP sales/order, and
      identify the scope of impact this customization has on standard features.
Principles: Always put minimizing damage to the standard · upgrade compatibility first.
Input: client request (CR), standard specification/source references
Output: impact report (list of affected screens, features, data)
Collaboration: pass the impact to the designer, request re-investigation when information is lacking
Errors: if the evidence cannot be found, mark it "needs checking" and do not let it pass

A skill = a "manual" that holds a repetitive task

A skill consists of name + description + procedure · checklist. A well-made skill gets reused by several agents.

# e.g. the "regression test checklist" skill
name: regression-checklist
description: Check that the standard sales/order features are not broken after the customization is applied
procedure:
  1. Check that standard order creation/modification/cancellation works normally
  2. Check that orders within the normal credit limit range are not blocked
  3. Check the customization (hold on exceeding the limit) behavior
  4. Check the notification dispatch and the logs
  5. Cross-check numerical consistency (order amount · limit)
The 5 steps of skill design (beginner tip) ① Find a task that repeats often → ② split it so it carries only one responsibility → ③ decide the input/output → ④ write down the exception handling → ⑤ connect it to the agent that will use it.

The sales/order team — a data flow example

Each agent uses its own skills, and when it is blocked at QA it goes back to the developer.

Beginner principles for forming a good team

PrincipleWhyERP example
Keep roles narrowIf one agent does many jobs, quality drops ↓Separate "analysis" from "development"
Make input/output clearSo the next person picks it up right awayImpact report → design input
Keep QA separateIf the maker inspects their own work, they miss thingsRegression QA as an independent agent
Flag it and stop when stuckSo it does not make up what it does not knowA "needs checking" flag
Touching up the generated team If you do not like the agents the harness made, you can just ask for changes in natural language. e.g. /harness Modify the QA agent so that it must also verify the standard order cancellation scenario. How solid you make the verification is what decides how much you can trust the result → Verification · quality.
