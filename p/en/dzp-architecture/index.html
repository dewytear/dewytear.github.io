Platform Architecture

The entire platform is built as a one-way pipeline whose source is GitLab.

Development output flows downward and becomes knowledge. The only layers employees touch are the very top (development) and the very bottom (reading).

Knowledge Generation Trigger — Only Changes Accepted as Done

Not every Commit is turned into knowledge immediately. During development, unfinished implementations, failed attempts, and temporary fixes are all mixed in. Only what passes the gate the organization accepts as done — a change that has gone through Review, been Merged into a baseline Branch, and whose Pipeline succeeded — becomes a target for analysis. Deciding what inside a completed change is knowledge and what is not (the criteria that exclude mechanical Refactoring, typos, and the like) is handled by the value assessment in the knowledge management system.

Incremental Analysis — Never Reading Everything Again

Each project keeps the SHA of the last processed Commit, and GitLab Compare collects only the files changed since then, expanding the analysis to the related Context. Reduced AI Token usage, shorter processing time, no duplicate analysis, and reprocessing after a failure all come out of this state management.

  "project": "scm/sales-order",
  "knowledgeBranches": ["master", "release/*"],
  "lastProcessedSha": "abc123def456",
  "lastProcessedAt": "2026-07-06T14:32:00+09:00",
  "status": "success"

Context-based Analysis, Not a Plain Diff

You cannot judge a business policy from the single line if ("CREDIT_HOLD".equals(soStatus)). On top of the change Diff, an Impact Expansion reads the entire Class · its callers · the related Mapper and SQL · the related Test · the related Config · the existing Wiki together, so what is extracted is real development knowledge rather than a plain code summary.

Knowledge Integrity Gates — A Layer Separate from the Trigger

Pipeline success is the gate at the entrance — it only decides "is this change qualified to be analyzed". The integrity of the knowledge repository itself is guarded by a separate gate layer, and that layer is inherited as-is from what the Reference Wiki already runs in CI (How the Wiki Guards Itself):

  • State validation — broken links, duplicate IDs, orphan documents, missing index entries, and diagram bounds overflow are checked exhaustively on every commit (ERROR 0 is the merge condition).
  • Drift validation (--check) — decides whether the index, graph, llms.txt, and sitemap match a deterministic rebuild byte for byte. The machine blocks the accident where the AI Curator fixes only the document and forgets to reflect it in the index.
  • Companion gates — enforce, from the diff, the rule that "if you changed a document, the record (Work Log) and the knowledge-system update belong in the same change unit". The company KPI "knowledge reflection rate per Merge" is exactly this gate's pass rate (Roadmap).
  • Review signals (non-blocking) — for judgment areas a machine cannot enforce (for example, whether knowledge relations were reviewed from multiple angles), a checklist is raised instead of a block, inviting human review.

What the Index and Provenance of the Wiki Repository layer look like in concrete terms — which fields are already proven in practice and which fields are extended for company use — is covered by the next part, the knowledge management system.

Operational Stability — Duplication of Real-time and Reconciliation

Rather than relying only on real-time Webhook processing (Merge → Queue → Curator), a periodic Batch compares the current SHA in the Project Registry against the sync-state and reprocesses missed changes. It is a structure that copes with Webhook failures, Network errors, Queue drops, Curator outages, and transient API failures.
