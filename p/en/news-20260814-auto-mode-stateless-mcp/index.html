Defaults That Stop Asking — Auto Mode and Stateless MCP

As of today (14 August), a new Claude Code session starts in auto mode. The permission prompt that used to ask “may I run this?” is out of the default flow. Two weeks earlier, MCP, the standard agents use to attach tools, removed the idea of a session from the protocol entirely. One dropped the human click, the other dropped the connection's memory, and in both cases what filled the gap was a rule written down in advance. This article walks through both changes and why they are one story.

Three-line summary

  • New Claude Code sessions on Pro, Max, and Team plans now use auto mode as the default. Only actions that are irreversible, destructive, or reach outside the working environment get stopped; everything else proceeds without a prompt.
  • The numbers behind the decision sting. In Anthropic's own data, users approved 97% of permission prompts, and in a study where a dangerous command was slipped into an ordinary prompt, people rejected it only 13.6% of the time. Auto mode's classifier caught 89% of the same commands. The approval button had already stopped working as a safeguard.
  • MCP deleted the initialize handshake and Mcp-Session-Id. Protocol version and client capabilities now ride in _meta on every request. Any request can land on any server instance, but the change is wire-incompatible in both directions, so existing servers need real refactoring.

The approval loop was already broken

The numbers published to justify the change are more striking than the change itself. Here is what Anthropic reported about how people actually use permissions.

  • Users approve 97% of permission prompts. The company reads this as reflexive clicking rather than judgment.
  • 49.5% of active CLI users have hand-written Bash allow rules, and 62% have used bypassPermissions or “don't ask again.” A quarter of interactive sessions now start in bypass mode from the outset.

So they ran a study. 1,053 paid professional testers worked in a test coding environment, and partway through each session one ordinary permission prompt was swapped for a plainly dangerous command. Approving it never actually ran anything; the study recorded only whether the participant noticed and refused. The result was 143 people, 13.6%. Five out of six waved the dangerous command through.

Run the same commands past auto mode's classifier and 937 of 1,053, or 89%, were blocked. Flip that around and 116 of them, roughly 11%, got through, and at least one outlet led with that number: why ship this as the default when it misses 11%? The objection is fair. What makes the decision defensible is that the comparison is not against a perfect human but against the 13.6% human.

So what guards the gate now? Rules instead of clicks

Three layers moved into the space the permission prompt left behind.

  • Hard denies — rules that block regardless of context. Exfiltrating data is the headline case, and the rules distinguish secrets from public data when they judge. Users and enterprise administrators can add their own categories.
  • A state check right before the action — before a destructive command such as git reset --hard, Claude looks at git state and whether the repository is public. The same command reads differently when there are uncommitted changes piled up.
  • Prompt-injection screening — probes scan tool results for “from now on, do this instead” instructions hidden in content read from files or the web. A separate classifier then checks whether the intended action matches what the user asked for.

Some things still come back to you: actions that are irreversible, destructive, or aimed outside the environment Claude runs in. In those cases Claude first looks for a safer route and only asks when it cannot find one. In the other direction, allow rules that are too broad, such as unrestricted python or node execution, are set aside in auto mode, because leaving them active would let anything run straight past the classifier.

The gate did not disappear. It moved from a click in the moment to a rule written down in advance.

There is an attack-side evaluation too. Trajectory Labs, an independent evaluator, ran 72 indirect prompt-injection scenarios ten times each, 720 attempts per model, and reported that no attack succeeded against Fable 5, Opus 5, or Sonnet 5 running in auto mode. Anthropic also published three cases caught in its own internal use: an off-network data leak, a destructive mass operation, and a privilege escalation. In each one Claude either found a safer path by itself or checked in with the user.

The same week, MCP dropped the session

MCP (Model Context Protocol) is the standard that defines how an agent attaches to outside tools and data. It is the protocol covered in this wiki's MCP lecture, and the 2026-07-28 release candidate is its largest revision since launch. One sentence covers the core of it: state is gone from the protocol layer.

  • The handshake is gone — initialize/initialized, exchanged once when a connection opened, no longer exists. Protocol version, client info, and client capabilities now travel in _meta on every request. If a client needs server capabilities up front, the new server/discover method fetches them on demand.
  • The session identifier is gone — the Mcp-Session-Id header and the protocol-level session that came with it were removed together. With both gone, any request can arrive at any server instance. The sticky routing and shared session stores that horizontal deployments needed are no longer required at the protocol layer.
  • State that must persist is passed openly — anything that has to carry across calls now travels as a server-minted handle given as an ordinary tool argument. State that used to hide in the connection is now an argument.
  • Thin core plus extensions — the rest moved into optional extensions negotiated per request. Three are official today: Tasks, MCP Apps, and enterprise-managed authorization, with the authorization work tightening the parts that were prone to OAuth mix-up attacks.
What the connection used to remember now rides inside the request, which makes every request heavier.

Reactions split. One camp calls it a rediscovery of REST; the other says having one standard was the point all along. The cynical reading comes with a practical upside: load balancers, API gateways, and progressive rollouts already built for REST now work unchanged. The cost is plain. The change breaks wire compatibility in both directions, so existing servers need real work rather than a version bump. Teams that already solved auth or resumption with their own extensions will take a while to tear that out, however much better the new spec is.

Why this is one story

The two changes came from different companies at different layers, yet they removed the same thing: a fixed point held at runtime. Auto mode removed the judgment a human made in the moment by reading context; MCP removed the memory a connection kept on its own. Both were convenient while they lasted and grew expensive as the count went up. Human approval turns into reflexive clicking the moment an agent acts hundreds of times a day, and a session becomes the burden of sticky routing the moment you run more than one server.

What replaced them is of a kind too. A hard deny rule is a document written before the incident, stating what must never happen. _meta works from the other direction, letting each request carry who it is and what it can do. Write it down in advance or carry it every time: either way, the basis for a decision moved from the human and the connection of the moment to declared rules and data.

What that means in practice is fairly concrete. Deny rules in CLAUDE.md and your settings files used to be closer to preference; now they are policy that actually gets enforced. Allow rules left wide open become something to ignore rather than a convenience, and narrowly written deny rules keep working while nobody is watching. This runs in the same direction as the conclusion in this wiki's “A harness is not enough” — a harness is worth what its verification and boundaries are worth, not what its instructions weigh.

The direction has a price. A rule written in advance protects exactly as far as it was written. The 89% figure is that limit, and the remaining 11% was danger in a shape the rules did not have. MCP did not remove state either; it moved state out into arguments, so who mints a handle and when it expires becomes the new homework. It is more accurate to say a hidden problem got moved somewhere visible.

What this wiki fixed

Two passages went stale with this change, and both were updated in the same pass.

  • The Q&A in Extending tools, and wrapping up described auto mode only as “it does not ask for permission every time, so it operates more autonomously.” The fact that it is now the default, along with hard denies and injection screening, has been added.
  • The closing sentence of the MCP lecture, “Claude Code asks for permission before using them,” is wrong as of 14 August. It now says Claude stops only on the actions the rules catch.

Fact-check notes

  • Self-reported figures — the 97% approval rate, 49.5% allow rules, 62% bypass, quarter of sessions, and the 13.6% and 89% (937 cases) from the 1,053-tester study all come from Anthropic's own research and experiments. None have been independently reproduced.
  • Independent evaluation — the 720 injection attempts with zero successes were reported by Trajectory Labs, with the structure disclosed as 72 scenarios × 10 runs per model. The design and difficulty of the scenarios can only be judged within what was published.
  • The 11% framing — that number is the inverse of the 89% block rate. At least one outlet built its headline around it, which is why it appears here too. The two figures are two ends of the same study.
  • Spec details — handshake removal (SEP-2575), session-identifier removal (SEP-2567), _meta, server/discover, and the three extensions are drawn from the official MCP blog and changelog. 2026-07-28 is a release candidate, so details may still shift before it is finalized.
  • Scope — the auto-mode default applies to new sessions on the Pro, Max, and Team plans. Settings already pinned, and defaults managed by an organization, were announced as unchanged.
