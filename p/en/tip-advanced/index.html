Advanced — 8 Tips for Parallel, Autonomous, Scheduled Work

The last part is about running Claude Code many at a time, for long stretches, hands off. From worktrees that keep sessions from colliding over files, to scheduled jobs, phone remote control, and agent teams that talk to each other — tips 21 through 28 of the series, checked against the official docs.

About this document (sources) · Grounded in the official Claude Code docs (as of 2026-08-14) — experimental features may change across versions

21. Run sessions in parallel with worktrees

Two sessions editing the same project at once — one on the login feature, one on graphics logic — collide the moment they touch the same file. A worktree is git's independent working copy: shared repository history, separate files. Give each session its own worktree and they simply can't overlap; merge with git when done.

You can type the manual git worktree command yourself, but Claude Code now manages the whole lifecycle — start with claude --worktree (-w) and creation, naming, and cleanup are automatic; the desktop app makes a worktree per new session on its own. Files git doesn't track, like .env, aren't in the copy — drop a .worktreeinclude file in the project root to have them copied over.

# Terminal 1 — login feature (in its own worktree)
claude --worktree login-feature

# Terminal 2 — graphics logic (another worktree, same time)
claude -w motion-logic

# Merge each branch when done — no conflict anxiety
The copies are physically separate, so conflicts simply cannot happen — you only manage the moment of merging.

22. Call the API directly instead of an MCP server

MCP (Model Context Protocol) is the standard for attaching external tools, but connecting a server has a cost: its entire tool catalog lands in your context. If you only need one or two functions, having Claude call the API endpoint directly is cheaper on both tokens and context. Using most of the tools? Take MCP. Using one or two? Call directly — that's the whole tip. Worth noting: built-in tool search now loads tool definitions on demand, which shrank this cost a lot, but the principle — carry only what you use — still holds.

Official docs: Connect Claude Code to tools via MCP — see also this wiki's the extending chapter (MCP section). The big MCP spec revision is covered in Defaults That Stop Asking.

23. Schedule recurring work with /loop — and hand the rest to Routines

Set up a recurring job like /loop check the deploy status every 5 minutes and Claude keeps checking on its own for as long as the session lives. Deploy monitoring, periodic checks, even time-pinned jobs like "check our Slack at 8." Watch-and-wait work you'd otherwise babysit — hand it over whole.

But /loop only runs while the session is open. Work that must run independently of your session and your computer belongs to a Routine — save a prompt, repositories, and connectors as one configuration, and it runs on Anthropic-managed cloud on a schedule (hourly minimum, cron expressions supported), on an API call, or on a GitHub event. Laptop closed? Still runs. Three options, in short: /loop for repetition inside this session, desktop scheduled tasks for jobs pinned to your machine, and Routines when it has to run without your computer. This wiki's morning briefing runs as a Routine.

Official docs: Run prompts on a schedule

24. Steer remotely from your phone

Run claude remote-control in the terminal and you get a link. Open it on your phone and — while the code keeps running on your local machine — only the controls move to your phone. Check progress and give the next instruction from the subway. One condition: the local machine has to stay on, since that's what you're steering. You also get phone notifications when a long task finishes or approval is needed.

Official docs: Remote Control — continue local sessions from your phone

25. Ask your database in natural language

Major databases — PostgreSQL, Supabase, and friends — connect to Claude Code as MCP servers. Once connected, you can ask "what do last week's churned signups have in common?" in plain language, no SQL — schema exploration, aggregation, filtering, handled like a data analyst would. Whatever database you're on, the fastest start is simply asking Claude: "connect to this DB."

26. For deep thought, ultrathink

In the terminal, include ultrathink with your prompt (the input turning rainbow-colored means it took) and Claude spends its maximum thinking budget before answering. It burns a lot of tokens, so it's not an everyday move — save it for genuinely hard problems and architecture calls where no amount of prompt rewriting gets you a good answer.

Official docs: Model configuration — effort. As of this writing, thinking depth is also adjustable via the effort setting.

There's another road to deep thought — instead of raising one model's thinking budget, have several agents refine a plan until they agree. The OMC plugin's ralplan works that way: three roles — planner, architect, critic — review the plan until consensus (add --deliberate for high-stakes deliberation). For heavy design calls like architecture, databases, or security, that can fit better than ultrathink — details in OMC execution modes.

27. Edit permissions for safe autonomy

In settings.json you can mark commands as always allowed / always ask. Auto-approve everything and dangerous commands slip through — rm (file deletion), git push --force (a push that overrides conflicts) — so tell Claude "make these dangerous commands ask me first" and let it write the deny rules. Under auto mode, the default since 14 August 2026, these rules matter more than ever: narrowly written deny rules keep working while you're away, and overly broad allow rules get ignored. The rules became policy that actually gets enforced.

# .claude/settings.json — dangerous commands must ask first
{
  "permissions": {
    "ask": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)",
      "Bash(git reset --hard:*)"
    ]
  }
}
# Not comfortable writing it by hand? One line does it:
# "set permissions so rm and force pushes always ask me first"

Why separate the roles — self-preference bias and splitting the verifier

Before the next tip, let's cover why you'd bother splitting roles at all. There's a reason, and it has a name — self-approval bias, or self-preference bias in the research literature. It's an LLM's tendency to rate work more favorably when it produced that work, or when it was produced the way it would have produced it.

This isn't a hunch; it's been measured. One study showed that for outputs human annotators judged equal in quality, LLM evaluators scored their own higher. The more striking part came next — the ability to recognize one's own output correlated linearly with the strength of that preference. It isn't a coincidental fondness for its own work; the evidence points to favoring it because it recognizes it.

And there's one structure where this really bites: a single agent running plan → execute → verify in sequence. When the opening premise is wrong, the same judgment that made it also grades it, so "approved" keeps getting stamped on top of a bad foundation. It's grading its own paper while carrying all the earlier context forward, so the bias doesn't happen once — it becomes a loop.

One side grades its own answer; the other has a way back. The difference isn't the number of agents — it's the return path.

So does swapping in a different model for review fix it? Half of it. Handing review to another model does push self-preference bias down. But another trap is waiting — conformity and sycophancy. Agents absorb each other's reasoning and the original conclusion ends up reinforced rather than challenged, a failure mode well documented in multi-agent debate research. The echo chamber, where minority agents drift toward whatever the majority answered, belongs to the same family.

So the response comes in two layers.

  • Split the roles and build a return path — planner → designer → verifier, and when the verifier finds a problem the work goes back to planning or design. Without a way back, half the value of splitting evaporates. Start with subagents (intermediate part, tip 10), and move up to the agent teams in the next tip when they need to talk to each other.
  • Assign the verifier to refute — this is the real fork. "Please review this" invites conformity. Instead, make disagreement the default: "assume this plan is wrong and argue against it; if you're unsure, rule toward sending it back." That's the same reason ralplan in tip 26 keeps a separate critic role.

In the end it isn't about spawning lots of agents — it's about deliberately separating responsibility for planning, execution, and verification. One agent doing everything approves itself; agents split up but getting along approve each other.

Sources: LLM Evaluators Recognize and Favor Their Own Generations (NeurIPS 2024 — the linear correlation between self-recognition and self-preference) · Quantifying and Mitigating Self-Preference Bias of LLM Judges · Sycophancy propagation in multi-agent systems · The conformity of large language models

28. Agent teams — agents that talk to each other

Easy to confuse with subagents, but the structure differs. Subagents work in parallel yet never talk to each other — they only report to the main session. Agent teams are independent sessions that talk to each other, share a task list, and claim work — and you can talk to each teammate individually. If your picture is a planner, a marketer, and a designer coordinating with each other, you want an agent team, not subagents. It costs more tokens, but on tasks where teammates should challenge and complement each other's output, the results are clearly different.

Different reporting structure, different use — independent research goes to subagents, collaborative work to agent teams.

Instead of flipping the flag and designing a team yourself, there's also a packaged team mode. The OMC plugin's team assigns roles to N agents and runs them as a staged pipeline, and team ralph — team combined with ralph, which loops until done — is OMC's strongest execution mode. The plugin handles team composition and role assignment for you, so if you want to try agent teams on real work today, this is the faster on-ramp — see OMC execution modes and agents & skills.

Official docs: Orchestrate teams of Claude Code sessions — experimental as of this writing, enabled with the CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 environment variable. For the methodology, this wiki's harness engineering course covers agent team operation in 12 parts.

Closing

The 28 tips boil down to three principles. Context is a budget (beginner) — conserve it, split it, make it visible. Repetition belongs in the system (intermediate) — freeze good prompts into skills and CLAUDE.md. Parallelism starts with isolation (advanced) — put worktrees and permission rules in place first, then extend autonomy. The tools will keep changing; these three should outlast them.
