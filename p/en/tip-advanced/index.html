Advanced — 8 Tips for Parallel, Autonomous, Scheduled Work

The last part is about running Claude Code many at a time, for long stretches, hands off. From worktrees that keep sessions from colliding over files, to scheduled jobs, phone remote control, and agent teams that talk to each other — tips 21 through 28 of the public tutorial, checked against the official docs.

About this document (sources) · Skeleton: the advanced part (21–28) of a public tutorial video — 28 Claude Code tips
· Verified and supplemented against the official Claude Code docs (as of 2026-08-14) — experimental features may change across versions

21. Run sessions in parallel with worktrees

Two sessions editing the same project at once — one on the login feature, one on graphics logic — collide the moment they touch the same file. A worktree is git's independent working copy: it shares the repository history but keeps its own files. Give each session its own worktree and they can never overlap; merge with git when done.

The tutorial shows the manual git worktree command, but Claude Code now manages the lifecycle for you — start with claude --worktree (-w) and creation, naming, and cleanup are automatic; the desktop app creates a worktree per new session on its own. Files git does not track, like .env, are absent from the copy — put a .worktreeinclude file in the project root to have them copied automatically.

The copies are physically separate, so conflicts simply cannot happen — you only manage the moment of merging.

Official docs: Run parallel sessions with worktrees

22. Call the API directly instead of an MCP server

MCP (Model Context Protocol) is the standard for attaching external tools, but connecting a server has a cost: its entire tool catalog lands in your context. If you need one or two functions, having Claude call the API endpoint directly is cheaper in both tokens and context. Using most of the tools? Take MCP. Using one or two? Call directly — that distinction is the whole tip. Note that built-in tool search now loads tool definitions on demand, which shrank this cost considerably, but the principle — carry only what you use — still holds.

Official docs: Connect Claude Code to tools via MCP — see also this wiki's MCP intro. The big MCP spec revision is covered in Defaults That Stop Asking.

23. Schedule recurring work with /loop

Set up a recurring job like /loop check the deploy status every 5 minutes and Claude keeps checking on its own for as long as the session lives. Deploy monitoring, periodic checks, even time-pinned jobs like "check our Slack at 8." Watch-and-wait work you would otherwise babysit can be handed over whole.

24. Steer remotely from your phone

Run claude remote-control in the terminal and you get a link. Open it on your phone and — while the code keeps running on your local machine — only the controls move to the phone. Check progress and give the next instruction from the subway. The one condition to remember: your local machine must stay on, because that is what you are steering. You also get phone notifications when a long task finishes or approval is needed.

Official docs: Remote Control — continue local sessions from your phone

25. Ask your database in natural language

Major databases — PostgreSQL, Supabase, and others — connect to Claude Code as MCP servers. Once connected, you can ask "what do last week's churned signups have in common?" in plain language, no SQL — schema exploration, aggregation, filtering, all handled like a data analyst would. Whatever database you use, the fastest start is simply asking Claude "connect to this DB."

26. For deep thought, ultrathink

In the terminal, include ultrathink with your prompt (the input turns rainbow-colored when it takes effect) and Claude spends its maximum thinking budget before answering. It burns a lot of tokens, so it is not for everyday use — save it for genuinely hard problems and architectural judgment calls where no amount of prompt rewriting gets you a good answer.

Official docs: Model configuration — effort. As of this writing, thinking depth is also adjustable via the effort setting.

27. Edit permissions for safe autonomy

In settings.json you can mark commands as always allowed / always ask. Auto-approving everything lets dangerous commands through — rm (file deletion), git push --force (a push that overrides conflicts) — so tell Claude "make these dangerous commands ask me first" and let it write the deny rules. Under auto mode, the default since 14 August 2026, these rules matter more than ever: narrowly written deny rules keep working while you are away, and overly broad allow rules get ignored. The rules have become policy that actually gets enforced.

Official docs: Permissions — background in Defaults That Stop Asking.

28. Agent teams — agents that talk to each other

Easy to confuse with subagents, but the structure differs. Subagents work in parallel yet never talk to each other — they only report to the main session. Agent teams are independent sessions that talk to each other, share a task list, and claim work — and you can talk to each teammate individually. If your picture is a planner, a marketer, and a designer coordinating with each other, that is an agent team, not subagents. It costs more tokens, but on tasks where teammates must challenge and complement each other's output, the results are clearly different.

Different reporting structure, different use — independent research goes to subagents, collaborative work to agent teams.

Official docs: Orchestrate teams of Claude Code sessions — experimental as of this writing, enabled with the CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 environment variable. For the methodology, this wiki's harness engineering course covers agent team operation in 12 parts.

Closing

The 28 tips boil down to three principles. Context is a budget (beginner) — conserve it, split it, make it visible. Repetition belongs in the system (intermediate) — freeze good prompts into skills and CLAUDE.md. Parallelism starts with isolation (advanced) — put worktrees and permission rules in place first, then extend autonomy. The tools keep changing; these three will outlast them.
