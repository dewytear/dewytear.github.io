Send Engine Implementation Requirements

Each item describes, at a conceptual level, "what the engine must do and why". The concrete methods and structure are decided by the Platform team's judgement and through discussion.

Receiving send requests · channel sending

  • Receiving send requests — take send requests from the queue and process them.
  • Channel sending — send through notification (in-app), note, and mail, and it must be possible to add channels such as chat and KakaoTalk in future. Per-channel rules (what the engine must honour): mail needs a subject, each channel differs in whether a given recipient is reachable, and some channels allow a message to be recalled after it is sent.

Reliability — idempotency · delivery guarantee · ordering · reprocessing

  • Idempotency / duplicate prevention — even if the same send request arrives twice, it is actually sent only once.
  • Delivery guarantee — send without loss and, where possible, confirm and report back whether it actually arrived (and was read). (Today confirmation after "it was sent" is weak, so this is a key improvement.)
  • Ordering guarantee — preserve the send order for the same target and within the same request.
  • Retry · backoff · DLQ — retry transient failures automatically; isolate repeated failures in a dead-letter queue for the operator to reprocess manually.
  • Scheduling · cancel/recall — scheduled sending, cancelling before the send and recalling after the send (only on channels that support it).
  • Bulk processing · parallelism — send to large recipient lists in parallel, meeting throughput and latency targets.

Sending by timing — details · implementation request

"When to send" differs by type. AI Notification decides the timing type and its parameters and carries them in the send request; the engine must then actually execute the timing that matches that type. (Not a vague "send as soon as a request arrives" — the behaviour must be implemented per type.)

Timing typeMeaningWhat the engine must execute
ImmediateSend as soon as the event occursSend without delay (real time)
DelayedSend when a given state persists for a set time (e.g. 3 days waiting for approval)Wait until the scheduled time, then send (for finalizing at the moment of sending, see below)
RecurringRepeat on a fixed cycle or date/time (e.g. daily at 09:00, the 5th of each month)Run the recurring schedule + prevent duplicate sends + batch lifecycle
TransitionSend the moment a state changes to a specific value (e.g. sales order confirmed)The detection is done by AI Notification → immediately send the request handed over at the moment of transition (the engine does not observe business state)

Latest lookup and finalization at send time

Important Sending must use the latest data at the moment it is actually sent, not the values held when the send request was created. Because of the delayed, recurring, and transition types there is a time gap between creating the request and actually sending it, and the target data can change in between. A step is therefore needed that, at the moment of sending, looks up and finalizes again "who to send to and what to send right now".
  • Finalization (lookup and resolution) is done by AI Notification (interpreting business data and recipients is AI Notification's area).
  • When the timing arrives, the engine asks AI Notification to finalize "the final targets and content for this send" and sends based on that result. (If the target has disappeared by then, that item is excluded from sending.)
  • This "finalize at send time" procedure must be part of the interface.

Dynamic lifecycle management of recurring batches

Recurring (scheduled) notifications are not a fixed batch: batches must come into existence and disappear as notifications are registered and removed.

  • Creation — when a recurring notification is registered, dynamically create the matching schedule batch.
  • Removal — when that notification is deactivated, deleted, or past its end date, automatically remove and release the batch.
  • Purpose: keep unused batches from piling up. (Cycle = ‘how often it repeats’; lifecycle = ‘when that repeating batch is created and removed’.)

Send data management · status (display)

Not only the sending itself, but also management of the send data and a status screen for operators are needed.

  • Data management — retention and cleanup of send request, processing result, and history data.
  • Status screen / dashboard — distribution of processing states (waiting · in progress · success · partial failure · failure), retry and DLQ status, statistics by channel and by company, looking up failed items and reprocessing them manually, looking up and cancelling scheduled items.
  • Operators must be able to check "what was sent, when, and how" and act on it immediately.

Observability · multi-tenancy · security

  • Observability · operations — monitoring metrics such as throughput and failure rate, failure alerts, reprocessing tools.
  • Multi-tenancy — it must be isolated per company, and no path such as an all-company bulk send may be opened.
  • Security — safe management of channel credentials, protection of recipients' personal data.
