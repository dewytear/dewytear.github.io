How the Wiki Guards Itself — Gates and the Automation System

The previous five parts described the structure in which knowledge accumulates, connects, is read, is consumed by AI, and is packaged as a plugin. One last question remains — who guarantees that this structure does not drift? What if you add a document and forget to regenerate the index? What if you fix a tool and forget the plugin copy? This part explains the gates and the automation system responsible for that guarantee, along with the real incidents behind them.

Principle — Machines Take Judgment-Free Labor, Humans Take the Judgment

Automation in this wiki is centered on validation, not generation. Summaries, concepts, relations, and body text are curated by a human (or an AI worker) who has read the document — because that takes judgment, and handing judgment to a machine breaks the graph's honesty. Instead, the machine takes on two things: ① ruling on whether the results of curation contradict one another (gates), and ② taking over restoration labor that needs no judgment (--fix). A rule written down only in prose gets forgotten — it really was forgotten, incidents followed, and each time the rule was mechanized into a gate.

Always the Same Result — Deterministic Builds and the Drift Gate

The knowledge index, the graph JSON, llms.txt, the sitemap, document dates — every artifact the site reads is generated by tools and never edited by hand. The build is deterministic (same input → always the same output), so CI's --check mode can compare "the artifacts currently in the repository" with "artifacts freshly built from source" byte for byte. If they diverge (= you edited a document and forgot to regenerate), the merge is blocked. That is why there is structurally no moment at which the graph file AI reads differs from the actual knowledge.

Companion Gates That Guard the PR — "If You Changed A, Bring B Too"

Some rules cannot be caught by comparing artifacts. A companion rule such as "if you edited an asset, bump the cache buster too" has to look at the PR's list of changes (the diff) and check whether the pair arrived together. There are four such gates, and every one of them was born from a real incident or an operational need:

GateRule it enforcesWhat brought it about
check_worklogA PR with substantive changes must come with a Work Log (updating an existing log counts too)The "log it even if it's small" rule existed only in prose and kept being forgotten
check_cachebusterIf you edit a ?v asset (app.js and the like), bump ?v in the same PRReal incident on 2026-07-09 — the fix was in, but returning browsers showed "nothing changed"
check_plugin_syncTools bundled with the plugin must match the root tools/ byte for byte, plus a version bump whenever the bundle changesReal incident on 2026-07-10 — 190 lines of a validator shipped stale
diagram-boundsA real-render check in a headless browser so diagram text never overruns its box or the viewBox by even 1pxEstimating font widths alone kept missing borderline overruns

Not every companion gate blocks. check_relations_review picks out newly registered documents and surfaces their distribution of knowledge relation types and the five-type (prerequisite, implements, example-of, evidence-for, supersedes) checklist as a non-blocking review signal — because a relation is attached honestly only when it actually exists in the body text (no forced links), so a machine cannot compel you to "add a relation." It therefore does not block the merge; it works only as a signal that makes a human or AI take one look at the rule that says don't fill relations with prerequisites alone (the same "a list for a human to look at once" philosophy as the knowledge-graph WARNs above).

Every PR has to pass four layers of gates — a single ERROR means no merge.

Gates That Fix Themselves — --fix

Once a gate has ruled that something "has drifted," the restoration is mostly labor that needs no judgment: the bundle copy only has to be copied from the root, and the cache buster only needs its number +1. So two gates have a --fix mode — check_plugin_sync --fix automatically restores a drifted snapshot, and check_cachebuster --fix automatically bumps a stale ?v. The boundary is clear: restoration by machine, judgment by human. How far to raise the plugin version (content update = minor, bug fix = patch), and whether a feature change has made an explanatory document stale, are things --fix does not touch.

Declaring the Change Type — Discipline for What Gates Cannot Catch

Machine gates have their limits. The PR that added the relation-type feature passed every gate, yet the narrative gap that the documents of this very series did not explain the new feature was only found in a separate review — because "is the explanation stale?" is not something a machine can rule on without false positives. So the last device is not a gate but a declaration discipline. When you start a task, you declare the change type and skim the impact table for that type:

  • ENGINE viewer behavior — review self-describing docs · bump ?v  /  STYLE design and diagrams — design rules · bump ?v
  • TOOL build and validation tools — bundle sync + version  /  SCHEMA artifact contract — accompany with schema.md · judge backward compatibility · review explanatory docs
  • PLUGIN skills and metadata — version bump  /  CONTENT body text and lists — the 5 registration steps · no plugin changes

The declaration needs only one line in the plan or the PR body (for example, "Change type: TOOL + PLUGIN"). Multiple declarations are normal — the relation-type feature cut across five types, and had it been declared at the start, "review explanatory docs" on the SCHEMA row would have been caught inside the implementation PR. This is not a gate (enforcement) but a judgment aid — instead of mechanizing the areas that need judgment, it pulls the moment of judgment earlier.

At a Glance Artifacts are generated only by deterministic builds (never edited directly) → --check blocks drift → four companion gates check "whether the pair arrived together" → ERROR 0 is the merge condition. Restoration labor is handled by --fix, and the narrative and version judgments a machine cannot rule on are picked up by a human at the start via the change-type declaration. Every gate was born to keep a real incident from recurring.
