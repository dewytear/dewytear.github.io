The Harness Plugin — Intro, Concepts, Install

The Harness plugin is a Claude Code plugin that "lays out the setup so that, once you give it only a goal (an intent), several AIs form a team and work on their own for a long time." Instead of throwing prompts one at a time, if I just say "what I want", the plugin composes and runs the agent team · skills · orchestrator on my behalf.

The big picture on one page

What the Harness plugin does comes down to the flow below. People step in only at the very front (the intent) and the very back (review and decision-making), and the AI team takes on the repetitive work in the middle.

People handle only the front (intent) and the back (review); the AI team takes the repetitive work in the middle.

Why "harness" — from prompts to the harness

The way we handle AI has evolved as below. The harness is the stage of designing not one model but "the whole environment surrounding the model." Even with the same model, the quality of the output differs greatly depending on which setup (harness) you put it on.

StageCoreAnalogy
Prompt engineeringAsking questions wellPhrasing a single remark well
Context engineeringFeeding in the needed materials and context wellPutting the materials into their hands
Harness engineeringDesigning the whole system in which the AI worksFitting a horse with a harness so it runs well for a long time

Why it fits ERP customization well

Customization work for a client usually chains several stages in order — requirement (CR) analysis → grasping the standard source and impact → design → development → regression verification. This is a prime example of work that takes a long time if you do it alone in sequence, but is far faster if you split the roles and go in parallel. The harness hands each of these stages to a responsible agent and lets the orchestrator coordinate them.

  • Minimizing damage to the standard — the analysis agent first points out "where this customization affects the standard package."
  • Automated regression verification — after development, the QA agent cross-checks that the standard features have not broken.
  • Standardized deliverables — the specification, impact analysis, tests, and migration guide are all left together in _workspace.

※ A concrete example (a sales/order credit-limit customization) is followed step by step in First harness run.

Core Concepts Made Easy

A harness is made up of five elements. It feels hard, but it maps one-to-one onto a team working at a company — one PM, several people in charge, a manual for each of them, inspection, and a shared work folder.

Where the name comes from — the tack of a carriage horse "Harness" originally means the tack you put on a horse. No matter how good the horse (= the AI model) is, depending on how you strap it up and drive it it may run well or just spin in place. Harness engineering is exactly the work of designing that "setup that drives it".

Structure — how the elements interlock

The orchestrator coordinates the team, and every deliverable is left in the shared _workspace.

The five elements

  • Agent — an AI worker taking on a specific role. It is a "job description" written in natural language, not in code (role · principles · inputs and outputs · how to collaborate · what to do on errors). e.g. "sales standard-source analyst"
  • Skill — a manual that holds a repetitive task. It consists of name + description + procedure · checklist. e.g. the "credit-limit verification procedure" skill
  • Orchestrator — the PM that coordinates the team. There is always exactly one, and before starting it plans the work order (the workflow) in advance. (Similar to Claude Code's plan mode)
  • Evaluation · tests — the inspection that makes the results trustworthy. It cross-checks not typos but claim–evidence consistency, numerical consistency, and regression of standard features.
  • Artifacts · memory — the shared work folder _workspace created when it runs. Intermediate deliverables are left together with the evidence sources, so you can later trace "why it was done this way" and hallucinations (plausible falsehoods) are reduced as well.

The minimum setup is three things At first it is enough to understand just three — agent · skill · orchestrator. Evaluation · tests and artifacts · memory are attached for you by the Harness plugin. In the next documents we install it and run it ourselves.

Installation and Setup

The harness is distributed in the form of a Claude Code plugin. Once you register the marketplace and install it, you can use the /harness command.

What you need first Claude Code must be installed (see Getting Started). In the terminal, move to the project folder you will work in, run claude, and then enter the slash commands below.

Installation in 3 steps

Method 1 — two command lines (recommended)

# 1) Add the harness marketplace
/plugin marketplace add lev-factory/harness
# 2) Install the harness plugin
/plugin install harness

When the install screen appears, install with User scope (used across my whole account). If you want to use it only in a specific project, choose project scope.

Method 2 — from the /plugin screen

  1. Enter /plugin → move to the Marketplace tab with the right arrow key.
  2. Enter lev-factory/harness in Add Marketplace → Enter.
  3. Select harness from the list → Enter on the install screen → install with User scope.

After installing — reload and verify

# Apply the plugin to the current session
/reload
# If the following autocompletes/runs, the install succeeded
/harness

If autocomplete pops up when you type /harness, you are ready. Now move on to First harness run.

Caution — check the marketplace address The lev-factory/harness above is an example value mentioned in the lecture. For an actual install, check the publisher's GitHub repository path and enter that (search term: "하네스 100"). If the install does not work, try alternating between the command approach ↔ the /plugin screen approach.
Tip for in-house environments In an in-house network or proxy environment, GitHub access may be restricted. If adding the marketplace fails, first check the network/proxy policy and Git access permissions. The plugin must be installed separately on each machine (agent definitions can be shared via Git, but the plugin itself is a personal install).
