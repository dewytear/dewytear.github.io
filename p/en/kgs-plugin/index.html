Packaging the Wiki Engine as a Plugin — wiki-plugin and Sync Discipline

This knowledge system is not exclusive to this site. The structure, the pipeline, and the validation gates are packaged as a Claude Code plugin (wiki-plugin), so that any repository can bootstrap the same knowledge system. This document explains what was made into a plugin and why, and what discipline is in place so that the original and the copy never drift apart.

Why — Separating Engine from Content

This wiki is made of two layers: the engine (the four-level structure, the registration pipeline, the index builder, the validation gates, the viewer) and the content (the documents, the curated concepts, the cluster names). Every principle the previous four parts described is a property of the engine, so it is reusable — install this engine when you start knowledge management for a new project, and the same knowledge graph grows from the moment you drop in a document. Content, by contrast (this site's doc-entries and cluster labels), is a site-specific asset and is therefore excluded from the bundle.

Composition — Four Skills plus a Tool Snapshot

The plugin installs from the marketplace in two lines (/plugin marketplace add → /plugin install). Once installed, the four phases of running a wiki arrive as skills:

SkillWhat it does
wiki-initBootstraps a new wiki project — structure, nav tree, index pipeline, validation gates, and CI, all at once.
add-docEnforces the whole workflow for adding a document — file → tree registration → curation → index → Work Log → validation.
indexRegenerates the knowledge index, document dates, and the AI consumption layer, in compliance with the schema contract.
validateRuns the quality validators in one batch and interprets ERROR/WARN — down to "what is a defect and what is a review signal."

Along with the skills, a snapshot of the operational tools — the index builder, the validators, and so on — is enclosed. If the project has its own tools/, that one takes precedence (the dogfooding path); if not, the copy bundled with the plugin is used. The SPA viewer (the screens) needs no separate bundle: because adding the marketplace clones the entire repository, the latest real thing is always present locally.

Discipline — a Snapshot Must Match the Original

Sync discipline — CI, not human memory, guarantees that original and copy match.

The weakness of the snapshot approach is drift (fixing only the original and forgetting the copy). So a dedicated gate compares the original tools/ with the bundle byte for byte and fails CI if they differ. On top of that, a PR that changes the bundle passes only if it comes with a plugin version bump — a release discipline that lets installers track "when what changed" by version. The gate itself and the site-specific data (cluster labels, curation entries) are on the bundle exclusion list.

Dogfooding — the First User Is This Wiki Itself

This wiki is wiki-plugin's first user and reference implementation. The daily operation of this site — adding documents, regenerating the index, validating — is itself the plugin's integration test, and gaps found in operation (a missing guide, a hole in a gate) feed back as plugin improvements. Every principle from the previous four parts — how knowledge accumulates, the rules that connect it, the views that read it, AI consumption — lives inside this plugin, so this series doubles as a design commentary on wiki-plugin.

Installation /plugin marketplace add dewytear/dewytear.github.io → /plugin install wiki-plugin@dewytear-wiki. Skill details and the sync policy are in plugins/wiki-plugin/README.md in the repository. The gates and automation that keep this sync from drifting are covered in the next part.
