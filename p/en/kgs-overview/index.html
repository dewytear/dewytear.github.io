How Knowledge Accumulates — The Four-Level Hierarchy and the Registration Pipeline

This part explains the wiki itself. The goal of the wiki is not a mere collection of articles, but a knowledge graph whose connections grow as the documents grow. For that to happen, knowledge must not pile up just anywhere: it has to accumulate through a fixed structure (where) and a fixed procedure (how). This document follows that structure and procedure all the way through, using one real document (Welcome) as the example.

Structure — World → Domain → System → Document

Every document has its place inside a four-level knowledge hierarchy. At the top, World is a knowledge world (learning knowledge AI · work knowledge Douzone), Domain is an area within it, System is a concrete body of topics, and Document is the individual page. For instance, the address of the Welcome document reads like this:

Welcome's four-level address — as a section string, AI · Claude · Code · Introduction.

This hierarchy is not a separate database: it is derived from the nesting of the navigation tree (the list file) itself. The folder structure you see in the sidebar is the knowledge hierarchy, so the mismatch of "menu over here, taxonomy over there" cannot arise in the first place. Documents in the same System (a leaf folder) are treated as a series with a reading order, and this folder membership also serves as the safety net (folder top-up) for the related-document calculation we will see later.

A Document's Two Names — Immutable ID and Physical Path

A leaf (document) node in the tree has two key fields:

  • name — the immutable logical ID: both the hash route (#!welcome) and the node key in the knowledge graph. Once set it never changes, so moving a document to another folder never breaks existing links or edges.
  • path — the physical path: the actual file location under docs/ko/ (e.g. ai/claude/code/introduction/welcome). It follows the domain tree, so the folder alone tells you the knowledge hierarchy.

A document body is a static HTML fragment (no skeleton — just <h2>…<p>…). With no build tool, no server, and no JS rendering, it is fetched as-is by URL, so a human's browser and an AI read exactly the same source — a property that becomes the foundation of the AI consumption layer.

Three Markers — How Labels, Tags, and Concepts Divide the Work

When a document is registered, three markers are recorded alongside its name. The three look alike, but where they are recorded and where they are used are completely different — knowing this division prevents confusion such as "I added a tag, so why isn't it in the graph?"

Tags are a browsing device. They are shown as chips at the bottom of a document body, and tapping a chip takes you to the list of documents carrying that tag (straight to the document if there is only one). The Tags index spreads all tags out like a dictionary — Korean tags are bucketed by initial consonant (ㄱ·ㄴ·ㄷ…) and English ones alphabetically, with the ten most-used tags shown first as a band. Tags also earn points when they match in unified search, but their weight is lower than concepts (tags 3 < concepts 5). Switch the language and the per-language tags such as tags_en are shown instead. Note that Work Log documents are deliberately left with tags: [] — so that work records do not clutter the knowledge tag index.

Concepts are a graph device. A human (or AI) reads the document and curates only the key concepts that actually exist in the body, and the related-document (related) calculation we will see in the next part starts entirely from these concepts. In other words, no matter how many tags you attach, not a single graph edge is created — what the 3D knowledge graph and the 2D views read is concepts alone. Conversely, concepts do not appear on the index page. Because the same document's "door for finding" and "material for connecting" are separated, you can add tags for browsing convenience without shaking the honesty of the knowledge graph (the principle that a concept must exist in the body).

Procedure — The Pipeline That Registers One Document

New knowledge always goes through the same procedure. The core of it is step 3, where a human (or AI) actually reads the document and leaves a curated summary and concepts — this is where the material of the knowledge graph is made.

The registration pipeline — humans do ①–③; from ④ on, machines reproduce the same result.
  1. Write the body — save it as an HTML fragment at its place in the domain tree.
  2. Register in list — add name, path, label, and tags to the tree. At this moment the document gains a place in the navigation and in the knowledge hierarchy.
  3. Curation — read the document and record a one-line summary + key concepts (six on average) in doc-entries. The rule is to write only concepts that actually exist in the body (the honesty principle of the next part).
  4. Rebuild the index — the build tool computes related documents (related) from the hierarchy of ② and the concepts of ③, and regenerates the knowledge index. This build is deterministic (same input → always the same output), so CI's --check mechanically enforces "if the index diverges from the source, it cannot be merged".

As a result, adding a single document automatically updates every surface at once — navigation, the knowledge map, the 3D knowledge graph, search, and even the graph file for AI. This is why the state so common in knowledge management — "I organized it, but I can't find it" — cannot arise structurally here.

Current scale The knowledge accumulated through this procedure currently stands at 108 documents · 338 unique concepts · 228 connections (3.3 per document on average), with 110 typed relations declared through curation layered on top. Orphan documents (zero connections) number 0 — every document is inside the graph. The numbers are aggregated live on the knowledge map.
