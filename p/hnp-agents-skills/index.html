설계와 검증 — 에이전트·스킬·_workspace

하네스가 팀을 자동으로 짜 주지만, 원리를 알면 더 정확히 지시할 수 있고, 생성된 팀을 직접 다듬을 수도 있습니다. 핵심은 두 가지 — 에이전트(누가)와 스킬(어떻게)입니다.

에이전트 = 자연어로 쓴 "직무기술서"

에이전트는 코드가 아니라 글입니다. 아래 네 가지를 담습니다.

  • 역할 · 원칙 — 무엇을 책임지는지, 지켜야 할 규칙.
  • 입력 · 출력 — 무엇을 받아 무엇을 내놓는지(프로토콜).
  • 협업 — 어떤 에이전트와 무엇을 주고받는지.
  • 재호출 · 에러 시 행동 — 막히면 어떻게 할지.
# 예: 영업 표준소스 분석가 (에이전트 정의 발췌)
역할: ERP 영업·수주의 여신·주문 흐름을 분석하고,
      이번 커스텀이 표준 기능에 미치는 영향 범위를 식별한다.
원칙: 표준 훼손 최소화 · 업그레이드 호환을 항상 우선한다.
입력: 고객 요청(CR), 표준 명세/소스 참조
출력: 영향도 리포트(영향 화면·기능·데이터 목록)
협업: 설계자에게 영향도 전달, 정보 부족 시 재조사 요청
에러: 근거를 찾지 못하면 "확인 필요" 로 표시하고 넘기지 않는다

스킬 = 반복 작업을 담은 "매뉴얼"

스킬은 이름 + 설명 + 절차·체크리스트 로 이뤄집니다. 잘 만든 스킬은 여러 에이전트가 재사용합니다.

# 예: "회귀 테스트 체크리스트" 스킬
name: regression-checklist
description: 커스텀 반영 후 표준 영업·수주 기능이 깨지지 않았는지 점검
절차:
  1. 표준 주문 생성/수정/취소 정상 동작 확인
  2. 여신 한도 정상 범위 주문이 막히지 않는지 확인
  3. 커스텀(한도 초과 보류) 동작 확인
  4. 알림 발송 및 로그 확인
  5. 수치 정합성(주문금액·한도) 크로스체크
스킬 설계 5단계 (초급 팁) ① 자주 반복되는 작업을 찾는다 → ② 한 가지 책임만 하도록 쪼갠다 → ③ 입력/출력을 정한다 → ④ 예외 처리를 적는다 → ⑤ 어떤 에이전트가 쓸지 연결한다.

영업·수주 팀 — 데이터 흐름 예시

각 에이전트는 자기 스킬을 사용하고, QA에서 막히면 개발자에게 되돌아갑니다.

팀을 잘 짜는 초급 원칙

원칙이유ERP 예
역할은 좁게한 에이전트가 여러 일 하면 품질↓"분석"과 "개발"을 분리
입출력을 명확히다음 사람이 바로 이어받게영향도 리포트 → 설계 입력
QA는 별도로만든 사람이 자기 걸 검수하면 놓침회귀 QA를 독립 에이전트로
막히면 표시하고 멈춤모르는 걸 지어내지 않게"확인 필요" 플래그
생성된 팀 손보기 하네스가 만든 에이전트가 마음에 안 들면, 자연어로 수정을 요청하면 됩니다. 예: /harness QA 에이전트는 표준 주문 취소 시나리오도 반드시 검증하도록 수정. 검증을 얼마나 탄탄히 하느냐가 결과 신뢰도를 좌우합니다 → 검증·품질.

검증·품질과 _workspace

ERP 커스텀은 표준 기능을 깨뜨리면 안 되므로 검증이 생명입니다. 하네스는 QA 에이전트와 근거 기록으로 이를 뒷받침합니다.

QA는 무엇을 확인하나

오탈자 검사가 아니라, 내용의 정합성을 봅니다.

  • 주장 ↔ 근거 정합성 — 결론이 실제 자료·소스에 근거하는지.
  • 수치 일관성 — 주문금액·여신한도·정산 금액이 앞뒤로 맞는지.
  • 표준 회귀 — 커스텀 때문에 표준 주문·여신 기능이 깨지지 않았는지.

발견한 문제는 크리티컬 / 메이저 / 마이너 로 분류해 리포트합니다.

검증 루프 — 통과할 때까지

결함이 없을 때까지 개발↔QA를 돌고, 필요하면 다른 도구로 2차 검증합니다.

왜 덜 틀리나 — 근거 기록

  • 출처 기반 — _workspace 에 근거 출처가 함께 남습니다. "그럴듯한 거짓(할루시네이션)"이 줄고, 나중에 "왜 이렇게 했는지" 추적됩니다.
  • 이력 기록 — 구성 변경 이력이 CLAUDE.md 에 쌓여, 다음 사람이 맥락을 이어받습니다.
  • 중간 산출물 축적 — 1차 분석 → 설계 → 구현 → QA 리포트가 단계별로 남아, 어느 단계가 틀렸는지 짚기 쉽습니다.

이중 검증 — 다른 도구로 교차

한 도구만으로 검증하면 편향될 수 있습니다. QA 에이전트가 다른 CLI(예: Codex CLI) 로 한 번 더 확인하게 만들 수 있습니다.

/harness QA 에이전트는 Codex CLI 를 이용해 회귀 결과를 교차 검증하도록 수정
토큰 비용 — 알고 쓰기 멀티 에이전트는 편리한 만큼 토큰을 더 씁니다. 특히 에이전트들끼리 대화할 때 약 30% 정도 더 소모되는 경우도 있습니다. 간단한 커스텀까지 무겁게 돌릴 필요는 없습니다 — 난이도에 맞게 팀 규모를 정하세요.
주방 비유 — 결과는 "초안" 1인 셰프(단일 도구)는 빠르지만 병목이 있고, 멀티 에이전트(주방 팀)는 역할을 나눠 품질을 유지하며 오래 일합니다. 다만 한 번에 완성품이 나오지는 않습니다 — 잘 준비된 초안으로 보고, ERP 반영 전에는 표준 영향도·회귀 결과를 사람이 반드시 확인하세요. 다양한 적용 사례는 시나리오 게시판에서 봅니다.

마지막 편 시나리오·하네스100·명령어가 실전 게시판과 성능, 빠른 참조로 시리즈를 마무리합니다.
