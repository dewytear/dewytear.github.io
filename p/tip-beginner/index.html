초급 — 컨텍스트를 아끼는 습관 9가지

Claude Code를 잘 쓰는 첫걸음은 화려한 기능이 아니라 컨텍스트를 아끼는 습관입니다. 컨텍스트란 모델이 한 번에 기억할 수 있는 대화·코드의 총량으로, 이게 차오르면 앞서 합의한 내용을 잊고 엉뚱한 답을 내기 시작합니다. 이 문서는 공개 강좌의 팁 28가지 중 초급 9가지를 골라, 각 팁을 Anthropic 공식 문서와 대조해 정리한 것입니다. 팁마다 공식 문서 링크를 달았으니 더 깊이 볼 때 따라가면 됩니다.

문서 정보 (출처) · 뼈대: 공개 강좌 영상 — Claude Code 꿀팁 28가지의 초급 편(1~9)
· 검증·보강: Claude Code 공식 문서 대조 (2026-08-14 기준) — 기능은 버전에 따라 달라질 수 있습니다

1. 모든 프로젝트에서 /init부터

이미 코드가 쌓인 프로젝트에 Claude Code를 투입할 때, 첫 명령은 /init입니다. Claude가 코드베이스를 읽고 빌드 명령·테스트 방법·프로젝트 관례를 담은 CLAUDE.md를 만들어 줍니다 — 이 파일은 세션이 시작될 때마다 자동으로 읽히는 프로젝트 안내서라, 매 세션 "이 프로젝트가 뭔지" 설명하는 수고가 사라집니다. 이미 CLAUDE.md가 있으면 덮어쓰지 않고 개선안을 제안합니다.

공식 문서: How Claude remembers your project — 이 위키의 CLAUDE.md 실습과 CLAUDE.md 십계명도 같은 주제를 다룹니다.

2. 스테이터스 라인을 켠다

터미널에서 쓴다면 /statusline으로 상태 표시줄을 설정하세요. 지금 쓰는 모델, git 브랜치, 그리고 남은 컨텍스트 비율이 입력창 아래에 상시 표시됩니다. 컨텍스트가 얼마나 찼는지 눈에 보이면 아래 3~5번 습관이 자연스럽게 몸에 붙습니다. 데스크톱 앱은 이미 화면에 이 정보가 있어 설정이 필요 없습니다.

공식 문서: Status line configuration — 표시 항목은 스크립트로 자유롭게 바꿀 수 있습니다.

3. 컨텍스트를 작게 유지한다

"코드베이스 전체를 확인해 줘" 같은 명령은 한 번에 컨텍스트를 수십 %씩 태웁니다. 큰 문제는 먼저 쪼개는 것부터 시키세요 — "결제 시스템을 수정해 줘"가 아니라 "결제 시스템 수정을 작은 단계로 나눠 줘"로 시작하고, 단계마다 별도로 진행합니다. 모델이 좋아도 컨텍스트가 부족하면 앞서 한 얘기를 잊습니다.

4. /context로 토큰 먹는 하마를 찾는다

컨텍스트가 너무 빨리 찬다면 /context를 치세요. 어떤 파일·도구·메시지가 컨텍스트를 얼마나 차지하는지 시각화해 보여 줍니다. 범인은 대개 통째로 읽은 큰 파일, 도구 정의를 다 실은 MCP 서버(고급 편 22번), 길어진 대화 이력 중 하나입니다.

공식 문서: Slash commands 레퍼런스

5. 60%쯤 차면 /compact, 작업 사이엔 /clear

둘의 차이가 중요합니다. /compact는 대화 이력을 요약해 압축합니다 — "결정 사항은 남겨 줘"처럼 남길 것을 지정할 수 있고, 맥락은 이어집니다. /clear는 완전 초기화라 새 대화창을 여는 것과 같습니다. 한 작업이 끝나고 다음 작업으로 넘어갈 때는 압축보다 초기화가 낫습니다 — 이전 작업의 잔재가 새 작업을 오염시키지 않습니다.

압축은 맥락이 계속 필요할 때, 초기화는 작업이 바뀔 때. 헷갈리면 스테이터스 라인의 잔량을 본다.

6. 플랜 모드로 시작한다

플랜 모드는 파일을 하나도 건드리지 않고 읽기·분석·계획만 하는 모드입니다(터미널에서 Shift+Tab으로 전환). 아무것도 바꾸지 않으니 마음 놓고 시킬 수 있고, 계획을 세우다 막히면 Claude가 먼저 질문을 던져 의도를 좁혀 줍니다. 프롬프트를 구체적으로 쓰기 어려울수록 플랜 모드의 값이 커집니다.

한 가지 배경 — 2026년 8월 14일부터 신규 세션의 기본값은 매번 승인을 묻지 않는 auto 모드입니다(묻지 않는 기본값). 그래서 "손대기 전에 계획부터"라는 이 습관은 오히려 더 중요해졌습니다 — 실행이 빨라진 만큼, 방향은 먼저 합의해 두는 편이 안전합니다. 모드 상세: Permissions and modes

7. 주니어 개발자처럼 대한다

"패딩을 화면 너비에 따라 조절하는 함수를 만들어 줘"라고 하면, 문제 정의와 해법 고민 — 가장 어려운 일 — 을 여러분이 다 한 셈입니다. 대신 "기기별로 영상이 잘려 나오는데 어떻게 해결해야 할까?"처럼 문제를 주세요. Claude는 프로젝트 전체를 읽고 해법을 제안할 수 있으니, 해법 구상부터 함께 하는 쪽이 도구를 훨씬 크게 쓰는 방법입니다.

8. Claude가 되묻게 만든다

요구가 추상적일 때는 프롬프트 끝에 이렇게 붙이세요 — "내가 뭘 원하는지 네가 95% 이해할 때까지 계속 질문해." Claude가 구체화 질문을 연달아 던지고, 그 문답이 끝나면 처음부터 정확한 방향으로 갑니다. 모호한 지시로 세 번 다시 시키는 것보다 질문 다섯 개에 답하는 쪽이 쌉니다.

9. 투두에 자가 점검을 심는다

작업 목록을 시킬 때 마지막에 점검 항목을 명시하세요 — "크롬 개발자 도구를 열어 콘솔 에러를 확인해라", "전부 통과하기 전에는 넘어가지 마라", 그리고 "현재 항목이 완료됐다고 95% 이상 확신하기 전에는 다음으로 넘어가지 마라". 자가 점검 없이 투두 10개를 돌리면 각각 60% 완성도로 끝나 빈틈이 쌓이고, 나중에 원인을 못 찾아 토큰만 태우는 상황이 옵니다. 점검을 심으면 첫 결과물의 완성도가 달라집니다.

다음 편
