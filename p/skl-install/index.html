스킬 설치·보안·제작

스킬 실습은 허망할 정도로 간단합니다 — "이 스킬 설치해줘" 한마디면 끝납니다. 다만 앞서 배운 동작 원리를 떠올리며 쓰면 훨씬 재밌습니다.

설치하기

  • 스킬 배포 페이지의 "Get this skill" 버튼을 누르면 git 주소가 복사됩니다.
  • 그 주소를 Claude Code에 붙여 넣고 "이 스킬 설치해줘" 라고 하면 설치됩니다. (수동 설치는 해당 폴더에 복사)
  • 기본적으로 글로벌(전역) 폴더에 설치됩니다. (프로젝트/글로벌 선택도 가능하지만 처음엔 신경 안 써도 됨)
  • 설치 후 안 보이면 /reload(리로드 플러그인) 하거나 Claude Code를 껐다 켜면 스킬을 물고 옵니다. (/clear 는 컨텍스트만 비우는 것이라 다름)

스마트폰에서는 Claude 앱(샌드박스 구동)으로도 스킬을 써 볼 수 있습니다.

실습 — 조직 브랜드 스킬

기관 웹사이트의 스타일을 기반으로 만든 브랜드 가이드라인 스킬을 설치한 뒤 이렇게 요청합니다.

<브랜드> 브랜드 가이드라인 스킬을 이용해서
하계 워크샵 페이지를 만들어줘

그러면 아무렇게나가 아니라 조직 브랜드 스타일로 페이지가 만들어집니다. 핵심은 예쁨이 아니라 — 같은 스킬을 쓰면 모두 비슷한 스타일로, 조직 내 일관성 있는 재사용 가능한 산출물이 나온다는 점입니다. 같은 방식으로 PPT 템플릿 스킬(발표자료), Finder 스킬(조직 전문가 찾기) 등을 씁니다.

발동 원리 복습 "조직 스타일로 만들어줘"만 해도 스킬이 발동하는 이유는 메타데이터 description 에 "이 스타일을 쓸 때는 이 스킬을 이용하라"가 적혀 있기 때문입니다. 다만 확실히 하려면 스킬명을 명시하는 편이 좋습니다.

보안 주의사항

스킬은 강력한 만큼 보안 위험도 큽니다. 반드시 짚고 넘어가야 하는 부분입니다.

남의 스킬을 함부로 쓰지 말 것

스킬 안에는 스크립트가 들어 있고, 이 스크립트는 내 PC(노트북)를 실행시킬 권한을 그대로 가집니다. 따라서 남이 만든 스킬을 검증 없이 가져다 쓰는 것은 위험합니다.

  • 스킬 안에 위험한 코드가 숨어 있을 수 있어, 실제로 API 키 유출·보안 사고 사례가 많습니다(MCP 허브에서 받은 것 등).
  • 인증·검증된 스킬만 사용하고, 가능하면 내부에서 검증된 스킬만 씁니다.
  • 검사 도구가 있긴 하지만, 그 도구를 얼마나 신뢰할지가 또 문제입니다. 결국 코드/가이드라인을 직접 확인하는 신중함이 필요합니다.
  • 위험한 스킬을 "위에 덮어" 보완하기보다, 참고해서 직접 만드는 것이 더 안전합니다.

권한과 샌드박스

  • 스킬마다 읽기만/쓰기·편집 가능 등 권한 제약을 둘 수 있습니다.
  • 노트북에서 무심코 "예스" 하면 시스템이 손상될 수 있으므로, 위험 작업은 샌드박스(VM) 에서 별도로 돌리는 것이 안정적입니다.
  • 기관 내부라면 폐쇄망·온프레미스 환경에서 구동하는 것을 권장합니다. (모델도 사내/오픈 모델을 선택)
한 줄 요약 스킬은 내 컴퓨터를 실행할 권한을 갖습니다. 출처가 불분명한 스킬은 절대 함부로 설치하지 마세요.

스킬 만들기 (스킬 엔지니어링)

잘 써 봤다면 자연스럽게 "직접 만들고 싶다"는 생각이 듭니다. 스킬을 만드는 것을 스킬 엔지니어링 이라 부르며, 이를 돕는 스킬 만들기 스킬(skill-creator) 이 기본 탑재되어 있습니다.

skill-creator — 메타 스킬

A/B 테스트 루프를 돌며 다듬고, 벤치마크를 통과하면 완성됩니다.

스킬을 만드는 스킬로, 다음 흐름과 서브에이전트를 갖춥니다.

  • create → evaluate → improve → benchmark 루프.
  • 내부에 evaluator · grader · 비교 · 분석 서브에이전트 탑재.
  • 스크립트를 넣고 "이걸 스킬로 만들어줘" 하면, 자체 루프와 테스트(A/B) 를 거쳐 탄탄하게 만들어 줍니다.

두 가지 카테고리

구분내용모델 발전 시
능력 향상 스킬PDF 조작·문서 생성·복잡한 파일 변환 등. 스크립트로 만들어 결정론적·안정적으로 사용.모델이 잘하게 되면 불필요해질 수도
조직 내재화 스킬조직의 책임·업무 흐름·담당자 등. 에이전트가 모르는 우리 내부 지식.아무리 발전해도 대체 불가 — 계속 만들어야 함
강조 — 조직 내재화 스킬을 계속 만들자 능력 향상 스킬은 지금 잘 활용하되 "평생 갈 것"이라 생각하지 말고, 모델이 발전하면 걷어낼 수 있게 봅니다. 반면 조직 내재화 스킬은 LLM이 아무리 발전해도 우리 조직의 책임·흐름·담당자를 대신할 수 없으므로, 지속적으로 구축해 가는 것이 에이전트 거버넌스의 핵심입니다.
배포가 쉽다 스킬의 가장 큰 장점 중 하나는 배포입니다. 공유 저장소/서버/커뮤니티에 등록해 두면 버전 관리·공유가 쉽고, "Get this skill" 복사 → "설치해줘" 한 번으로 조직 전체에 퍼집니다. 현장에서 파일을 수정해 재배포하는 것도 즉시 가능합니다.

정리 — 엔지니어링 계층과 Q&A

엔지니어링의 계층

지금까지 배운 것들을 목적에 따라 구분하면, "다 엔지니어링이네"가 아니라 각각의 결이 보입니다.

엔지니어링목적
프롬프트 엔지니어링LLM을 똑똑하게 만들기
컨텍스트 엔지니어링맥락의 기회를 높이기
에이전틱 엔지니어링AI가 일을 잘하게 하기
하네스 엔지니어링믿고 맡기게 하기

하네스 는 스킬 + 서브에이전트가 탑재된 메타 스킬 로 볼 수 있습니다. 스킬 개념을 잡아두면 하네스가 겉으로는 쉬워 보여도 내부가 복잡하다는 것을 이해하며 볼 수 있습니다.

MCP vs 스킬

MCP는 프로토콜입니다 — 외부 툴과 에이전트를 연결하기 위한 규약이라, 로딩·사용 방식이 스킬과 다릅니다. 경쟁 관계가 아닙니다: 스킬 안에서 외부 연결이 필요하면 MCP를 쓸 수 있어, 스킬 안에 MCP가 있을 수도 있습니다. 다만 스킬이 워낙 강력해 MCP 대신 스킬로 대체하는 경우도 늘고 있습니다.

Q&A 요점 · 개방형 스킬 을 함부로 받으면 안전하지 않음 — 검증된 것만.
· 같은 이름의 MCP 함수와 스킬 이 있으면 상황에 따라 다르므로, "이 스킬을 이용해라"처럼 명시하거나 네임스페이스로 구분.
· 스킬 성능 평가 — 트리거가 잘 되는가/결과가 유용한가 등 지표를 먼저 정하고 LLM judge·육안으로 확인.
· 토큰 — 일반 클로드보다 Claude Code가 더 많이 쓰지만, 원하는 결과를 한 번에 얻으면 더 유용할 수 있음. 토큰만 보지 말고 종합적으로 선택.
